## Module 2: HMAC request signing

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/hmac-request-signing/index.html> (source: `topics/hmac-request-signing/index.html`)
- Last reviewed by the author: 2026-10-02
- Lab: `labs/hmac_lab.py`, run with `python3 labs/hmac_lab.py`

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **02-S1** Use HMAC as RFC 2104 section 2 and FIPS 198-1 section 4 define it. FIPS 198-1 section 1 requires an approved hash function: "HMAC shall use an Approved cryptographic hash function". RFC 9421 section 3.3.3 defines HMAC with SHA-256.
- **02-S2** Use a key at least as long as the hash output length L, which is 32 bytes for SHA-256. This is a recommendation, not a requirement: RFC 2104, an Informational RFC, says in section 2 that "the minimal recommended length for K is L bytes", and in section 3 it strongly discourages shorter keys.
- **02-S3** Compare signatures with a constant-time function. The Python 3.14 documentation for the hmac module recommends hmac.compare_digest instead of == when verifying a digest, "to reduce the vulnerability to timing attacks". RFC 2104, FIPS 198-1 and RFC 9421 say nothing about comparison timing.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **02-B1** Sign method, host, path, query, timestamp, nonce, content type, and the SHA-256 of the raw body, in a documented fixed order.
- **02-B2** Verify in this order: key lookup, time window, body hash, signature, nonce record. Record the nonce only after the signature verifies.
- **02-B3** Accept timestamps within 5 minutes of server time. Keep nonces for at least the same period. Keep clocks synchronized.
- **02-B4** Store keys in a secrets manager on both sides, versioned. Rotate with a short overlap in which both versions verify, then retire the old one.
- **02-B5** Ensure proxies and gateways pass signed components through unchanged, or verify at the edge.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **02-O1** Use RFC 9421 HTTP Message Signatures, with the content-digest field from RFC 9530, instead of a custom format.
- **02-O2** Use asymmetric signatures when the receiver must not be able to forge caller requests.

## Module 3: Asymmetric request signing

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/asymmetric-request-signing/index.html> (source: `topics/asymmetric-request-signing/index.html`)
- Last reviewed by the author: 2026-10-02
- Lab: `labs/asymmetric_signing_lab.py`, run with `python3 labs/asymmetric_signing_lab.py`

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **03-S1** Sign the signature base of RFC 9421 section 2.5, an ASCII string "containing the canonicalized HTTP message components covered by the signature", not a format of your own.
- **03-S2** The @signature-params component is required as the last line of the signature base and must not be enumerated within the covered components of any signature, including itself. RFC 9421 section 2.3.
- **03-S3** Carry the covered components and parameters in Signature-Input and the signature in Signature, both Dictionary structured fields. RFC 9421 sections 4.1 and 4.2.
- **03-S4** RFC 9421 section 2.3 defines the value of the alg parameter as an algorithm from the HTTP Signature Algorithms registry. Section 6.2.2 lists its initial contents, which include ed25519, ecdsa-p256-sha256 and rsa-pss-sha512.
- **03-S5** RFC 9421 section 1.4 requires an application or profile to specify, at a minimum, the set of component identifiers and signature parameters that are expected and required, a means of retrieving key material, the "set of allowable signature algorithms to be used by signers and accepted by verifiers", a "means of determining that the signature algorithm used to verify the signature is appropriate for the key material and context of the message", and the errors returned when validation fails, among other items. Write these down before you implement.
- **03-S6** To protect the body, cover a digest of it. RFC 9421 section 1 states that the specification "does not define a means to directly cover HTTP message content", and section 7.2.8 that a digest field from RFC 9530 "can be included just like any other field", so the body is only protected by covering a digest field that describes it.
- **03-S7** Treat anything outside the covered components as untrusted. RFC 9421 section 7.2.1 says "The verifier should only trust message components that have been signed", because portions not covered are "susceptible to modification by an attacker without affecting the signature".
- **03-S8** Compute Content-Digest as defined in RFC 9530 section 2, using an algorithm whose status is Active, which section 5 recommends. The initial registry contents in section 7.2 list two: sha-512 and sha-256.
- **03-S9** For ecdsa-p256-sha256 the signature value is R followed by S, each zero-padded to 32 octets (RFC 9421 section 3.3.4), not a DER encoding.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **03-B1** Verify in this order: resolve keyid, check alg against the allowlist, check alg against the key, check required coverage, rebuild the base, verify the signature, recompute the digest, check created and expires, record the nonce.
- **03-B2** Recompute the digest from the received bytes on every request. Covering content-digest without recomputing it protects the header and not the body.
- **03-B3** Accept a created value within 300 seconds of server time in either direction, and document that number as the replay window for anything you do not record.
- **03-B4** Require a nonce, record it only after the signature verifies, and store it where every instance serving the endpoint can see it.
- **03-B5** Resolve keyid only against keys established out of band. Never fetch key material from a location the caller supplies.
- **03-B6** Issue a new keyid for every key and accept both during a rotation overlap.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **03-O1** Keep an HMAC where both parties are the same organisation, there is one receiver, and no request will ever need attributing to one side. RFC 9421's hmac-sha256 lets you do that inside the same format.
- **03-O2** Sign responses as well as requests, and bind a response to its request, where a client needs to prove what it was told. RFC 9421 supports both directions.
- **03-O3** Hold the private key in a hardware-backed or non-exportable keystore, which is what makes the last row of the attack table hard rather than merely unlikely.

## Module 4: OAuth basics

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/oauth-basics/index.html> (source: `topics/oauth-basics/index.html`)
- Last reviewed by the author: 2026-10-05
- Lab: `labs/oauth_lab.py`, run with `python3 labs/oauth_lab.py`

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **04-S1** Public clients must use PKCE, and authorization servers must support it. For confidential clients RFC 9700 section 2.1.1 recommends it rather than requiring it.
- **04-S2** A client that can use S256 must use S256. RFC 7636 section 4.2 makes S256 mandatory to implement on the server, and section 7.2 says plain should not be used.
- **04-S3** The code verifier is 43 to 128 characters from the unreserved set, generated with a high-entropy cryptographic random source. RFC 7636 section 4.1.
- **04-S4** Authorization servers must match redirect URIs by exact string comparison, except for port numbers in localhost redirect URIs of native apps. RFC 9700 section 2.1.
- **04-S5** A client must not use an authorization code more than once. On reuse the server must deny the request and should revoke tokens previously issued from that code. RFC 6749 section 4.1.2, which also recommends a maximum code lifetime of 10 minutes.
- **04-S6** The resource owner password credentials grant must not be used. RFC 9700 section 2.4.
- **04-S7** RFC 9700 section 2.1.2 says clients should not use the implicit grant, or any response type that returns an access token in the authorization response, unless access token injection in the authorization response is prevented and the token leakage vectors that section names are mitigated.
- **04-S8** For the client credentials grant, a refresh token should not be included in the response. RFC 6749 section 4.4.3.
- **04-S9** Send bearer tokens in the Authorization header. RFC 6750 section 2.1 says clients should use it and resource servers must support it.
- **04-S10** Token endpoint errors use the codes defined in RFC 6749 section 5.2 with HTTP 400 unless specified otherwise: invalid_request, invalid_client, invalid_grant, unauthorized_client, unsupported_grant_type, invalid_scope.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **04-B1** Verify the challenge with the method recorded at the authorization request. Ignore any method supplied at redemption.
- **04-B2** One client registration per application and environment, with its own redirect URIs and its own narrow scope list.
- **04-B3** Issue codes with a 60 second lifetime. The legitimate client redeems immediately; a long lifetime only helps an attacker.
- **04-B4** Resource servers check the audience first, then the scope for the specific operation, then object-level authorization.
- **04-B5** Error responses name the RFC 6749 error code and nothing about which check failed.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **04-O1** Sender-constrain access tokens with mTLS (RFC 8705) or DPoP (RFC 9449) where token theft is a material risk. RFC 9700 section 2.2.1 recommends this rather than requiring it. Module 7.
- **04-O2** Use a backend for frontend so a browser application's tokens are held server side and never reach page scripts.
- **04-O3** Add OpenID Connect when the client needs standardized user authentication rather than delegated access. Module 35.

## Module 5: JWT validation

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/jwt-validation/index.html> (source: `topics/jwt-validation/index.html`)
- Last reviewed by the author: 2026-10-02
- Lab: `labs/jwt_lab.py`, run with `python3 labs/jwt_lab.py`

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **05-S1** The caller must be able to specify a supported set of algorithms, and no others may be used. RFC 8725 section 3.1, which also requires that the alg header specifies the same algorithm actually used.
- **05-S2** Applications must only allow cryptographically current algorithms that meet their security requirements. RFC 8725 section 3.2.
- **05-S3** Implementations must not accept Unsecured JWSs, the alg value none, by default, and applications must not signal acceptance of them at a global level. RFC 7518 section 3.6.
- **05-S4** When a JWT contains iss, the application must validate that the keys used belong to that issuer, and must reject the JWT if they do not. RFC 8725 section 3.8.
- **05-S5** Where one issuer can issue JWTs for more than one relying party, the audience value must be validated, and the JWT rejected if the audience is absent or not associated with the recipient. RFC 8725 section 3.9. RFC 7519 section 4.1.3 says that when aud is present, the JWT must be rejected if the principal is not identified by a value in it.
- **05-S6** Where one issuer can issue more than one kind of JWT, the validation rules must be mutually exclusive and reject JWTs of the wrong kind. RFC 8725 section 3.12. Explicit typing is covered in section 3.11.
- **05-S7** The current time must be before exp. RFC 7519 section 4.1.4, which allows a small leeway for clock skew.
- **05-S8** An OAuth JWT access token requires iss, exp, aud, sub, client_id, iat and jti, and RFC 9068 section 2.1 requires the typ header to carry the access token media type, recommending the short form at+jwt. Section 4 requires the resource server to reject a token whose typ is neither at+jwt nor application/at+jwt. Under RFC 9068 section 2.2, a client credentials token still has sub, and the RFC recommends that it identify the client rather than a user.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **05-B1** Declare the whole profile in configuration: algorithms, type, issuer, audience, required claims, key source and leeway. Read none of it from the token.
- **05-B2** Verify in this order: algorithm allowlist, token type, signature, required claims present, then claim values. Reject before reading anything you have not yet authenticated.
- **05-B3** Select the key from the issuer's published key set by kid. Never follow jku or x5u from the token header.
- **05-B4** Allow 60 seconds of clock leeway in both directions, and document it.
- **05-B5** Return 401 with no indication of which check failed. Log the specific reason with a correlation ID.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **05-O1** Use a reviewed JWT library rather than writing the parsing yourself, and configure its algorithm, audience and issuer options explicitly, because most default to checking less than this list.
- **05-O2** Sender-constrain the token with mTLS or DPoP where theft is a material risk. Module 7.

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **06-S1** A JWK Set is a JSON object that must have a keys member whose value is an array of JWKs. RFC 7517 section 5.
- **06-S2** A server providing a jwks_uri endpoint shall serve it only over TLS. FAPI 2.0 section 5.4.2.
- **06-S3** RFC 7517 section 4.5 recommends that different keys within a set use distinct kid values, and FAPI 2.0 section 5.4.2 recommends against serving a set with multiple keys sharing a kid. Both are recommendations, not requirements.
- **06-S4** FAPI 2.0 section 5.4.2 recommends against using the jku and x5u JOSE headers.

- **06-S6** A revocation endpoint returns HTTP 200 whether the token was revoked or was already invalid, because "invalid tokens do not cause an error response since the client cannot handle such an error in a reasonable way". RFC 7009 section 2.2.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **06-B1** Refresh the key set on a schedule once it passes a maximum age, independently of whether any kid is missing.
- **06-B2** On an unknown kid, allow one bounded refresh, coalesce concurrent misses into a single fetch, and apply a cooldown so caller-supplied identifiers cannot drive a fetch storm.
- **06-B3** After a failed refresh attempt, make no other attempt until a back-off has passed. Time it from the failure and track it separately from the last successful load, so a failing endpoint is not fetched on every request and a healthy one is still refreshed on schedule.
- **06-B4** A successful, well formed key set is authoritative even when it contains zero usable signing keys. It replaces what you hold.
- **06-B5** A malformed, truncated, non-success or transport-failed refresh is not authoritative. Keep the last known good set, and fail the request that required the refresh. Keep serving the kept set while the endpoint is down, up to the staleness limit, and count the outage and one back-off in the revocation bound.
- **06-B6** Set a hard limit on staleness. Once the last successful load is as old as the limit, serve no key from the set and reject every token with a distinct reason until a refresh succeeds, still retrying at the back-off rate. This fails closed: a removed key cannot outlast the limit, and a longer outage of the key endpoint rejects every caller.
- **06-B7** Run the scheduled refresh from a background task as well as on requests, with the same back-off, so the last successful load stays within about one maximum age on an API with no traffic. An outage then starts with at least the staleness limit less one maximum age still to run. The cost is one fetch per maximum age from every verifier instance, whatever the traffic. It does not shorten the worst case for a removed key during an outage.
- **06-B8** Reject a kid that matches more than one eligible key rather than selecting by array order, and report it as an issuer fault.
- **06-B9** State the revocation bound as a sum of the token lifetime and every cache TTL on the path, and test it by disabling an account and timing the result.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **06-O1** Use introspection or a denylist at the resource server when the revocation bound must be shorter than the token lifetime. The cost is a live dependency on the authorization server.
- **06-O2** Serve the stale key set with a much longer limit, or none, where rejecting every caller is the worse failure and the path to the key endpoint is hard for an attacker to block. The cost is that a removed key verifies for as long as the endpoint is unreachable. Write that into the revocation bound and alert on the outage.
- **06-O3** Use short token lifetimes instead, accepting that the bound cannot go below one lifetime and that the authorization server sees more traffic.

### The project's defaults (Baseline)

- **27-B1** Count failed attempts both per submitted username and per source, and check both before any password hash is computed. Count attempts, not requests, so a batch of ten logins in one request is ten attempts.

- **27-B5** After a reset, end the account's sessions, notify the user and require a normal sign-in.
- **27-B6** Require the current password or a second factor to change the sign-in address, the password or the second factor, and notify the previous address.

| oidc-04 | High | `oidc` | **Every login sends a fresh nonce bound to the browser session, and the client compares it** A missing nonce, a different nonce and a second response for the same login are all refused, and no token is used before the comparison passes. |
| oidc-05 | High | `oidc` | **Expiry and issue time are enforced with a small leeway** An ID token past exp is refused, and so is one issued longer ago than a stated limit. The leeway is seconds or a few minutes, and is not shared carelessly with other verifiers. |
| oidc-06 | High | `oidc` | **Step-up requests are checked in the ID token, not assumed from the request** After max_age the client checks auth_time, and after acr_values it checks acr. A request parameter that the browser carries can be removed on the way. |
| oidc-07 | Critical | `oidc` | **UserInfo is used only when its sub equals the ID token's sub, and accounts are keyed on iss and sub** A mismatching response is discarded whole. Email, phone number and name never select an account. |
| oidc-08 | High | `oauth` | **No token is taken from a redirect without its binding checks** The authorization code flow is the default and the implicit flow is disabled at the provider. Where a hybrid response is used, at_hash and c_hash are compared, a missing one is a refusal, and the ID token from the token endpoint is validated too. |
| oidc-09 | High | `oauth` | **The discovery document's issuer matches the configured issuer exactly** The document is fetched over TLS from the configured URL, and a document that names a different issuer is refused. The issuer is not taken from user input. |
| oidc-10 | High | `oidc` | **A valid ID token is treated as a record of one login and nothing more** Authorization is decided per request by the API. The client's session has its own timeouts and ends on the server, and the design says how a logout or a disabled account at the provider reaches it. |

## Module 36: Client authentication, PAR and high-assurance OAuth

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/advanced-oauth/index.html> (source: `topics/advanced-oauth/index.html`)
- Last reviewed by the author: 2026-10-05
- Lab: `labs/advanced_oauth_lab.py`, run with `python3 labs/advanced_oauth_lab.py`

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **36-S1** RFC 9700 section 2.5 recommends asymmetric cryptography for client authentication, such as mutual TLS (RFC 8705) or signed JWTs (private_key_jwt), and says authorization servers should enforce client authentication where issuing and protecting client credentials is feasible.
- **36-S2** The client must not use more than one authentication method in a request. RFC 6749 section 2.3. The server must not rely on public client authentication to identify the client. Same section.
- **36-S3** A JWT used for client authentication must contain iss, sub equal to the client_id, an aud that identifies the authorization server, and exp, and must be signed or carry a MAC. The server must reject one with an invalid signature or MAC, one that does not name it as audience, and one that has expired. RFC 7523 section 3. Failures are reported as invalid_client. RFC 7523 section 3.2.
- **36-S4** RFC 7523 section 3 allows, and does not require, a jti claim and replay tracking. OpenID Connect Core 1.0 incorporating errata set 2, section 9, requires jti for private_key_jwt and client_secret_jwt and requires that the assertion be used only once unless the parties negotiated otherwise.
- **36-S5** For JWT client authentication the client should use the authorization server's issuer identifier as the audience, and the server must accept its issuer identifier, its token endpoint URL or its PAR endpoint URL. RFC 9126 section 2.
- **36-S6** The PAR endpoint must authenticate the client as the token endpoint does, must reject a pushed request that contains request_uri, and must validate the request as it would an authorization request. RFC 9126 section 2.1.
- **36-S7** The request_uri must contain a part generated with a cryptographically strong pseudorandom algorithm so that guessing a valid value is computationally infeasible, and must be bound to the client that posted the request. RFC 9126 section 2.2.
- **36-S8** An expired request_uri must be rejected. The server should treat request_uri values as one-time use and may allow a duplicate caused by a reload. The client must use a value only once. RFC 9126 section 4.
- **36-S9** Server policy may make PAR the only way to pass authorization request data, globally or per client, signalled by require_pushed_authorization_requests. The server then refuses other authorization requests with invalid_request. RFC 9126 sections 4, 5 and 6.
- **36-S10** The server must accept new redirect URIs in a pushed request only from authenticated clients. RFC 9126 section 7.2. Clients should use PKCE, a unique state or the OpenID Connect nonce against request URI swapping. RFC 9126 section 7.5.
- **36-S11** Each authorization_details object requires a type. The server must refuse an unknown type, unknown fields, fields of the wrong type, invalid values and missing required fields, with invalid_authorization_details. RFC 9396 sections 2 and 5.
- **36-S12** The token response must return the authorization_details as granted, and the authorization server must make them available to the resource server. RFC 9396 sections 7 and 9.
- **36-S13** If the integrity of authorization_details is a concern, clients must protect them against tampering and swapping, with a signed request object or with PAR. The server must sanitize the data to prevent injection. RFC 9396 section 12.
- **36-S14** A resource server signals that the authentication behind a token is not sufficient with the error code insufficient_user_authentication, and may state the requirement with acr_values, max_age or both. RFC 9470 section 3. The client should use those values in a new authorization request. RFC 9470 section 4.
- **36-S15** The authorization server should treat a requested acr as necessary when issuing the access token, and fail the request if it cannot be met. RFC 9470 section 5. RFC 9470 must not be used to position OAuth as an authentication protocol. RFC 9470 section 9.
- **36-S16** The resource owner password credentials grant must not be used. RFC 9700 section 2.4. Clients should not use the implicit grant or other response types that return an access token in the authorization response, unless access token injection is prevented and the leakage vectors that section names are mitigated. RFC 9700 section 2.1.2.
- **36-S17** A client that can interact with more than one authorization server is required to have a defense against mix-up attacks, and should use the iss parameter of RFC 9207 or an equivalent issuer value in the response. RFC 9700 section 2.1. A client that supports RFC 9207 must compare iss with the issuer of the server the request was sent to and reject a mismatch. RFC 9207 section 2.4.
- **36-S18** Under the FAPI 2.0 Security Profile, authorization servers shall authenticate clients with mutual TLS or private_key_jwt, shall reject authorization requests sent without PAR, shall require PKCE with S256, shall return iss, shall issue only sender-constrained access tokens, and shall reject the password grant. FAPI 2.0 Security Profile sections 5.3.2.1 and 5.3.2.2. Resource servers shall verify the token and that the authorization it represents is sufficient. Section 5.3.4.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **36-B1** Register private_key_jwt for every confidential client. Accept one audience, the issuer identifier. Cap the assertion lifetime and record each jti until exp, after the signature and claims have passed.
- **36-B2** Take the assertion's algorithm and key from the client's registration, never from the JWT header.
- **36-B3** Require PAR for every client whose request parameters matter. Use only what was pushed, and ignore anything else on the authorization URL.
- **36-B4** Put anything with an amount, a payee or a named object in authorization_details. At the API, compare every field of the granted object with the request. Build the consent text from the same object.
- **36-B5** Validate the token before applying the step-up policy, so that an invalid token is not told what the policy is.
- **36-B6** Treat a profile claim as a list to verify row by row, and test object-level authorization separately.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **36-O1** Mutual TLS client authentication (tls_client_auth or self_signed_tls_client_auth, RFC 8705 section 2) where client certificates are already managed.
- **36-O2** A signed request object (RFC 9101), pushed through PAR, where the client must be able to prove afterwards what it requested.
- **36-O3** Adopt the FAPI 2.0 Security Profile whole, with a certified implementation, where an ecosystem or a regulator requires it.

## Module 37: SAML assertions and where they meet APIs

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/saml/index.html> (source: `topics/saml/index.html`)
- Last reviewed by the author: 2026-10-05

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **37-S1** SAML V2.0 Profiles section 4.1.4.3 requires the service provider to verify any signatures present on the assertion or the response, to verify that the Recipient in the bearer confirmation data matches the assertion consumer service URL the response was delivered to, to verify that its NotOnOrAfter has not passed "subject to allowable clock skew between the providers", to verify that InResponseTo equals the ID of its original request unless the response is unsolicited, in which case the attribute must not be present, and to verify that any assertions relied upon are valid in other respects.
- **37-S2** SAML V2.0 Profiles section 4.1.4.3 states these at lower strength. The service provider may check the client address against an Address attribute. An assertion that is not valid, or whose subject confirmation requirements cannot be met, should be discarded and should not be used to establish a security context. A session should be discarded at SessionNotOnOrAfter.
- **37-S3** SAML V2.0 Profiles section 4.1.4.5, as reworded by the approved errata (E26, with the same change to section 4.1.3.5 in E93), requires for the HTTP POST binding that "each assertion MUST be protected by a digital signature", by signing each assertion or by signing the response. The same section requires the service provider to ensure that bearer assertions are not replayed, by keeping the set of used ID values for as long as the assertion would be considered valid from the NotOnOrAfter of its confirmation data.
- **37-S4** SAML V2.0 Profiles section 4.1.4.2, as reworded by the approved errata (E26 and E52), requires the identity provider to put a bearer subject confirmation in the assertion, with a Recipient and a NotOnOrAfter, and requires each bearer assertion to contain an audience restriction naming the service provider. Section 4.1.4.1 requires the identity provider to verify that an assertion consumer service named in a request belongs to the service provider. Section 4.1.2 forbids the HTTP Redirect binding for the response.
- **37-S5** SAML V2.0 Profiles section 4.1.5 allows an identity provider to send an unsolicited response, and requires that it contain no InResponseTo. The approved errata (E90) add that service providers should have a means of disabling the acceptance of unsolicited responses.
- **37-S6** SAML V2.0 Core section 5.4.2 requires a signature to contain a single reference, to the ID of the root element of the assertion or message being signed. Section 5.4.1 requires enveloped signatures. Section 5.4.4 says signatures should not contain transforms other than the two it names, allows a verifier to reject others, and requires a verifier that does not to ensure that no content of the message is excluded from the signature. Section 5.4.5 neither requires <ds:KeyInfo> nor restricts it. Section 5.1 makes signing an assertion optional in general.
- **37-S7** SAML V2.0 Core section 2.3.3 requires a relying party to verify a signature that is used, and says that if it is invalid the relying party "MUST NOT rely on the contents of the assertion". Section 2.5.1.1 requires a relying party to reject an assertion whose conditions are Invalid or Indeterminate. Section 2.5.1.4 says the audience restriction is Valid if and only if the relying party is a member of one of the audiences.
- **37-S8** SAML V2.0 Bindings section 3.5.5.2 requires, when a message sent with the POST binding is signed, that its Destination hold the URL it was sent to and that the recipient verify it. Section 3.5.3 requires a RelayState value to be no longer than 80 bytes and says it should be integrity protected by its creator. The approved errata (E90) require implementations to sanitize the URL schemes they permit in RelayState.
- **37-S9** The approved errata (E92) say SAML system entities should allow for reasonable clock skew and call 3 to 5 minutes reasonable defaults. E91 says <ds:Object> should not be present in a SAML signature and that verifiers should reject a signature that contains one.
- **37-S10** RFC 7522 section 3 requires an authorization server that takes a SAML assertion as a grant to validate it: an issuer, an audience that identifies the authorization server (it "MUST reject any Assertion that does not contain its own identity as the intended audience"), a subject, an expiry, a bearer subject confirmation whose Recipient, when present, it must verify against the token endpoint, and a signature or MAC by the issuer. It allows replay protection and, in section 6, says the specification "does not mandate" it. Section 3.1 requires the error code invalid_grant for an assertion that is not valid.
- **37-S11** RFC 8693 section 3 defines the token type identifier urn:ietf:params:oauth:token-type:saml2 for a base64url-encoded SAML 2.0 assertion. Section 2.1 requires the authorization server to perform the appropriate validation procedures for the indicated token type and leaves the criteria for any particular token out of scope.
- **37-S12** The W3C note sets no requirements. It recommends that a verifier establish trust in the verification key (Best Practice 2), check both the name and the position of a referenced element (Best Practice 14), and that signers sign all parts of a document unless impractical (Best Practice 15) and not transmit unparsed external entity references (Best Practice 23).
- **37-S13** The OWASP SAML Security Cheat Sheet sets no requirements. It recommends validating the document against local, trusted copies of schemas, obtaining the key directly from the identity provider and ignoring KeyInfo in the document, never selecting security elements with getElementsByTagName without prior validation, validating the audience, Recipient, InResponseTo and both time limits, implementing replay detection, and validating a RelayState URL against an allowlist. It calls unsolicited responses inherently less secure by design.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **37-B1** Read the user and every condition only from the assertion element that a verified signature covers. Never look the assertion up a second time.
- **37-B2** Take the verification key from configuration, by issuer. Refuse an issuer with no configured key.
- **37-B3** Refuse any message that contains a document type declaration, before parsing, and configure the parser to resolve nothing external.
- **37-B4** Treat an invalid assertion as a refusal, although the profile says only that it should be discarded. Refuse unsolicited responses unless a named partner needs them.
- **37-B5** Allow 180 seconds of clock skew. Keep used assertion IDs until the delivery window plus the skew has passed, in a store all servers share.
- **37-B6** Send a random handle as RelayState and look the destination up in the session.
- **37-B7** Create the service provider's own session and do not keep the assertion. No resource API accepts an assertion. An authorization server's token endpoint that takes one under RFC 7522 refuses a second use, although RFC 7522 only allows that.
- **37-B8** Use a maintained SAML library with its strict options on, and run the negative tests in section 6 against it.
