## Module 0: Security concepts for the course

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/security-foundations/index.html> (source: `topics/security-foundations/index.html`)

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **00-S1** TLS authenticates the server by default and the client only if you configure it. "The server side of the channel is always authenticated; the client side is optionally authenticated." RFC 9846 section 1.
- **00-S2** TLS protects the channel, not the stored data. The properties it lists are that data sent "after establishment is only visible to the endpoints" and "cannot be modified by attackers without detection". RFC 9846 section 1. Both end at the endpoints.
- **00-S3** An HMAC is computed with a key shared by both parties, so verification capability equals production capability. RFC 2104 section 1 says message authentication codes "are used between two parties that share a secret key" and that HMAC "uses a secret key for calculation and verification". FIPS 198-1 section 1 says the same. Use HMAC as specified in RFC 2104 and FIPS 198-1. That is this page's advice: RFC 2104 is Informational and "does not specify an Internet standard of any kind".

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **00-B1** Never treat a hash sent alongside the data it describes as integrity protection. Carry it inside something a key protects.
- **00-B2** For every value in a request, be able to name who can produce it and who can check it, and record the answer where the design is written down.
- **00-B3** Name the last TLS termination before your code, and treat everything past it as a separate trust relationship.
- **00-B4** Authorize as a separate check, after authentication, naming the object. Never derive it from authentication having succeeded.
- **00-B5** Place checks in the service that owns the data. Treat a gateway check as additional unless nothing else can reach the service.
- **00-B6** Compare secrets and tags with a constant-time function. No functional test will catch the difference.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **00-O1** Use mutual TLS where you want the transport layer to carry caller identity, and confirm the certificate reaches the code that checks it rather than stopping at a proxy.

## Module 9: Object-level authorization

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/object-level-authorization/index.html> (source: `topics/object-level-authorization/index.html`)
- Last reviewed by the author: 2026-10-02
- Lab: `labs/object_authorization_lab.py`, run with `python3 labs/object_authorization_lab.py`

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **09-S1** Object level authorization is "usually implemented at the code level to validate that a user can only access the objects that they should have permissions to access". OWASP API Security Top 10 2023, API1:2023.
- **09-S2** Validate the caller's permission against every object reached using an identifier from client input, in every handler that reaches it. OWASP API1:2023, How To Prevent.
- **09-S3** Write tests for the authorization mechanism and do not deploy a change that fails them. OWASP API1:2023, How To Prevent.
- **09-S4** Prefer random, unpredictable values for record identifiers, such as GUIDs. OWASP API1:2023, How To Prevent. This raises the cost of discovery; it is not the access control.
- **09-S5** A server may answer 404 in place of 403. RFC 9110 section 15.5.4 says an origin server that wishes to hide the current existence of a forbidden target resource "MAY instead respond with a status code of 404 (Not Found)", and section 15.5.5 says a 404 indicates that the origin server "did not find a current representation for the target resource or is not willing to disclose that one exists". The RFC allows either code, so choose the refusal code deliberately.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **09-B1** Load the object, read the owner from the loaded record, compare with the identity authentication produced, and refuse before any part of the response is built.
- **09-B2** Never read the owner from a request parameter, header or body field.
- **09-B3** Filter list endpoints in the query. Never after serialisation and never in the client.
- **09-B4** Apply the check on every verb the object is exposed under, not only reads.
- **09-B5** Give every related object its own check in its own handler. Reaching it through an object you own does not transfer ownership.
- **09-B6** Return 404 for anything the caller may not see, consistently across the service.
- **09-B7** Enumerate every path that reaches each object type, including older versions still serving traffic, and confirm each one carries the check.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **09-O1** Return 403 where the caller is entitled to know the object exists, such as a shared resource their access to was removed. Document it, and keep it out of the paths where existence is itself the secret.
- **09-O2** Enforce ownership in the data access layer, so a handler that forgets the check cannot load the row at all. This trades some flexibility for a default that fails closed.

## Module 10: Property and function authorization

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/property-and-function-authorization/index.html> (source: `topics/property-and-function-authorization/index.html`)

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **10-S1** An endpoint is vulnerable where it "exposes properties of an object that are considered sensitive and should not be read by the user", or "allows a user to change, add/or delete the value of a sensitive object's property which the user should not be able to access". OWASP API3:2023, Is the API Vulnerable? The entry merges the 2019 edition's excessive data exposure and mass assignment categories.
- **10-S2** "When exposing an object using an API endpoint, always make sure that the user should have access to the object's properties you expose." OWASP API3:2023, How To Prevent.
- **10-S3** "Avoid using generic methods such as to_json() and to_string()." OWASP API3:2023, How To Prevent.
- **10-S4** "If possible, avoid using functions that automatically bind a client's input into code variables", and "allow changes only to the object's properties that should be updated by the client". OWASP API3:2023, How To Prevent.
- **10-S5** "Implement a schema-based response validation mechanism as an extra layer of security", and "keep returned data structures to the bare minimum, according to the business/functional requirements". OWASP API3:2023, How To Prevent.
- **10-S6** "The enforcement mechanism(s) should deny all access by default, requiring explicit grants to specific roles for access to every function." OWASP API5:2023, How To Prevent.
- **10-S7** "Don't assume that an API endpoint is regular or administrative only based on the URL path." OWASP API5:2023, Is the API Vulnerable? The same section notes it is "very common to find these administrative endpoints under other relative paths together with regular endpoints".

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **10-B1** Declare two lists per endpoint, one readable and one writable, and build the response and the update from them rather than from the record.
- **10-B2** Count and log the fields an update ignored, by name and never by value.
- **10-B3** Key function rules by method and path together. A rule for GET says nothing about DELETE.
- **10-B4** Refuse any request whose method and path have no rule, so a new endpoint is unreachable until somebody writes one.
- **10-B5** Have somebody read the route table against what each operation does. Deny by default covers the routes nobody considered, not the rules somebody got wrong.
- **10-B6** Keep the object check from module 9 on every one of these requests. Property and function checks say nothing about whose record it is.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **10-O1** Generate the response allowlist from the published API schema, so the contract and the filter cannot drift apart. This helps only if the schema is the source of truth rather than a document produced from the code.
- **10-O2** Fail a build when a model gains a field that no endpoint's list mentions, which turns the silent version of this defect into a visible one.

## Module 11: Business flows and idempotency

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/business-flows-and-idempotency/index.html> (source: `topics/business-flows-and-idempotency/index.html`)
- Last reviewed by the author: 2026-10-02
- Lab: `labs/idempotency_lab.py`, run with `python3 labs/idempotency_lab.py`

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **11-S1** A method is idempotent "if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request". GET, HEAD, PUT, DELETE, OPTIONS and TRACE are idempotent; POST is not. RFC 9110 section 9.2.2 for the definition, and the method table in section 18.2 for the list.
- **11-S2** Identify the business flows that might harm the business if they are excessively used. OWASP API6:2023 says mitigation planning should be done in two layers and gives this as the first, the business layer, ahead of the engineering one.
- **11-S3** OWASP API6:2023 describes the attack as "understanding the business model backed by the API, finding sensitive business flows, and automating access to these flows, causing harm to the business", with scalping, seat reservation and referral farming as its examples.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **11-B1** There is no standard for the Idempotency-Key header. draft-ietf-httpapi-idempotency-key-header reached revision 07 in October 2025 and expired on 18 April 2026 without becoming an RFC. Treat the header as a convention, document your own semantics, and do not assume another service shares them.
- **11-B2** Follow the expired draft's error behaviour, because each code names a distinct case: replay the stored response for a repeat of a completed request, 409 while a request with that key is in progress, 422 when the key arrives with a different payload.
- **11-B3** Reserve the key before performing the operation, and store the response against it afterwards.
- **11-B4** Store a fingerprint of the request payload with the key and compare it on every reuse.
- **11-B5** Scope keys per caller and per operation type. Never a single global namespace.
- **11-B6** Store and replay the original status and body, including failures. Do not recompute the response.
- **11-B7** Keep keys for a documented period, 24 hours by default, and treat it as the outer bound on how late a retry can be recognised.
- **11-B8** Log the idempotency key with each request, so duplicate execution and excessive use can be told apart from the data.
- **11-B9** Enforce rate and quantity limits on the flow, across every endpoint that advances it, rather than per endpoint.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **11-O1** Model the operation as a PUT to a client-chosen identifier where the resource has a natural identity, which takes the idempotency from the method and needs no key at all.
- **11-O2** Where a flow is valuable enough to attract automation, OWASP also lists device fingerprinting, human detection and non-human pattern analysis. These raise the cost of automation; they do not replace a limit.

### Sources as the page pins them

- [RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110): RFC 9110: HTTP Semantics, June 2022. Section 9.2.2, idempotent methods, and the method table in section 18.2.
- [OWASP API Security Top 10 2023, API6:2023 Unrestricted Access to Sensitive Business Flows](https://api-security.owasp.org/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/): OWASP API Security Top 10 2023, API6:2023 Unrestricted Access to Sensitive Business Flows.
- [draft-ietf-httpapi-idempotency-key-header: The Idempotency-Key HTTP Header Field](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-07): draft-ietf-httpapi-idempotency-key-header: The Idempotency-Key HTTP Header Field. Revision 07, October 2025, expired 18 April 2026. An expired Internet-Draft, not a standard, cited here for the convention it describes.

## Module 13: Request and response contracts

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/request-and-response-contracts/index.html> (source: `topics/request-and-response-contracts/index.html`)

- Lab: `labs/contracts_lab.py`, run with `python3 labs/contracts_lab.py`

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **13-S1** RFC 8259 section 4 recommends, and does not require, unique names: "The names within an object SHOULD be unique." When they are not, it records three behaviours in use: "many implementations report the last name/value pair only. Other implementations report an error or fail to parse the object, and some implementations report all of the name/value pairs, including duplicates."
- **13-S2** "Numeric values that cannot be represented in the grammar below (such as Infinity and NaN) are not permitted." RFC 8259 section 6.
- **13-S3** RFC 8259 section 6 notes that "good interoperability can be achieved by implementations that expect no more precision or range than" IEEE 754 double precision provides, and that numbers implying more may indicate interoperability problems.
- **13-S4** "A JSON parser MUST accept all texts that conform to the JSON grammar", and an implementation "may set limits on the size of texts that it accepts", "may set limits on the maximum depth of nesting" and "may set limits on the range and precision of numbers". RFC 8259 section 9. The limits are yours to set.
- **13-S5** "Define and enforce a maximum size of data on all incoming parameters and payloads, such as maximum length for strings, maximum number of elements in arrays, and maximum upload file size". OWASP API4:2023, How To Prevent.
- **13-S6** OWASP API4:2023 lists execution timeouts, maximum allocable memory, the number of operations in a single request and the number of records per page among the limits whose absence makes an API vulnerable.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **13-B1** Reject a body containing a repeated name. Do not resolve it.
- **13-B2** Parse each request once, or prove that every component parsing it resolves the same bytes the same way.
- **13-B3** Configure the parser to refuse NaN, Infinity and -Infinity.
- **13-B4** Limit nesting depth to 64, measured from the text before parsing.
- **13-B5** Enforce the decoded-size limit during decompression, stopping the decoder at the threshold, and bound the expansion ratio.
- **13-B6** Give every numeric field an explicit range and every string and array field an explicit maximum length, per field rather than globally.
- **13-B7** Return one status and a stable error shape naming the rule that refused the request, never echoing the offending value.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **13-O1** Do not accept compressed request bodies at all, which removes the decoded-size problem instead of bounding it.
- **13-O2** Apply the same limits to responses you consume from other services, since a response is somebody else's body arriving at your parser.

### Sources as the page pins them

- [RFC 8259: The JavaScript Object Notation (JSON) Data Interchange Format](https://www.rfc-editor.org/rfc/rfc8259): RFC 8259: The JavaScript Object Notation (JSON) Data Interchange Format, December 2017. Sections 4, 6 and 9.
- [OWASP API Security Top 10 2023, API4:2023 Unrestricted Resource Consumption](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/): OWASP API Security Top 10 2023, API4:2023 Unrestricted Resource Consumption.
- [Python 3.14 documentation: json, JSON encoder and decoder](https://docs.python.org/3.14/library/json.html): Python 3.14 documentation: json, JSON encoder and decoder. Standard Compliance and Interoperability: by default the module accepts NaN and Infinity, keeps only the last value of a repeated name, and imposes no limits beyond those of Python's datatypes and interpreter. parse_constant and object_pairs_hook are the parameters that alter the first two.
- [Python 3.14 documentation: Built-in Types, Integer string conversion length limitation](https://docs.python.org/3.14/library/stdtypes.html#int-max-str-digits): Python 3.14 documentation: Built-in Types, Integer string conversion length limitation. CPython's default limit is 4300 digits, and a conversion past it raises ValueError.

| csrf-06 | High | `always` | **Sessions end on the server** Idle and absolute timeouts are enforced server-side, and logout deletes the session record. A copied identifier is refused after each of the three. |
| csrf-07 | Medium | `always` | **Endpoints refuse content types they do not parse** A JSON endpoint answers 415 to text/plain and form content types. This is a layer, not the CSRF defence. |
| csrf-08 | High | `browser_client` | **Every host under the registrable domain is known and trusted to the same level** A sibling subdomain is same-site, so SameSite cookies are sent with its requests and it can set cookies for the parent domain. Remove unused DNS records. |
| csrf-09 | Medium | `browser_client` | **The place a browser app keeps its tokens is a recorded decision** Tokens in script-readable storage are exposed to any injected script. A backend for frontend keeps them on the server and needs the CSRF controls above. |

## Module 29: Security misconfiguration

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/security-misconfiguration/index.html> (source: `topics/security-misconfiguration/index.html`)
- Last reviewed by the author: 2026-10-04

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **29-S1** OWASP API8:2023 says an API might be vulnerable if hardening is missing across any part of the API stack or cloud permissions are improperly configured, the latest security patches are missing, unnecessary features are enabled, "There are discrepancies in the way incoming requests are processed by servers in the HTTP server chain", TLS is missing, security or cache control directives are not sent to clients, a CORS policy is missing or improperly set, or error messages include stack traces or expose other sensitive information. It is an awareness document and sets no requirements. API8:2023, Is the API Vulnerable?
- **29-S2** OWASP API8:2023 says the API life cycle should include "A repeatable hardening process leading to fast and easy deployment of a properly locked down environment", a task to review and update configurations across the entire API stack, and "An automated process to continuously assess the effectiveness of the configuration and settings in all environments". It goes on to say: use an encrypted channel (TLS) for all API communications, internal or public-facing; be specific about which HTTP verbs each API can be accessed by and disable the others; for APIs that browser-based clients call, implement a proper CORS policy and include applicable security headers; restrict incoming content types and data formats; make all servers in the HTTP server chain process incoming requests in a uniform manner; and, where applicable, define and enforce all response payload schemas, error responses included. API8:2023, How To Prevent.
- **29-S3** RFC 9457 defines the problem details format and the application/problem+json media type. It says "Problem details are not a debugging tool for the underlying implementation" (section 4) and encourages generators that provide links to occurrence information "to avoid making implementation details such as a stack dump available through the HTTP interface" (section 5). It does not require an API to use the format. The OWASP Error Handling Cheat Sheet recommends that "a generic response is returned by the application but the error details are logged server side for investigation, and not returned to the user".
- **29-S4** An origin server should answer 501 to a method it does not recognize or implement, and 405 to a method it implements but does not allow for the target resource (RFC 9110 section 9.1). It must generate an Allow header in a 405 response (RFC 9110 section 15.5.6). The final recipient of a TRACE request should exclude request fields that are likely to contain sensitive data when it generates the response (RFC 9110 section 9.3.8).
- **29-S5** Implementations must not negotiate SSL version 2, SSL version 3, TLS 1.0 or TLS 1.1 (RFC 9325 section 3.1.1). "TLS 1.0 MUST NOT be used." and "TLS 1.1 MUST NOT be used." (RFC 8996 sections 4 and 5).
- **29-S6** RFC 9325 section 3.1.1 says implementations must support TLS 1.2, should support TLS 1.3, and must prefer TLS 1.3 when they implement it. RFC 9852 section 5 changes that for new protocols that use TLS: "this document mandates that TLS 1.3 MUST be supported for new protocols using TLS", and "this document says that TLS 1.2 MAY be supported as described above". The changes apply to TLS and not to DTLS.
- **29-S7** In TLS 1.2 connections, clients must not offer and servers must not select cipher suites that use RSA key exchange, ephemeral finite field Diffie-Hellman, or non-ephemeral finite field Diffie-Hellman, and should not offer or select non-ephemeral elliptic curve Diffie-Hellman (RFC 10015 sections 2, 3 and 4, with the changes to RFC 9325 tabulated in section 6). Implementations must not negotiate NULL or RC4 cipher suites (RFC 9325 section 4.1). RFC 9325 section 4.2 recommends four ECDHE suites with AES-GCM for TLS 1.2.
- **29-S8** Service providers "SHOULD ensure that all servers providing the same service provide equivalent levels of security" in their TLS configuration, because an attacker might direct a client to the server that is easier to exploit (RFC 9325 section 3.9).
- **29-S9** With the no-store response directive, "a cache MUST NOT store any part of either the immediate request or the response". The same section says: "This directive is not a reliable or sufficient mechanism for ensuring privacy." RFC 9111 section 5.2.2.5. The OWASP HTTP Headers Cheat Sheet recommends: "Use no-store for sensitive data to prevent any form of caching."
- **29-S10** An HSTS host should include the Strict-Transport-Security field in responses sent over secure transport (RFC 6797 section 7.1) and must not include it in responses sent over non-secure transport (section 7.2). A user agent must ignore the field when it arrives over insecure transport (section 8.1). Web servers should use HSTS unless it would weaken security in their deployment (RFC 9325 section 3.2).
- **29-S11** A sender that generates a message containing content should generate a Content-Type header unless the media type is unknown to it (RFC 9110 section 8.3). An origin server should not generate a Server header "containing needlessly fine-grained detail" (RFC 9110 section 10.2.4). The OWASP HTTP Headers Cheat Sheet recommends X-Content-Type-Options: nosniff together with a correct Content-Type.
- **29-S12** The OWASP Transport Layer Security Cheat Sheet recommends that API-only endpoints disable HTTP altogether, or fail requests made over unencrypted HTTP "instead of redirecting them". The OWASP REST Security Cheat Sheet recommends an allowlist of permitted HTTP methods with a 405 for everything else, and says to avoid exposing management endpoints via the internet. Cheat sheets are guidance and set no requirements.
- **29-S13** OWASP Top 10:2025 A10 names failing open among the scenarios it covers and says that part way through a transaction "it is extremely important that you roll back every part of the transaction and start again (also known as failing closed)". OWASP Top 10:2025 A02 lists "Default accounts and their passwords are still enabled and unchanged." among its conditions. Both are awareness documents and set no requirements.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **29-B1** One global exception handler returns application/problem+json with type about:blank, the status, the standard title and an instance that carries a correlation ID. The exception is logged under the same ID and nowhere else.
- **29-B2** An error inside an authentication or authorization check denies the request. No setting exists that turns such an error into "allowed".
- **29-B3** The plain HTTP listener of an API is off. TLS 1.2 and TLS 1.3 are enabled, nothing older, with the four TLS 1.2 suites RFC 9325 section 4.2 recommends.
- **29-B4** Each route has a method allowlist. TRACE, debug endpoints, sample content and default accounts are off in every environment, not only in production.
- **29-B5** Every response carries Cache-Control: no-store, X-Content-Type-Options: nosniff and, when it has content, a correct Content-Type. No response names a product version.
- **29-B6** Every environment is built from one baseline. The settings allowed to differ are listed by name. An automated audit compares each environment with the baseline and probes the running service.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **29-O1** Offer only TLS 1.3 once every caller supports it. RFC 9325 section 1 names this as a decision a service provider might make.
- **29-O2** Redirect plain HTTP to HTTPS and send HSTS when people reach the same host in a browser. Keep API hosts and browser-facing hosts separate so the API host can refuse.
- **29-O3** Publish a security.txt file so that someone who finds a misconfiguration knows where to report it. RFC 9116 defines the format.
