- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/mcp-server-authorization/index.html> (source: `topics/mcp-server-authorization/index.html`)

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **20-S1** "A protected MCP server acts as an OAuth 2.1 resource server, capable of accepting and responding to protected resource requests using access tokens." MCP 2026-07-28, Authorization, Roles.
- **20-S2** Authorization is "OPTIONAL for MCP implementations". HTTP transports "SHOULD conform to this specification"; STDIO transports "SHOULD NOT follow this specification, and instead retrieve credentials from the environment". MCP 2026-07-28, Authorization, Protocol Requirements.
- **20-S3** "MCP servers MUST validate that access tokens were issued specifically for them as the intended audience, according to RFC 8707 Section 2." MCP 2026-07-28, Authorization, Token Handling.
- **20-S4** "MCP clients MUST NOT send tokens to the MCP server other than ones issued by the MCP server's authorization server." "MCP servers MUST only accept tokens that are valid for use with their own resources." "MCP servers MUST NOT accept or transit any other tokens." MCP 2026-07-28, Authorization, Token Handling.
- **20-S5** "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server." MCP 2026-07-28, Security Best Practices, Token Passthrough.
- **20-S6** "The access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server MUST NOT pass through the token it received from the MCP client." MCP 2026-07-28, Authorization Security Considerations, Access Token Privilege Restriction.
- **20-S7** The resource parameter "MUST be included in both authorization requests and token requests", "MUST identify the MCP server that the client intends to use the token with", and "MUST use the canonical URI of the MCP server". "MCP clients MUST send this parameter regardless of whether authorization servers support it." MCP 2026-07-28, Authorization, Resource Parameter Implementation. RFC 8707.
- **20-S8** "MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC9728). MCP clients MUST use OAuth 2.0 Protected Resource Metadata for authorization server discovery." MCP 2026-07-28, Authorization, Overview.
- **20-S9** Clients "MUST implement PKCE" and "MUST verify PKCE support before proceeding", "MUST use the S256 code challenge method when technically capable", and "MUST refuse to proceed" when code_challenge_methods_supported is absent. MCP 2026-07-28, Authorization Security Considerations, Authorization Code Protection.
- **20-S10** Clients compare the iss parameter to the recorded issuer using simple string comparison (RFC 3986 section 6.2.1), and "MUST NOT apply scheme or host case folding, default-port elision, trailing-slash, or percent-encoding normalization" first. MCP 2026-07-28, Authorization, Authorization Response Validation. RFC 9207 section 2.4.
- **20-S11** Servers "SHOULD include a scope parameter in the WWW-Authenticate header", clients "MUST treat the scopes provided in the challenge as authoritative for the current operation", and clients "MUST NOT assume any particular set relationship between the challenged scope set and scopes_supported". MCP 2026-07-28, Authorization, Scope Selection Strategy.
- **20-S12** Insufficient scope at runtime: the server "SHOULD respond with" 403 with error="insufficient_scope", a scope parameter and resource_metadata; servers "SHOULD include all scopes required for the current operation in a single challenge". Clients compute "the union of the client's previously requested scope set and the scopes from the current challenge". MCP 2026-07-28, Authorization, Scope Challenge Handling and Step-Up Authorization Flow.
- **20-S13** "MCP servers that implement authorization MUST verify all inbound requests. MCP servers MUST NOT treat possession of a state handle as authentication." Servers "SHOULD bind handles server-side to the authenticated user, for example by keying stored state as <user_id>:<handle> where the user ID is derived from the verified token rather than supplied by the client". MCP 2026-07-28, Security Best Practices, State Handle Hijacking.
- **20-S14** "MCP proxy servers using static client IDs MUST obtain user consent for each dynamically registered client before forwarding to third-party authorization servers (which may require additional consent)." MCP 2026-07-28, Authorization Security Considerations, Confused Deputy Problem.
- **20-S15** Authorization servers and MCP clients "SHOULD support OAuth Client ID Metadata Documents" and "MAY support the OAuth 2.0 Dynamic Client Registration Protocol", which is "deprecated and retained for backwards compatibility". MCP 2026-07-28, Authorization, Overview.
- **20-S16** "descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server". MCP 2026-07-28, Specification, Security and Trust & Safety.
- **20-S17** MCP clients deployed to a server "MUST consider SSRF risks" when fetching OAuth-related URLs, "SHOULD require HTTPS" and "SHOULD block requests to private and reserved IP address ranges". MCP 2026-07-28, Security Best Practices, Server-Side Request Forgery. RFC 9728 section 7.7.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **20-B1** Record the protocol revision the implementation targets, and recheck it against the current one on a schedule.
- **20-B2** Test audience validation with a token your own authorization server issued for a different resource, not only with a forged one.
- **20-B3** Keep scopes_supported to the minimal set for basic functionality, since the client's documented fallback requests all of it.
- **20-B4** Require authorization on any HTTP-transport server, treating the specification's optionality as covering stdio servers only.
- **20-B5** Generate state handles from a secure random source and bind them to the authenticated user.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **20-O1** Bind the MCP server's access tokens to their holder with the mechanisms in module 7 where a stolen bearer token is in the threat model.
- **20-O2** Expire state handles as well as binding them, where the workflow has a natural lifetime.
- **20-O3** Route the client's OAuth discovery requests through an egress proxy that blocks internal destinations, which the Security Best Practices document suggests for server-side client deployments.

## Module 21: Agent-to-agent

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/agent-to-agent/index.html> (source: `topics/agent-to-agent/index.html`)

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **21-S1** "A2A Servers MUST make an Agent Card available. The Agent Card describes the server's identity, capabilities, skills, and interaction requirements." A2A v1.0.1 section 8.1.
- **21-S2** Clients can find Agent Cards at a well-known URI, https://{server_domain}/.well-known/agent-card.json, the first of three discovery mechanisms the specification lists. A2A v1.0.1 section 8.2.
- **21-S3** "Agent Cards MAY be digitally signed using JSON Web Signature (JWS) as defined in RFC 7515 to ensure authenticity and integrity", and before signing the content "MUST be canonicalized using the JSON Canonicalization Scheme (JCS) as defined in RFC 8785". A2A v1.0.1 sections 8.4 and 8.4.1.
- **21-S4** "The signatures field itself MUST be excluded from the content being signed to avoid circular dependencies." A2A v1.0.1 section 8.4.1.
- **21-S5** Credentials "must be transmitted in standard HTTP headers as per the requirements of the chosen authentication scheme"; A2A payloads "don't carry user or client identity information directly"; the documentation says servers should respond 401 when credentials are missing or invalid and 403 when valid credentials lack permission. A2A: Enterprise Implementation of A2A.
- **21-S6** Authorization "should be applied based on the authenticated identity", can be controlled per skill as advertised in the Agent Card, and agents "must grant only the necessary permissions required for a client or user". A2A: Enterprise Implementation of A2A.
- **21-S7** Where an agent needs further credentials during a task, the "client is then responsible for obtaining these secondary credentials through a process outside of the A2A protocol itself". A2A: Enterprise Implementation of A2A. The specification adds: "Agents MUST arrange to receive credentials via an out-of-band means, unless an in-band mechanism has been negotiated out-of-band or via an extension." A2A v1.0.1 section 7.6.1.
- **21-S8** "Servers SHOULD NOT blindly trust and send POST requests to any URL provided by a client", with SSRF and amplification named as the risks and allowlisting, ownership verification and network controls as mitigations. A2A Streaming and Asynchronous Operations. The specification says agents "SHOULD validate webhook URLs to prevent SSRF". A2A v1.0.1 section 13.2.
- **21-S9** The server "MUST authenticate itself to the client's webhook URL"; the webhook "MUST rigorously verify the authenticity of incoming notification requests"; notifications "SHOULD include a timestamp" to prevent replay. A2A Streaming and Asynchronous Operations. In the specification, agents "MUST include authentication credentials in webhook requests" and clients "MUST validate webhook authenticity using the provided authentication credentials". A2A v1.0.1 section 13.2.
- **21-S10** "Clients MUST validate the task ID matches an expected task". A2A v1.0.1 section 4.3.3. Section 13.2 states the same duty as a recommendation: "Clients SHOULD verify the task ID in the payload matches an expected task they created". A2A v1.0.1 section 13.2.
- **21-S11** Push notification configuration carries "a url (the HTTPS webhook URL), an optional token (for client-side validation), and optional authentication details". A2A Streaming and Asynchronous Operations.
- **21-S12** "Any Agent Card containing sensitive data must be protected with authentication and authorization mechanisms", and the documentation "strongly recommends the use of out-of-band dynamic credentials rather than embedding static secrets within the Agent Card". A2A Agent Discovery.
- **21-S13** Tasks can reach an interrupted state such as input-required or auth-required. To continue an interaction, clients can send later messages with the same contextId. A2A Life of a Task.
- **21-S14** Under JCS, "JSON object properties MUST be sorted recursively", with names "formatted as arrays of UTF-16 [UNICODE] code units" for the comparison. RFC 8785 section 3.2.3, June 2020, which is Informational and an Independent Submission rather than an IETF standard.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **21-B1** Verify a card only against a key obtained out of band for that counterparty, and never against a key the card or its domain supplies.
- **21-B2** Refuse a card whose interface URL is not on the origin the card was served from, signature notwithstanding.
- **21-B3** Compare each counterparty's declared skills with the ones its endpoint answers, and treat the difference as a finding.
- **21-B4** Maintain a list of systems your agent may obtain credentials for, with the out-of-band path for each, and match mid-task requests against it.
- **21-B5** Allowlist webhook hosts and check the resolved address, treating the two as separate checks because one tests a name and the other an address.
- **21-B6** Verify every inbound notification on signature, freshness, task token, expected task id and identifier, and treat the webhook URL as public.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **21-O1** Serve a minimal public card and put the detail behind an authenticated extended card, which the documentation recommends for sensitive content.
- **21-O2** Put mTLS, network restrictions or HTTP authentication on the card endpoint itself where the card's existence is not public information.
- **21-O3** Re-resolve and re-check the webhook address immediately before each POST, where the gap between validation and connection is in the threat model.

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/prompt-injection-and-output-handling/index.html> (source: `topics/prompt-injection-and-output-handling/index.html`)

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **22-S1** "A prompt-injection vulnerability occurs when input to a large language model (LLM), whether direct user input, retrieved content, tool output, image, audio, or video content, intermediate reasoning, or persistent memory, alters the model's behavior in ways the application developer did not intend." OWASP LLM01:2026 Prompt Injection, Description.
- **22-S2** "The model ingests content from an external source (a web page, a document, an email, a tool response, a retrieved RAG passage, an image, an MCP server's output, a database row, or an issue title) that contains data which acts as prompt injection. The user did not supply or see those instructions." OWASP LLM01:2026, Indirect Prompt Injection.
- **22-S3** "Prompt injection is intrinsic to current generative AI: LLMs make no architectural distinction between instructions and data, and their behavior is stochastic, so no reliable prevention mechanism exists today". OWASP LLM01:2026, Prevention and Mitigation Strategies.
- **22-S4** "Pass external content through a structurally separate, provenance-labeled channel so the model can distinguish data from instructions". OWASP LLM01:2026, mitigation 6, which adds that this "reduces attack success in non-adaptive tests only: an attacker who knows the marking scheme can mimic it".
- **22-S5** "Hold credentials and state-change capability in application code, not the model, and grant least privilege per operation." OWASP LLM01:2026, mitigation 4.
- **22-S6** "Define a strict output schema and validate every response in trusted application code before any downstream system acts on it, using structural validation rather than a second LLM call." OWASP LLM01:2026, mitigation 2, which adds that this "catches format violations, not semantic manipulation".
- **22-S7** "Require explicit human confirmation before any privileged, irreversible, or externally visible action, surfacing the exact rendered action rather than a summary to the reviewer." OWASP LLM01:2026, mitigation 7.
- **22-S8** "Improper Output Handling refers specifically to insufficient validation, sanitization, and handling of the outputs generated by large language models before they are passed downstream to other components and systems." OWASP LLM10:2026 Improper Output Handling, Description.
- **22-S9** "Treat the model as any other user, adopting a zero-trust approach, and apply proper input validation on responses coming from the model to backend functions." OWASP LLM10:2026, mitigation 1.
- **22-S10** OWASP LLM10:2026 recommends encoding model output according to where it will be used (mitigation 4) and parameterized queries or prepared statements for all database operations involving it (mitigation 5). It lists shell execution, JavaScript or Markdown interpreted by the browser, SQL executed without parameterization, file paths built without sanitization and unescaped email templates among its examples.
- **22-S11** Goal hijack through injected content is OWASP's ASI01 Agent Goal Hijack; the resulting misuse of a legitimate tool is ASI02 Tool Misuse and Exploitation. OWASP Top 10 for Agentic Applications for 2026.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **22-B1** Fence untrusted content with a delimiter containing a per-request nonce, and keep a provenance map, so the untrusted bytes remain identifiable after assembly.
- **22-B2** Dispatch tools from a deny-by-default table keyed on the exact name, then check the role, then the argument names, then the values.
- **22-B3** Keep every tool credential in the application. A model that holds a token makes the table advisory.
- **22-B4** Choose the encoding at the sink, every time, and never route model output through a single sanitize function.
- **22-B5** Keep the agent's scope to the narrowest the task needs, because that is the only control that bounds an injection you did not detect.
- **22-B6** Log the provenance alongside the action, so an incident can ask which document was being read when a call was proposed.
- **22-B7** Treat an input filter as defence in depth, never as coverage, and state the phrasings it covers rather than reporting it as handled.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **22-O1** Normalise with NFKC and strip format characters before filtering, accepting that the lab shows this changing no verdict for the zero-width case.
- **22-O2** Run the model's proposed call past a second model or a rules engine before executing it, where the operation warrants the cost, remembering that the reviewer can be persuaded too.
- **22-O3** Refuse to act at all on a turn where untrusted content was in the prompt and a privileged tool was proposed, deferring to a human instead.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **23-B1** Bind the approval to the parameters with a MAC, never to a proposal identifier.
- **23-B2** Cover every field that changes the outcome, and prove coverage by changing each field in turn.
- **23-B3** Derive the approver's summary from the covered fields, so the sentence and the call cannot disagree.
- **23-B4** Give each approval a nonce, spend it on execution, and refuse a second use.
- **23-B5** Give each approval a lifetime measured in minutes.
- **23-B6** Record, for any session-wide approval, how many of an operation's fields it constrains.
- **23-B7** Log the approved parameters next to the executed parameters for the same action.

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **23-O1** Require a second approver for actions above a threshold, accepting that this doubles the exposure to ASI09 rather than halving it.
- **23-O2** Show the approver a diff against the last similar action, where the risk is a plausible-looking change rather than an implausible one.
- **23-O3** Carry the approval to the downstream service as a request signature, where the executing service is not the service that collected the approval.
