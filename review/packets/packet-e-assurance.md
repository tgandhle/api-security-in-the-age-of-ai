## Module 30: Logging, detection and response

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **30-S1** The OWASP Logging Cheat Sheet, under Which events to log, recommends always logging, where possible, input validation failures, authentication successes and failures, authorization (access control) failures, session management failures, application errors and system events, use of higher-risk functionality, and suspicious business logic activities. It is guidance and sets no requirement.
- **30-S2** The OWASP Logging Cheat Sheet, under Event attributes, says each event records "when, where, who and what", and describes an interaction identifier as "a method of linking all (relevant) events for a single user interaction".
- **30-S3** The OWASP Logging Cheat Sheet, under Data to exclude, says session identification values, access tokens, authentication passwords, database connection strings, encryption keys and other primary secrets, payment card holder data and sensitive personal data "should usually not be recorded directly in the logs, but instead should be removed, masked, sanitized, hashed, or encrypted".
- **30-S4** The OWASP Logging Cheat Sheet, under Event collection, recommends sanitizing all event data "to prevent log injection attacks e.g. carriage return (CR), line feed (LF) and delimiter characters", encoding data correctly for the logged format, and synchronizing time "across all servers and devices".
- **30-S5** The OWASP Logging Cheat Sheet, under Protection, recommends tamper detection, copying log data to read-only media as soon as possible, recording and monitoring all access to the logs, and restricting the privileges to read them. Under Disposal of logs it says log data must not be destroyed before the required retention period ends, "and must not be kept beyond this time".
- **30-S6** The OWASP Logging Vocabulary Cheat Sheet "proposes a standard vocabulary for logging security events". It gives authn_login_success the level INFO, authn_login_fail and input_validation_fail the level WARN, and authz_fail the level CRITICAL, and says all dates "should be logged in ISO 8601 format WITH UTC offset". It is a proposal, not a standard.
- **30-S7** OWASP Top 10:2025 A09 lists among its failures auditable events that "are not logged or logged inconsistently", log integrity that is not protected from tampering, logs that are not monitored, and too many false positive alerts. Among its preventions: log all login, access control and server-side input validation failures "with sufficient user context to identify suspicious or malicious accounts", and encode log data correctly. It is an awareness document and sets no requirement.
- **30-S8** NIST SP 800-92 (September 2006) section 5.1.3 says users should not have access to most log files beyond append-only privileges where they must create entries, that logging should be configured not to record unneeded sensitive data such as passwords, and that protecting archived logs "could include creating and securing message digests for the files". Section 5.5 lists ensuring "that each system's clock is synched to a common time source" among operational duties.
- **30-S9** NIST SP 800-61r3 (April 2025) section 2.1 replaces the four-phase life cycle of the previous revision with a model based on the six CSF 2.0 Functions, in which Detect, Respond and Recover are the incident response itself and Govern, Identify and Protect are preparation. It recommends that organizations use the model that suits them best. In Table 3 it recommends tuning monitoring to reduce false positives and false negatives (DE.CM), declaring incidents against defined criteria (DE.AE-08), triaging and validating each report (RS.MA-02) and determining the sequence of events (RS.AN-03).
- **30-S10** RFC 5424 section 6.2.1 requires a syslog Severity value to be in the range 0 to 7 and lists the names, from Emergency (0) to Debug (7), in a table. It says the Facility and Severity values "are not normative but often used" and that the tables are there "for purely informational purposes". The Logging Cheat Sheet's example of a severity scale uses the same numbers. Section 8.2 warns that an attacker may include control characters in a message.
- **30-S11** For agents, the OWASP AI Agent Security Cheat Sheet, section 6, recommends: "Log all agent decisions, tool calls, and outcomes." The OWASP Top 10 for Agentic Applications for 2026, ASI02, says: "Maintain immutable logs of all tool invocations and parameter changes."

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **30-B1** Log every refusal an authentication, authorization or validation control makes, with the account, the object, the route and a request id. A success-only log hides the attacks your controls stopped.
- **30-B2** Write each event as one JSON object per line through an encoder. Do not build log lines by joining strings, and do not strip characters by hand.
- **30-B3** Put an allowlist of field names in the logger. Validate identifiers before logging them, and log the name of a field that failed validation, not its value.
- **30-B4** Keep the event name in a field of its own and its parameters in separate fields. Treat the level as a ranking, and let rules decide who is told.
- **30-B5** Run at least these rules: refusals per account in a short window, the same in a long window, different accounts failing sign-in from one address, and a count on each sensitive business flow. Replay the attack after every threshold change.
- **30-B6** For an agent, record which agent acted, on whose behalf, which tool it called and the outcome.
- **30-B7** Report "no rule fired", with the rules and the rate below which each is silent. Never report "no attack".

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **30-O1** A hash chain over log entries, with the latest digest stored where the log's writer cannot reach. It shows an edit or a deletion. It does not prevent one.
- **30-O2** Automatic blocking when a rule fires. The Logging Cheat Sheet warns that such an action must not become a way to deny service to other users.
- **30-O3** Honeytokens: records or identities that no real user touches, so that any access to them is an alert with almost no false positives. OWASP Top 10:2025 A09 suggests them.

## Module 34: Testing API security

- Lesson: <https://tgandhle.github.io/api-security-in-the-age-of-ai/topics/security-testing/index.html> (source: `topics/security-testing/index.html`)

### Claims attributed to a source (Standard)

Confirm the cited source says this, at the strength stated: must, should or may.

- **34-S1** The OWASP WSTG v4.2, under Deriving Functional and Non-Functional Test Requirements, says positive requirements "state the expected functionality that can be validated through security tests", and that "Security tests must also be risk-driven. They need to validate the application for unexpected behavior, or negative requirements." Under Deriving Security Test Requirements Through Use and Misuse Cases it derives requirements from both. It is a guide and sets no requirement.
- **34-S2** The OWASP WSTG v4.2, under Security Test Data Analysis and Reporting, says: "The fact that a security test is clear of issues does not mean that the software or application is good." Under Reporting Requirements it says the best practice is to report, for each vulnerability, its type, the threat, the root cause, the testing technique that found it, the remediation and a severity rating, and that the report should tell the developer how to re-test.
- **34-S3** NIST SP 800-115 (September 2008) section 2.1 says an assessment methodology "should contain at minimum" the phases planning, execution and post-execution. Section 2.2 recommends combining techniques, "Since no one technique can provide a complete picture of the security of a system or network". Section 2.3 says testing "does not provide a comprehensive evaluation of the security posture of an organization".
- **34-S4** NIST SP 800-115 section 6.5 recommends that each assessment has a plan answering what is in scope, who is authorized, the logistics, how sensitive data is handled and what happens in an incident. It says the plan should list systems that are not authorized, and that the owner of a third-party network "usually must also consent in writing". Section 5.2 recommends that penetration testing "be performed only after careful consideration, notification, and planning". Appendix B is a rules of engagement template.
- **34-S5** OWASP ASVS 5.0.0 requirement 8.2.1 (Level 1): function-level access is restricted to consumers with explicit permissions. Requirement 8.2.2 (Level 1): data-specific access is restricted to consumers with explicit permissions to specific data items. Requirement 8.2.3 (Level 2): field-level access is restricted likewise. Requirement 8.1.1 (Level 1): authorization documentation defines the rules. Each is written as "Verify that".
- **34-S6** OWASP ASVS 5.0.0, under Assessment and Certification, says automated tools "will be unable entirely to verify many of the more complicated ASVS requirements or those that relate to business logic and access control", that application-specific automated verifications can be written for those, and that testing without access to necessary additional information "is an inefficient and ineffective mechanism for security verification". Requirement 16.5.1 (Level 2) requires a generic message, with no stack trace or query, when an unexpected error occurs. Requirement 15.3.3 (Level 2) requires countermeasures against mass assignment.
- **34-S7** The OpenAPI Specification 3.2.1, under Security Requirement Object, says that when the security field holds several objects, "only one of the entries in the list needs to be satisfied to authorize the request", and that an empty object "indicates anonymous access is supported". Under Validating readOnly and writeOnly it cites the JSON Schema expectation that a resource may either ignore a readOnly field or treat it as an error. Under Specification Extensions it requires extension field names to begin with x-. That the specification describes an API and sets no security requirement on one is this project's reading of it.
- **34-S8** The OWASP Authorization Testing Automation Cheat Sheet describes an authorization matrix of features, logical roles and sometimes data, and recommends that developers "automate the evaluation of the authorizations and perform a test when a new release is created". It is guidance and sets no requirement.
- **34-S9** The OWASP REST Assessment Cheat Sheet recommends reconciling an OpenAPI description with observed behaviour, fuzzing from the schema one constraint at a time, building a test matrix for each operation from its security requirements (no credentials, a valid token, and a token that lacks the requirement), the swap test with two accounts on reads and writes, and confirming that an undeclared field "persisted and changed behavior" before reporting mass assignment.
- **34-S10** OWASP API9:2023 Improper Inventory Management lists documentation that does not exist or is not updated as a documentation blindspot, and among its preventions: "Generate documentation automatically by adopting open standards. Include the documentation build in your CI/CD pipeline." It is an awareness document and sets no requirement.

### The project's defaults (Baseline)

Confirm each is technically sound. These are the project's position, not a source's.

- **34-B1** No security test starts without written permission that names the scope, the exclusions, the environment, the rate and a contact. Third-party systems behind the API are out of scope unless their owner agreed in writing.
- **34-B2** Every operation in the description has a row in an authorization matrix, with two test accounts for each role that owns data and one column with no credentials. Expected results are derived from written rules before the run.
- **34-B3** Every operation with a request body gets inputs derived from its schema, one mutation at a time, with valid control cases. A 5xx is a finding. An accepted undeclared property is read back.
- **34-B4** The description is compared with what answers on every change, in both directions.
- **34-B5** Each finding records the request, the expected and observed results, the control that failed and how to re-test. Each is kept as an automated test that runs on every change.
- **34-B6** Report "the cases run were refused", with the cases. Never report "no vulnerabilities".

### Alternatives (Option)

Confirm each is technically sound where the page says it applies.

- **34-O1** Randomly generated inputs in larger numbers. They widen the search for 5xx answers and crashes. Record the seed, and keep them out of shared environments unless the rate is agreed.
- **34-O2** A penetration test by people who did not build the API, with the description and the source. It finds what nobody wrote a case for. It samples and does not prove.
- **34-O3** A covert test, run without telling the operations staff, to find out whether detection and response work when nobody is expecting it. NIST SP 800-115 section 2.4.2 describes it as performed "with the full knowledge and permission of upper management".
