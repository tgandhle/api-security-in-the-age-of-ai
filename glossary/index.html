Glossary

Terms used across the site, in plain language. Each module links here the first time it uses a term.

Access token
A credential a client presents to a resource server for access the resource owner granted. In OAuth it carries authorization, not identity, and it is usually a bearer credential.
Act claim
The act claim in a token, naming the party that has been delegated authority. The outermost one is the current actor and nested ones are prior actors, and a consumer applying access control policy must consider only the top-level claims and the current actor. RFC 8693 section 4.1.
Agent card
A JSON document an A2A server publishes, by default at /.well-known/agent-card.json, declaring its name, interfaces, skills and security schemes. It may be signed, and a signature establishes that the key holder wrote it, not who the key holder is.
Algorithm confusion
An attack that changes which algorithm a verifier uses, so a value the attacker knows becomes the verifying key. The classic case swaps RS256 for HS256 and signs with the issuer's public key.
API gateway
A component every request is meant to pass through, applying checks that need only the request. It is a control while it is the only path to the service, which is a property of the network rather than of the gateway.
API key
A credential issued to an application for API access. In this course, it is a secret bearer value checked against a server-side record.
Asymmetric signature
A signature made with a private key and checked with the matching public key. Knowing the public key lets you verify, not sign, so the verifier can't forge signatures.
Authentication
Checking a claimed identity using evidence such as a credential. Possession of a stolen credential can pass that check.
Authorization
Deciding whether an identity may perform an action on a resource.
Authorization code
A short-lived, single-use value returned through the browser that a client exchanges for a token on a server-to-server request. It is not a credential for the API itself.
Authorization server
The server that authenticates clients, obtains the resource owner's consent, and issues tokens. It owns the authorization and token endpoints.
Back channel
A direct server-to-server request that does not pass through the user's browser. Values sent here are not exposed to browser history or to anything on the redirect path.
Bearer credential
A credential that grants access to whoever presents it, like an API key or most access tokens. If it's stolen, the thief can use it.
Blanket approval
One approval covering a whole session or class of actions. Its worth is the number of an operation's fields it constrains, which is often zero, and then it records that somebody was present rather than controlling what happened.
Bound approval
An approval carrying a signature over the parameters as the approver saw them, so the executor can confirm it is running the same thing rather than the same identifier. Approving an identifier approves whatever that identifier holds later.
Canonical string
An agreed, exact text description of a request that both sides build the same way before signing. Any difference in bytes produces a different signature.
Canonicalization
Reducing a document to one agreed byte representation before signing, so that reserialising it does not break the signature. For JSON, RFC 8785 sorts object properties recursively and compares names as UTF-16 code units.
Certificate binding
Tying an access token to the client certificate used on the TLS connection, so the token only works from a connection presenting that certificate. RFC 8705.
Claim
A name and value inside a token payload, such as iss, aud or exp. In plain JWT every registered claim is optional, so which ones must be present is decided by the profile you verify against.
Client credentials grant
The OAuth grant a service uses to obtain a token for itself, with no user involved. The client authenticates and receives a scoped token.
Client ID Metadata Document
A client identifier that is itself an HTTPS URL, which the authorization server fetches to read the client's metadata. Preferred over dynamic client registration in MCP revision 2026-07-28. It proves control of a domain, not control of whichever local process is listening on a localhost redirect URI.
Code challenge
The value a client sends in the authorization request to commit to a verifier it has not yet revealed. With the S256 method it is the base64url-encoded SHA-256 hash of the verifier.
Code verifier
A high-entropy random string the client keeps to itself and presents only on the back channel, proving it started the flow. RFC 7636 requires 43 to 128 unreserved characters.
Confidential client
A client that can keep a secret, such as a server-side application. It authenticates to the authorization server in its own right.
Confirmation claim
The cnf claim in a token, naming a key its holder must be able to use. It turns a bearer token into one that also requires proof of possession.
Confused deputy
A service that uses its own authority to carry out a request made on someone else's behalf. The downstream service sees the service's identity and not the user's, so an object check has nothing to compare the request against.
Constant-time comparison
A comparison that takes the same time whether values differ at the first byte or the last. Ordinary string comparison stops at the first difference, which can leak information through timing.
Content-Digest
A header carrying a hash of the message body, defined by RFC 9530. It is the only way a request body enters an HTTP message signature, and then only if it is a covered component and the receiver recomputes it.
CORS
Cross-origin resource sharing. The set of HTTP headers by which a server tells a browser that a response may be handed to a page from a different origin. The browser enforces it and the server only declares; a client that is not a browser is unaffected by it.
Covered components
The ordered list of message parts a signature is computed over. Anything not in the list is outside the signature and can be changed without invalidating it.
Cryptoperiod
"The time span during which a specific key is authorized for use or in which the keys for a given system or application may remain in effect" (NIST SP 800-57 Part 1 Rev. 5). The specifications give you the concept; the length is your judgment to make and defend.
Data minimisation
Putting only the fields a task needs into a prompt, chosen from an allowlist. It removes copies rather than filtering them, so it acts on every sink at once: logs, traces, caches, the provider and the answer.
Delegation
An arrangement where one party acts for another while keeping its own identity, so a token names both. RFC 8693 section 1.1 contrasts it with impersonation.
Derived component
A signature input derived from the control data or other parts of the message rather than from a header field, written with a leading @, such as @method, @authority or @path. RFC 9421 section 2.2.
DPoP
Demonstrating Proof of Possession. The client signs a small JWT per request with a key it holds, and the access token names that key, so a stolen token alone is not enough. RFC 9449.
Enumeration
Walking a range of identifiers to discover which ones exist. Sequential identifiers make it a loop; a refusal that distinguishes "forbidden" from "not found" makes it a map.
Fetch
The browser API that issues HTTP requests from a page, and the name of the WHATWG standard that defines request and response handling, including CORS. A fetch states whether credentials are omitted, included, or sent only to the same origin.
Front channel
A request or response that travels through the user's browser, usually as a redirect. Anything in a front-channel URL may reach browser history, referrer headers, proxy logs, and other apps on the device.
Hash
A fixed-length fingerprint of data, such as SHA-256. Anyone can compute it, and changing one byte of input changes the output completely. A hash alone proves nothing about who made it.
HMAC
Hash-based message authentication code. A hash computed with a secret key mixed in, so only key holders can produce or check it.
ID token
A JWT from OpenID Connect that tells a client who signed in. It is for the client, not for an API, and a verifier expecting an access token must reject it.
Idempotency key
A value, such as a transaction ID, that lets the receiver recognize a repeated business operation and return the original result instead of doing the work twice.
Impersonation
An arrangement where the acting party is given the rights of another and is "indistinguishable from" it in that context, so nothing downstream can tell a different party made the call. RFC 8693 section 1.1.
Improper output handling
Passing a model's output downstream without validating or encoding it for where it is going. OWASP LLM05:2025. The bug is in the calling code rather than in the model's answer.
Indirect prompt injection
Injection that arrives in content the model retrieves, such as a web page or a document, rather than from the person typing. Nobody has to attack the system; a document is edited and the agent reads it.
Insufficient coverage
A signature or approval that protects some of a message and not the rest, so the uncovered parts can change without invalidating it. RFC 9421 section 7.2.1 names it for HTTP signatures; the same reasoning decides which fields an approval must cover.
Introspection
Asking the authorization server whether a token is active right now. It answers for the moment you ask, so caching the answer trades liveness for load.
JWKS
JSON Web Key Set. The set of public keys an issuer publishes so verifiers can check its signatures, each identified by a key id. Covered in module 6.
JWT
JSON Web Token. A base64url-encoded header, payload and signature, separated by dots. The header and payload are readable by anyone holding the token; the signature only shows they were not altered.
Key rotation
Replacing a key on a schedule or after exposure. Usually both old and new keys are accepted during a short overlap, then the old one is retired.
keyId
An identifier sent with a signed request telling the receiver which key to verify with. It must never be the key itself.
Luhn check
The check digit algorithm card numbers satisfy. In a redactor it separates a card number from any other long number, which stops the redactor blanking order and invoice numbers that people need to read.
may_act claim
A claim in a token naming the party authorized to become the actor and act on behalf of its subject. It lets the authorization server decide whether a requested delegation was permitted when the subject token was issued, rather than at the moment an actor asks. RFC 8693 section 4.4.
MCP
Model Context Protocol. A JSON-RPC protocol for exposing data and tools to LLM applications. Revisions are dated strings such as 2026-07-28, incremented when a backwards incompatible change lands, and a protected MCP server is an OAuth 2.1 resource server.
mTLS
Mutual TLS. Both client and server present certificates, so each proves its identity to the other when the connection opens.
Non-repudiation
The property that a signer cannot plausibly deny having signed. An asymmetric signature gives a technical version of this, because the verifier could not have produced it, and it holds only as far as private key custody holds.
Nonce
A value used once. The receiver remembers nonces it has seen for a limited time and rejects repeats.
Object-level authorization
Comparing the authenticated caller with the owner recorded on the specific object a request names, after loading it. Its absence is OWASP API1:2023, Broken Object Level Authorization, or BOLA.
Origin
The scheme, host and port of a URL taken together, serialised with no path and no trailing slash, for example https://app.example. Two URLs are same-origin only when all three agree, so the same host over http is a different origin.
PKCE
Proof Key for Code Exchange. The client commits to a secret verifier by sending its hash, then proves possession of the verifier when redeeming the code, so a stolen code on its own is useless.
Post-filtering
Ranking a whole corpus and then removing results the caller may not see. It returns fewer results than asked for, which discloses that something was removed, and lets other tenants' documents outrank the caller's own. Pre-filtering the corpus avoids both.
Preflight
An OPTIONS request a browser sends before a cross-origin request that is not safelisted, carrying Access-Control-Request-Method and sometimes Access-Control-Request-Headers. It asks whether the CORS protocol is understood, not whether the caller is authorised.
Prompt injection
Content that alters a model's behaviour because instructions and data occupy the same sequence with nothing marking which is which. OWASP LLM01:2025 notes that fool-proof prevention is unclear, so the controls that hold sit either side of the model.
Protected resource metadata
A document a resource server publishes at a well-known location, naming its authorization servers and its supported scopes. RFC 9728. MCP requires servers to implement it and clients to use it to find the authorization server.
Provenance
The record of where a document or a claim came from, attached to it. Without it an untrusted retrieved claim becomes an unattributed fact, and deleting the source document does not reach what was written from it.
Public client
A client that cannot keep a secret, such as a mobile app or code running in a browser. It relies on PKCE rather than a client secret.
Push notification configuration
In A2A, the webhook a client gives a server for task updates: an HTTPS URL, an optional token tying notifications to one task, and optional authentication details. The URL is supplied by the client, so the server must not POST to it blindly.
Query string
The part of a URL after the question mark and before any fragment. It often contains named parameters and may be recorded in request logs.
Redirect URI
The address the authorization server returns the user to with the authorization code. It must be registered in advance and matched exactly, or an attacker can choose where the code goes.
Replay attack
Resending a captured, valid request unchanged. The signature is still correct, so only freshness and nonce checks stop it.
Resource indicator
The resource request parameter, which names the service a token is being requested for so the authorization server can bind the token's audience to it. RFC 8707.
Resource server
The server hosting the protected API. It validates the access token, including that the token was issued for it and that the scope covers the operation.
Retrieval-augmented generation
Answering with documents fetched from an index at request time. It makes the document store part of the authorization surface: who may read a document, and who may put one in.
Revocation
Withdrawing a grant before its token expires. A self-contained token does not change when this happens, so a resource server only notices if it consults current state.
Scope
The set of permissions a client requests and the resource owner grants. A scope limits what a token can do; it does not decide who may act on a specific object.
Sender-constrained token
A token that only works for a holder who can prove possession of a particular key, through a client certificate or a per-request proof.
Shared secret
A key known to both parties. Either party can create a valid signature, which is why a shared secret can't prove which one did.
Signature
A value computed from data and a key that lets a receiver check the data wasn't changed and came from a key holder.
Signature base
The exact ASCII string an HTTP message signature is computed over: one line per covered component, with the signature parameters as the last line. RFC 9421 section 2.5.
SPIFFE ID
A URI naming a workload, of the form spiffe://trust-domain/path, carried in a certificate's Subject Alternative Name. It is an identity, not an authorization, and the trust domain has no central registry.
State handle
A value a stateless server mints to carry state across requests, handed back to it as an ordinary argument. Possession of one is not authentication, so the server binds it to the caller it was minted for and refuses it from anyone else.
System prompt
The instructions an application puts in front of a model. It travels in the request payload like any other field, so OWASP states it is neither a secret nor a security control, and credentials do not belong in it.
TLS
Transport Layer Security. Encrypts a connection and proves the server's identity to the client. It protects data in transit, not after it arrives.
Token exchange
The OAuth grant urn:ietf:params:oauth:grant-type:token-exchange, which trades one security token for another. RFC 8693 requires three request parameters and leaves audience, resource, scope and the issued lifetime to the deployment.
Token passthrough
A server accepting a token that was not issued for it and forwarding it unchanged to a downstream API. Both halves are forbidden by the MCP specification: the audience check is the first, and the forwarding is what turns it into a confused deputy.
Token profile
The rules an application declares before verifying any token: allowed algorithms, token type, expected issuer and audience, required claims, key source and clock leeway. Nothing in it is read from the token.
Trust boundary
Any point where a request or a value moves from somewhere you do not control to somewhere you do. Checks belong on the boundary, and a check is only a control if every path to the handler crosses it.
Workload identity
An identity issued to a running service by its platform, rather than a secret handed to it at deployment. It removes the long-lived value that had to be rotated and distributed; it does not remove ownership, scope or retirement.
