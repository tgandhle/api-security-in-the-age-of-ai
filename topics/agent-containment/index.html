Part 5: Hardening and operations · Module 31

Agent code execution and containment

Last reviewed 2026-10-04 · Jump to reference

Objective. After this module you can say what an agent's code execution tool is able to reach, write a deny-by-default policy for it, put enforced budgets on a run, stop one agent's bad output before the next agent acts on it, and disable an agent that has left its declared behaviour, including the credential it holds.

Before you start. Part 4 covered what an agent is allowed to do. Module 22 showed that prompt injection cannot be reliably prevented, and module 23 showed what a human approval does and does not cover. This module assumes both controls are in place and the agent does the wrong thing anyway. It is about what limits the damage then.

1. The attack

Running example: ExampleAir runs an agent that counts bookings in a file and writes a summary. Company names are fictional. To do the work, the agent has a code execution tool: it can read and write files, fetch a URL and run a program. The task folder also holds a vendor's notes, and somebody has added one line to them addressed to the assistant.

The model reads the notes and its plan grows from four steps to ten. The six new steps read a credential file, dump the environment, send both to attacker.example, write a scheduled job outside the working directory, and try to evaluate a line of code. Nothing was exploited in the usual sense. The tool did what the plan said, and the plan came from text. This is an illustration, not a command.

OWASP's Top 10 for Agentic Applications for 2026 has three entries for what happens next, and this module takes one thread from each:

  • ASI05: Unexpected Code Execution (RCE). "Prompt injection, tool misuse, or unsafe serialization can convert text into unintended executable behavior."
  • ASI08: Cascading Failures. "Agentic cascading failures occur when a single fault (hallucination, malicious input, corrupted tool, or poisoned memory) propagates across autonomous agents, compounding into system-wide harm." This is a cascading failure.
  • ASI10: Rogue Agents. A rogue agent is one of the "malicious or compromised AI Agents that deviate from their intended function or authorized scope".

2. Why it works

Four broken assumptions sit behind the three entries.

  • "The tool only runs what we meant it to run." A code execution tool runs what the model asks for, and the model can be steered by anything it reads. ASI05 lists the routes: prompt injection that leads to attacker-defined code, shell commands taken from reflected prompts, unsafe function calls, object deserialization or code evaluation, exposed eval() functions in agent memory, and package installs where "hostile code executes during installation or import". It adds that because this code is "often generated in real-time by the agent it can bypass traditional security controls". Nobody reviewed it, scanned it or deployed it.
  • "The tool can only reach the task." By default the tool runs with whatever the agent process has: its files, its network and its environment variables. In the lab's Part A the credential is in a file and in the environment, and both leave. OWASP says ASI05 leads to "host or container compromise, persistence, or sandbox escape", which it calls "outcomes that require host and runtime-specific mitigations beyond ordinary tool-use controls". The tool table from module 22 decides which tool may be called and with which arguments. It does not decide what the tool can touch once it runs.
  • "A mistake stays where it was made." In a pipeline of agents, each one treats the previous one's output as its input. ASI08 "focuses on the propagation and amplification of faults rather than their origin", and lists among the observable symptoms "rapid fan-out where one faulty decision triggers many downstream agents or tasks in a short time". In the lab one message becomes five published fares.
  • "If every call is allowed, the agent is behaving." ASI10 says the agent's "actions may individually appear legitimate, but its emergent behavior becomes harmful, creating a containment gap for traditional rule-based systems". Each call can pass its check while the sequence does something nobody intended.

OWASP's LLM list files the root condition as LLM03:2026 Excessive Agency, and says that in agentic systems it "can manifest as ASI02: Tool Misuse & Exploitation, ASI03: Identity & Privilege Abuse and ASI08: Cascading Failures". The runaway loop in the table is LLM06:2026 Unbounded Consumption, which lists tools that force an application "into recursive or infinite tool-calling loops". The agentic document is older than the 2026 LLM list and cites the 2025 numbering: where it says LLM06:2025 it means Excessive Agency, which is LLM03 in the 2026 edition this course pins.

How the three entries relate, in OWASP's words: tool misuse is ASI02, but "if the misuse results in arbitrary or injected code execution, it is classified under ASI05 (Unexpected Code Execution)". ASI08 is about the spread and not the first fault. And "ASI10 focuses on the loss of behavioral integrity and governance once the drift begins, not the initial intrusion itself."

3. The control

None of the OWASP documents cited in this section sets requirements. Each OWASP entry is a list of guidelines, and the steps below report them in their own words. The order is the order a wrong step meets them.

Contain the execution (ASI05)

  1. Give the tool a fixed vocabulary, not an evaluator. ASI05: "Ban eval in production agents: Require safe interpreters, taint-tracking on generated code." LLM03:2026 says the same from the other side: "Avoid the use of open-ended tools where possible (e.g., run a shell command, fetch a URL, etc.) and use tools with more granular functionality."
  2. Run it in a sandbox. ASI05: "Never run as root. Run code in sandboxed containers with strict limits including network access". A sandbox is enforced from outside the thing it restricts.
  3. Limit files to a working directory. ASI05: "Where possible, restrict filesystem access to a dedicated working directory and log file diffs for critical paths." Check the normalized path, so /work/out/../../etc is judged as /etc.
  4. Limit the network with an egress allowlist. LLM06:2026: "Restrict the LLM's access to network resources, internal services, and APIs." Parse the URL and compare the host exactly against an allowlist. The lab compares the host and nothing else. It does not check the scheme or the port and has no redirects. Module 14 covers those, and the other ways a URL check goes wrong.
  5. Keep credentials out of the execution environment. No token in an environment variable, no credential file in reach. A call that needs a credential goes through a component outside the sandbox that holds it, which is module 22's rule that the application holds the credential and the model does not.
  6. Separate generating a plan from executing it. ASI05: "Isolate per-session environments with permission boundaries; apply least privilege; fail secure by default; separate code generation from execution with validation gates." A gate reads the whole plan before any step runs.
  7. Review before elevated runs. ASI05: "Require human approval for elevated runs; keep an allowlist for auto-execution under version control; enforce role and action-based controls." Module 23 is about making that approval mean something. ASI05 also lists static scans before execution, runtime monitoring, and logging of all generation and runs.

Bound the run (LLM06:2026)

  1. Enforce a step budget and a spend ceiling on every run. LLM06:2026: "Enforce step limits, recursion depth limits, time limits, and per-run cost ceilings on all agent executions. Use state hashing to detect recursive loops." On spending caps it says: "These must be enforcement mechanisms that halt inference when exceeded, rather than alerting thresholds that fast-accumulating workloads can outpace." Module 15 covers limits per caller. These are limits per run.

Stop the spread (ASI08)

  1. Put a trust boundary between agents. ASI08: "Isolation and trust boundaries: Sandbox agents, least privilege, network segmentation, scoped APIs, and mutual auth. to contain failure propagation."
  2. Validate output at a checkpoint before the next agent acts on it. ASI08: "Checkpoints, governance agents, or human review for high risk before agent outputs are propagated downstream."
  3. Cap the blast radius and add a circuit breaker. ASI08: "Implement blast-radius guardrails such as quotas, progress caps, circuit breakers between planner and executor." And: "Detect fast-spreading commands and throttle or pause on anomalies." The OWASP AI Agent Security Cheat Sheet also says: "Apply circuit breakers to prevent cascading failures."

Disable a rogue agent (ASI10)

  1. Declare what the agent is for, and sign the declaration. ASI10: "Attach signed behavioral manifests declaring expected capabilities, tools, and goals that are validated by orchestration services before each action." The lab signs the profile with an HMAC key the agent never sees.
  2. Monitor behaviour against that declaration. ASI10: "Monitor for anomalies such as excessive or abnormal actions executions."
  3. Have a kill switch, and make it revoke the credential. ASI10: "Implement rapid mechanisms like kill-switches and credential revocation to instantly disable rogue agents. Quarantine suspicious agents in sandboxed environments for forensic review." Quarantine stops the orchestrator dispatching calls. Revocation stops the credential working in the system that accepts it, which is where module 8 says revocation happens.
  4. Bring it back deliberately. ASI10: "Require fresh attestation, dependency verification, and human approval before reintegration into production networks."

ASI08 and ASI10 both also ask for a record: ASI10 for "comprehensive, immutable and signed audit logs of all agent actions, tool calls, and inter-agent communication". Module 30, Logging, detection and response, covers what to record and how to act on it. The lab keeps refused calls in the orchestrator's log for that reason.

If the task does not need a code execution tool, the best sandbox is not having one.

5. What it proves, and what it doesn't

Proves: that a step outside the policy did not run, that a run ended at its budget, that an output outside the checkpoint's limits did not reach the next agent, and that a revoked credential is refused.

Doesn't prove: that what ran was right. Lab check 53 sends a poisoned instruction that is inside every limit, a 30 percent cut on one route, with the checkpoint on and the breaker closed. It is published. A checkpoint validates shape and range. It cannot tell a legitimate 30 percent from an attacker's.

Doesn't detect the injection. Nothing in this module notices that the model was steered. The sandbox refuses the steps whatever their cause.

Doesn't make a sandbox out of a policy object. The lab's policy is consulted by the interpreter it restricts. A real sandbox is enforced by the operating system or a hypervisor, and sandboxes have had escapes. The lab also judges a path as text, and it uses one URL parser for both the check and the request. A real file system has symbolic links, which a check on the text does not see, and a real HTTP client may read a URL differently from the code that checked it. ASI05 names sandbox escape as an outcome, which is why the credential stays outside as well.

Doesn't keep up without automation. ASI08 describes "a potential discrepancy in the speed and scale of fault propagation in a multi-agent system and the ability of humans to keep up with them", and says this "leaves some unmitigated risks that the enterprise must evaluate carefully". A breaker that needs a person to open it is not a breaker.

Quarantine is not revocation. Check 59 of the lab takes a quarantined agent and has it call the fares API directly with the credential it already holds. The call succeeds. Quarantine is enforced by the orchestrator, and the agent did not go through the orchestrator. Check 60 revokes the credential and the same call is refused. A kill switch that only stops dispatching is a request to the agent to stop.

6. Prove it

A working deployment must refuse every one of these. If any is accepted, the control is broken:

  • A read of a file outside the working directory, including a credential file in the agent's home directory.
  • A write whose path leaves the write directory through .. segments.
  • A request to a host that is not listed, to a lookalike that ends in another domain, and to a URL that puts the allowed host in the userinfo position before @.
  • A program that is not on the list, and an allowed program pointed at a path outside the read directory.
  • A dump of the environment that contains any credential. Run it inside the sandbox and read the output.
  • A step the tool has no command for. It must be refused, not passed to an evaluator.
  • Step number budget plus one of a loop, and the step that would take spend over the ceiling.
  • An output from one agent with a field out of range, an unknown field, or more items than the cap, before the next agent is called.
  • A valid message while the breaker is open.
  • A tool call that is not in the agent's signed profile, and a profile the agent edited.
  • A call with a revoked credential, made directly to the resource and not through the orchestrator.

The OWASP AI Agent Security Cheat Sheet lists two of these as abuse cases to keep as repeatable tests: for recursive tool abuse, "Chain depth, retry, token, and cost limits stop runaway loops", and for multi-agent chaining, "One compromised agent cannot cause another agent to exceed its trust boundary".

8. Check your understanding

The agent's tool table from module 22 allows only run_code. Why is that not containment?

The table decides which tool may be called and with which arguments. It says nothing about what the tool can reach once it runs. A code execution tool with the agent's files, network and environment can do anything the agent's process can. OWASP describes the outcomes of ASI05 as needing "host and runtime-specific mitigations beyond ordinary tool-use controls".

The spend ceiling sends an alert when it is crossed. Is the run bounded?

No. LLM06:2026 says caps "must be enforcement mechanisms that halt inference when exceeded, rather than alerting thresholds that fast-accumulating workloads can outpace". In the lab the alert-only ceiling raises 988 alerts while the loop runs to 1000 steps.

The checkpoint refused three messages from the intake agent. The fourth is valid. Should it go through?

Not automatically. The checkpoint only sees shape and range, and the fourth message in the lab is a poisoned instruction that happens to be inside the limits. The breaker opens after three consecutive failures and holds everything from that source until a person has looked.

You quarantined an agent ten minutes ago. What have you not done yet?

Revoked its credential. Quarantine stops the orchestrator dispatching its calls. If the agent, or whoever controls it, holds a credential and can reach the resource directly, the credential still works until it is revoked where it is accepted. Then confirm that it is refused, as module 8 teaches.

Review checklist items

These are collected into the site checklist.

  • Agent-generated code and commands run only inside a sandbox Not as root, not in the agent's own process, and with no evaluator that takes model output as code.
  • File access is limited to a working directory, judged on the normalized path Test a read of a credential file and a write that leaves the directory through dot-dot segments. Both must be refused.
  • Egress from the execution environment is denied by default Allowed hosts are listed by exact name and compared after parsing the URL. Test a lookalike host and the userinfo form.
  • No credential is present in the execution environment Dump the environment and list the readable files from inside the sandbox. Neither contains a token or a key.
  • Every run has an enforced step budget and spend ceiling The run halts. The ceiling is charged before the step, so it is never exceeded, and it is not an alert.
  • A plan is checked before it executes Steps outside the auto-execution policy hold the plan for human approval, and nothing runs while it is held.
  • Output is validated between agents, behind a circuit breaker The checkpoint refuses unknown fields, out-of-range values and more items than the cap. The breaker opens on consecutive failures.
  • Each agent has a declared profile that it cannot edit Tools and call limits are checked before each action. A call outside the profile quarantines the agent.
  • The kill switch revokes the agent's credential where it is accepted Evidence is a refused call made directly to the resource after the switch, not a record that the switch was used.
  • Agents do not share credentials, and a quarantined agent returns only after review Revoking one agent leaves the others working. Its call log is kept, and reintegration needs human approval.
