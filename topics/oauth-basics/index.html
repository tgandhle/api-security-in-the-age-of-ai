1. The attack

Running example: a customer signs in at ExampleHotels so the ExampleAir app can read their points balance. Company names are fictional.

OAuth splits the exchange in two. The user's browser carries an authorization code back to the app over the front channel, then the app's server swaps that code for a token over the back channel. The split exists because the front channel is not private. The code travels through a redirect, so it can land in browser history, a referrer header, a proxy log, a malicious app registered for the same URI scheme, or an attacker sitting anywhere on the redirect path.

Whoever holds that code can try to redeem it. What stops them depends entirely on which protections the authorization server requires:

An attacker tries toNo PKCEPKCE plainPKCE S256
Redeem a code copied from the redirectWorksBlockedBlocked
Redeem a code when the authorization request was also observedWorksWorksBlocked
Redeem a code the real client has already usedBlockedBlockedBlocked
Redeem the code at a redirect URI they controlBlockedBlockedBlocked
Use an access token stolen from the clientWorksWorksWorks

The last row never turns green. PKCE protects the code, not the token that comes back. Binding the token to its holder is module 7.

2. Why it works

Four broken assumptions cause most of these failures:

  • "The redirect is private." It is not. A redirect is a URL handled by a browser, an operating system, and everything in between. Treat every value in it as published.
  • "Only my app can receive the code." Only if the redirect URI is matched exactly against a registered value. Prefix or wildcard matching lets an attacker choose where the code goes.
  • "A valid code means a valid client." Without PKCE it means only possession. A public client has no secret to prove anything else with, which is exactly why PKCE exists.
  • "A token proves who the user is." An OAuth access token is an authorization artifact. It says the resource owner granted this scope to this client. With the client credentials grant the client is its own resource owner: RFC 6749 section 1.3.4 describes the client as "acting on its own behalf (the client is also the resource owner)". It is not an identity assertion, and it is not permission for every operation the scope touches.

PKCE closes the third gap with a value that never crosses the front channel. The client generates a random code verifier, sends only its SHA-256 hash as the code challenge, and presents the verifier later on the back channel. An attacker who captures the code has the hash at best, and cannot work backwards to the verifier.

That is why the method matters. With plain, the challenge is the verifier, so anyone who sees the authorization request can redeem the code. RFC 7636 section 7.2 says plain "SHOULD NOT be used and exists only for compatibility with deployed implementations".

3. The control

What the client sends

Two requests, on two different channels. Only the second one carries anything worth stealing.

Front channel, in the browser, visible to everything on the path:
  GET /authorize
    response_type=code
    client_id=app-exampleair
    redirect_uri=https://app.exampleair.example/callback
    scope=balance:read
    state=<random, checked on return>
    code_challenge=<BASE64URL(SHA256(verifier))>
    code_challenge_method=S256

Back channel, server to server over TLS:
  POST /token
    grant_type=authorization_code
    code=<from the redirect>
    redirect_uri=https://app.exampleair.example/callback
    client_id=app-exampleair
    code_verifier=<43 to 128 unreserved characters, never sent before>

The verifier appears once, on the back channel. The challenge is all the front channel ever sees.

The state value in the first request is the client's defence against a forged return. The client puts a random value there, keeps it with the browser session, and when the browser comes back refuses a response whose state does not match. RFC 9700 section 4.7.1 describes it as "a random value, also known as a CSRF Token, in the state parameter" and adds: "The same protection is provided by PKCE or the OpenID Connect nonce value." Section 2.1 lets a client rely on PKCE for this only when it has "ensured that the authorization server supports" PKCE. Module 35 shows what state does not prove, and module 28 covers forged requests in general.

How the authorization server verifies

  1. At the authorization request, match redirect_uri exactly against the registered list. Record the challenge and the method with the code. Anything unregistered: reject before issuing a code.
  2. At redemption, look up the code. Unknown, expired, or already used: reject. On reuse, also revoke tokens already issued from that code.
  3. Check the code is bound to this client_id and this redirect_uri. Different either way: reject.
  4. Verify the challenge using the method recorded at step 1, never a method supplied at redemption. Compare with a constant-time comparison.
  5. Authenticate the client if it is a confidential client. PKCE and client authentication answer different questions; do both where both apply.
  6. Issue a token scoped to what was granted and addressed to the resource server that will receive it. Mark the code used.

The resource server then does its own work: validate the token, check it was issued for this audience, and check the scope covers this operation. A token that passes validation at the wrong resource server is a broken deployment, not a valid request.

5. What it proves, and what it doesn't

Proves: that a resource owner granted this scope to this client, and, with PKCE, that the party redeeming the code is the party that started the flow.

Doesn't prove: who the user is, that the user is still present, or that the operation is permitted. It proves nothing about the holder of the resulting token, which is a bearer credential like any other.

An access token is not an identity. OAuth authorizes a client; it does not authenticate a user to that client. If your application signs a user in on the strength of an access token, any client that can obtain a token for the same user can impersonate them. Standardized user authentication is OpenID Connect (module 35), which adds a separate ID token with its own validation rules. Do not send an ID token to a resource server, and do not treat an access token as a login.

6. Prove it

A working authorization server must reject every one of these. If any is accepted, the control is broken:

  • A code redeemed without a verifier, when a challenge was recorded.
  • A code redeemed with a verifier that does not hash to the recorded challenge.
  • A code redeemed with code_challenge_method set to plain at redemption, when S256 was recorded.
  • A code redeemed twice, with tokens from the first redemption revoked.
  • A code redeemed with a different client_id or a redirect_uri that differs by one character.
  • An authorization request with an unregistered redirect URI, or with response_type=token.
  • A token request with grant_type=password.
  • A scope the client was never granted.
  • A token presented at a resource server it was not issued for.

8. Check your understanding

Why does PKCE use a hash rather than sending the verifier in the authorization request?

The authorization request travels through the browser, so anything in it can be read. Sending the hash means an attacker who captures the request still cannot produce the verifier the token endpoint will ask for. With plain the challenge is the verifier, which is why RFC 7636 says not to use it.

A public mobile app has no client secret. What stops a malicious app on the same device from redeeming its code?

PKCE. The malicious app can register for the same redirect URI and receive the code, but it never saw the verifier, which was generated in the real app's memory and sent only on the back channel.

Your service uses client credentials and the authorization server returns a refresh token. What do you do?

Question it. RFC 6749 section 4.4.3 says a refresh token SHOULD NOT be included. The client can authenticate and request a new token whenever it needs one. A refresh token here is extra long-lived credential to protect for no benefit.

You validate a token's signature, issuer and expiry, and it passes. Is the request authorized?

No. Those checks say the token is genuine and current. They do not say it was issued for your resource server, or that its scope covers this operation, or that this caller may touch this particular object. Audience and scope are in this module; object-level authorization is module 9.

Exercises

Change one thing and predict the output

Each exercise edits one place in labs/oauth_lab.py and asks what the run prints. The lab records every result and prints a failure summary at the end. The answers are the real output of each variant.

1. The PKCE method is taken from the token request

In _authorization_code, honour a code_challenge_method sent at redemption time: if it says plain, compare the verifier against the stored challenge directly instead of hashing it first.

How many checks change?

Every option, and why
  • Check 10 does become accept, but it does not stop there. Look at what redeeming a code does to the code.
  • Correct. Exit 1, three failures. Check 10 becomes accept: the attacker holds the challenge, claims plain, and the server compares the challenge to itself. Then check 11, the real client with its real verifier, becomes reject: invalid_grant, and check 12 becomes reject: invalid_token, because the attacker's redemption already marked the code used. The downgrade does not just let the attacker in, it locks the legitimate client out, and that is what the run shows. Check oauth-01 in the Reference layer is why the method is the one recorded at the authorization request.
  • Check 8 sends no verifier at all, so there is nothing to compare under either method. It still rejects.
  • It was, and that is the point: the attacker does not need to change the challenge, only the method used to check it against.

2. The redirect URI is matched by prefix

In authorize, accept a redirect URI that starts with a registered one instead of requiring an exact match:

if not any(params.get("redirect_uri", "").startswith(u)
           for u in client["redirect_uris"]):
Which check changes?

Every option, and why
  • Check 7 uses the registered callback exactly, so it accepts either way. That check is about the absence of PKCE, not about the URI.
  • Correct. Exit 1, one failure: check 15 goes from reject: invalid_request to accept. That request adds a character to the end of the registered callback, which a prefix match cannot see. Where the added characters go is what decides how bad it is, and a path or a query the attacker controls is enough to read the code out of the redirect. RFC 9700 section 2.1 requires exact string matching, and check oauth-02 in the Reference layer says the same.
  • Check 16 sends the registered callback exactly, so it passes the URI match either way. It is refused for its challenge method.
  • It does still reject a different host, which is exactly why this bug survives review. The attack is a suffix on the host you already registered, not a different one.

3. A reused code is denied, but nothing is revoked

In _authorization_code, keep returning invalid_grant when a code is reused, but delete the loop that removes tokens issued from that code.

Which check changes?

Every option, and why
  • Check 13 still rejects. Denying the second redemption is the part this edit leaves alone.
  • Correct. Exit 1, one failure: check 14 goes from reject: invalid_token to accept. A replayed code is evidence that somebody other than the client has it, so the token already issued from it is suspect. RFC 6749 section 4.1.2 says the server MUST deny the request and SHOULD revoke the tokens previously issued from that code. Denying without revoking leaves the attacker's token working, and check oauth-04 in the Reference layer is where that gets caught.
  • Only one of the two moves. The denial and the revocation are separate behaviours, which is the distinction the exercise is for.
  • It is, and that is not enough. The question is what happens to the token issued the first time.

4. The code is not bound to the client that requested it

In _authorization_code, delete the two lines that reject when the client_id in the token request is not the one the code was issued to.

What does the run print differently?

Every option, and why
  • Check 7 already sends the right client id. Every redemption in this lab does.
  • Those three are refused by the PKCE checks, which this edit does not touch.
  • Correct. Exit 0, 27 of 27 lines identical, all lab checks passed. Every redemption in the lab uses the client the code was issued to, so the binding check never fires and removing it costs nothing that the lab can see. Measured separately, with a second client registered at the same callback and holding the verifier: as published the server answers reject: invalid_grant, and without the binding it answers accept. The verifier is handed over on purpose there, because that is the only way to see which check was doing the work. Check oauth-04 in the Reference layer asks for codes bound to client and redirect URI, and this lab tests neither half at redemption: check 15 tests the redirect URI at the authorization request, not the binding of the code.
  • Check 13 rejects on reuse, which is recorded against the code itself and is unaffected.

Reference

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardPublic clients must use PKCE, and authorization servers must support it. For confidential clients RFC 9700 section 2.1.1 recommends it rather than requiring it.
  • StandardA client that can use S256 must use S256. RFC 7636 section 4.2 makes S256 mandatory to implement on the server, and section 7.2 says plain should not be used.
  • StandardThe code verifier is 43 to 128 characters from the unreserved set, generated with a high-entropy cryptographic random source. RFC 7636 section 4.1.
  • StandardAuthorization servers must match redirect URIs by exact string comparison, except for port numbers in localhost redirect URIs of native apps. RFC 9700 section 2.1.
  • StandardA client must not use an authorization code more than once. On reuse the server must deny the request and should revoke tokens previously issued from that code. RFC 6749 section 4.1.2, which also recommends a maximum code lifetime of 10 minutes.
  • StandardThe resource owner password credentials grant must not be used. RFC 9700 section 2.4.
  • StandardRFC 9700 section 2.1.2 says clients should not use the implicit grant, or any response type that returns an access token in the authorization response, unless access token injection in the authorization response is prevented and the token leakage vectors that section names are mitigated.
  • StandardFor the client credentials grant, a refresh token should not be included in the response. RFC 6749 section 4.4.3.
  • StandardSend bearer tokens in the Authorization header. RFC 6750 section 2.1 says clients should use it and resource servers must support it.
  • StandardToken endpoint errors use the codes defined in RFC 6749 section 5.2 with HTTP 400 unless specified otherwise: invalid_request, invalid_client, invalid_grant, unauthorized_client, unsupported_grant_type, invalid_scope.
  • BaselineVerify the challenge with the method recorded at the authorization request. Ignore any method supplied at redemption.
  • BaselineOne client registration per application and environment, with its own redirect URIs and its own narrow scope list.
  • BaselineIssue codes with a 60 second lifetime. The legitimate client redeems immediately; a long lifetime only helps an attacker.
  • BaselineResource servers check the audience first, then the scope for the specific operation, then object-level authorization.
  • BaselineError responses name the RFC 6749 error code and nothing about which check failed.
  • OptionSender-constrain access tokens with mTLS (RFC 8705) or DPoP (RFC 9449) where token theft is a material risk. RFC 9700 section 2.2.1 recommends this rather than requiring it. Module 7.
  • OptionUse a backend for frontend so a browser application's tokens are held server side and never reach page scripts.
  • OptionAdd OpenID Connect when the client needs standardized user authentication rather than delegated access. Module 35.

Review checklist items

These are collected into the site checklist.

  • Public clients use the authorization code grant with PKCE S256 The server records the challenge and method at the authorization request and verifies against the recorded method, not one supplied at redemption.
  • Redirect URIs are matched by exact string comparison No prefix, wildcard, or substring matching. Localhost port numbers for native apps are the only documented exception.
  • The implicit and password grants are disabled at the authorization server Test that response_type=token and grant_type=password return errors. Existing integrations that use them have a dated migration plan.
  • Authorization codes are single use, short lived, and bound to client and redirect URI A second redemption is denied and revokes tokens already issued from that code. Test the replay path, not just the happy path.
  • Resource servers validate the token audience and the scope for the operation A token issued for one resource server is rejected by another. A valid token is not permission for every operation its scope touches.
  • Service-to-service clients have their own identity, narrow scopes, and no refresh token One registration per service and environment. The client secret or key comes from an approved runtime secret mechanism.
  • An access token is never treated as proof of user identity Sign-in uses standardized user authentication. ID tokens are not sent to resource servers, and access tokens do not create sessions.
  • Token endpoint errors use the defined codes and leak nothing else Responses do not reveal which check failed, whether a client exists, or whether a code was valid but expired.
