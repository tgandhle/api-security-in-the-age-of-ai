Request and response contracts

Last reviewed 2026-09-30 · Jump to reference

Objective. After this module you can explain how two parsers reading the same bytes reach different answers and what that costs you, name the values a JSON parser accepts that no contract describes, and place limits in the only order that works: before the parser, not in the schema.

Before you start. Every check in this course so far ran on a parsed request. This module is the step before that, and it is the step where the object those checks inspect gets decided.

1. The attack

Running example: ExampleAir's partner transfer endpoint, taking a JSON body with a transaction identifier and a number of miles. Company names are fictional. Authentication passes, the object and property checks pass, and the schema validator approves the body.

The body is {"partnerTxnId": "EXA-42", "miles": 10, "miles": 90000}.

The validator read miles as 10 and approved it. The handler read miles as 90000 and credited it. Both were correct, in the sense that neither did anything its library does not do by default, and both reported success. Nothing logged an error, because from each component's point of view nothing went wrong.

That is one of three ways the parsing step betrays the checks built on top of it. The second is values the parser will hand you that your contract never described. The third is inputs whose cost lands during parsing, before any validator exists to refuse them.

Five of these reach the schema in a state the schema cannot describe, and one of them never reaches it at all. That is the shape of the module: a contract is a statement about a parsed object, and most of these problems are decided before there is one.

2. Why it works

The same bytes, two objects

RFC 8259 is unusually direct about the repeated-name case. It says "the names within an object SHOULD be unique", which is a recommendation rather than a requirement, and then describes what actually happens when they are not: "Many implementations report the last name/value pair only. Other implementations report an error or fail to parse the object, and some implementations report all of the name/value pairs, including duplicates."

Three behaviours, all conformant. So the question "what does this body mean" has no single answer, and any two components that parse it separately can disagree. The exposure is largest wherever a request is parsed more than once: a gateway and a service, a validator and a handler, a service written in one language calling one written in another. The attacker does not need to know which parser does what. Sending both values and seeing which one takes effect is one request.

Values with no place in the contract

RFC 8259 section 6 is equally clear that "numeric values that cannot be represented in the grammar below (such as Infinity and NaN) are not permitted", and Python's json module parses both by default. It is not alone in this, and the reason is compatibility with what other implementations emit. The result is that a field your contract says is a positive number can arrive as infinity and satisfy a check for being greater than zero.

The range problem is next to it. JSON's grammar puts no limit on the magnitude of a number, and section 6 notes only that "good interoperability can be achieved by implementations that expect no more precision or range than" an IEEE 754 double provides. So 1e400 is valid JSON, and what your parser gives you for it is a decision your parser made, not one the format made. Python gives you infinity.

Cost that lands before any check

Section 9 requires that "a JSON parser MUST accept all texts that conform to the JSON grammar", and then says the thing that makes this tractable: an implementation "may set limits on the size of texts that it accepts", "may set limits on the maximum depth of nesting", and "may set limits on the range and precision of numbers". The specification anticipates exactly the defence this module is about, and it is the API's job to set those limits because the format will not.

The reason they have to come first is mechanical. Deeply nested input costs you during parsing, so a schema validator that runs on the parsed object never executes. A compressed body costs you during decoding, so a size check on the decoded object happens after you already paid. OWASP's API4:2023 puts the instruction plainly: "define and enforce a maximum size of data on all incoming parameters and payloads, such as maximum length for strings, maximum number of elements in arrays, and maximum upload file size".

3. The control

  1. Limit the declared size, and the decoded size while decoding. Not after. A body that expands from kilobytes to megabytes has already cost you by the time you can measure the result.
  2. Inspect the text before building an object. Nesting depth and repeated names are both visible in the bytes, and both are cheap to measure without a parser.
  3. Reject repeated names outright. Not last-wins, not first-wins: rejected. Any resolution you choose is a resolution some other component will choose differently.
  4. Configure the parser to refuse what the format forbids. NaN and Infinity are not JSON. Most libraries accept them and most offer a setting that does not.
  5. Bound number range and literal length at the parser or immediately after, since the grammar bounds neither.
  6. Then validate against the schema, on the object you now have, for types, required fields, ranges and formats.
  7. Apply the same discipline to responses. A response you consume from another service is somebody else's request body arriving at your parser, which is module 14.

5. What it proves, and what it doesn't

Proves: that the object your handler received is the object your validator approved, that it contains only values the format permits, and that producing it cost a bounded amount.

Doesn't prove: anything about whether the request should be allowed. A perfectly formed body from a caller who may not make this call is what Parts 1 and 2 are for. This module only makes sure those checks are looking at the same thing the handler will act on.

A schema is not a limit. It is a description of an object, evaluated once the object exists. Everything that stops an object existing, or makes existing expensive, happens earlier and has to be configured somewhere the schema cannot reach. Teams that adopt a schema often believe they have adopted input limits, and the two lists barely overlap.

6. Prove it

For each endpoint that accepts a body:

  • A body with a repeated name is rejected, not resolved.
  • Two components that parse the same request agree, or only one of them parses it.
  • NaN, Infinity and -Infinity are rejected.
  • A number outside the field's declared range is rejected, including one that becomes infinity.
  • A body nested past the limit is rejected without a stack trace and without the parser running to exhaustion.
  • A compressed body that decodes past the limit is rejected during decoding, measured by the bytes produced.
  • Every string and array field has a maximum length, and it is not one global number.
  • The rejection names the rule rather than echoing the value.
  • All of the above are tested, and the tests are in the build.

Checks 1 to 4 are the whole of Part A. One body, two parsers, two values, and both parsers returned successfully. There is no error to find later, because neither component did anything wrong.

Checks 8 and 9 are worth reading as a pair with the ones above them. Check 8 is a refusal you configured: parse_constant turning NaN into a rejection. Check 9 is not a refusal at all, it is the parser raising because the integer literal exceeds Python's digit limit. Both appear in a log as an exception, and only one of them is a control.

Check 11 is the one to try changing. A hundred thousand open brackets is 200 KB of input, well under any sensible body limit, and it exhausts the parser. Check 12 measures the same body's depth without parsing it, in a few lines, and check 13 refuses it. The order is the entire control.

Checks 14 to 17 are the compression case. A body that arrives under 64 KiB decodes to megabytes, and a limit that inspects the decoded object measures something you have already paid for.

Part D closes it. The nested body never reaches the schema at all, and the other two satisfy it completely. A schema was never going to be where this is caught.

8. Check your understanding

Two services parse the same request body. Why is that a security problem rather than a duplication problem?

Because a repeated name has no single meaning. RFC 8259 recommends unique names and documents three conformant behaviours when they are not: last wins, error, and all pairs kept. Two components can each behave correctly and reach different values, so a validator can approve one number while a handler acts on another. Either reject repeated names or make sure only one component parses the request.

Your schema says miles is a number greater than zero. Does infinity satisfy it?

In most implementations, yes. Infinity is not valid JSON, and Python's parser produces it anyway unless told otherwise, at which point it is a number and it is greater than zero. The fix is in the parser's configuration, not in the schema, and it needs a bounded range on the field as well.

Why can a nesting limit not live in the schema?

Because the schema runs on an object and a deeply nested body is an attack on the process of building one. The parser exhausts its stack first, so the validator that would have refused the input never executes. Depth is visible in the text, so it can be measured before parsing, which is the only place the check does any good.

You accept gzipped request bodies and limit bodies to 1 MiB. What is the limit on?

Whichever number you measured. If it is the bytes that arrived, a 64 KiB body can decode to megabytes and you have no limit on the thing that costs you. The limit has to be enforced during decompression, on the bytes produced, with the decoder stopped when it passes the threshold.

  • Standard"Define and enforce a maximum size of data on all incoming parameters and payloads, such as maximum length for strings, maximum number of elements in arrays, and maximum upload file size." OWASP API4:2023, How To Prevent.
  • StandardOWASP API4:2023 lists execution timeouts, maximum allocable memory, the number of operations in a single request and the number of records per page among the limits whose absence makes an API vulnerable.
  • BaselineReject a body containing a repeated name. Do not resolve it.
  • BaselineParse each request once, or prove that every component parsing it resolves the same bytes the same way.

Review checklist items

These are collected into the site checklist.

  • Repeated names are rejected, not resolved Test a body with one name twice. Any silent resolution is a resolution another parser makes differently.
  • Limits run before the parser Size, decoded size and nesting depth. A schema runs on an object, and these inputs are the ones that stop an object existing.
  • Decoded size is bounded during decompression Measured on the bytes produced, with the decoder stopped at the limit. A limit on the bytes received is not this.
  • The parser refuses NaN and Infinity Neither is valid JSON. Most libraries accept them by default and offer a setting that does not.
  • Every numeric field has an explicit range The grammar bounds neither magnitude nor digit count. Test a value that becomes infinity.
  • Either one component parses the request, or they demonstrably agree Gateway and service, validator and handler, or two languages. Test the same body through each.
  • String and array fields have per-field maximum lengths A single global limit sized for the largest field is no limit for the rest.
  • Rejections name the rule and do not echo the value One status, one error shape, no attacker-controlled bytes in logs or responses.
