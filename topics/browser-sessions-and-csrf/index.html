Browser sessions, cookies and CSRF

Last reviewed 2026-10-04 · Jump to reference

Objective. After this module you can explain how a cookie session works, show why a browser will send a request the user never asked for, say what each cookie attribute and each anti-forgery control stops, and review a session's whole life from login to logout.

Before you start. You should be able to read an HTTP request and a Python function, and you should know what an origin is. Module 17, CORS, covers who may read a response from another origin. This module covers requests that are sent and take effect whether or not anyone can read the response. The two fit together, and this page does not repeat that one.

1. The attack

ExampleAir's members manage their miles at app.exampleair.example. The page and its API share that origin. When a member logs in, the server creates a session and sends the browser a cookie that holds a session identifier. From then on the browser attaches that cookie to every request it sends to that host, and the API treats the cookie as proof of who is asking. The company and the people are fictional.

Maya is logged in. In another tab she opens a page on evil.example. That page contains a hidden form whose target is https://app.exampleair.example/api/transfer, and a script that submits it. Maya's browser sends the POST and attaches her session cookie, because the cookie belongs to the host the request is going to. In this first version the cookie is set with SameSite=None, an attribute section 3 explains, so the browser attaches it whichever site caused the request. The API sees a valid session and moves 10,000 miles to the attacker. This is cross-site request forgery (CSRF): the attacker never sees the cookie and never needs to.

2. Why it works

A bearer credential in a header is attached by code that chose to attach it. A cookie is attached by the browser, by rule. The cookie specification names the problem: "user agents attach cookies even if the remote party does not know the contents of the cookies", and "the issue stems from cookies being a form of ambient authority" (RFC 6265 section 8.2, and the same words in section 8.2 of the rfc6265bis draft). The attacker chooses the request. The browser supplies the authentication. That is a confused deputy, and here the deputy is the browser.

Five assumptions keep this bug alive:

  • "A request with our session cookie came from our page." It came from the user's browser. Any page open in that browser can cause it.
  • "The attacker cannot read the response, so nothing happened." CORS decides who may read. The transfer happens when the server processes the request. Module 17 shows the same row from the other side.
  • "Our API only accepts JSON." Under the Fetch Standard a browser sends a preflight for "requests that are more involved than what is possible with HTML's form element". That sentence is in section 3.3.1. A POST whose Content-Type is application/x-www-form-urlencoded, multipart/form-data or text/plain is not one of those (sections 2.2.1, 2.2.2 and 4.1). A script can put JSON text in a text/plain body. A note in section 2.2.2 of the standard, written about a request that carries Content-Type twice, names the same danger: such a request would go out with no preflight, and "a naïve parser on the server might treat the request body as JSON". The claim is true only if the server refuses every other content type.
  • "GET is harmless." Only if no GET changes anything. A link, an image tag and a redirect all send GET.
  • "Our subdomains are us." Same-origin means the scheme, host and port all match. Same-site is wider: the scheme and the registrable domain match, where the draft defines the registrable domain as the public suffix plus the label to its left, and a public suffix as the part of a domain that a public registry controls (section 2.3). Here the public suffix is example and the registrable domain is exampleair.example. app.exampleair.example and promo.exampleair.example are two origins and one site. A forgotten marketing host, a host that serves customer content, or a subdomain an attacker has taken over is inside that boundary, and RFC 10017 section 6.1.3.3.1 names the result: a takeover of one subdomain enables CSRF against its sibling.

3. The control

No single item below is enough. Apply them in this order, because each one covers a gap the one before it leaves.

What the cookie says

Set-Cookie: __Host-sid=<session id>; Path=/; Secure; HttpOnly; SameSite=Strict

__Host-          name prefix: the browser stores it only with Secure, Path=/ and no Domain
<session id>     random, meaningless, looked up on the server
Path=/           sent for every path on this host
Secure           sent only over HTTPS
HttpOnly         hidden from scripts (document.cookie)
SameSite=Strict  withheld from requests another site caused
(no Domain)      sent to this host only, not to its subdomains

The right-hand notes are for this page only. Secure, HttpOnly, Path and Domain are defined in RFC 6265. SameSite and the __Host- and __Secure- prefixes are not in RFC 6265. They are defined in draft-ietf-httpbis-rfc6265bis-22, an Internet-Draft that has not been published as an RFC. The CSRF Prevention Cheat Sheet reports that current browsers support both, but the document that defines them can still change.

What the server does, in order

  1. Make sure no safe method changes state. GET, HEAD, OPTIONS and TRACE are the safe methods. RFC 9110 section 9.2.1 says that when a URL selects an unsafe action, "the resource owner MUST disable or disallow that action when it is accessed using a safe request method". Every later control assumes this one.
  2. Set SameSite explicitly. Strict: the cookie goes only with same-site requests. Lax: also with a top-level navigation from another site, if the method is safe. A top-level navigation is a request that loads a new page into the tab, as a followed link or a submitted form does. None: with every request, and the browser accepts it only with Secure. With no attribute, the draft applies a default equal to Lax, and it allows a looser mode for recently created cookies, so do not rely on the default.
  3. Require a CSRF token on every state-changing request. With a synchronizer token, the server keeps a random value in the session, the page receives it in a response body, and the page sends it back in a custom header or a form field. With a double-submit cookie, the server keeps nothing: the token is an HMAC over the session identifier and a random value, delivered in a cookie the page can read and sent back in a header. Compare with a constant-time comparison. Never put the token in a URL.
  4. Check where the request came from. Read Sec-Fetch-Site. Refuse cross-site on unsafe methods, and refuse same-site too unless you trust every host under your site. If the header is absent, compare Origin with your own origin, exactly, and refuse if it is absent or different.
  5. Refuse content types you do not parse. A JSON API answers 415 to anything that is not application/json, and never guesses the format from the body.
  6. Issue a new session identifier at login. Destroy the one from before login. Accept a session identifier from the cookie only, never from a URL. This stops session fixation.
  7. End sessions on the server. Apply an idle timeout and an absolute timeout, and delete the session record on logout. Clearing the cookie is not enough.

If the page holds a token instead of a cookie

A single-page app can send an access token in an Authorization header instead of using a cookie. The browser does not attach that header by itself, so a form on another site sends no credential and classic CSRF does not apply. A script on another site that tries to set Authorization triggers a preflight, and it does not know the token anyway.

The cost is where the token lives. The page's script must be able to read it, so any script that runs in the page's origin can read it too. RFC 10017, the best current practice for OAuth in browser apps, says that "localStorage does not protect against unauthorized access from malicious JavaScript" (section 8.5), and that none of the persistent storage APIs it lists can fully stop token theft once an attacker runs code in the app.

RFC 10017 ranks three designs "in decreasing order of security" (section 6). The first is the backend for frontend (BFF): a server component that belongs to the app, runs the OAuth flow, keeps the tokens, and gives the browser only a session cookie. The browser calls the BFF, and the BFF adds the access token and forwards the call. RFC 10017 strongly recommends this design for business applications, sensitive applications and applications that handle personal data (section 6.1.4.3), and does not recommend a browser-only OAuth client for those (section 6.3.4.3). A BFF is a cookie session again, so everything in this module applies to it: "The BFF MUST implement a proper CSRF defense" (section 6.1.3.3). Module 4, OAuth basics, covers the flow, and module 7, Sender-constrained tokens: mTLS and DPoP, covers what a stolen token can still do.

5. What it proves, and what it doesn't

Proves: a valid session cookie proves that the request came from a browser that holds the cookie. A valid CSRF token proves that the sender could read a value that only your own origin can read. A Sec-Fetch-Site: same-origin header proves that a browser says your own origin made the request.

Doesn't prove: that the user meant it. None of these controls survive a script running in your own origin. That script reads the token, sends same-origin requests, and the cookie goes with them. The CSRF Prevention Cheat Sheet says cross-site scripting "can defeat all CSRF mitigation techniques". RFC 10017 section 5.1.4 calls this proxying requests through the user's browser and says: "It is commonly accepted that this scenario cannot be stopped or prevented by application-level security measures." Preventing injected script is a separate job.

SameSite is one layer. The draft says Lax "does not offer a robust defense against CSRF as a general category of attack" (section 5.6.7.1), and of Strict that it is "prudent to ensure that this designation is not the extent of a site's defense against CSRF" (section 8.8.1). The cheat sheet's reason is the boundary: "SameSite is scoped to the registrable domain, not the origin." A browser that does not implement the attribute ignores it.

The source headers mean something only from a browser. A script on the attacker's own machine sets Origin and Sec-Fetch-Site to anything. It has no session cookie, so it gains nothing, but that is the cookie doing the work. The headers are a filter for forged browser requests. They are not authorization, and a proxy can strip them, which is one more thing to test at the gateway (module 12, Gateway enforcement).

A CSRF defence is only as good as your CORS policy. The synchronizer token is safe because a page on another origin cannot read the response that carries it. An API that reflects any Origin and allows credentials, the fault module 17 teaches, hands the token to the attacker's page, and the forged request then carries a valid token.

6. Prove it

A working implementation must pass every one of these. If any fails, the control is broken:

  • A state-changing request with a valid session and no CSRF token is refused. So is one with a wrong token, and one with a valid token from a different session.
  • No GET, HEAD or OPTIONS request changes anything. Test every route, including the old ones.
  • A POST with Sec-Fetch-Site: cross-site is refused, and so is one with Sec-Fetch-Site: same-site unless that is a recorded decision.
  • A POST with no Sec-Fetch-Site and an Origin that is absent, a sibling subdomain, or a lookalike such as https://app.exampleair.example.evil.example is refused.
  • A JSON endpoint answers 415 to text/plain and to form content types.
  • The session cookie in a real response carries Secure, HttpOnly, an explicit SameSite, and no Domain.
  • The session identifier after login differs from the one before, and the old one is refused.
  • A session identifier supplied in a URL is ignored.
  • A session identifier copied before logout is refused after logout, after the idle timeout, and after the absolute timeout.
  • All of the above are tests in the build, sent with a plain HTTP client that sets the headers itself.

8. Check your understanding

A page on another site posts a form to your API. The browser will not let that page read the response. Why is that not a defence?

The server processes the request before any response exists. Reading is what CORS controls, and module 17 covers it. The forged request needs only to arrive with the session cookie attached, and the attacker learns that it worked when the miles show up.

Your API parses JSON bodies only. Is it safe from forged requests?

Only if it also refuses every request whose Content-Type is not application/json. A request with that content type from another origin needs a preflight, and an API that allows no other origin refuses it. A request labelled text/plain needs no preflight, and a server that parses the body as JSON anyway accepts it. Keep the other controls as well: the preflight rule is a browser behaviour, and the CSRF Prevention Cheat Sheet advises adding tokens in case a browser fails to enforce it.

promo.exampleair.example is taken over. The session cookie is SameSite=Strict. What still stops a forged transfer from that host?

Not the cookie attribute: the two hosts share a site, so the cookie is sent. A synchronizer token or a signed, session-bound double-submit token stops it, because the attacker's page cannot read a value from your origin. An exact Origin comparison stops it, and so does refusing Sec-Fetch-Site: same-site. A __Host- prefix on your cookies stops that host from planting cookies of the same name.

A team replaces the session cookie with an access token kept in localStorage and sent in an Authorization header. What did they gain and what did they lose?

They gained immunity to classic CSRF, because the browser no longer attaches the credential by itself. They lost HttpOnly: any script that runs in the page's origin can read the token and take it away, where before it could only send requests while the page was open. RFC 10017 ranks this design last of its three and recommends a backend for frontend for sensitive applications.

Reference

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardA user agent that attaches a Cookie header must include a cookie with the Secure attribute only when the request uses a secure protocol, and must leave a cookie with HttpOnly out of the cookie string it builds for a non-HTTP API such as script access. Without a Domain attribute a cookie is host-only. RFC 6265 sections 5.3 and 5.4, summarized in sections 4.1.2.3 to 4.1.2.6.
  • StandardCookies are ambient authority: "user agents attach cookies even if the remote party does not know the contents of the cookies", which can let a remote party exercise authority at an unwary server. RFC 6265 section 8.2. This is the security considerations section and sets no requirement.
  • StandardSafe methods are GET, HEAD, OPTIONS and TRACE, and when a URL selects an unsafe action "the resource owner MUST disable or disallow that action when it is accessed using a safe request method". RFC 9110 section 9.2.1.
  • StandardDraft: a user agent that attaches cookies must leave out a cookie whose same-site flag is not None when the request is cross-site, unless the flag is Lax or the default, the request is HTTP, the method is safe and the request's target is the active browsing context or a top-level traversable. The draft takes that term from the HTML Standard, and this page reads it as a tab or a window. draft-ietf-httpbis-rfc6265bis-22 sections 5.8.1 and 5.8.3. An Internet-Draft, not a standard.
  • StandardDraft: a user agent must ignore a cookie with SameSite=None and no Secure, a cookie named __Secure- without Secure, and a cookie named __Host- unless it has Secure, no Domain and Path=/, matching the prefix without regard to case. Servers should use the prefixes. draft-ietf-httpbis-rfc6265bis-22 sections 5.7, 5.4 and 4.1.3.
  • StandardDraft: Lax "does not offer a robust defense against CSRF as a general category of attack", and developers are strongly encouraged to deploy the usual server-side defences, for which it gives CSRF tokens and ensuring that safe methods are idempotent as examples. The server should take care to avoid session fixation. draft-ietf-httpbis-rfc6265bis-22 sections 5.6.7.1, 8.8.1 and 8.4.
  • StandardA cross-origin request avoids a preflight when its method is GET, HEAD or POST and every header is CORS-safelisted, and a Content-Type of application/x-www-form-urlencoded, multipart/form-data or text/plain is safelisted. The Origin header is sent on CORS requests and on requests whose method is neither GET nor HEAD. Fetch Standard sections 2.2.1, 2.2.2, 3.2 and 4.1.
  • StandardWorking Draft: Sec-Fetch-Site carries cross-site, same-origin, same-site or none, where none marks a navigation the user caused directly. The Sec- prefix makes the header "unmodifiable from JavaScript". Servers should ignore the header if its value is invalid. Fetch Metadata Request Headers sections 2.3 and 4.2. A W3C Working Draft, not a Recommendation.
  • StandardThe CSRF Prevention Cheat Sheet recommends the synchronizer token pattern for stateful software and the signed double-submit cookie, bound to the session, for stateless software. It discourages the unsigned form, says a Fetch Metadata check needs a fallback to Origin or Referer verification, and says not to use GET for state-changing operations. OWASP CSRF Prevention Cheat Sheet, Introduction and the sections "Signed Double-Submit Cookie (RECOMMENDED)", "Naive Double-Submit Cookie Pattern (DISCOURAGED)" and "Fetch Metadata headers". Guidance, not a requirement.
  • StandardThe Session Management Cheat Sheet says the session identifier is to be renewed after any privilege level change, with login the most common case, that idle and absolute timeouts are to be enforced on the server, that logout is to invalidate the session on the server, and that "deleting a cookie alone does not invalidate a stolen copy of the session ID". OWASP Session Management Cheat Sheet, sections "Renew the Session ID After Any Privilege Level Change", "Idle Timeout", "Absolute Timeout" and "Expire and Max-Age Attributes". Guidance, not a requirement.
  • StandardFor a backend for frontend, RFC 10017 requires Secure and HttpOnly on its cookies and a CSRF defence, and recommends SameSite=Strict, a path of /, no Domain attribute and a name prefix that shows the cookie was set over HTTP, for which its example is __Host-Http- from a separate Internet-Draft this page does not cover. It notes that SameSite=Strict falls short when another application shares the site. RFC 10017 sections 6.1.3.2, 6.1.3.3 and 6.1.3.3.1.
  • StandardOWASP Top 10:2025 lists reusing the session identifier after login and failing to invalidate sessions on logout or inactivity under A07 Authentication Failures, and maps CWE-352, cross-site request forgery, to A01 Broken Access Control. A07 section "Description" and A01 section "List of Mapped CWEs". An awareness document: it sets no requirements.
  • BaselineName the session cookie with the __Host- prefix and set Path=/; Secure; HttpOnly; SameSite=Strict with no Domain. Use Lax only where links from other sites must arrive logged in.
  • BaselineRequire a CSRF token on every state-changing request: a synchronizer token, or a signed double-submit token bound to the session. Compare in constant time. Never accept it from a cookie alone or put it in a URL.
  • BaselineRefuse unsafe methods whose Sec-Fetch-Site is cross-site or same-site. When the header is absent, require Origin to equal your own origin exactly, and refuse when it is absent.
  • BaselineAnswer 415 to any content type the endpoint does not parse. Never infer the format from the body.
  • BaselineIssue a new session identifier at login, destroy the old one, and accept identifiers from the cookie only.
  • BaselineEnforce a 15 minute idle timeout and an 8 hour absolute timeout on the server, and delete the session record on logout.
  • OptionUse SameSite=Lax for a cookie that grants read access and a second Strict cookie that is required for changes, as section 8.8.2 of the draft describes.
  • OptionRequire a custom request header on API calls so that a cross-origin script request always needs a preflight. RFC 10017 section 6.1.3.3.2 recommends this for a BFF that relies on CORS as its CSRF defence.
  • OptionAsk the user to authenticate again before the most sensitive operations, such as a password change or a large transfer.
  • OptionSend an access token in the Authorization header instead of a cookie when there is no backend to hold a session. Classic CSRF no longer applies, and the token becomes readable by any script in the origin.

Review checklist items

These are collected into the site checklist.

  • Every state-changing request in a cookie session carries a CSRF token the server verifies A missing token, a wrong token and a valid token from another session are all refused. A double-submit token is signed and bound to the session.
  • No safe method changes state GET, HEAD and OPTIONS routes are read-only, including legacy routes. A link or an image tag sends GET, and SameSite=Lax sends the cookie with a link.
  • The session cookie sets Secure, HttpOnly, an explicit SameSite, Path=/ and no Domain Prefer the __Host- name prefix and SameSite=Strict. Read the attributes from a real response, not from configuration.
  • Unsafe requests are refused unless Sec-Fetch-Site or Origin shows the app's own origin Cross-site and same-site are refused, the Origin comparison is exact, and a request with neither header is refused. Test a sibling subdomain and a lookalike host.
  • The session identifier is replaced at login and at every change of privilege The identifier from before login is destroyed, and an identifier supplied in a URL is never accepted.
  • Sessions end on the server Idle and absolute timeouts are enforced server-side, and logout deletes the session record. A copied identifier is refused after each of the three.
  • Endpoints refuse content types they do not parse A JSON endpoint answers 415 to text/plain and form content types. This is a layer, not the CSRF defence.
  • Every host under the registrable domain is known and trusted to the same level A sibling subdomain is same-site, so SameSite cookies are sent with its requests and it can set cookies for the parent domain. Remove unused DNS records.
  • The place a browser app keeps its tokens is a recorded decision Tokens in script-readable storage are exposed to any injected script. A backend for frontend keeps them on the server and needs the CSRF controls above.
