Object-level authorization

Last reviewed 2026-09-30 · Jump to reference

Objective. After this module you can write an ownership check that reads the owner from the stored object, recognise the five shapes in which the check exists in a codebase and not in effect, choose between 403 and 404 on purpose, and say what an ownership check does not decide.

1. The attack

Running example: ExampleAir's booking API. Company names are fictional. The caller is acct-77, a real customer, correctly authenticated on every request below.

The attack is changing a number in a URL. GET /bookings/bkg-1001 returns your booking, so you try bkg-1002. Every credential check passes, because nothing about the credential changed. The only thing that changed is the object being asked for, and nothing looked at that.

OWASP lists this first, as API1:2023 Broken Object Level Authorization, and rates it easy to exploit, widespread, and easy to detect. The detectability rating is worth sitting with: it is easy to detect by trying, and it produces no errors, no anomalies and a completely ordinary access log while it happens.

The last two rows stay open, and they are the two halves of the rest of Part 2. A related object needs its own check, in its own handler. An action needs a check about the action, which is module 10.

2. Why it works

OWASP's definition of object-level authorization is worth quoting because the important word is where the check lives: "Object level authorization is an access control mechanism that is usually implemented at the code level to validate that a user can only access the objects that they should have permissions to access."

At the code level. Not in a gateway, not in a policy file, not in a middleware that never sees the object. The check needs two values, and one of them can only be obtained by loading the object: who the caller is, and who the object belongs to. Anything upstream of the data access has the first and not the second.

Which is why this defect survives good architecture. A team with a solid gateway, validated tokens, scopes and mutual TLS still has to write this comparison, per object, in every handler, and nothing above the handler can write it for them. It is repetitive, it is easy to omit once, and omitting it once is the whole vulnerability.

The identifier being guessable is not the cause. Sequential integers make enumeration a loop instead of a search, so unguessable identifiers are worth using, and OWASP does recommend random values such as GUIDs. But an unguessable id is a delay, not a control: identifiers leak in referrals, logs, exports, support tickets and shared links, and the moment one leaks the missing check is exactly as missing as before.

3. The control

The check

Load the object, read the owner from the object you loaded, compare it with the caller established by authentication, and refuse before returning anything. Four steps, and each one of them is a place this goes wrong:

  1. Load the object first. You cannot check ownership of a record you have not read. A check that runs before the load is checking something else.
  2. Read the owner from the loaded record. Not from a parameter, a header, a body field or a hidden form value. If the caller can supply it, the caller can supply yours.
  3. Compare against the identity authentication produced. The subject from the validated token, not a user id in the request that happens to match it.
  4. Refuse before the response is built. Including before any part of it is logged, cached, or emitted in an error message.
The requestWhere the check belongsEvery route to the objectRefusal

403 or 404

A refusal has to say something, and what it says is information. RFC 9110 defines both codes and is explicit that the choice is available to you. Under 403 it notes that "if the server wishes to hide that the target resource exists, the server can respond with a 404 (Not Found) status code instead", and under 404 that "the server does not need to reveal whether the target resource exists or merely refuses access to it".

So: 403 tells the caller the object exists and they may not have it. 404 tells them nothing. The difference matters because 403 turns an id range into a map. An attacker walking identifiers learns which ones are real, which is useful on its own and more useful combined with anything else they find later.

The project baseline is 404 for an object the caller may not see, and 403 only where the caller is known to be entitled to know the object exists, such as a shared resource they have been removed from. Whichever you choose, choose it once and apply it consistently, because a service that returns 404 from most handlers and 403 from one has disclosed exactly the same thing through the inconsistency.

5. What it proves, and what it doesn't

Proves: that the caller this request authenticated as is the owner recorded on the object this request named, at the moment it was loaded.

Doesn't prove: that they may perform this action on it. Ownership is one question and the operation is another, which is why a customer who owns a booking can still be refused a refund on it. It also says nothing about which fields of the object they may see or set, and nothing about objects reached through this one.

The check exists in most of the codebases where this is found. It is in the main read handler, written correctly, and missing from the bulk export, the admin-adjacent route, the v1 endpoint still serving traffic, or the handler for the object the response embeds. Finding this defect is not a search for code that is absent; it is an enumeration of every path that reaches the object and a check that each one carries it.

6. Prove it

For every object type your API exposes, all of these must hold:

  • A second, authenticated caller is refused the object, on every verb it is exposed under.
  • The list endpoint returns nothing belonging to anyone else, verified against the query, not the response.
  • Supplying an owner identifier in the request changes nothing about the outcome.
  • Every object referenced in a response is refused to the same second caller when requested directly.
  • The refusal is the same code and body whether the object exists or not, unless you documented a deliberate exception.
  • Older API versions still serving traffic pass all of the above.
  • The tests for all of the above run in the build, and a failure stops the deployment.

Check 7 is there because a cancelled booking is the part customers notice. Part A's check 3 is not a read of data that should have been private; it destroyed a stranger's travel plans, and the caller needed no tooling to do it.

Part C is five pairs, and each pair is the same request against two handlers. Check 8 is the most common shape in real code: the handler compares the caller with an owner the caller supplied, which is an elaborate way of comparing a value with itself. Check 10 is the second most common: the query returns every row and the filtering is somewhere later, so the data left the database and the API's job was already done wrong. Check 12 is the one that survives reviews, because the booking handler is correct and the invoice handler was written by someone reading a different ticket. Check 14 is a one-word bug: if caller and booking["owner"] != caller skips the comparison entirely on any path that arrives without a caller.

Checks 16 and 17 put a number on it. With no check, five identifiers in a range return five records. With the check, the same walk returns the two that belong to the caller, and the other three are indistinguishable from identifiers that were never issued.

Checks 18 and 19 are the boundary of this module. The caller owns that booking, so the ownership check has done its job and has no opinion about refunds. Module 10 is where the second question gets asked.

Try next:

  • Change bkg-1002's owner to acct-77 and rerun. Watch which checks move and satisfy yourself that the verdict follows the stored record rather than the identifier.
  • Delete the caller and guard from get_guarded_check. Check 14 flips, and that is the entire fix for a defect that returns another customer's booking.
  • Add a sixth booking owned by acct-77 and rerun. Check 17 changes and check 16 does not, which tells you which number is about your data and which is about your code.
  • Make probe return 403 for unknown identifiers as well as forbidden ones. Check 20 flips. Decide whether you would rather leak existence or leak nothing.

8. Check your understanding

Why can a gateway not make this decision for you?

Because it has the caller and not the object. The comparison needs the owner recorded on the record being requested, and that value exists only after the record is loaded, which happens in the service. A gateway can enforce that a caller may use an endpoint. It cannot enforce which rows they may have from it.

Your handler compares the caller with an owner id from the request body, and they match. What have you checked?

That a value the caller sent equals a value the caller sent. The comparison succeeds for every request an attacker constructs, because they supply both sides. The owner has to come from the record you loaded.

The item endpoint is correct and the list endpoint returns everything, filtered in the front end. How bad is that?

It is the same vulnerability with a better yield. The item endpoint leaks one record per request and requires guessing identifiers; the list endpoint hands over every record in one response, and the filtering that hides them is running on the attacker's own machine. Filter in the query.

You switch every refusal from 403 to 404. What have you gained and what have you not?

You have stopped confirming which identifiers exist, which makes enumeration blind. You have not added a single access control: the check that refuses the request is the same check it was before. If the check is missing, the status code it would have returned is not the problem.

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardObject level authorization is "usually implemented at the code level to validate that a user can only access the objects that they should have permissions to access". OWASP API Security Top 10 2023, API1:2023.
  • StandardValidate the caller's permission against every object reached using an identifier from client input, in every handler that reaches it. OWASP API1:2023, How To Prevent.
  • StandardWrite tests for the authorization mechanism and do not deploy a change that fails them. OWASP API1:2023, How To Prevent.
  • StandardUse random, unpredictable values for record identifiers, such as GUIDs. OWASP API1:2023, How To Prevent. This raises the cost of discovery; it is not the access control.
  • StandardChoose the refusal code deliberately. RFC 9110 section 15.5.4 notes that "if the server wishes to hide that the target resource exists, the server can respond with a 404 (Not Found) status code instead", and section 15.5.5 that "the server does not need to reveal whether the target resource exists or merely refuses access to it".
  • BaselineLoad the object, read the owner from the loaded record, compare with the identity authentication produced, and refuse before any part of the response is built.
  • BaselineNever read the owner from a request parameter, header or body field.
  • BaselineFilter list endpoints in the query. Never after serialisation and never in the client.
  • BaselineApply the check on every verb the object is exposed under, not only reads.
  • BaselineGive every related object its own check in its own handler. Reaching it through an object you own does not transfer ownership.
  • BaselineReturn 404 for anything the caller may not see, consistently across the service.
  • BaselineEnumerate every path that reaches each object type, including older versions still serving traffic, and confirm each one carries the check.
  • OptionReturn 403 where the caller is entitled to know the object exists, such as a shared resource their access to was removed. Document it, and keep it out of the paths where existence is itself the secret.
  • OptionEnforce ownership in the data access layer, so a handler that forgets the check cannot load the row at all. This trades some flexibility for a default that fails closed.

Review checklist items

These are collected into the site checklist.

  • Every handler compares the caller with the owner read from the loaded object Quote the line for each object type. A comparison against a value from the request is not a check.
  • The check is present on every verb and every path to the object Reads, writes, deletes, bulk exports, and any older API version still serving traffic. One path without it is the vulnerability.
  • List endpoints filter in the query Verified against the query, not the response. Filtering after serialisation or in the client means the data already left.
  • Related and embedded objects are checked in their own handlers Test each referenced object directly as a second caller. Reaching it through an object you own does not make it yours.
  • A second authenticated caller is refused, and there is a test that proves it Per object type, in the build, and a failure stops the deployment.
  • Refusals do not disclose existence The same status and body whether the object exists or not, consistently across the service, unless an exception is documented.
  • Identifiers are unguessable, and nothing depends on that Random values raise the cost of discovery. Removing the check because identifiers are UUIDs is not a trade, it is the vulnerability.
