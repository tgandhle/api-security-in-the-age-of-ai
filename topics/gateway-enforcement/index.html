Gateway enforcement

Last reviewed 2026-09-30 · Jump to reference

Objective. After this module you can list every path that reaches a service, tell the controls a gateway can carry from the ones it cannot, explain why a header the gateway sets is a credential, and reconcile an architecture diagram against the connections that actually exist.

Before you start. Parts 1 and 2 put checks in handlers. This module is about the network those handlers sit on, and it reuses the reconciliation habit from module 8: a document is a claim until it has been compared with the thing it describes.

1. The attack

Running example: ExampleAir's booking, loyalty and reporting services behind an API gateway. Company names are fictional. The gateway authenticates every request, applies rate limits, validates against the schema and logs everything. The diagram is accurate about what the gateway does.

It is wrong about something else: the arrow. The diagram shows one arrow into each service, and there are more. A batch job calls reporting directly because that was simpler than issuing it a token. The loyalty service calls booking over the cluster network because they are neighbours. A partner reaches an old version over a VPN that was set up for a migration. A staging deployment with production data is answering on the public internet because a load balancer rule outlived the test it was created for.

None of those is an attack. They are four ordinary decisions, each sensible at the time, and together they mean the gateway is enforcing nothing for any of the services behind it, for any caller who can reach them another way.

The last row is the one that makes this hard to find. Every other defect in this course leaves evidence in the place you would look. A request that never reached the gateway is absent from the gateway's logs, which is the source most teams use to answer "who is calling this service".

2. Why it works

An API gateway is a choke point, and a choke point is a control only while it is the only way through. That sounds obvious stated plainly and is easy to lose, because the gateway is genuinely enforcing those controls on the traffic it sees, and the traffic it sees is the traffic anyone looks at.

NIST SP 800-207 puts the underlying principle as a tenet of zero trust: "All communication is secured regardless of network location", and "network location alone does not imply trust". Being inside the cluster is not a credential. In the running example, the loyalty service is a well-behaved internal component, and the reason it can call booking without authenticating is not that anyone decided it should be allowed to, it is that nothing stopped it.

The second mechanism is the header. A gateway that authenticates typically tells the service who the caller is, in a header. That header is now a credential, and it has the property every credential must not have: anything that can reach the service can set it. RFC 7239, defining Forwarded, states the general case precisely: such a field "cannot be relied upon to be correct, as it may be modified, whether mistakenly or for malicious reasons, by every node on the way to the server, including the client making the request". The same is true of X-Caller-Id or whatever your gateway uses, and unlike Forwarded it usually has no specification at all telling anyone to be careful with it.

The third is inventory. OWASP's API9:2023 is about knowing what exists, and its questions are exactly the ones this exercise asks: "Which environment is the API running in (e.g. production, staging, test, development)? Who should have network access to the API (e.g. public, internal, partners)? Which API version is running?" A service you cannot answer those three questions about is not protected by a gateway, whatever the diagram says, because nobody knows whether it is behind one.

3. The control

Which controls a gateway can carry, and which it cannot

This is the distinction that makes the rest of the module tractable. Some controls need only the request, and a gateway has the whole request. Others need the object, the caller's relationship to it, or the business state, and a gateway has none of those.

ControlA gateway canThe service must
AuthenticationValidate the credential and reject a bad oneValidate it too, because the gateway is not the only path
Object authorizationNothing: it has not loaded the objectAll of it. Module 9
Property authorizationNothing: it does not know which fields mean whatAll of it. Module 10
Function authorizationRefuse a method and path a role may not useEnforce it too, for the same reason as authentication
Rate limitingApply a shared limit across callersApply its own where the limit protects something the service owns
Schema validationReject a body that does not match the contractValidate its own input regardless
Request size and timeoutsEnforce them, and this is worth having at the edgeEnforce its own, because a bypass path has none
Access loggingLog every request it seesLog too, or bypass traffic is invisible

Read the middle column as "worth doing at the edge" and the right column as "the thing that is actually load bearing". A gateway is a good place to stop obvious traffic cheaply and early. It is a poor place to be the only thing standing between a caller and a decision.

The exercise

  1. List the services, and for each one record its environment, who should have network access to it, its version, whether that is the current version, and whether it holds production data. The first three are OWASP API9's questions.
  2. List the paths, meaning every source that can open a connection to it: the gateway, other services, batch jobs, partner networks, operator tooling, anything.
  3. Get that list from the network, not from the diagram. Connection logs, service mesh telemetry, security group rules, whatever your platform can tell you. The diagram is the claim being tested.
  4. For each path that does not cross the gateway, ask what the service does for itself, and treat every gateway control as absent on that path.
  5. For every identity header, ask which paths can set it. If any path that reaches the service can, the header is not evidence of anything.
  6. Record the date. The answer is true as of the reconciliation and decays from there, exactly as in module 8.

5. What it proves, and what it doesn't

Proves: for the paths you have enumerated, which controls apply on each one, and which services are relying on a control that is not present on every route to them.

Doesn't prove: that you enumerated them all. This is module 8's limit in a different domain: the answer is exactly as complete as the path list, the path list has to come from the network rather than the diagram, and it is accurate on the day it is produced. A connection made the following week is in nobody's review.

A gateway is not a bad control. It is a control with a precondition. The precondition is that it is the only path, and that is a property of your network rather than of the gateway. Nothing about buying, configuring or tuning the gateway establishes it, and it stops being true quietly, by way of a change nobody thought was a security change.

6. Prove it

For each service:

  • A list of every source that can open a connection to it, produced from the network rather than from a diagram, and dated.
  • For each path, which of the gateway's controls apply, stated explicitly rather than assumed.
  • Evidence that a request without a credential is refused by the service itself, tested on a path that does not cross the gateway.
  • For every identity header the service reads, the list of paths that can set it, and what makes the gateway distinguishable from them.
  • The environment, version and intended audience of the deployment, which are OWASP API9's three questions.
  • For every non-current version reachable at all, a retirement date.
  • For every non-production deployment, evidence it holds no production data or has production controls.
  • Service-side access logs, so traffic that skipped the gateway is still visible somewhere.

Part A is the part that makes this defect survive reviews. Three paths, all through the gateway, no findings, and every statement in the architecture document is true. A review that reads the document and stops here concludes correctly from the evidence it was given.

Part B is the same reconciliation module 8 applied to credentials, in a different domain. Seven paths exist and three were written down, and two of the five services appear in no document at all. Those two are the staging deployment and the old version, which is not a coincidence: the services nobody documents are disproportionately the ones nobody has thought about since they were created.

In Part C, batch-nightly -> svc-reporting collects four findings, and the second one is the header. The reporting service reads the caller's identity from a header the gateway sets, and the batch job reaching it directly can set that header to anything. The identity is not weakly authenticated; it is supplied by the caller.

Part D closes every Critical with three changes: each service authenticates for itself, the reporting service stops trusting the header, and staging loses its production data. Authentication and authorization alone leave two. Every path that skips the gateway keeps one finding. That residue is honest: schema validation, size limits and request logging really were the gateway's, and on a path that skips it they really are absent. The fix for those is either to remove the path or to implement them in the service.

Part E is the standing cost. One connection made after the review is in none of Part C's checks, not because it is safe but because the review had already run.

8. Check your understanding

Your gateway authenticates every request. Which services are protected by that?

The ones that cannot be reached any other way. For every other service the statement is about the traffic the gateway happens to see, which is not the same as the traffic the service receives. The way to find out is to enumerate the paths from the network, not to read the architecture diagram.

The gateway strips client-supplied identity headers and sets its own. Is the service safe to trust them?

Only on connections that came from the gateway, and only if the service can tell. Anything else that can reach the service can set the same header, and RFC 7239 makes the point about the Forwarded header, and it holds for any header a proxy adds: it can be modified by every node on the way, including the client. Either give the gateway a connection the service can authenticate, such as mutual TLS, or have the service validate the original credential itself.

Which of the controls in this course can a gateway actually perform?

The ones that need only the request: credential validation, method and path rules, rate limits, schema validation, size limits, logging. Not the ones that need the object or the business state, so not object authorization, not property authorization, and not anything about whether this particular caller should have this particular record. Those have to be in the service because only the service has loaded the data.

A service-to-service call inside the cluster does not authenticate. What is the argument against fixing it?

Usually that the network is trusted, which NIST SP 800-207 addresses in one sentence: network location alone does not imply trust. The practical version is that the boundary protecting that call is a network control somebody else maintains, and you will not be told when it changes.

Reference

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • Standard"All communication is secured regardless of network location", and "network location alone does not imply trust". NIST SP 800-207 section 2.1.
  • StandardThe Forwarded header "cannot be relied upon to be correct, as it may be modified, whether mistakenly or for malicious reasons, by every node on the way to the server, including the client making the request". RFC 7239 section 8.1. The same applies to any identity header a gateway injects.
  • StandardRFC 7239 section 8.1 also notes that whitelisting trusted proxies is limited, because the chain before the proxy cannot be trusted and, "unless the communication between proxies and the endpoint is secured, the data can be modified by an attacker with access to the network".
  • StandardThe Forwarded header "should never be copied into response messages", as it can reveal the whole proxy chain to the client. RFC 7239 section 8.2.
  • StandardBe able to answer, for every API host: which environment it runs in, who should have network access to it, and which version is running. OWASP API9:2023.
  • Standard"Avoid using production data with non-production API deployments. If this is unavoidable, these endpoints should get the same security treatment as the production ones." OWASP API9:2023, How To Prevent.
  • StandardApply protective measures to all exposed versions of an API, not only the current production one. OWASP API9:2023, How To Prevent.
  • BaselineAuthenticate in the service on every request, regardless of what the gateway did.
  • BaselineProduce the path list from the network, not the diagram, and record the date it was produced.
  • BaselineTreat every gateway control as absent on any path that does not cross the gateway, and write down which those are.
  • BaselineDo not use a gateway-injected identity header as the caller's identity unless the service can authenticate the connection it arrived on.
  • BaselineGive service-to-service calls, batch jobs and operator tooling credentials of their own.
  • BaselineLog in the service as well as at the gateway, so bypass traffic is visible somewhere.
  • OptionUse mutual TLS between the gateway and the services, so an injected header arrives on a connection the service can attribute. This makes the header meaningful; it does not make the gateway the only path.
  • OptionEnforce at the network layer that only the gateway can reach the service, which is worth doing and is a second control to maintain rather than a replacement for the first.

Review checklist items

These are collected into the site checklist.

  • Every service authenticates for itself, on every path Tested from a path that does not cross the gateway. A service that only works because the gateway checked is unauthenticated on every other route.
  • The path list comes from the network and is dated Connection logs, mesh telemetry or firewall rules. A diagram is the claim being tested, not the evidence.
  • No gateway-injected identity header is trusted without an authenticated connection List every path that can set it. If any path that reaches the service can, the header is caller-supplied.
  • Non-production deployments hold no production data and are not publicly reachable Or they carry production controls, which OWASP states as the alternative.
  • Every reachable non-current version has a retirement date Reachability is the test, not whether the gateway routes to it.
  • Service-to-service calls, batch jobs and operator tooling carry their own credentials Network position is not a credential.
  • Each gateway control is recorded as present or absent per path Schema validation, size limits, rate limits and logging are absent on any path that skips the gateway. Say so explicitly.
  • Services log requests themselves Otherwise the traffic that bypassed the gateway is also the traffic that left no record.
