Attacks on authentication endpoints

Last reviewed 2026-10-04 · Jump to reference

Objective. After this module you can name the attacks that target login, password reset and credential change endpoints, say which control stops each one and which it leaves open, and review a password reset flow for the faults that turn it into a way around the login.

Before you start. You should know what a hash is and what a rate limit does. The primer covers the first and module 15 (Rate limiting and cost controls) covers the second. Modules 1 to 8 covered API keys, request signing, OAuth and tokens. This module covers what they left out: the endpoints where a person proves who they are with a password.

1. The attack

Running example: ExampleHotels members sign in to their rewards account with an email address and a password. Company names are fictional. Three endpoints accept a claim about identity: login, password reset and the change of a sign-in address. OWASP lists the failures of all three as API2:2023 Broken Authentication, and its test for a vulnerable API starts from the point this module is built on: "Authentication endpoints and flows are assets that need to be protected."

A second site, ExampleForum, is breached. Its list of email and password pairs circulates. Some ExampleHotels members used the same password on both sites. Nobody has broken into ExampleHotels, and its login endpoint is about to tell an attacker which of those pairs work.

The guessing attacks come in three shapes. The OWASP Authentication Cheat Sheet defines them in one line each:

  • Brute force. "Testing multiple passwords from a dictionary or other source against a single account."
  • Credential stuffing. "Testing username/password pairs obtained from the breach of another site."
  • Password spraying. "Testing a single weak password against a large number of different accounts."

Each one is shaped to get past a different limit, which is why the table needs more than one column. Every cell was measured by running the two services from the lab in section 7 with that column's controls switched on. The lab's own transcript prints a selection of them.

Guessing is half of the module. The other half needs no guess at all: an error message that says which addresses have accounts (enumeration), a reset token that can be predicted or used twice, and an email change that asks for nothing except a session. Part A of the lab runs all of them.

2. Why it works

OWASP's summary of the attacker's position is short: "The authentication mechanism is an easy target for attackers since it's exposed to everyone." A login endpoint cannot require authentication, because it is where authentication happens. Six broken assumptions do the rest:

  • "Only the user knows the password." People reuse passwords, and other sites lose them. The OWASP Multifactor Authentication Cheat Sheet says to plan for it: "it should be assumed that users' passwords will be compromised at some point". A stuffed password is not a guess. It is right on the first attempt.
  • "A wrong guess costs the attacker something." Without a limit on failures it costs one request. The vulnerable service in the lab answers 11 dictionary guesses and gives up the account on the eighth.
  • "An error message only helps the user." "No such account" and "wrong password" together are a membership test for any email address. The same leak has two quieter forms: a different status code, and a different amount of work. A login that returns early for an unknown account skips the password hash, so it answers faster.
  • "We already have a rate limit." Module 15 limits what an identified caller may spend. A login attempt has no identified caller: the only names available are the account being claimed and the address the request came from, and the attacker chooses both. The thing to count is failed attempts, not requests: the first attack scenario in API2:2023 is a login limited to three requests a minute, which the attacker gets around by putting many login attempts into one batched request. And refusing has a victim, because locking an account also locks out its owner. OWASP asks for more than the general limit: "This mechanism should be stricter than the regular rate limiting mechanisms on your APIs."
  • "Password reset is a convenience feature." It is a second way to sign in, and OWASP says to treat it as one: "Credential recovery/forgot password endpoints should be treated as login endpoints in terms of brute force, rate limiting, and lockout protections." A reset token is a temporary password that the service chose. If it is a counter, anyone who has seen one token knows the next.
  • "A valid session means the user is present." A session identifier is a bearer credential. Whoever holds it can use it. If a session alone can change the sign-in address, then a stolen session becomes a stolen account, by way of the reset flow. That is the second attack scenario in API2:2023.

API2:2023 also lists token faults: unsigned tokens, missing expiry checks, weak keys. Module 5 (JWT validation) covers those. It also says "API keys should not be used for user authentication", which is the boundary between this module and module 1 (API keys).

3. The control

At sign-in, in this order

  1. Check the limits before doing any work. Count recent failures for the submitted username and for the source address. If either is over its limit, answer 429 and stop. No password hash is computed for a refused attempt.
  2. Verify the password with a slow, salted hash, every time. If the account does not exist, verify against a dummy record anyway, so an unknown account costs the same work as a known one. Compare with a constant-time comparison.
  3. Check the second factor if the account has one. Multi-factor authentication asks for evidence of a different kind, usually a one-time password from a device the user holds. Accept each code once.
  4. On any failure, give one answer. The same status, the same body and the same headers for an unknown account, a wrong password and a wrong code. Count the failure against the username and the source.
  5. On success, clear the account's failure count and issue a new session. What happens to that session afterwards is the subject of module 28 (Browser sessions, cookies and CSRF).

Why two counters

Each counter stops the attack the other one misses. A counter per account stops brute force, and the Authentication Cheat Sheet explains why it should not be per address: "The counter of failed logins should be associated with the account itself, rather than the source IP address", because an attacker can spread guesses over many addresses. A counter per account alone misses spraying, which is designed to touch each account only a few times. A counter per source catches that, as long as the spray comes from one place. Neither catches a list replayed from many addresses with one attempt per account. The Credential Stuffing Prevention Cheat Sheet says so about the tools that do this: "This may defeat both IP block-lists and rate limiting, as per IP request volume may remain relatively low, even on high volume attacks."

That is why the same cheat sheet leads with a different control. It calls multi-factor authentication "by far the best defense against the majority of password-related attacks, including credential stuffing and password spraying", and says of the alternatives: "In isolation none of these are as effective as MFA".

Lockout or delay

Account lockout refuses every attempt on an account for a period after too many failures. It caps the guessing rate, and it hands the attacker a new tool: anyone who knows a username can keep its owner out. The Authentication Cheat Sheet warns that "care must be taken to prevent it from being used to cause a denial of service by locking out other users' accounts", and OWASP's A07:2025 entry puts both halves in one sentence: "Limit or increasingly delay failed login attempts but be careful not to create a denial of service scenario."

The lab's answer is a lock that is short, grows with each further failure, and never exceeds a cap: 60 seconds after the fifth failure, doubling up to 15 minutes. Attempts made while the lock is active are refused without being counted, so hammering does not extend it. A correct sign-in clears the count. And the reset flow stays open to a locked account, which is the escape route the same cheat sheet suggests: "One way this could be performed is to allow the use of the forgotten password functionality to log in, even if the account is locked out."

When a password is set

Compare the whole candidate with a blocklist of common, expected and breached passwords, including the service's own name and the username. Enforce a minimum length. Do not add rules about character types. Then store it with a password hashing scheme: a function built to be slow, given a salt that is random and different for every user. A fast hash such as SHA-256 is the wrong tool here, because the attacker who steals the table can try guesses as fast as the hash runs.

Password reset

  1. Request. Give the same answer whether or not the address has an account. Send the token to the address already on file, never to one supplied in the request. Limit how many messages one account can be sent.
  2. Token. Random bytes from a cryptographic generator, long enough that guessing is hopeless. Store only its hash. Tie it to one account, give it a short life, and delete it when it is used.
  3. Use. Check the token, the account it belongs to and its expiry. Limit failed attempts by source, not by account: the Forgot Password Cheat Sheet says "Accounts should not be locked out in response to a forgotten password attack, as this can be used to deny access to users with known usernames." Apply the same password rules as registration.
  4. Afterwards. End the account's existing sessions, tell the user that the password changed, and make them sign in. Do not sign them in from the reset.

Sensitive changes

Before changing the sign-in address, the password or the second factor, ask for the current password again, or the second factor. API2:2023 lists it under prevention: "Require re-authentication for sensitive operations". Then notify the old address, because that is the one the real owner still reads.

The lab's hash settings are not a default. The lab uses PBKDF2 with HMAC-SHA-256 and 1,000 iterations. That is a lab value, chosen so the lab finishes quickly, and it is 600 times lower than the cheat sheet's figure for PBKDF2. Python's hashlib has no Argon2id on the Python 3.13 and 3.14 builds the lab was run on. It has hashlib.scrypt and hashlib.pbkdf2_hmac, and the documentation for the second says: "Function only available when Python is compiled with OpenSSL." So the lab carries its own copy of PBKDF2, written with the hmac module, for a Python where the library function is missing, and check 50 compares the copy with the library function wherever both exist. The cheat sheet's rule of thumb for tuning is about the server, not the lab: "As a general rule, calculating a hash should take less than one second."

Reading NIST. SP 800-63B-4 is written for government systems, and several of its requirements name federal agencies: "This guideline focuses on the authentication of subjects who interact with government information systems". Where this page says NIST requires something, it means NIST requires it of the systems that guideline covers. For everyone else it is a well-argued reference, and most of the defaults above follow it.

5. What it proves, and what it doesn't

Proves: that the caller presented the account's password, and, with a second factor, a code from the device enrolled on that account, at that moment.

Doesn't prove: that the caller is the account's owner. NIST says it of both pieces of evidence: "Passwords are not phishing-resistant." and "OTP authentication is not phishing-resistant." A fake sign-in page can collect the password and the code and use them within the same 30 seconds. That is the row that stays red in section 1. Authenticators that are tied to the real site's address, such as passkeys, are the answer to phishing, and they are outside this module.

Doesn't stop a reused password on an account with no second factor. Throttling counts failures. A breached password does not fail. Checks 28 and 29 in the lab show a stuffing run that is never throttled. Of the two members who reused a password, it opens the account of the one with no second factor. For those accounts the remaining controls are indirect: screening new passwords against breach lists, forcing a change when a password is known to be compromised, and noticing the pattern in the logs.

Doesn't protect the stored hashes. Throttling limits guesses made through the endpoint. An attacker holding a copy of the password table guesses on their own hardware with no limit at all, and the only things in the way are the salt and the cost of the hash.

Doesn't cover what happens after sign-in. A correct login produces a session. How that session is stored, sent and ended is module 28. What a signed-in user may do is Part 2 of the course.

Lockout is not free. Check 52 in the lab is the cost: after five wrong guesses by someone else, the account's owner presents the right password and is refused. Every lockout design chooses how much of that to accept. A lock that is short and capped bounds each lock, not the attack: one more wrong guess when a lock ends starts the next one, so an attacker who keeps guessing keeps the owner out for as long as they keep going. The reset route, which stays open and clears the count, is what lets the owner back in (checks 57 and 58). A permanent lock hands anyone who knows a username a way to close the account.

6. Prove it

A working implementation must pass every one of these. If any fails, the control is broken:

  • A wrong password for a real account and any password for an unknown account get the same status, body and headers, and take the same work.
  • The reset request gives the same answer for a known and an unknown address.
  • After the configured number of failures on one account, the next attempt is refused with 429, even from a new address and even with the correct password.
  • One source that fails across many accounts is refused, although no single account has locked.
  • A batch of attempts in one request, or attempts through a second login route such as a mobile or legacy endpoint, hit the same counters.
  • A lock ends by itself, a correct sign-in after it clears the count, and a locked user can still complete a password reset.
  • A correct password without the second factor does not sign in, and the same code is refused the second time.
  • A reset token is refused for another account, refused after one use, and refused after its lifetime.
  • A thousand guesses at a reset token change nothing and do not lock the account.
  • A common password, the service's name and a short password are refused when a password is set, with the reason.
  • An email change with a valid session and no current password is refused, and the old address is told when a change succeeds.
  • Two accounts with the same password have different stored hashes.

8. Check your understanding

Your login endpoint locks an account after five failures. Why does that not stop password spraying?

Spraying tries one password on every account before moving to the next password, so each account sees one failure per round and never reaches five. The lab's spray is three passwords over five accounts, so no account can collect more than three failures, and none locks (check 21). A limit on failures per source stops a spray that comes from one address, and nothing based on counting stops one that comes from many.

A stuffing run from thousands of addresses tries one breached pair per account. Which controls on this page still do something?

A second factor on the account, because the password alone no longer signs in. For accounts without one: the blocklist check when a password is set, a forced change once a password is known to be breached, and detection from the logs. The two counters do nothing, because nothing fails often enough from any one place or against any one account.

Both failure messages now read "invalid credentials". How could the endpoint still reveal which accounts exist?

By status code, by headers, or by work. If the code returns early for an unknown account, it skips the slow hash and answers faster, and it may also skip the failure counters, so repeated attempts on a real account eventually get a 429 and attempts on an unknown one never do. The fixed service hashes against a dummy record and counts failures by the submitted username whether or not it exists.

An attacker has a member's session but not their password. What stops them taking the account for good?

Re-authentication. Changing the sign-in address, the password or the second factor asks for the current password again, so the session alone is not enough. Without that check the attacker changes the address to their own, requests a reset, and owns the account. The notice sent to the old address is what tells the real owner if the check ever fails.

One correct password among thousands

  • StandardThe OWASP Credential Stuffing Prevention Cheat Sheet calls multi-factor authentication "by far the best defense against the majority of password-related attacks, including credential stuffing and password spraying", and says blocking IP addresses "should not be used as the sole or primary defense". Credential Stuffing Prevention Cheat Sheet, Multi-Factor Authentication and IP Mitigation and Intelligence.
  • StandardThe OWASP Authentication Cheat Sheet, which is guidance and sets no requirements, says that for login, password reset and password recovery "an application must respond with a generic error message" whether the user ID or password was wrong, the account does not exist, or the account is locked or disabled, and warns that a different HTTP status code or processing time leaks the same thing. Authentication Cheat Sheet, Authentication and Error Messages.
  • StandardThe same cheat sheet recommends that the counter of failed logins be associated with the account and not the source IP address, and that a lockout design take care not to let an attacker deny service by locking other users' accounts. Authentication Cheat Sheet, Account Lockout.
  • StandardFor the systems it covers, NIST requires a verifier to limit consecutive failed attempts on one account to no more than 100, allows lower limits, allows a wait that grows as the account nears its limit, and recommends disregarding earlier failures after a successful authentication. NIST SP 800-63B-4 section 3.2.2.
  • StandardFor the systems it covers, NIST requires a minimum of 15 characters for a password used as the only factor and 8 when it is only used with another factor, recommends allowing at least 64, forbids other composition rules and scheduled changes, and requires each new password to be compared in full with a blocklist of commonly used, expected or compromised values, with the reason given on rejection. NIST SP 800-63B-4 section 3.1.1.2.
  • StandardFor the systems it covers, NIST requires stored passwords to be salted and hashed with a suitable password hashing scheme, with a salt of at least 32 bits, and recommends a cost factor as high as practical and a further keyed hash whose key is stored separately. NIST SP 800-63B-4 section 3.1.1.2.
  • StandardThe OWASP Password Storage Cheat Sheet recommends Argon2id with a minimum of 19 MiB of memory, an iteration count of 2 and 1 degree of parallelism; scrypt with a cost parameter of at least 2^17, block size 8 and parallelization 1 if Argon2id is not available; bcrypt with a work factor of 10 or more for legacy systems; and PBKDF2 with HMAC-SHA-256 and 600,000 or more iterations if FIPS-140 compliance is required. Password Storage Cheat Sheet, Introduction.
  • StandardThe OWASP Forgot Password Cheat Sheet recommends a consistent message and a uniform response time for existing and non-existing accounts; tokens that are randomly generated with a cryptographically safe algorithm, long enough to resist brute force, stored securely, single use, expiring and linked to an individual user; no change to the account until a valid token is presented; and no account lockout in response to a forgotten password attack. Forgot Password Cheat Sheet, Introduction, General Security Practices and Account Lockout.
  • StandardFor the systems it covers, NIST requires a recovery code that is issued to an address to be valid for at most 24 hours when sent by email and 10 minutes when sent by text message or voice, requires its verification to be throttled, and requires a notification to the subscriber whenever an account is recovered. NIST SP 800-63B-4 section 4.2.
  • StandardThe 429 (Too Many Requests) status code "indicates that the user has sent too many requests in a given amount of time". The response may include a Retry-After header and must not be stored by a cache. A server is not required to use 429. RFC 6585 sections 4 and 7.2.
  • StandardA server that generates a 401 (Unauthorized) response must send a WWW-Authenticate header field with at least one challenge. RFC 9110 sections 15.5.2 and 11.6.1. The lab models status and message only.
  • StandardRFC 6238, an Informational RFC, recommends a default time step of 30 seconds and at most one time step of allowance for network delay, and says a verifier "MUST NOT accept the second attempt of the OTP after the successful validation has been issued for the first OTP". RFC 4226, also Informational, recommends throttling one-time password validation at the server. RFC 6238 section 5.2 and RFC 4226 section 7.3.
  • BaselineCount failed attempts both per submitted username and per source, and check both before any password hash is computed. Count attempts, not requests, so a batch of ten logins in one request is ten attempts.
  • BaselineLock for a short period that grows with each further failure up to a fixed cap. Do not count attempts refused during a lock. Clear the count on a successful sign-in or reset.
  • BaselineFor an unknown account, verify against a dummy record and count the failure, so the status, the body, the work and the eventual 429 are the same as for a real account.
  • BaselineGenerate reset tokens with 32 bytes from a cryptographic generator, store only a hash, tie each to one account, expire it after 15 minutes, delete it on use, and let a new request replace the old token.
  • BaselineAfter a reset, end the account's sessions, notify the user and require a normal sign-in.
  • BaselineRequire the current password or a second factor to change the sign-in address, the password or the second factor, and notify the previous address.
  • BaselineLog every failure, lockout and reset, and alert on the patterns: many accounts from one source, and many sources against one account. Module 30 (Logging, detection and response) covers what to do with them.
  • OptionRequire a CAPTCHA after a few failures. The Authentication Cheat Sheet treats it as defence in depth that makes guessing slower and more expensive, not as prevention.
  • OptionAsk for the second factor only when a sign-in looks unusual: a new device, an unusual location, an address that has tried several accounts.
  • OptionOffer phishing-resistant authenticators such as passkeys. For the systems it covers, NIST requires a verifier to offer at least one phishing-resistant option at authentication assurance level 2 (section 2.2.2).
  • OptionDo not build it. OWASP A07:2025 suggests using a premade, well-trusted system for authentication, identity and session management where possible. The checklist below then becomes the list of questions to ask about that system.

Review checklist items

These are collected into the site checklist.

  • A second factor is available to every user and required for privileged accounts A correct password alone does not sign in to an account that has one, each code is accepted once, and every login route enforces it, including mobile and legacy endpoints.
  • Failed sign-in attempts are limited per account and per source Both counters exist, both are checked before any password hash is computed, the limit is stricter than the general API rate limit, and a batch of attempts in one request counts as that many attempts.
  • Login, reset and registration answer the same for known and unknown accounts The status, body, headers and work are the same, and an unknown username reaches the 429 after the same number of failures as a real one.
  • Lockout is temporary and bounded, and refused attempts do not extend it The longest lock is a chosen value, attempts refused during a lock are not counted, a correct sign-in clears the count, and a locked user can still reset the password.
  • Reset tokens are random, single use, short-lived and bound to one account They come from a cryptographic generator, only a hash is stored, failed attempts are limited by source without locking the account, and a successful reset ends existing sessions and notifies the user.
  • Changing the sign-in address, password or second factor requires re-authentication A valid session alone is refused, the current password or second factor is checked, and the previous address is notified of the change.
  • Passwords are stored with a salted password hashing scheme at published parameters Argon2id, scrypt or PBKDF2 at the settings the Password Storage Cheat Sheet gives, a random salt per user, and no fast or unsalted hash anywhere, including old accounts.
  • New passwords are checked against a blocklist and a minimum length The whole password is compared with common, breached and service-specific values, the reason for a refusal is shown, and there are no character-type rules or scheduled changes.
  • Authentication failures, lockouts and resets are logged and alerted on The alerts cover one source failing across many accounts and many sources failing against one account, and a user is told when their password was right and the second factor was not.
  • Every way to sign in is inventoried and held to the same controls Web, mobile, partner and legacy login routes and every recovery route share the counters, the responses and the second factor.
