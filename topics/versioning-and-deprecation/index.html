Versioning and deprecation

Last reviewed 2026-10-02 · Jump to reference

Objective. After this module you can announce a deprecation in a way machines can act on, set the two dates in the order the specification requires, tell what a client can work out at any point on that timeline, and say why announcing perfectly changes nothing on its own.

Before you start. Every module in this course has assumed there is one version of the service to secure. There is rarely one, and the extra ones are where every control you have built is a version behind.

1. The attack

Running example: ExampleAir's booking API, currently on v3. Company names are fictional. Five deployments answer requests. Three are in the documentation.

The attack is picking the oldest one. Old versions are where the object check from module 9 had not been written yet, where the response still carries the fields module 10 removed, where the rate limit is the one you set two years ago. None of that was a mistake at the time. It became one when the fix shipped to v3 and stopped there.

OWASP files this as API9:2023 Improper Inventory Management, and its advice is pointed: use external protection measures "for all exposed versions of your APIs, not just for the current production version". The word doing the work is exposed, which is a fact about your network rather than about your documentation.

2. Why it works

Two headers, two dates, one ordering rule

There are two RFCs for saying this in a way a client can act on, and they are short.

RFC 9745, published March 2025, defines the Deprecation response header field, "used to signal to consumers of a resource (identified by a URI) that the resource will be or has been deprecated". Its value is a date, so a future date announces a deprecation that has not happened yet and a past date says it already has.

RFC 8594, from May 2019, defines Sunset, which "indicates that a URI is likely to become unresponsive at a specified point in the future". It is honest about what happens afterwards: "after the Sunset time has arrived, it is likely that interactions with the resource will result in client-side errors (HTTP 4xx status codes), redirect responses (HTTP 3xx status codes), or the client might not be able to interact with the resource at all".

The two are related by one rule, in RFC 9745 section 4: "the timestamp given in the Sunset HTTP header field MUST NOT be earlier than the one given in the Deprecation header field". Deprecated, then gone, in that order. It sounds too obvious to state until you have seen a migration plan with the dates the wrong way round, which is what happens when the sunset date comes from a contract and the deprecation date from an engineer.

Both specifications add the same caution, and it is the point of Part E of the lab: the header is a hint. RFC 8594 and RFC 9745 both say so in their security considerations. A client that ignores it is not doing anything wrong at the protocol level, and your traffic graph is the only thing that knows whether anyone listened.

Why announcing is the easy half

A deprecation has four steps and most teams do the first one: announce it, stop new callers, move the existing ones, withdraw it. The gap between the third and the fourth is where the exposure lives, and it is usually held open by the same fact: nobody knows who is still calling.

That is why the lab treats "still receiving traffic from callers nobody can name" as a finding in its own right. A version with traffic and identified callers is a migration. A version with traffic and no identified callers is a version you cannot withdraw, because the decision to break somebody has no one to notify, and so it never gets made.

This is also where module 12 comes back. The question is not which versions you documented, it is which ones answer. The lab's Part D is that comparison, and the two versions it finds are the ones nobody would have thought to look for.

3. The control

  1. Inventory by reachability, not by documentation. The list is every deployment that answers, produced from the network. Module 12's argument, one layer up.
  2. Give every superseded version a deprecation date and a sunset date, in that order, at the moment its successor ships rather than later.
  3. Emit both headers from the deprecated version, with a Link to the documentation, so the announcement reaches a machine and not only a changelog.
  4. Name the remaining callers. A version with traffic and no identified callers cannot be withdrawn, which is why it never is.
  5. Apply current controls to every exposed version until it is gone. OWASP recommends external protection for all exposed versions, not just the current one.
  6. Withdraw it on the date. This is the only step that changes anything, and the previous five exist to make it possible rather than to replace it.
  7. Verify afterwards that it stopped answering, from the network, the way you verified it was reachable in the first place.

5. What it proves, and what it doesn't

Proves: that every version you know about has an announced end, that the announcement reaches machines, and that the dates are in an order the specification permits.

Doesn't prove: that anybody acted on it. Both RFCs describe their header as a hint, so a client that ignores it is not misbehaving, and the only measurement that matters is traffic. It also proves nothing about versions that were never in the inventory, which is the case the lab's Part D is built around.

Announcing is not deprecating. A version with perfect headers, a clear migration guide, a date that has passed, and a live deployment is exactly as exposed as one with none of those things. Part E of the lab gives v1 a flawless announcement and a fresh sunset date, and the finding that survives is the 9,400 requests a month from callers nobody can name.

6. Prove it

  • A list of every version that answers, produced from the network and dated.
  • Every entry on that list appears in the documentation, or has a finding against it.
  • Every superseded version has a deprecation date and a sunset date, in that order.
  • Every deprecated version emits Deprecation, Sunset and a Link, verified against a live response rather than a design document.
  • For each version with remaining traffic, a named list of callers.
  • Evidence that current security fixes reached every exposed version.
  • For each version past its sunset date, either it no longer answers or there is a dated decision saying why.
  • A check in the build that fails when a sunset date precedes a deprecation date.

8. Check your understanding

What is the difference between the Deprecation and Sunset headers?

Deprecation carries the date a resource became or will become deprecated, which is a statement about support. Sunset carries the date it is likely to stop responding, which is a statement about availability. RFC 9745 requires the sunset timestamp not to be earlier than the deprecation one: deprecated first, gone afterwards.

Your deprecated version emits both headers correctly and traffic has not dropped. What does that tell you?

That the headers are a hint, which both specifications say plainly, and that whoever is calling either has not noticed or cannot move yet. The signal has done its job; the migration has not started. Identify the callers from the logs, because that is the step that has actually stalled.

Why is a version missing from the documentation worse than one that is deprecated?

Because every process you have operates on the documented list. A deprecated version is being tracked, has dates, and someone can name it in a meeting. An undocumented one gets no security fixes, no dashboard, no review and no end date, and the only way it appears is by comparing the documentation with what actually answers.

A version is past its sunset date and still answering. Who should act?

Whoever owns the deployment, and the action is to withdraw it. Announcing again does not change the exposure, and extending the date teaches every caller that the next date is negotiable too. Measure the remaining traffic so you know who to call afterwards, then withdraw it.

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardThe Deprecation response header field "is used to signal to consumers of a resource (identified by a URI) that the resource will be or has been deprecated". Its value is a date. RFC 9745, March 2025, abstract and section 2.1.
  • StandardThe Sunset response header field "indicates that a URI is likely to become unresponsive at a specified point in the future" (section 1), with an HTTP-date value (section 3). RFC 8594, May 2019.
  • Standard"The timestamp given in the Sunset HTTP header field MUST NOT be earlier than the one given in the Deprecation header field." RFC 9745 section 4.
  • StandardRFC 8594 section 3 states that after the sunset time "it is likely that interactions with the resource will result in client-side errors (HTTP 4xx status codes), redirect responses (HTTP 3xx status codes), or the client might not be able to interact with the resource at all".
  • StandardBoth specifications treat the field as a hint rather than a guarantee, in their security considerations: RFC 9745 section 7 and RFC 8594 section 8.
  • StandardRFC 9745 section 3 defines the deprecation link relation type: a server can use a Link header with it to point at the documentation. It does not require one. RFC 8594 section 6 defines a sunset relation type, for linking to information about how a resource or service will be retired.
  • StandardOWASP recommends using external protection measures "for all exposed versions of your APIs, not just for the current production version", and an inventory that records for each host its environment, who should have network access to it, and which version it runs. OWASP API9:2023, How To Prevent.
  • BaselineProduce the version list from the network, not the documentation, and date it.
  • BaselineSet both dates at the moment the successor ships, in the required order, and check that order in the build.
  • BaselineEmit both headers plus a Link, and verify them against a live response.
  • BaselineTreat a version with traffic and unidentified callers as a finding, because it cannot be withdrawn until they are named.
  • BaselineWithdraw on the date, then verify from the network that it stopped answering.
  • BaselineKeep internal and non-production versions in the same inventory as the public ones.
  • OptionReturn 410 Gone rather than 404 for a withdrawn version where you want clients to distinguish a retired resource from a wrong path. RFC 9110 section 15.5.11 says 410 "indicates that access to the target resource is no longer available at the origin server and that this condition is likely to be permanent", and section 15.5.5 says "the 410 (Gone) status code is preferred over 404 if the origin server knows, presumably through some configurable means, that the condition is likely to be permanent".
  • OptionThrottle a deprecated version progressively as its sunset approaches, so that the migration pressure is felt before the date rather than at it.

Review checklist items

These are collected into the site checklist.

  • The version list comes from the network and is dated Every deployment that answers, not every version in the documentation. Compare the two and act on the difference.
  • No version answers after its sunset date Or there is a dated decision recording why, owned by a named person.
  • Current security fixes reach every exposed version, or the version is withdrawn OWASP asks for a risk analysis of older versions when a newer one adds a security improvement: backport it, or take the old version out. "It is deprecated" is not a remediation while it still answers.
  • Every superseded version has both dates, in the required order RFC 9745 forbids a sunset earlier than the deprecation. Check it in the build; the two dates usually come from different people.
  • Deprecated versions emit Deprecation, Sunset and a Link Verified against a live response, not a design document.
  • Remaining callers are named for every version with traffic A version with traffic and no identified callers cannot be withdrawn, which is why it never is.
  • Internal and non-production versions are in the same inventory These are the ones missing from the documentation, which is why they last longest.
  • Withdrawal is verified from the network afterwards The same way reachability was established in the first place.
