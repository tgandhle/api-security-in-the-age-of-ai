API keys

Last reviewed 2026-09-24 · Jump to reference

Objective. Find an API key leak in a request log, explain why someone can reuse the key, and test both prevention and recovery.

Before you start. You should be able to read a URL and a Python function. An API key is a credential issued to an application. Here it is a bearer credential: whoever presents it can act within its assigned permissions.

1. The attack

ExampleAir reads its rewards balance from ExampleHotels. These companies are fictional. The caller puts its key in the URL's query string, the part after ?. The request target has this shape: /balance?api_key=<api-key>. This is an illustration, not a command.

The receiver records that target. An attacker who can read the log extracts the key and submits it on another request. The lab models that exact path without sending any network traffic.

2. Why it works

The toy receiver checks possession of a value, not which process sent it. Extracting that value is enough to pass the same check. A longer random key would not fix this leak: the attacker copies it rather than guesses it.

TLS protects the connection. It does not remove credentials from logs at either endpoint. OWASP advises keeping keys out of URLs and using HTTPS for REST endpoints (REST Security).

Headers are not automatically safe either. A debug trace that records the credential header recreates the same problem.

3. The control

What the caller sends

Use the API's documented credential header over HTTPS. No universal API-key header name is assumed here. The lab's header_key argument stands in for that header after parsing; it is not an HTTP field name.

How the receiver verifies

  1. Reject query credentials, even if a header credential is also present. Reject empty and duplicate credential inputs at the HTTP boundary.
  2. Read the single credential from the agreed header. Missing or unknown value: reject. Compare secret values with a constant-time comparison.
  3. Check its server-side record is active and within its allowed lifetime. This is authentication, checking the claimed identity through its credential.
  4. Apply authorization: check this caller's permission for this action and resource. A matching key alone is not permission for every operation.
  5. Record a route label, decision, and non-secret record identifier. Exclude raw credentials from all logs and traces, including rejected requests. OWASP's logging guidance identifies tokens and primary secrets as data to exclude (Logging).

The whole system

ExampleAir's server obtains its credential from a secrets manager, then calls ExampleHotels over HTTPS. The receiver checks the credential record and permissions. Logs record the decision without the key. On a leak, the operator disables the old record and provisions a replacement.

5. What it proves, and what it doesn't

Proves: the request supplied a credential the receiver currently accepts.

Doesn't prove: the original application sent it, a person consented, or the operation is permitted. An API key does not bind the credential to the request body or make a request single-use.

Prevention is not recovery. Lab check 8 still accepts the previously stolen key after the logging fix. Check 9 rejects it after revocation. Review all verifier caches when applying that result to a real service.

For high-value operations, evaluate stronger identity controls rather than relying only on a key (OWASP REST Security). The next module teaches HMAC request signing.

6. Prove it

Use generated test credentials, never production keys. Lab checks cover query leakage, reuse, missing and wrong keys, revocation, replacement, mixed header/query input, encoded parameter names, and blank values.

Integration tests must also prove these properties; the in-memory lab does not:

  • Expired keys and credentials for another environment fail at every receiver.
  • Duplicate credential headers are rejected consistently by the proxy and application.
  • A valid key cannot access another caller's resources or an unassigned operation.
  • Gateway logs, application logs, traces, and error reports contain no test credential.
  • Revocation takes effect within the documented bound, including cached records.
  • HTTPS is enforced and clients validate the server certificate.

7. Lab

Download labs/api_keys_lab.py. From the project root, run it with Python 3. It uses only the standard library. Credentials and the deliberately vulnerable log remain in memory; generated values are never printed or saved. No server is started. On Windows, use py -3 wherever this page shows python3.

The scanner parses this lab's request-target strings and recognizes the decoded, case-sensitive name api_key. It is not a general log scanner: other field names, log formats, and header leaks need their own tests. Safe logging uses a fixed route label so it also avoids reflecting an arbitrary path.

8. Check your understanding

Does HTTPS stop the attack in check 3?

No. The attacker reads the receiver's log after transport protection has ended. Keeping the key out of that log prevents this disclosure.

Why does the stolen key still work in check 8?

The receiver still accepts its value. A header-only rule changes where credentials are read, not who can possess them. Revocation disables the compromised credential.

The scanner finds zero keys. Is the service secure?

No. It checks one parameter name in one log format. It says nothing about header traces, authorization, TLS configuration, or logs outside this model.

Reference

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model. This module assigns no Standard labels: its controls are project defaults, not a universal API-key protocol.

  • BaselineUse HTTPS and the documented credential header. Reject query credentials. See REST Security.
  • BaselineGenerate keys from 32 random bytes using a secure generator, such as secrets.token_urlsafe(32). See Python secrets.
  • BaselineKeep credentials out of logs and traces at every hop. Test rejection paths too. See Logging.
  • BaselineUse owned, scoped, expiring credential records and a secrets manager for caller storage. Test replacement and revocation separately from log prevention.
  • BaselineCheck permissions after authentication; do not treat a valid key as unlimited access.
  • OptionUse stronger caller authentication for higher-impact operations. Evaluate request signing in module 2, including its shared-secret limitations.

Review checklist items

These are collected into the site checklist.

  • Credentials stay out of URLs and telemetry Reject query credentials and test every logging layer with generated test values, including failure paths.
  • Exposed keys can be revoked everywhere Measure the revocation bound across caches and confirm the old key fails while its replacement works.
  • Key validation is followed by permission checks Test denied actions and cross-caller resources with an otherwise valid credential.
  • Keys have secure generation, storage, ownership, and expiry Keep separate records per caller and environment; the caller retrieves the secret from a secrets manager.
  • Transport and credential parsing are tested end to end Require HTTPS, certificate validation, and consistent rejection of missing or ambiguous credentials.
