Model and artifact supply chain

Last reviewed 2026-10-04 · Jump to reference

Objective. After this module you can explain why loading a model file can run code, resolve a model by its digest and not by its name, say what a hash, a signature and a provenance record each prove and what none of them proves, put one gate in front of every model, adapter and converted file, install packages so that a changed or invented package is refused, and keep an inventory that matches what is loaded.

Before you start. You should know what a hash is and how a signature differs from one. The primer, Security concepts for the course, covers both. Module 25, Supply chain, retrieval, and memory, is the data side of this subject: who can put a document into a retrieval index or a memory store. This module is the other side: the models, adapters, datasets and packages an API team takes in from outside.

1. The attack

Running example: ExampleAir's refund API asks a small model, fare-model, whether a refund request can be paid without a person looking at it. The model answers approve or review. The company is fictional. ExampleAir's data science team published the model to a public model hub as exampleair/fare-model. On every deploy the pipeline downloads exampleair/fare-model:latest, loads it with a Python library, applies an adapter from another hub, and installs the packages in a requirements file.

The API team reviewed its own code. It did not write the weights, the adapter, the serving framework or the packages, and it fetches each of them by name. Each one is an artifact: a file that was built somewhere else and is supposed to arrive unchanged. OWASP covers this as LLM04:2026 Supply Chain: "in ML the risks extend to third-party pre-trained models, datasets, and model artifacts, which can be manipulated through tampering, poisoning, or malicious artifact replacement."

The table lists what can arrive, the control aimed at it, and what the lab in section 7 measured. With no control, each of these gets in: checks 3, 24, 44, 52 and 58 show five of them doing so.

2. Why it works

Six broken assumptions. Each one is about something the API team did not build.

  • "A model file is data." It depends on the format. Serialization turns an object into bytes, and some formats let the bytes name a function to call when they are loaded. Python's pickle is one, and LLM04 names it as an unsafe serialization format that model files use. The Python 3.14 documentation opens the pickle module with a warning: "The pickle module is not secure. Only unpickle data you trust." It goes on: "It is possible to construct malicious pickle data which will execute arbitrary code during unpickling." Loading such a file is running a program its author wrote, with the permissions of the process that loaded it.
  • "The name still means what it meant." A name or a tag is a pointer that its owner can move. A digest is the hash of the artifact's bytes, so it cannot be pointed at different bytes. SLSA describes a registry as resolving "a mutable package name into an immutable package artifact". LLM04 lists pipelines that "resolve artifacts by a mutable reference (for example, a latest tag) instead of an immutable digest", and its fifth scenario is a model referenced "solely by its Author/ModelName identifier": the author's account is deleted, an attacker registers the same name, and every pipeline that resolves by name pulls the attacker's model.
  • "It is signed, so it is safe." A hash, a signature and a provenance record answer three different questions, and none of them is whether the model behaves well. Section 5 takes them one at a time. LLM04 says it in seven words: "Signing proves integrity and origin, not safety".
  • "We checked the base model." What deploys is often not what was checked. An adapter changes the weights. A conversion service rewrites the file in another format. Quantization stores the weights at lower precision. Each step produces a new artifact with a new digest. LLM04 says a malicious adapter "can compromise the integrity of the pre-trained base model", that conversion and merge services "can introduce malicious changes during transformation between formats, bypassing review controls", and that "full-precision assurances do not transfer to the deployed quantized artifact".
  • "The package manager installs what I meant." It installs what the index serves for the name you typed. The pip documentation says that by default pip "does not perform any checks to protect against remote tampering and involves running arbitrary code from distributions." The name may also be wrong. LLM04 describes coding assistants that "hallucinate plausible but nonexistent package names at scale", which attackers register in advance. It calls this slopsquatting.
  • "Somebody knows what we run." A team that cannot list its models, adapters, datasets and packages cannot answer the first question after an advisory: are we affected. OWASP Top 10:2025 A03 puts it first in its list: you are likely vulnerable if "you do not carefully track the versions of all components that you use".

LLM04 points to the 2021 edition of the OWASP Top 10 for the package side, A06:2021 Vulnerable and Outdated Components. The 2025 edition's introduction says A03:2025 Software Supply Chain Failures "is an expansion of A06:2021-Vulnerable and Outdated Components", so this page cites A03:2025.

Where this module stops

Four neighbours are taught elsewhere or not at all, and the boundaries matter in a review.

  • Documents in a retrieval index or a memory store. Module 25, Supply chain, retrieval, and memory.
  • How a backdoor gets into a model during training. That is LLM05:2026 Data and Model Poisoning. LLM04 says some of its risks "are also discussed in LLM05:2026 Data and Model Poisoning" and that it "focuses on their supply-chain aspect". This module starts where a finished artifact arrives at your pipeline. It does not teach training.
  • MCP servers, tool registries and other agents. LLM04 says: "Supply-chain risks specific to agentic applications, including MCP servers and tool registries, are covered by ASI04 Agentic Supply Chain Vulnerabilities in the OWASP Top 10 for Agentic Applications".   • Models shipped on devices. This course is about APIs and does not teach it further.

3. The control

The control is one promotion gate that every artifact from outside passes before it reaches production, and a rule that production loads only what passed. In order:

  1. Accept only formats that cannot name code. Prefer a data-only format: a header that describes the numbers, then the numbers. The safetensors README describes one such layout (a header length, a JSON header, a byte buffer) and says its main rationale "is to remove the need to use pickle on PyTorch". If a pickle cannot be avoided, load it with a restricted loader. The Python documentation shows how under Restricting Globals: override Unpickler.find_class(), which "is called whenever a global (i.e., a class or a function) is requested", so that it is "possible to either completely forbid globals or restrict them to a safe subset". Do that inside a sandbox as well.
  2. Resolve by digest, never by name. Record the digest of the artifact you reviewed and refuse anything else. This is pinning. Keep a copy in an internal store keyed by digest, so that a deleted upstream account breaks nothing.
  3. Verify a signature over a manifest of every file, against the signer you expect. The model signing project signs a list of "(file path, digest) pairs", one per file in the model directory. Its verifier first checks the signature and then computes the file hashes again "to compare against the signed ones". A valid signature is not enough: the signer has to be the identity your policy names.
  4. Verify provenance against expectations. For an artifact, provenance is a record of how it was built, and this gate accepts it only when the platform that built it has signed it. SLSA defines provenance as "Attestation (metadata) describing how the outputs were produced, including identification of the platform and external parameters." Check that the record is about this artifact, that it names the builder you expect, and that it names the source repository you expect.
  5. Treat every transformation as a promotion point. Applying an adapter, merging, converting and quantizing each make a new artifact. Steps 1 to 4 and step 6 apply to the artifact that deploys, not to the one it was made from. LLM04's sixth mitigation: "treat model conversion and merge services as high-risk promotion points."
  6. Evaluate behaviour before promotion, and keep evaluating. LLM04's third mitigation asks for red teaming and evaluations when selecting third-party models, "focused on the use cases in scope", and for anomaly detection and adversarial robustness testing to continue in production. Run scanners on what you take in, and count them as one layer.
  7. Pin and hash every package, from an index you curate. Every line of the requirements file carries an exact version and a hash. The index is one your organisation controls, holding the packages it reviewed. A name that an assistant suggested is checked before it is added: LLM04's second mitigation says to "verify that AI-suggested dependencies exist and are the intended package before adopting them."
  8. Keep one inventory, and compare it with what is loaded. An SBOM lists software components. LLM04's fourth mitigation extends it "to models, adapters, and datasets" and says to track licences in the same inventory.
  9. Protect the pipeline that builds and signs. Everything above trusts it. A03:2025 lists the conditions: "your CI/CD pipeline has weaker security than the systems it builds and deploys", and no separation of duty, where one person can write code and promote it to production without oversight from another.
  10. Read the supplier's terms before the first download. LLM04's first mitigation: "Carefully vet data sources and suppliers, including T&Cs and privacy policies, and only use trusted suppliers." Two of its examples are review items and not attacks: licences that restrict use, distribution or commercialization, and operator terms that allow your application data to be used for training.

5. What it proves, and what it doesn't

Three checks are easy to confuse. Keep them apart.

  • A digest proves integrity: these bytes are the bytes you pinned. It says nothing about who made them or whether they were good on the day you pinned them.
  • A signature proves origin: a holder of this signer's key vouched for this manifest. The model signing README says users "can check that the signature comes from a known or trusted identity and thus that the model hasn't been tampered with after training."
  • Provenance proves how it was built, as far as you trust the platform that wrote the record. SLSA says of its own strongest build level: "SLSA Build L3 does not cover compromise of the build platform itself, such as by a malicious insider."

None of the three proves the model behaves well. LLM04's fifth mitigation: "Signing proves integrity and origin, not safety (a validly signed model from a compromised or trusted-but-malicious supplier can still be backdoored)". SLSA draws the same line for software: "SLSA does not address organizations that intentionally produce malicious software".

A signature from your own pipeline is only as good as the pipeline. LLM04's seventh scenario is an attacker inside the CI/CD system that fine-tunes and publishes models. "Because the backdoored artifact is built and signed by the organization's own release infrastructure, it passes downstream provenance checks, internal attestation, and supply-chain scanners that only flag externally sourced components." The lab reproduces it: check 33 is a backdoored model whose signature verifies, and check 40 is the same model passing the whole gate. Nothing in a digest, a signature or a provenance record can catch this, because all three faithfully describe what the pipeline did.

An evaluation proves the model gave the expected answers to the cases you ran. Check 40 passes a backdoored model because the evaluation set has no request with the trigger in it. Check 41 stops the same model because the set does. An evaluation finds the behaviour it tests for, and an attacker chooses a trigger you are unlikely to test. LLM04 says of its second scenario that a model with modified parameters spread misinformation "while evading detection by standard benchmark evaluation".

A data-only format proves that loading does not call a function the file names. It does not make the weights honest. LLM04: moving away from pickle "reduces but does not eliminate this risk", because a backdoor can live in the model itself, and because "a crafted model file can exploit memory-corruption bugs in a format's native parser". The safetensors README says of its own format: "Tensor values are not checked against", and gives NaN and infinity as values that could be in a file. Check 15 is the lab's version: the backdoored weights parse without complaint.

A scanner or a safe-loading flag is a layer. LLM04's sixth scenario describes scanners and loader options documented as safe that were bypassed, and ends: "Treat scanners and safe-loader flags as defense-in-depth layers rather than guarantees, alongside provenance verification and patched loaders and parsers." Check 6 is a scanner with a list of known bad names passing a file that calls a name nobody listed.

A package hash proves the archive is the one you hashed. It does not prove you hashed the package you meant. Check 59 is a lock file that faithfully pins the attacker's package. SLSA says the same of provenance: "SLSA does not yet cover adversaries tricking a consumer to use an unintended package, such as through typosquatting."

An inventory proves nothing about safety. It tells you what to look at when an advisory arrives, and that is all it is for.

6. Prove it

A pipeline that takes in models and packages must pass every one of these. If one fails, the control is broken:

  • A weights file in a pickle format is refused at the gate, and no code path in production calls an unrestricted pickle loader on a file from outside.
  • A model file whose header length, offsets or keys are wrong is refused by the parser, and the parser's version is in the inventory.
  • Publishing different bytes under the same name and tag upstream changes nothing in production, and the pipeline reports a digest mismatch.
  • Deleting the upstream copy does not stop a deploy, because the pinned bytes are in the internal store.
  • Changing, adding or removing any one file in a model directory fails signature verification.
  • A model with a valid signature from any identity other than the expected one is refused.
  • A release whose provenance names another artifact, another builder or another source repository is refused.
  • A verified base model with an adapter applied, or converted, or quantized, is refused until that output has its own digest, signature, provenance and evaluation.
  • The evaluation runs on the artifact that will be served, and a model that fails one case is not promoted.
  • An install with an unpinned line, a line with no hash, a hash that does not match, or a name that is not in the curated index installs nothing.
  • Every model, adapter, dataset and package loaded in production has an inventory entry with the same digest or version, and something reports the difference when it does not.

7. Lab

Download labs/model_supply_chain_lab.py and run it with Python 3. It needs no packages beyond the standard library. On Windows, use py -3 wherever this page shows python3.

Nothing opens a socket, writes a file or starts a process. The model is five integer weights and a threshold: it adds up the weights of the words in a refund request and answers approve or review. The backdoored model has a sixth weight, for the word ref-zz9, large enough to turn every request the lab sends to review into an approval. The hub, the package index and the build pipeline are Python objects.

The pickle in Part A is built at run time and calls record_load, a function in the lab that appends to a list. The lab registers that function under a module name first, because a pickle names a function by module and name. A real attack names a function that is already importable on the victim. The lab unpickles nothing except bytes it built. The data-only format is the lab's own: an 8-byte header length, a JSON header and raw bytes, following the layout the safetensors README describes. It is not safetensors.

Signatures in Parts C and D are an HMAC with a key per identity, generated at run time. That is a stand-in. With an HMAC the verifier holds the signing key and could forge. The model signing project signs with Sigstore, with public keys or with signing certificates, so a verifier cannot sign, and with Sigstore "signing events are recorded to Sigstore's append-only transparency log". The lab has neither property. Module 2, HMAC request signing, and Module 3, Asymmetric request signing, explain the difference. The provenance record has three fields where SLSA provenance has more. The quantization in Part D is not an attack: it rounds honest weights to a coarser step.

8. Check your understanding

A supplier sends a model as a pickle and its SHA-256. The hash matches. Is it safe to load?

The hash tells you the file is the one the supplier hashed. It tells you nothing about what the file does when it loads. A pickle can call a function during loading, so loading it runs the supplier's code, or the code of whoever compromised the supplier. Ask for a data-only format, or convert the file inside a sandbox and pin the converted output.

Your pipeline verifies a model's signature and the signer is your own release pipeline. What have you learned?

That the files are the ones your pipeline signed. You have not learned that the model is good. If the pipeline was compromised, it signed what the attacker built, and the signature and the provenance are both valid. LLM04's seventh scenario is this case. The checks that remain are the behavioural evaluation and the protection of the pipeline itself.

The base model passed every check. The team then applies an adapter from a public hub at load time. Which artifact did the gate judge?

The base, which is not what serves requests. The adapter changes the weights, so the deployed model has a different digest, no signature and no evaluation. Treat the output of applying an adapter as a new release and run the gate on it. The same holds for a merge, a format conversion and quantization.

A coding assistant suggests a package. You add it to the requirements file with its version and hash. What does hash-checking protect, and what does it not?

It protects against the index serving different bytes for that version later, and against a compromised download. It does not tell you the package is the one you meant, or that it existed before an attacker registered the name the assistant made up. Check that the package exists, is the intended one and is in your curated index before you hash it.

Quick check

What three passing checks leave open

A model release passes three checks: its digest equals the pinned one, its signature verifies against the expected signer, and its provenance names the expected builder and source. What have you still not learned?

Review checklist items

These are collected into the site checklist.

  • No model, adapter or dataset file from outside is loaded by a loader that can run code from the file Production accepts data-only formats, and a pickle is refused at the gate or converted once inside a sandbox.
  • Every model, adapter and dataset is resolved by digest No pipeline resolves a name or a tag at deploy time, and the pinned bytes are held in an internal store keyed by digest.
  • A signature over a manifest of every file is verified against one expected signer A valid signature from any other identity is refused, and a changed, added or removed file fails verification.
  • Provenance is checked against expectations The record is about this artifact's digest and names the expected builder and the expected source repository.
  • The gate judges the artifact that deploys The output of an adapter, a merge, a conversion or quantization gets its own digest, signature, provenance and evaluation.
  • A behavioural evaluation runs before promotion and is not reported as proof It covers the use cases in scope and adversarial cases, and scanners and safe-loading flags are counted as layers.
  • Every package is pinned with a version and a hash, from a curated index The install runs in hash-checking mode, the hashes are in the requirements file, and an AI-suggested name is verified before it is added.
  • One inventory lists every model, adapter, dataset and package that is loaded Each entry has a digest or version and a licence, and the list is compared with what is running.
  • The pipeline that builds and signs models is protected like production No single person can change it and promote the result, and a signature from it is never the only check on a release.
  • Supplier terms, privacy policies and licences are reviewed before adoption The review is repeated when the supplier's terms or security posture change.
