Property and function authorization

1. The attack

Running example: ExampleAir's customer profile endpoint. Company names are fictional. The caller is a real customer, correctly authenticated, asking for its own profile. Module 9's ownership check passes on every request in this module.

Three separate things go wrong, and they are usually found in the same codebase because they have the same cause: a handler that treats an object as one indivisible thing.

  • The response carries more than it should. The handler serialises the record, and the record has a fraud score, internal notes and a staff flag on it. The customer asked for their profile and received the company's assessment of them.
  • The request writes more than it should. The handler merges the request body into the record, so the body decides which fields exist. Adding "loyalty_tier": "platinum" to a profile update works, because nothing said it would not.
  • The operation should not have been available. The promote endpoint is guarded by a rule that says administrative routes live under /api/admin/, and this one does not.

OWASP splits these across two entries. The first two are API3:2023 Broken Object Property Level Authorization, which merges what earlier editions called excessive data exposure and mass assignment. The third is API5:2023 Broken Function Level Authorization.

The last row is the reminder that these checks compose rather than replace. A writable-property list has no opinion about whose record it is, and an ownership check has no opinion about which fields. You need both, on the same request.

2. Why it works

All three have one root: a framework offering a convenient way to move a whole object across a boundary. to_json() on a model, a body bound straight into a struct, a router that maps URL shapes to handlers. Each of them is a productivity feature, each of them is correct on the day it is written, and each of them is defined by the shape of your data rather than by a decision anyone made.

That is why this defect arrives later than the code does. Nobody exposes a fraud score on purpose. Someone adds a column, and a serialiser that was accurate in March starts returning it in June, in an endpoint nobody reopened. OWASP's guidance is direct about the mechanism: "avoid using generic methods such as to_json() and to_string()" and "avoid using functions that automatically bind a client's input into code variables".

It also explains why allowlists and denylists are not two styles of the same control. A denylist is a statement about the fields that exist today. An allowlist is a statement about what the endpoint is for. Add a column to the table and the denylist silently starts leaking it; the allowlist does not change its behaviour at all. That difference is the entire value, and it only shows up months after the decision.

The function-level version has its own specific trap. Teams write a rule like "anything under /api/admin/ requires staff", which is a statement about URL shape, not about what the endpoint does. OWASP names it: "don't assume that an API endpoint is regular or administrative only based on the URL path", and notes that "it's very common to find these administrative endpoints under other relative paths together with regular endpoints". The promote operation lives at /api/users/promote because that is where the users controller is, and the rule was never wrong about the path. It was wrong about what the path meant.

3. The control

Two property lists, not one

Readable and writable are different questions with different answers, and collapsing them into one list gets one of them wrong. A customer may read their loyalty tier and points and may not set either. A password field may be writable and never readable. Keep two lists, declared next to the endpoint, and build the response and the update from them rather than from the record.

  1. Declare what the response contains, field by field, and build it from that list. Not the record minus some fields: the list, positively stated.
  2. Declare what the client may set, field by field, and copy only those. Everything else in the body is ignored.
  3. Record what you ignored. A request trying to set is_staff is not a malformed request, it is a signal. Silently dropping it loses that.
  4. Validate the response against the declared shape before it leaves. OWASP recommends schema-based response validation as an extra layer, and it is the thing that catches the field somebody added last week.

A route table, denying by default

Function-level authorization is a rule per operation, and an operation is a method and a path together, not a path. OWASP's first prevention bullet is the design principle: "the enforcement mechanism(s) should deny all access by default". The practical form is a table keyed by method and path, where a request with no matching rule is refused rather than allowed, so a new endpoint is unreachable until somebody writes its rule.

That last property is what makes it worth the bureaucracy. Under a prefix rule, forgetting to think about a new endpoint means it is public. Under a table that denies by default, forgetting means it returns 403 and someone opens a ticket on the first day rather than the vulnerability being found on some later day by somebody else.

5. What it proves, and what it doesn't

Proves: that this caller's role may invoke this operation, that the response contains only fields somebody decided to expose here, and that the request changed only fields somebody decided a client may set.

Doesn't prove: that the record belongs to them. A writable-property list is per property, not per object, so an allowed field written to someone else's record passes it cleanly. That is module 9's check, and this module does not replace it.

Deny by default protects the routes nobody thought about, not the ones somebody got wrong. A table with a default-deny still hands an administrative report to customers if that route was listed with the customer role. The default is a floor. The rules themselves still need reviewing by someone who knows what each operation does, which is why the checklist item asks for the table to be read, not just for it to exist.

6. Prove it

For each endpoint:

  • The response fields are listed somewhere you can read without running the code, and the list is what builds the response.
  • Adding a column to the underlying table changes no response, and there is a test that proves it.
  • A request body containing every field of the record changes only the writable ones.
  • Attempts to set non-writable fields are counted, with the field names and not the values.
  • Every operation has a rule keyed by method and path, and a request to an unlisted route is refused.
  • Every verb the route accepts has its own rule, including the ones you did not intend to expose.
  • Somebody has read the route table end to end and can say what each operation does, not just that a rule exists.
  • All of the above hold for older API versions still serving traffic.

Check 1 and check 3 are the same record through two serialisers, and the gap between ten fields and five is the whole of the read-side problem. Nobody decided to publish a fraud score; a serialiser decided, on their behalf, in a language that looks like convenience.

Check 8 is the one to sit with. A customer set is_staff to true on their own profile, in a request that is otherwise an ordinary profile update, and every check before this module passed. That is the shape mass assignment takes: no injection, no malformed input, one extra key in valid JSON.

Check 10's output is the part teams skip. The allowlisted update reports what it ignored, which turns four rejected fields into a log line somebody can alert on. Dropping them silently is correct behaviour and wasted evidence.

Checks 15 and 19 are the prefix rule failing in both directions: an administrative function that does not live under /api/admin/ is allowed, and a route nobody has thought about at all is allowed. Check 20 is the same request against a table that denies by default, which refuses it because no rule exists, not because someone predicted this route.

Checks 22 to 25 are the boundary. Check 22 writes an allowed field to a record the caller does not own, and the property check passes it because property checks do not look at owners. Check 24 shows the limit of deny-by-default: the rule was written, and it was written wrong.

Try next:

  • Add a field to the profiles in seed() and rerun. Check 1 moves and check 3 does not, which is the difference between an allowlist and a denylist expressed as two numbers.
  • Add "points" to WRITABLE and rerun. Decide how you would have caught that change in review, given that it is one word in a tuple.
  • Remove the ("DELETE", "/api/profile") entry from ROUTES and rerun. Check 18 changes from forbidden to no rule, and both are refusals. That is what deny-by-default buys you.
  • Write the route table for an API you work on. Count the operations you had to look up because you were not sure who should be able to call them.

8. Check your understanding

Why is an allowlist of response fields different from a denylist of sensitive ones?

Because they behave differently when the data changes, which is the only time it matters. A denylist enumerates the fields that exist now; a column added next quarter is not on it and ships in every response. An allowlist enumerates what the endpoint is for, and a new column changes nothing until somebody adds it deliberately.

Your update endpoint binds the request body to the model. What is the full set of fields a caller can set?

Every field on the model. The body decides which keys are present, so the answer is not determined by your code at all, it is determined by whatever the attacker sends and whatever your schema happens to contain today. That includes the fields somebody adds later.

Your rule is that anything under /api/admin/ requires staff. What does that rule actually enforce?

A statement about URL shape. It is correct for every administrative endpoint that happens to live under that prefix and silent about every one that does not, which OWASP notes is common, because administrative operations tend to sit in the controller for the thing they operate on. Bind the rule to the operation, not to the path it was filed under.

Your route table denies by default and every route has a rule. Are you done?

No. Denying by default protects the routes nobody wrote a rule for. It does nothing about a rule that names the wrong role, which is an ordinary mistake that produces an ordinary-looking table entry. Somebody has to read the table against what each operation does.

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardAn endpoint is vulnerable where it "exposes properties of an object that are considered sensitive and should not be read by the user", or "allows a user to change, add/or delete the value of a sensitive object's property which the user should not be able to access". OWASP API3:2023, which merges the earlier excessive data exposure and mass assignment categories.
  • Standard"Always make sure that the user should have access to the object's properties you expose." OWASP API3:2023, How To Prevent.
  • Standard"Avoid using generic methods such as to_json() and to_string()." OWASP API3:2023, How To Prevent.
  • Standard"Avoid using functions that automatically bind a client's input into code variables", and "allow changes only to the object's properties that should be updated by the client". OWASP API3:2023, How To Prevent.
  • Standard"Implement a schema-based response validation mechanism as an extra layer of security", and "keep returned data structures to the bare minimum, according to the business/functional requirements". OWASP API3:2023, How To Prevent.
  • Standard"The enforcement mechanism(s) should deny all access by default." OWASP API5:2023, How To Prevent.
  • Standard"Don't assume that an API endpoint is regular or administrative only based on the URL path." OWASP API5:2023, which notes it is "very common to find these administrative endpoints under other relative paths together with regular endpoints".

  • BaselineCount and log the fields an update ignored, by name and never by value.
  • BaselineKey function rules by method and path together. A rule for GET says nothing about DELETE.
  • BaselineRefuse any request whose method and path have no rule, so a new endpoint is unreachable until somebody writes one.

  • OptionFail a build when a model gains a field that no endpoint's list mentions, which turns the silent version of this defect into a visible one.

Review checklist items

These are collected into the site checklist.

  • Updates copy an allowlist of writable fields, never bind the body Send a body containing every field of the record and confirm only the writable ones changed, including is_staff or its equivalent.
  • Every operation has a rule keyed by method and path, and unlisted routes are refused Deny by default. Test an unlisted route and a second verb on a route you do allow.
  • Administrative functions are identified by what they do, not by their path List them and check each one's rule. A prefix rule is not an authorization mechanism.
  • Responses are built from a declared field list No generic serialiser. Adding a column to the table changes no response, and a test proves it.
  • Readable and writable are two separate lists Confirm the endpoint has both and that neither is derived from the other.
  • The object check is still present on these requests A writable field on another customer's record is refused. Property authorization does not look at owners.
  • Ignored fields are counted and logged by name Names only, never values. A body setting a non-writable field is a signal worth alerting on.
  • Somebody has read the route table against what each operation does Deny by default does not catch a rule written with the wrong role.
