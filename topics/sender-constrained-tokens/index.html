Sender-constrained tokens: mTLS and DPoP

Last reviewed 2026-10-02 · Jump to reference

Objective. After this module you can explain what binding a token to a key actually proves, choose between certificate binding and DPoP for a given deployment, list the checks a resource server must make on a DPoP proof, and say precisely which attacks binding does not stop.

Before you start. Modules 4 and 5 each ended with the same unblocked row: a stolen, current, genuine token still works. Module 6 added a second: a withdrawn grant is accepted until the token expires. You should know what an access token is, how it is validated, and why it is a bearer credential.

1. The attack

Running example: ExampleAir's service holds an access token for ExampleHotels' balance API. Company names are fictional.

Every control so far has answered one question: is this token genuine? None of them asks the other question: is the party presenting it the party it was issued to. A bearer token answers that by definition, which is to say it does not answer it at all. Whoever holds it is treated as its owner.

So the attacker's job is possession, and possession has many routes: a proxy log, a crash dump, a misconfigured trace, a compromised sidecar, a token in a URL, an SSRF that echoes a header back. Binding changes what possession is worth.

Two rows still do not turn green. Binding moves the target from the token to the key, and it says nothing at all about whether the grant is still live, which was module 6.

2. Why it works

A sender-constrained token carries a statement about a key its holder must be able to use. RFC 7800 calls that a confirmation, and it lives in the cnf claim. The token stops being "whoever holds this" and becomes "whoever holds this and can prove they hold that key".

The two mechanisms differ in which layer does the proving:

  • Certificate binding, RFC 8705. The client authenticates the TLS connection with a certificate. The token carries cnf with x5t#S256, a base64url-encoded SHA-256 hash of the DER encoding of the X.509 certificate. The resource server takes the certificate from its own TLS layer and compares. The proof is the TLS handshake, which already happened before your code ran.
  • DPoP, RFC 9449. The client holds a keypair and signs a small JWT per request, the proof. The token carries cnf with jkt, the thumbprint of the public key. The proof names the method and URL it is for, carries a hash of the access token, and has a unique identifier so it cannot be replayed. The proof is application-layer, so it survives TLS termination at a load balancer.

The failure modes are different too. Certificate binding fails when a proxy terminates TLS and the certificate never reaches the application, which is common and silent. DPoP fails when the server skips one of the proof's checks, because each omitted check reopens a specific attack: no ath and a proof works with any token bound to the same key, no htu and a proof captured from one endpoint works at another, no jti record and a captured proof can be replayed.

What a DPoP proof must contain, and what the server checks

  1. A proof is present at all. Its header typ is dpop+jwt and it carries the public key as a jwk.
  2. The proof's signature verifies against that embedded key. This proves possession, and nothing before this point is trustworthy.
  3. The thumbprint of that key equals the token's cnf.jkt. Without this, any well-formed proof from any key is accepted.
  4. htm and htu match this request's method and target URI. Without these, a proof for a harmless read works on a transfer.
  5. ath equals the base64url SHA-256 of this access token. Without it, a proof is not tied to the token it accompanies.
  6. iat is inside a short window. RFC 9449 section 11.1 says servers "MUST only accept DPoP proofs for a limited time after their creation (preferably only for a relatively brief period on the order of seconds or minutes)".
  7. jti has not been seen before, recorded only after everything above passes. This is module 2's nonce lesson, in a new place and for the same reason.

For certificate binding the list is much shorter, and that is its appeal: obtain the certificate from the TLS layer and compare its thumbprint. RFC 8705 section 3 requires exactly that, and requires rejection with 401 and invalid_token when they do not match.

The deployment decides this more than the threat model does. If TLS terminates anywhere before your code, certificate binding needs the certificate forwarded and trusted across that hop, which is a new trust relationship. DPoP does not care where TLS ends.

5. What it proves, and what it doesn't

Proves: that the party making this request can use the key the token names, for this method and this URL, recently, and, with a jti record, that this exact proof has not been used before.

Doesn't prove: that the party is who you think. It proves key possession, not identity. It does not prove the grant is still live, and it does not make the caller any more authorized than their scopes already made them.

Binding moves the target, it does not remove it. After binding, stealing the token is worthless and stealing the key is everything. That is a large improvement, because a key can live in a keystore while a token has to be sent on every request. But if your client keeps its private key in the same environment variable the token used to sit in, you have changed the file name and nothing else.

6. Prove it

A working implementation must reject every one of these. Each corresponds to one check, and skipping any one of them reopens a specific attack:

  • A bound token presented with no proof and no certificate at all.
  • A proof signed by a key whose thumbprint does not match the token's cnf.
  • A valid proof replayed a second time, even within its time window.
  • A proof whose htm or htu belongs to a different request.
  • A proof with no ath, or an ath for a different access token.
  • A proof whose iat is outside the accepted window, in either direction.
  • A proof whose header typ is not dpop+jwt.
  • A certificate-bound token presented over a connection with a different client certificate.
  • A certificate-bound token presented after a proxy stripped the certificate, which must fail rather than fall back to bearer behaviour.
  • The same bound token at a resource server it was not issued for, because binding does not replace audience validation.

8. Check your understanding

Your load balancer terminates TLS. Which mechanism still works, and why?

DPoP. Its proof is a signed JWT carried in a header, so it survives the hop untouched. Certificate binding needs the client certificate at the point where the check happens, and once TLS ends at the load balancer the certificate is gone unless you forward it, which makes the forwarding header itself a credential.

A DPoP proof is valid, its key matches the token, and the times are fine. What else must the server check before accepting it?

That the jti has not been seen before, that htm and htu match this request, and that ath matches this access token. Without those three, a single captured proof can be replayed, reused on a different endpoint, or paired with a different stolen token.

You bind every token. What has changed about your threat model, and what has not?

Token theft alone stops being sufficient, so logs, traces and proxy captures lose most of their value to an attacker. What has not changed: key theft is now equivalent to what token theft used to be, a withdrawn grant still works until the token expires, and the caller's scopes still decide what they may do.

Why does the proof carry a hash of the access token rather than just being signed?

Because a signature only proves the proof came from the key. Without ath, that proof is not attached to any particular token, so an attacker who captures one proof and steals a different token for the same key can pair them. ath is what makes the proof and the token one unit.

Exercises

Change one thing and predict the output

Each exercise edits one place in labs/bound_tokens_lab.py and asks what the run prints. The answers are the real output of each variant, and where a variant changes nothing the answer carries the measurement from a request the lab does not make.

1. The proof key is never compared with the token

In _check_dpop, delete the two lines that compare the proof key's thumbprint with the jkt in the token's cnf claim. Everything else, including the proof signature check, stays.

Which check changes?

Every option, and why
  • Check 4 sends no proof, so it is refused by the first line of the function, which this edit leaves alone.
  • Correct. Exit 1, one failure: check 5 goes from reject: proof key not bound to token to accept. This is the whole of DPoP collapsing into theatre. The attacker generates a key, signs a perfectly valid proof with it, and the server accepts, because nothing ever asked whether that key is the one the token was issued against. Check bind-02 in the Reference layer is this one comparison.
  • Check 6 replays the real client's own proof, so the thumbprint matches with or without this edit. The jti record is what refuses it.
  • It does not. The signature check proves the proof was signed by the key in its own header, which the attacker chose. The two checks answer different questions, and only one of them is about the token.

2. The ath claim is not checked

In _check_dpop, delete the two lines that compare the proof's ath claim with the hash of the access token being presented.

Which check changes?

Every option, and why
  • Check 7 is caught by the htm comparison, which is a separate line.
  • Check 11 is a correct request and accepts either way. Removing a check never breaks the happy path, which is the reason this class of change gets merged.
  • Correct. Exit 1, one failure: check 10 goes from reject: ath mismatch to accept. A proof with no ath is valid for any token bound to the same key, so one leaked proof can be paired with a different access token held by the same client. Check bind-04 in the Reference layer asks for proofs bound to the request and the token, and ath is the second half of that.
  • It ties the proof to a key, not to a token. One key can hold several tokens, and ath is what says which one this proof is for.

3. The proof jti is recorded before the proof is verified

In _check_dpop, move four lines so they sit directly above the try: that starts the proof signature check, in this order: claims = claims_of(proof), then the if that looks the jti up in seen_proofs, its return, and the self.seen_proofs.add line that records it. The first of the four has to move too, because the other three read claims; move only those three and the run stops at check 3 with an UnboundLocalError. Now a jti is recorded before anything about the proof is known to be valid.

What does the run print differently?

Every option, and why
  • Check 6 still rejects on the jti. That record was made by check 3, which succeeded, so it exists under either order.
  • Only if the record is added without the lookup that precedes it. Moving the pair together keeps check 3 working, and getting that distinction right is the exercise.
  • Correct. Exit 0, 27 of 27 lines identical. Every proof in the lab is either valid or fails on something the jti record does not depend on, so the order never shows. Measured on a request the lab does not make, where an attacker sends an invalid proof carrying a jti the real client is about to use: as published the attacker's proof is refused and the client's next request is accepted; with the record moved first, the attacker's proof is still refused and the client's request then answers reject: proof jti already used. Anyone who can send one invalid proof can lock out a legitimate request, which is why check bind-03 in the Reference layer is about where the record is written as well as that it exists.
  • That is what happens if the record is added on every call without the lookup in front of it, which is a different edit and a self-inflicted collision.

4. A missing client certificate means nothing to enforce

In _check_mtls, return accept when no client certificate was presented, on the reasoning that there is nothing to compare against.

Which check changes?

Every option, and why
  • Check 12 presents the right certificate and accepts either way.
  • Correct. Exit 1, one failure: check 13 goes from reject: no client certificate to accept, and the bound token is now a bearer token again for anyone who omits the certificate. This is the downgrade named in check bind-01 in the Reference layer, and it is worth noticing how reasonable the code reads: there genuinely is nothing to compare. The absence is the finding.
  • Check 14 presents a certificate, so it reaches the comparison and still fails it.
  • Only check 13 moves. Check 14 never gets to the early return.

Reference

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardWhen a certificate-bound access token is represented as a JWT, the certificate hash should be represented using the x5t#S256 confirmation method, a base64url-encoded SHA-256 hash of the DER encoding of the X.509 certificate. The value must omit padding and must not include line breaks or whitespace. RFC 8705 section 3.1.
  • StandardA protected resource must obtain the client certificate from its TLS implementation layer and must verify it matches the certificate associated with the access token, rejecting a mismatch with HTTP 401 and invalid_token. RFC 8705 section 3.
  • StandardA DPoP proof JWT must carry typ of dpop+jwt and the claims jti, htm, htu and iat. RFC 9449 section 4.2.
  • StandardWhen a DPoP proof accompanies an access token it must carry ath, the base64url SHA-256 hash of the ASCII encoding of that token. RFC 9449 section 4.2.
  • StandardThe jkt confirmation value must be the base64url encoding of the JWK SHA-256 thumbprint of the DPoP public key. RFC 9449 section 6.1, using the thumbprint of RFC 7638.
  • StandardA resource server must check that a DPoP proof was received, check it according to RFC 9449 section 4.3, and check that its public key matches the key the access token is bound to. RFC 9449 section 7.1.
  • StandardServers must only accept DPoP proofs for a limited time after creation, "preferably only for a relatively brief period on the order of seconds or minutes". RFC 9449 section 11.1.
  • StandardRFC 9700 section 2.2.1 recommends that authorization and resource servers use mechanisms for sender-constraining access tokens. It is a recommendation, not a requirement.
  • BaselineRecord every accepted proof jti for at least the proof time window, in a store shared across every instance serving the endpoint, and record it only after all other checks pass.
  • BaselineAccept proofs within 60 seconds of server time in either direction, and document that number as the replay window for anything you fail to record.
  • BaselineTerminate mutual TLS where the binding check happens. If a certificate must be forwarded in a header, treat that header as a credential and prove no other path can set it.
  • BaselineA bound token presented without its proof or certificate fails. Never fall back to bearer behaviour when the binding material is absent.
  • BaselineKeep audience, scope and object-level authorization exactly as they were. Binding answers who is calling, not what they may do.
  • OptionUse a DPoP nonce supplied by the server where you need to constrain proof creation time more tightly than a clock window allows. RFC 9449 defines the mechanism.
  • OptionStore the client private key in a hardware-backed or non-exportable keystore, which is what converts binding from a token-theft control into a meaningful one.

Review checklist items

These are collected into the site checklist.

  • A bound token without its proof or certificate is rejected, never downgraded No fall back to bearer behaviour when the binding material is missing, including when a proxy strips the client certificate.
  • The proof key thumbprint is compared with the token's cnf claim A valid proof from any other key is rejected. For certificate binding, the certificate comes from the TLS layer, not a header, unless that header is proven unsettable.
  • Proof replay is prevented by recording jti across all instances Recorded only after every other check passes. A shared store, not per-instance memory. Test replay against a second instance.
  • Proofs are bound to the request and the token htm, htu and ath are all checked. Test a proof from a different endpoint and a proof paired with a different token.
  • The proof time window is short and documented Stated in seconds, enforced in both directions, and understood as the replay window for anything not recorded.
  • Client private keys are stored at least as well as the tokens they replace Non-exportable or hardware-backed where the platform allows. Binding converts token theft into key theft.
  • Binding has not displaced any existing check Audience, scope, expiry, issuer and object-level authorization are all still enforced on bound tokens.
  • The revocation bound is unchanged and still stated A bound token remains valid until it expires unless active state is consulted. Module 6's sum still applies.
