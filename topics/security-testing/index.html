Testing API security

Last reviewed 2026-10-04 · Jump to reference

Objective. After this module you can plan a security test of an API you are authorized to test, derive its test cases from the API's own description and from the controls it is supposed to have, run them, write each finding so that someone else can repeat it, and say what the result shows and what it does not.

Before you start. You should know the difference between authentication and authorization, and you should have read module 9, Object-level authorization, module 10, Property and function authorization, and module 13, Request and response contracts. Every lesson in this course has a section 6, Prove it, that lists the tests its own control must pass. This module is about the step above that: testing one API as a whole. It teaches a method. It presents no tool, and every request in it is sent to an API defined inside the lab.

1. The attack

Running example: ExampleAir's customer API, version 1.4.0. Customers read, change and cancel their own bookings, transfer miles and edit their profile. Agents can read any booking and issue refunds. Company names are fictional.

The release went out with a passing build. The team's test suite has eight tests: a customer reads their booking, changes their seat, cancels, transfers miles, reads and edits their profile, and an agent reads a booking and refunds one. All eight pass. Every one of them sends a valid request from a caller who is allowed to make it, and checks that it works.

On the same build, customer cust-b sends DELETE /bookings/bkg-1001. The booking belongs to another customer. The API answers 200 and the booking is cancelled. Customer cust-a sends POST /admin/refunds, an operation meant for agents, and gets 200 as well. Nothing in the test suite could have noticed, because no test in it ever sends a request that ought to be refused.

The failure this module teaches is not one flaw. It is a way of testing that cannot see flaws: an API that ships with a green build and a broken control, because the tests only check that valid requests work. The build in the lab has six flaws of the kinds earlier modules teach, plus one missing business rule. The table shows which kind of test finds which. Every cell is a result from the lab.

2. Why it works

Four broken assumptions:

  • "The tests pass, so the control works." A functional test proves the API does what it should. A security test has to prove the API refuses what it should. The OWASP Web Security Testing Guide (WSTG) v4.2 separates the two. Positive requirements "state the expected functionality that can be validated through security tests". Then: "Security tests must also be risk-driven. They need to validate the application for unexpected behavior, or negative requirements." A test of a negative requirement is a negative test: it sends something that must be refused and passes only if it is. The WSTG says why they are the harder kind: "Negative requirements are more difficult to test, because there is no expected behavior to look for."
  • "We tested everything in the documentation." The API description is a claim about the API. The deployment is the fact. They drift apart in both directions: a route that answers and is not described, and an operation that is described and was never built. OWASP API9:2023 Improper Inventory Management counts an API as having a documentation blindspot when "There is no documentation or the existing documentation is not updated." Module 18, Versioning and deprecation, is about old versions that still answer. The same reasoning applies to single operations.
  • "A scanner would have found it." A tool that generates requests can tell a 500 from a 400. It cannot tell whose booking bkg-1001 is, so a 200 for someone else's booking looks like success. The WSTG says: "One reason that automated tools do a poor job of testing for vulnerabilities is that automated tools do not think creatively." The OWASP Application Security Verification Standard (ASVS) 5.0.0 is specific about where that bites: automated tools "will be unable entirely to verify many of the more complicated ASVS requirements or those that relate to business logic and access control". Its summary is one line: "testable using automation != running an off the shelf tool". The matrix in section 3 is automation. It works because a person first wrote down who may do what.
  • "The test found nothing, so there is nothing to find." A test run is a list of cases. It says nothing about the cases that are not on the list. The WSTG: "It is important to note that unknown security issues are not tested. The fact that a security test is clear of issues does not mean that the software or application is good." NIST SP 800-115, section 2.3, says the same of testing in general: "Testing does not provide a comprehensive evaluation of the security posture of an organization, and often has a narrow scope because of resource limitations".

3. The control

Before you send anything: permission and scope

Only test what you are authorized to test. The requests in this module are the same requests an attacker sends. What makes them a test is written permission from the owner of the system, obtained before the first request. Do not send them to an API you do not own or do not have that permission for, including a supplier's API that yours calls.

NIST SP 800-115 (September 2008) calls the document that grants the permission the rules of engagement, and defines it: "Detailed guidelines and constraints regarding the execution of information security testing. The ROE is established before the start of a security test, and gives the test team authority to conduct defined activities without the need for additional permissions." Section 6.5 describes an assessment plan, says the rules of engagement hold the same information, and lists the questions the plan should answer. For an API test they come to this:

  1. What is in scope, and what is not. Name the hosts, environments and API versions that may be tested, and keep a list of what must not be touched. NIST says the plan "should also list specific systems" that are not authorized, and that if part of the system sits on someone else's network, "the owner of the other network usually must also consent in writing to the assessment plan". A payment provider, an identity provider or a model API behind your API is somebody else's system.
  2. Who may test, and who signed. Appendix B of NIST SP 800-115 is a template. Its last section is a signature page: at a minimum the test team leader and the organization's senior management sign that they understand the scope and boundaries. Section 6.6 recommends that legal advisors are always involved for intrusive tests such as penetration testing.
  3. Which activities, in which environment, at what rate. NIST lists "conducting tests on duplicates of production systems" and testing off-hours among the ways to reduce the risk a test causes. Use a test environment and accounts made for the test. The WSTG notes that in a user acceptance environment "test data is used in place of real data". A run that sends tens of thousands of malformed requests is a load test whether you meant one or not, so agree a request rate and stay under it.
  4. How data is handled. A test can return real personal data, for example when an ownership check is missing. Section 7.4 and the template's data handling section ask for rules on collecting, storing, transmitting and destroying test data, and remind you that the results "will identify vulnerabilities that an adversary can exploit, and should be considered sensitive". Record that the data was reachable. Do not copy it.
  5. What happens when something goes wrong. Section 7.2 recommends that if a real intruder is found during the test, it is reported at once and "assessors stop assessing the systems involved in the incident". Section 7.1 asks that the right people are told of any critical finding "as soon as they are discovered", not in the final report. An incident during a test is still an incident.
  6. Keep a log of what you sent. Section 7.4.1 says an activity log "allows the organization to distinguish between the actions of assessors and true adversaries". It is also the raw material for every finding you write.

One limit on these sources. NIST SP 800-115 is from 2008, is written for United States federal agencies and is about networks and hosts more than APIs. Its appendix C says application security assessment is a complex topic and that specific techniques for it are outside the publication's scope. The WSTG v4.2 introduction and framework chapters, which this module read, do not discuss permission to test. This module uses NIST for the planning and the WSTG for the test design.

Derive the tests from the controls

The WSTG's method is to write the requirement first and the test second. It derives requirements from use cases and from their opposite: "misuse or abuse cases describe unintended and malicious use scenarios of the application". A misuse case takes one step of normal use and asks how it could be abused. Each one becomes a requirement that names a refusal, and each requirement becomes a negative test.

This course has already written most of them. Section 6 of every lesson is a list of negative requirements for one control. A security test of a whole API collects the lists that apply and runs them against every operation:

The authorization matrix

The OWASP Authorization Testing Automation Cheat Sheet describes an authorization as having two dimensions, the feature and the logical role that accesses it, and sometimes a third, the data. It continues: "Generally, the two dimensions of each authorization should be listed in a spreadsheet that is called an authorization matrix." An authorization matrix for an API always needs the third dimension, because object-level authorization is about whose data an operation touches.

  1. Rows: every operation. Take them from the description, not from memory.
  2. Columns: every role, with two test accounts for each role that owns data, and one column with no credentials. With one customer account you can only ever ask for your own bookings. The OWASP REST Assessment Cheat Sheet calls the fix the swap test: "Run the swap test: create the same kind of object with two accounts or tenants, then replay each request under the other session's identifiers."
  3. For each account, two objects: its own and someone else's. Cover every method. The same cheat sheet notes that "an ownership check on GET next to an unchecked PUT on the same resource is a common result".
  4. Write the expected status in every cell before the run. The lab derives it from the description: no credentials gets 401, a role the operation does not list gets 403, a customer asking for another customer's object gets 404, and everything else gets 200. If you fill in the expected column after seeing the answers, you have recorded what the API does, not tested it.
  5. Run every cell against known test data, and compare. A cell that is allowed where a refusal was expected is a finding. A cell that is refused where 200 was expected is not a security finding, and still needs an explanation.

The ASVS words each of these as a statement a verifier can pass or fail. Requirement 8.2.1 (Level 1): "Verify that the application ensures that function-level access is restricted to consumers with explicit permissions." The matrix needs something to derive its expected column from, and the ASVS asks for that too. Requirement 8.1.1 (Level 1): "Verify that authorization documentation defines rules for restricting function-level and data-specific access based on consumer permissions and resource attributes."

The description as the inventory

An OpenAPI description lists what an API offers in a form a program can read. OpenAPI 3.2.1 says of itself that it "defines a standard, language-agnostic interface to HTTP APIs which allows both humans and computers to discover and understand the capabilities of the service without access to source code, documentation, or through network traffic inspection". As this project reads it, the specification describes an API and sets no security requirement on one. For a tester it holds four things:

  • Paths and operations. The Paths Object holds each path, and a Path Item Object holds one Operation Object per method. That is the list of rows for the matrix.
  • Security requirements. Each operation's security field is a list of Security Requirement Objects. The specification says "only one of the entries in the list needs to be satisfied to authorize the request", and that "An empty Security Requirement Object ({}) indicates anonymous access is supported." For schemes other than OAuth 2.0 and OpenID Connect, the array in a requirement may list role names. The lab's description writes "customer or agent" as two entries.
  • Schemas. The request body's schema names each property with its type and limits. That is the source for the next subsection.
  • What it cannot say. This project found no field in OpenAPI 3.2.1 for "a customer may only touch their own bookings". The lab puts that rule in fields whose names begin with x-, which is how OpenAPI allows extensions. Those names are the lab's own. Wherever your organization writes the ownership rule, the matrix needs it in a form a program can read.

Then compare the description with the deployment. Send a request to every documented path with each method you want to rule out (the lab uses five), and to a list of paths that are not documented, and record which ones answer with something other than 404 or 405. The REST Assessment Cheat Sheet says: "Reconcile the description with observed behavior. Call endpoints the description does not mention and send fields the schema does not define". An operation that answers and is not described has had none of the tests above, because every one of them starts from the description. The lab finds one: GET /debug/config. Module 29 teaches why it is there.

A guessed list finds only what is on it. A second source for "what is deployed" is the route table of the gateway or the framework. Use it as well as the probe, not instead of it: the route table shows what was configured and the probe shows what answers. Module 12, Gateway enforcement, and module 18 produce their inventories from the network for that reason.

Inputs derived from the schema

For each operation with a request body, start from one valid request and change one thing at a time. The REST Assessment Cheat Sheet: "Fuzz from the schema: start with a valid request that satisfies the declared types, required fields and enum values, then mutate one constraint at a time". The lab generates these kinds from each property's entry in the schema:

  • A required property missing, and no body at all.
  • The wrong type, and null.
  • One past each limit: below the minimum, above the maximum, one character over the maximum length.
  • Far past the limit: a string of 100,000 characters, a number of 1012.
  • A property the schema does not declare, and each property the schema marks readOnly. This is the test for mass assignment.
  • A body that is a list where an object is expected, and a malformed or oversized identifier in the path.
  • As a control, a few valid values exactly at each limit, which must be accepted.

The OWASP Input Validation Cheat Sheet lists the same idea among common pitfalls: "Test rejected ranges, missing fields, invalid nested items, and oversized arrays, not just malformed syntax." Sending many generated malformed inputs and watching how the target reacts is fuzzing in the plain sense. Larger fuzzers generate far more inputs, often at random. The lab's list is short and fixed so that its output never changes.

Classify each answer:

  1. A 4xx is a refusal. That is the passing result for a case that must be refused.
  2. A 2xx is an acceptance. For an over-limit value, the limit is not enforced. For a property outside the contract, go one step further. The cheat sheet: "Confirm effect, not just reflection: a field echoed in the response means little until a following request shows that it persisted and changed behavior." The lab reports an accepted undeclared property as it stands, because the schema sets additionalProperties to false and the read operation would not return it. For a readOnly property it reads the profile back and sees tier change from basic to platinum. For a readOnly property an acceptance alone is not a finding: OpenAPI 3.2.1 cites the JSON Schema rule that the resource receiving it "MAY either ignore a readOnly field or treat it as an error". Stored is the finding.
  3. A 5xx is never a refusal. It means the input reached code that did not expect it. Record it even when the body is generic. Exercise 2 shows what a harness loses by counting it as refused.
  4. Read every body, whatever the status. A file path, a stack trace or a query in an error is a finding of its own. ASVS requirement 16.5.1 (Level 2): "Verify that a generic message is returned to the consumer when an unexpected or security-sensitive error occurs, ensuring no exposure of sensitive internal system data such as stack traces, queries, secret keys, and tokens." The lab counts such bodies in check 25 and raises a finding of its own for one that arrives with a status it would otherwise pass. In v1 both are on the two 5xx answers, so they are reported inside that finding.
  5. Against a real server, also watch time and consistency. A request that takes far longer than its neighbours, or the same malformed input getting 400 on one route and 200 on another, is worth a look. The lab has no clock and does not measure this.

What this kind of test cannot find is authorization and business logic. The generator knows the shape of a request. It does not know who owns bkg-1001, or that a booking may be refunded only once, so it has no way to call a well-formed request wrong. The WSTG says of business logic flaws: "This type of vulnerability cannot be detected by a vulnerability scanner and relies upon the skills and creativity of the penetration tester." In the lab, the generated inputs find none of the authorization flaws, and nothing generated finds the double refund.

Limits, sign-in, configuration and detection

Four more groups of tests belong in the plan. The lab runs none of the first three. Each has its own lesson and its own lab.

  1. Rate and resource limits. For each published rate limit, drive traffic past it and assert the number allowed, as module 15 section 6 lists. The REST Assessment Cheat Sheet asks you to "Record the observed limit, the point at which it triggers and the response returned, so each finding states the missing control precisely." This is the test most likely to hurt a shared environment. Agree it in the rules of engagement.
  2. Sign-in, reset and registration. Module 27 section 6 is the list: uniform answers, throttling per account and per source, reset tokens that are single use and bound to one account. ASVS requirement 6.3.1 (Level 1) is the verification statement for the throttling.
  3. Configuration. Module 29 section 6 is the list: methods a route does not allow, debug routes, default accounts, error bodies, TLS versions. The inventory probe above already covers two of them.
  4. Detection. A security test is also a test of logging and alerting. A matrix run produces a known number of refusals from known accounts at a known time. Afterwards, ask whether the log has them and whether the rule that should have fired did. NIST SP 800-115 lists among the uses of a penetration test determining "Defenders' ability to detect attacks and respond appropriately". ASVS requirement 16.3.2 (Level 2) begins: "Verify that failed authorization attempts are logged." Module 30, Logging, detection and response, builds the events and the detection rules. The lab counts both sides once: 27 refusals in a matrix run, 27 events in the API's log.

Kinds of assessment

NIST SP 800-115 names three assessment methods: testing, examination and interviewing. "Testing is the process of exercising one or more assessment objects under specified conditions to compare actual and expected behaviors." Examination is checking, inspecting, reviewing or analysing an assessment object, and section 2.3 gives documents, configurations and logs as what is usually examined. Section 2.2 gives the reason to use more than one: "Since no one technique can provide a complete picture of the security of a system or network, organizations should combine appropriate techniques to ensure robust security assessments." Section 2.1 says an assessment methodology should have at least three phases: planning, execution and post-execution, which is analysis and reporting.

Report each finding

A finding that cannot be repeated cannot be fixed with confidence. The WSTG asks that a report "should also allow another security tester to reproduce the results", and adds: "it is also important to provide guidance to the software developer on how to re-test and find the vulnerability". Write each finding with five parts. This is the first finding from the lab:

Three rules for the report as a whole:

  1. Group cases into findings. The lab's matrix has six cells that were allowed and should not have been. They are two findings, because two checks are missing. NIST section 7.3 puts this under analysis: the primary goals are "to identify false positives, categorize vulnerabilities, and determine the vulnerabilities' causes". Confirm each finding by hand before you report it. A false positive in a report costs the rest of the report its credibility.
  2. Severity is a judgment. This course marks each checklist item Critical, High or Medium, and those marks were chosen by reasoning about impact, not computed. If your organization uses a scoring method, use that one and name it. The WSTG notes that the most commonly used severity metric is the Common Vulnerability Scoring System (CVSS), which this course does not teach. Do not invent a formula.
  3. Say what was covered. The ASVS observes that penetration test reports traditionally list failures only, and says an ASVS certification report should include "scope, a summary of all requirements checked, the requirements where execptions were noted, and guidance on resolving issues" (again the standard's spelling). Module 26 makes the same demand of a design review in its check rev-03.

Keep every finding as a test

A fixed flaw comes back when someone rewrites the handler. The Authorization Testing Automation Cheat Sheet gives the cause: "most of the problems with authorizations occur because features are added/modified in updated releases without determining their effect on the application's authorizations". Its recommendation: "we recommend that developers automate the evaluation of the authorizations and perform a test when a new release is created".

So each finding becomes a regression test: the request, the expected answer, and the control it protects, stored as data and replayed on every change. The lab keeps seven. Each one fails on the build that has the flaw and passes on the build that fixed it. NIST section 8.3 gives the reason the stored request must be the same one: "the test team will be able to verify its implementation only if a mirror copy of the original test is performed". The WSTG's framework chapter makes the same point about releases in its phase 5.3: after a change is deployed, "it is vital that the change is checked to ensure that the level of security has not been affected by the change". Run the matrix, the schema inputs and the inventory comparison in the same pipeline, so a new operation gets its cells the day it enters the description. Module 9 section 6 ends with the rule this generalises: the tests run in the build, and a failure stops the deployment.

5. What it proves, and what it doesn't

Proves: that each case you ran, against that build, with that test data, on that day, was answered as recorded. A clean matrix proves that every operation in the description refused every identity you tried, on the objects you tried.

Doesn't prove the API is secure. A clean result proves only that the cases run were refused. In the lab the fixed build produces no findings from the whole harness, and the same build lets an agent refund one booking twice, 300 each time, 600 in total. Report "these cases were refused", with the list of cases. Never report "no vulnerabilities".

Doesn't cover what the description leaves out. Every generated test starts from the description. An undocumented operation gets no matrix cells and no generated inputs. The inventory probe finds it only if its path is on the list of guesses. The unreleased development version of the WSTG (commit 8df290a, 30 September 2026) says of a published description: "Keep in mind that this document, however well intentioned, may not be accurate, and also may not disclose the complete API."

Doesn't test the description itself. The matrix takes its expected results from the description. If the description wrongly says any customer may cancel any booking, the matrix expects 200, gets 200 and reports a match. The second Try next item in section 7 measures this. A design review is what questions the rule.

Doesn't test business rules. No schema says a booking may be refunded once. Each rule needs a person who knows it to write a test for it. WSTG test WSTG-v42-BUSL-05 is about exactly this kind of rule, a function that may only be used a limited number of times, and says misuse cases must be created for it.

Doesn't outlast the build. The result describes one build. The next change can remove a check. That is why the cases stay in the pipeline.

A refusal can be for the wrong reason. If every generated input is sent with a credential that is not allowed to call the operation, every one is refused with 403 before the API looks at the input, and the run looks clean. The valid control cases are what expose this: they are refused too. Exercise 3 measures it.

6. Prove it

A security test of an API is itself something that can be broken. A working one must pass every one of these:

  • Written permission and scope exist and are dated before the first request in the tester's log.
  • Every operation in the description has a row in the matrix, and the row count is checked by a program, not by eye.
  • Every role that owns data has two test accounts, and each is pointed at the other's objects on every method.
  • Every cell had its expected status before the run. The file of expected results is older than the file of observed ones.
  • Planting a known flaw in a copy of the API makes the suite fail. Remove an ownership check and a matrix cell must go red. A suite that stays green is not testing that control.
  • The generated inputs include valid control cases, and those are accepted. If they are refused, the negative cases prove nothing.
  • A 5xx answer is counted as a finding, never as a refusal.
  • An undeclared property that is accepted is followed by a read of the object, and the report says whether the value was stored.
  • The inventory comparison reports both directions: deployed and not described, and described and not deployed.
  • Each business flow that costs something when repeated has a test written for its rule.
  • After a matrix run, the number of refusals in the API's log equals the number of refusals the harness received.
  • Every finding has a stored request that fails on the build with the flaw and passes on the fixed build, and it runs on every change.
  • The report lists what was tested and what was not, and no real personal data appears in it.

7. Lab

Download labs/security_testing_lab.py and run it with Python 3. It needs no packages beyond the standard library. On Windows, use py -3 wherever this page shows python3. The lab is a small test harness and the API it tests, in one file. The API is a Python object, a request is a method call, and nothing opens a socket. Every test case runs against a fresh copy of the API with the same test data, and every generated input comes from a fixed list, so the output is the same on every run. 8. Check your understanding

The build is green and the API has a missing ownership check. How can both be true?

The tests in the build are positive tests. Each sends a valid request from a caller who is allowed to make it and checks that it works. A missing check changes nothing for those callers. Only a negative test, a request that must be refused, can fail because a check is missing. In the lab the eight functional tests send eight requests and none is answered with a refusal (check 6).

Why does the matrix need two customer accounts when both have the same role?

Because the question is not what a customer may do. It is whose objects a customer may do it to. With one customer account every request is for that account's own data, and every expected answer is 200. The second account supplies objects the first must be refused. Exercise 1 removes it and the missing ownership check is no longer found.

The generated inputs produced no findings on an operation. What can you say about its authorization?

Nothing. The generator changes the shape of a request: types, lengths, extra properties. It sends every case as a caller who is allowed, on that caller's own object. It never asks for someone else's object and it does not know any business rule. The matrix and the hand-written tests cover those.

A penetration test of your API came back with no findings. What do you tell the product owner?

That the testers found nothing in the time they had, with the scope, the build and the accounts listed in the report. Then give the list of what was tested and what was not. The WSTG states that a test clear of issues does not mean the application is good, and NIST SP 800-115 that testing does not provide a comprehensive evaluation. The lab's v2 has no harness findings and refunds a booking twice.

  • StandardThe OWASP WSTG v4.2, under Deriving Functional and Non-Functional Test Requirements, says positive requirements "state the expected functionality that can be validated through security tests", and that "Security tests must also be risk-driven. They need to validate the application for unexpected behavior, or negative requirements." Under Deriving Security Test Requirements Through Use and Misuse Cases it derives requirements from both. It is a guide and sets no requirement.
  • StandardThe OWASP WSTG v4.2, under Security Test Data Analysis and Reporting, says: "The fact that a security test is clear of issues does not mean that the software or application is good." Under Reporting Requirements it says the best practice is to report, for each vulnerability, its type, the threat, the root cause, the testing technique that found it, the remediation and a severity rating, and that the report should tell the developer how to re-test.
  • StandardNIST SP 800-115 (September 2008) section 2.1 says an assessment methodology "should contain at minimum" the phases planning, execution and post-execution. Section 2.2 recommends combining techniques, "Since no one technique can provide a complete picture of the security of a system or network". Section 2.3 says testing "does not provide a comprehensive evaluation of the security posture of an organization".
  • StandardNIST SP 800-115 section 6.5 recommends that each assessment has a plan answering what is in scope, who is authorized, the logistics, how sensitive data is handled and what happens in an incident. It says the plan should list systems that are not authorized, and that the owner of a third-party network "usually must also consent in writing". Section 5.2 recommends that penetration testing "be performed only after careful consideration, notification, and planning". Appendix B is a rules of engagement template.
  • StandardOWASP ASVS 5.0.0 requirement 8.2.1 (Level 1): function-level access is restricted to consumers with explicit permissions. Requirement 8.2.2 (Level 1): data-specific access is restricted to consumers with explicit permissions to specific data items. Requirement 8.2.3 (Level 2): field-level access is restricted likewise. Requirement 8.1.1 (Level 1): authorization documentation defines the rules. Each is written as "Verify that".
  • StandardOWASP ASVS 5.0.0, under Assessment and Certification, says automated tools "will be unable entirely to verify many of the more complicated ASVS requirements or those that relate to business logic and access control", that application-specific automated verifications can be written for those, and that testing without access to necessary additional information "is an inefficient and ineffective mechanism for security verification". Requirement 16.5.1 (Level 2) requires a generic message, with no stack trace or query, when an unexpected error occurs. Requirement 15.3.3 (Level 2) requires countermeasures against mass assignment.
  • StandardThe OpenAPI Specification 3.2.1, under Security Requirement Object, says that when the security field holds several objects, "only one of the entries in the list needs to be satisfied to authorize the request", and that an empty object "indicates anonymous access is supported". Under Validating readOnly and writeOnly it cites the JSON Schema expectation that a resource may either ignore a readOnly field or treat it as an error. Under Specification Extensions it requires extension field names to begin with x-. That the specification describes an API and sets no security requirement on one is this project's reading of it.
  • StandardThe OWASP Authorization Testing Automation Cheat Sheet describes an authorization matrix of features, logical roles and sometimes data, and recommends that developers "automate the evaluation of the authorizations and perform a test when a new release is created". It is guidance and sets no requirement.
  • StandardThe OWASP REST Assessment Cheat Sheet recommends reconciling an OpenAPI description with observed behaviour, fuzzing from the schema one constraint at a time, building a test matrix for each operation from its security requirements (no credentials, a valid token, and a token that lacks the requirement), the swap test with two accounts on reads and writes, and confirming that an undeclared field "persisted and changed behavior" before reporting mass assignment.
  • StandardOWASP API9:2023 Improper Inventory Management lists documentation that does not exist or is not updated as a documentation blindspot, and among its preventions: "Generate documentation automatically by adopting open standards. Include the documentation build in your CI/CD pipeline." It is an awareness document and sets no requirement.
  • BaselineNo security test starts without written permission that names the scope, the exclusions, the environment, the rate and a contact. Third-party systems behind the API are out of scope unless their owner agreed in writing.
  • BaselineEvery operation in the description has a row in an authorization matrix, with two test accounts for each role that owns data and one column with no credentials. Expected results are derived from written rules before the run.
  • BaselineEvery operation with a request body gets inputs derived from its schema, one mutation at a time, with valid control cases. A 5xx is a finding. An accepted undeclared property is read back.
  • BaselineThe description is compared with what answers on every change, in both directions.
  • BaselineEach finding records the request, the expected and observed results, the control that failed and how to re-test. Each is kept as an automated test that runs on every change.
  • BaselineReport "the cases run were refused", with the cases. Never report "no vulnerabilities".
  • OptionRandomly generated inputs in larger numbers. They widen the search for 5xx answers and crashes. Record the seed, and keep them out of shared environments unless the rate is agreed.
  • OptionA penetration test by people who did not build the API, with the description and the source. It finds what nobody wrote a case for. It samples and does not prove.
  • OptionA covert test, run without telling the operations staff, to find out whether detection and response work when nobody is expecting it. NIST SP 800-115 section 2.4.2 describes it as performed "with the full knowledge and permission of upper management".

Review checklist items

These are collected into the site checklist.

  • Written permission and scope exist before any security test is sent Signed by the system's owner, naming what is in scope, what is excluded, the dates and a contact. Third-party systems are tested only with their owner's written consent.
  • Tests run in a test environment, with test data, at an agreed rate Any real data a test returns is recorded as reachable and not copied. Findings and test logs are handled as sensitive.
  • Every control has negative tests, not only functional ones For each operation there is at least one request that must be refused, and the suite fails when a known flaw is planted.
  • An authorization matrix covers every operation, role and object owner Two test accounts for each role that owns data, one column with no credentials, every method, and the expected status written before the run.
  • What is deployed is compared with what is described From a probe and from the route table, in both directions. An operation that answers and is not described is a finding, and gets the same tests as the rest.
  • Each operation is sent inputs derived from its schema, with valid control cases Missing, wrong type, over limit, oversized and undeclared properties. A 5xx or an error body with internals is a finding, and an accepted property is read back.
  • Business rules have tests written by someone who knows the rule Each flow that costs something when repeated, reordered or exceeded has a misuse case and a test. Generated tests do not cover these.
  • A test run is checked against the logs and alerts The refusals the test caused appear in the log with the right account, and the detection rules that should fire did.
  • Each finding can be repeated and stays in the build as a test It records the request, the expected and observed results, the control that failed and how to re-test, and the stored request runs on every change.
  • The report states what was tested, what was not, and what a clean result means Scope, build, accounts and cases are listed. A clean result is reported as the cases run being refused, never as the absence of flaws.
