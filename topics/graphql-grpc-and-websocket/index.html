GraphQL, gRPC and WebSocket APIs

Objective. After this module you can say, for a GraphQL, gRPC or WebSocket API, which controls from the earlier modules stop applying by default, name the attack that follows from each gap, and place the protocol's own control where it works: in the resolver, the interceptor and handler, or the message loop.

Before you start. This module does not teach authorization, limits or request forgery again. It assumes them. You should know Module 9, Object-level authorization, Module 12, Gateway enforcement, Module 15, Rate limiting and cost controls, and Module 28, Browser sessions, cookies and CSRF. You do not need to have used any of the three protocols. Each is explained as far as the attack needs.

1. The attack

Running example: ExampleAir has an HTTP API for bookings and miles that passes the reviews in the earlier modules. Every request is one operation with a JSON body. A gateway counts requests and inspects bodies, each handler checks who owns the booking, the browser app is protected against CSRF, and the dashboards alert on HTTP status codes. The company is fictional.

Then three teams add three new ways in. The mobile team adds a GraphQL endpoint, so the app can ask for a customer, their bookings and their fellow travellers in one round trip. A GraphQL operation that reads is a query, and one that changes data is a mutation. The platform team moves service-to-service calls to gRPC and opens some of them to partners. The web team adds a WebSocket so that a page can show live changes to a booking. All three run over TLS, behind the same gateway, with the same sessions and tokens. No control was removed.

An attacker with one ordinary account then does the following. They send one HTTP request that holds 50 guesses at another customer's password, and the rate limit counts one request. They call an administrative gRPC method that the gateway cannot tell apart from any other binary body. They put a page on another site that opens the WebSocket from a logged-in customer's browser and reads that customer's bookings. The table shows what changed. Every result in this section is one the lab in section 7 measures.

2. Why it works

The earlier modules rest on a shape: one HTTP request carries one operation, a component in front can read it, and the status code says how it ended. The three protocols each break part of that shape. Six assumptions stop being true:

  • "One HTTP request is one operation." The GraphQL specification lets a client give a field an alias, which is a different name for its result: "you can define a different response name by specifying an alias". So a document can select the same field 50 times with 50 different arguments. Many servers also accept a JSON array of operations in one body. The OWASP GraphQL Cheat Sheet calls the result "Batching Attacks, a GraphQL-specific method of brute force attack", and says of request counting: "HTTP request counts alone do not account for expensive queries or multiple operations in one request." On a gRPC stream or a WebSocket there is one request and then any number of messages.
  • "The component in front can read the request." A gRPC body is binary. A GraphQL operation is text inside a JSON string. A WebSocket message arrives after the handshake, on a connection or HTTP/2 stream that carries no further HTTP request. A rule written for JSON bodies and URL paths passes all three unread.
  • "A check at the door covers what is behind it." With one operation per route, a check on the route covers the operation. A GraphQL query walks from object to object, and each step runs a different function. The OWASP Web Security Testing Guide says: "GraphQL does not enforce permissions by default, and so it is up to the application to perform authorization enforcement." A gRPC server that checks a token for every call has done authentication and no authorization. A WebSocket handshake that checks a session has authorized opening the socket, and nothing sent on it.
  • "The HTTP status says what happened." A gRPC response has HTTP status 200 whatever the outcome, and the outcome is a number in a trailer. A GraphQL reply can hold data and a list of errors together. A WebSocket message has no status at all.
  • "The browser stops other sites." A browser sends the cookies for a host with a WebSocket handshake to that host, whichever page opened it. No source this module cites says in one sentence that the CORS check of Module 17 does not apply to that handshake. That is this project's reading of two texts. RFC 6455 section 4.1 lists what a client checks in the server's reply: the status code and the Upgrade, Connection, Sec-WebSocket-Accept, extension and subprotocol fields. No permission header is among them. The Fetch Standard runs the CORS check on a response whose tainting is "cors" (section 4.4), and it gives a request whose mode is "websocket" the tainting "basic" (section 4.1). RFC 6455 leaves the decision to the server: "If the server does not validate the origin, it will accept connections from anywhere." For GraphQL, a server that accepts a mutation in a GET or a form post accepts a request any page can make a browser send (Module 28).
  • "Nobody knows what the API offers unless we publish it." GraphQL and gRPC can each describe themselves to a caller. The GraphQL specification says: "A GraphQL service supports introspection over its schema." gRPC has an optional service, server reflection, that lists a server's methods. Both exist for tools, and both answer an attacker.

None of these is a flaw in the protocol. Each protocol's documents say where the decision belongs. The failure is carrying over a control that was fitted to a different shape and not noticing that it now measures nothing.

3. The control

The controls are the ones you know, moved to the unit that now carries an operation: the field, the call or the message. In order, for each protocol:

GraphQL

  1. Accept mutations only by POST with a JSON body. A mutation is the GraphQL operation type that changes data. The GraphQL over HTTP working draft says: "GET requests MUST NOT be used for executing mutation operations." Refuse other request media types as well. Section 4 has what the draft says and how much weight a draft carries. The CSRF controls of Module 28 still apply to a cookie session.
  2. Authenticate at the endpoint, then authorize in the resolvers. A resolver is the function that produces one field's value. An id argument on any field is an object reference, exactly as an id in a URL path is in Module 9, and a field such as miles or adjustMiles is a property or a function in the sense of Module 10, Property and function authorization. The check goes in the resolver of every type that holds protected data, so that it runs whichever path the query took to reach the object. The OWASP GraphQL Cheat Sheet says to "Enforce authorization checks on both edges and nodes".
  3. Bound the document before any resolver runs. Limit the operations in a batch, how many times a sensitive field such as login may appear in one request, the nesting depth, the size a list argument may ask for, and an estimated cost for the whole query. Refuse a document that is over any limit without executing it. Add a timeout as a backstop.
  4. Count what runs, not what arrives. Keep the limits of Module 27, Attacks on authentication endpoints, on failed logins per account, and count them where the login runs. A limit in the resolver holds whether 50 guesses come as 50 requests, 50 aliases or 50 batch entries.
  5. Turn off what describes the schema to strangers. In production, unless the API is meant for other parties, disable introspection and schema exploration tools, turn off field suggestions (the "Did you mean" hint a server adds to an error about a misspelled field), and return generic errors, as Module 29, Security misconfiguration, teaches. Treat this as tidying, not as protection.
  6. Where you control every client, accept only known operations. A persisted operation is one the server already holds and the client names by an identifier. Accepting only those is an allowlist of queries.

gRPC

  1. Protect the channel, then identify the caller on every call. gRPC's authentication guide describes two kinds of credential: channel credentials, attached to the connection, such as TLS, and call credentials, attached to each call, such as a token in metadata. Metadata is the key-value pairs sent with a call, implemented as HTTP/2 headers. Use TLS always and mTLS between services (Module 7, Sender-constrained tokens: mTLS and DPoP).
  2. List the method paths the edge may forward. Each method has its own path, in the form /package.Service/Method. The path is the one thing a gateway that cannot decode the body can still decide on. A prefix route for a whole package forwards its admin service too. Module 12 still holds: the service authenticates for itself.
  3. Authorize per method in an interceptor, and deny what is not listed. An interceptor runs for every call, so it is the place for a table from method to allowed roles. A method missing from the table is refused. This is deny by default, and it is Module 10's route table under another name. Cover streaming methods as well as unary ones (a unary call is one request and one response).
  4. Check the object in the handler. The interceptor knows the method. Only the handler has decoded the message and loaded the booking, so the ownership check of Module 9 lives there. Validate the fields too: the message definition gives types, not rules. A handler that copies every field of a request message onto a stored record repeats the mass assignment of Module 10, so copy a list of named fields.
  5. Give every call a deadline, and make handlers stop. A deadline is the time after which the client stops waiting. Set one in every client, apply a maximum on the server to calls that arrive without one and to calls that ask for longer, and make long handlers check whether their call was cancelled.
  6. Limit message size, messages per stream and connection lifetime. A size limit applies to one message. A stream needs its own limits on count and duration.
  7. Turn reflection off where callers do not need it.
  8. Monitor grpc-status. Record the method path, the caller and the status code in an interceptor, and alert on the status code. This is the refusal event of Module 30, Logging, detection and response, read from a different field.

WebSocket

  1. Serve wss only. wss is WebSocket over TLS.
  2. At the handshake, compare the Origin header with an allowlist, then authenticate. The origin is the scheme, host and port of the page that opened the socket. A browser sets the header and a script in a page cannot change it. Refuse a handshake whose origin is not on the list with 403. This is the control for cross-site WebSocket hijacking. Over HTTP/2 the handshake is an extended CONNECT request and not a GET (RFC 8441), and the Origin header is used in the same way. It is the same kind of check as the request source check in Module 28, and like that one it is not authentication: Module 17, CORS, explains why an origin is never proof of who is calling.
  3. Prefer a credential the page has to send. A cookie is attached by the browser. A ticket is not: the page fetches a short-lived, single-use value over its authenticated HTTPS session and sends it in the first message, and the server accepts nothing else until it has verified it. A page on another origin cannot read the reply that carries the ticket, as long as the ticket endpoint's CORS policy does not let it (Module 17). Mark the session cookie SameSite as well.
  4. Authorize every message. Each message that names an object or an action gets the object check and the function check, as if it were a request.
  5. Tie the socket to the session. A socket can outlive the session that opened it. Check that the session is still valid on each message or on a short timer, and close a user's sockets at logout. Revocation that the socket never hears about is the stale-token problem of Module 6, JWKS, revocation and introspection.
  6. Apply limits per message. A rate per connection and per user, a maximum frame size and a maximum message size checked before the data is buffered, a limit on the decompressed size, and validation of each message against a schema, as Module 13, Request and response contracts, does for bodies.
  7. Log in the application. The HTTP access log holds one line per socket. Connection, refusal and security events for messages have to be written by the code that handles them.

Four subjects are left out. GraphQL subscriptions, which push results to a client over a long-lived connection, are outside the scope of the GraphQL over HTTP working draft and of this module. Injection through a GraphQL argument, a gRPC field or a WebSocket message is the same injection as through any other input. Attacks on HTTP/2 itself are not covered. Nor is gRPC-Web, the gRPC project's library for calls made from a browser.

4. Defaults and when to change them

GraphQL methods and media typesQueries and mutations by POST with application/json. A mutation by GET gets 405. Another request media type gets 415."GraphQL over HTTP" is a working draft, read at the commit of 28 September 2026. It is not a released standard, so treat its key words as the direction of the community's specification. It says a server must support POST and may support GET, that GET must not be used to execute mutations, and that for such a request "status code 405 (Method Not Allowed) is RECOMMENDED". It says a server "MAY support POST requests encoded with and/or accepting other media types or encodings", and a non-normative section warns that form media types can make a browser treat the request as one that needs no preflight, "thereby opening the server up to Cross-Site Request Forgery (CSRF/XSRF) attacks". It has no rule that limits depth, list size or cost. The working draft allows a server to add validation rules and gives depth and complexity limits as examples in a note. The OWASP GraphQL Cheat Sheet says of depth and amount: "By default these can both be unlimited which may lead to a DoS." It calls cost analysis the most thorough approach and says it "may not always be necessary". The numbers in the lab (depth 5, page 50, cost 1,000) are this project's, chosen for its data. 5. What it proves, and what it doesn't

Proves: that the unit the protocol really uses, the field, the call or the message, is counted, bounded, authorized and recorded. After that, the earlier modules' controls mean what they meant for the JSON API.

Hiding a schema is not a control. With introspection off, the lab's server still answers a misspelled field with Did you mean "adjustMiles"?. The cheat sheet says: "Keep in mind that even if introspection is disabled, attackers can still guess fields by brute forcing them." It also says "Although security by obscurity is not recommended, it might be a good idea to consider removing the Introspection to avoid any leak." The same holds for gRPC: with reflection off, the lab's admin method still runs for a customer who knows its path, when nothing authorizes the call. A mobile app or a published client library contains the schema anyway.

A depth limit does not bound cost. A query three levels deep that asks for a million items passes a depth limit of 5. A cost budget is an estimate. It is only as good as the list sizes it assumes, which is why a page size limit comes with it.

A deadline does not stop work by itself. In the lab the caller gets DEADLINE_EXCEEDED after one second, and a handler that never looks runs all 600 steps. Only the status reached the client.

An Origin check protects browser users. It does not identify anyone. RFC 6455 section 10.1 points out that a client that is not a browser can send any origin it likes. The check stops a browser, under the control of a hostile page, from spending a victim's cookie. A script with no cookie that forges the header gets 401 in the lab, from the session check, not from the origin check.

A timer leaves a window. Checking the session every 1,800 seconds means a logged-out session works for up to 1,800 seconds. That may be acceptable. It should be written down, as Module 6 asks for any revocation bound.

WebSocket masking is not encryption and does not protect the server's data. RFC 6455 requires a client to mask every frame it sends, by XOR with a 4-byte key. It says why in section 10.3: so that a script "does not have control over how the data being sent appears on the wire and thus cannot construct a message that could be misinterpreted by an intermediary as an HTTP request". It protects proxies from a hostile page. Section 5.3 says: "The masking key is contained completely within the frame". Anyone who captures the frame has the key. Confidentiality comes from TLS: "WebSocket implementations MUST support TLS and SHOULD employ it when communicating with their peers" (section 10.6). Check 72 of the lab unmasks a captured frame with nothing but the frame.

Doesn't replace the earlier modules. Every part of the lab has a check from Module 9 or Module 10, placed somewhere new. If the JSON API does not have those checks, changing the protocol will not add them.

6. Prove it

A deployment must pass every one of these. If one fails, the control is broken:

  • GraphQL: one request with 50 aliases of the login field, and one array of 50 login operations, each run at most the number of attempts that 50 separate requests would.
  • GraphQL: a query over the depth limit, a list argument over the page limit and a query over the cost budget are each refused with no resolver called.
  • GraphQL: a second customer's object is refused when it is requested by id at the root and when it is reached through every nested path, and a test names each path.
  • GraphQL: a mutation sent by GET returns 405 and one sent as a form post returns 415, and neither changes data.
  • GraphQL: with introspection off, a misspelled field name returns no suggestion, and an error returns no stack trace.
  • gRPC: every method, streaming ones included, returns UNAUTHENTICATED without a token, and a method that is not in the authorization table returns PERMISSION_DENIED for every role.
  • gRPC: a customer's call for another customer's object returns PERMISSION_DENIED.
  • gRPC: a call with no deadline and a call that asks for a longer one each end at the server's maximum, and the handler's work stops with it.
  • gRPC: a message one byte over the receive limit and a stream one message over its limit each return RESOURCE_EXHAUSTED.
  • gRPC: a refused call raises the same alert that a 403 from the JSON API does.
  • WebSocket: a handshake from an origin that is not on the list, from a lookalike origin, and with no Origin header each get 403, with a valid session cookie attached.
  • WebSocket: a message for another customer's object is refused on an open, authenticated socket.
  • WebSocket: after logout, the next message on an existing socket closes it.
  • WebSocket: a message flood, an oversized frame, a fragmented message over the limit and a small compressed frame that inflates over the limit each close the socket, and the last three are refused before the data is held in memory.
  • WebSocket: nothing answers on ws://.

7. Lab

Download labs/protocols_lab.py and run it with Python 3. It needs no packages beyond the standard library. On Windows, use py -3 wherever this page shows python3.

Nothing in the lab opens a socket, and it uses no GraphQL, gRPC or WebSocket library. Each protocol is a small model in plain Python, and the simplifications matter:

  • GraphQL. The parser accepts a subset of the language: one operation, fields, aliases, string and integer arguments and nested selections. It has no fragments, variables or directives. Validation only checks that a field exists, that it has the right kind of selection, and that a first argument is a whole number, zero or more. Introspection is a single field that returns a flat list of names, where the real one returns typed objects. The request parameters are passed in already decoded. The endpoint answers 401 to a request with no session unless it holds only login fields. The working draft says that decision should not be based on the contents of the request. The lab answers a result that contains errors with HTTP 200. The working draft recommends 200 when a field raises an error during execution, in its examples, and a code of its own, 294, which it says is not registered with IANA, for a result with both data and errors, in its status code section. Either way the code is in the 2xx range.
  • gRPC. A call is a path, a metadata dict and one or more messages with gRPC's 5-byte prefix. The message encoding is a tag, a length and a value per field. It is binary and it is not Protocol Buffers (protobuf), the format gRPC normally uses for messages. HTTP/2, flow control and TLS are not modelled. Reflection is one method that returns method paths; the real protocol is a streaming service that returns file descriptors. Time is a counter of 100 ms work steps, and the slow handler needs 600 of them. The server's default deadline also caps a longer grpc-timeout.
  • WebSocket. The handshake is an object with headers, with no Sec-WebSocket-Key exchange. A frame is a declared length, a payload and flags, and it is not masked. A compressed frame is raw DEFLATE data in one frame, without the negotiation that RFC 7692 defines. The lab counts a frame's declared length as buffered and sends no megabyte payloads. The browser attaches a cookie by host. For a cookie marked SameSite=Lax it leaves the cookie out when the page is on another site, which follows the cheat sheet's advice and is not a full model: Module 28's lab models cookies. The rule that a page on another origin cannot read the ticket endpoint's reply is stated in the lab, not simulated.
  • Passwords, session ids, tokens and tickets are random on each run and are never printed. The edge and handshake limiters have no clock: each counts within one window. The WebSocket message limit uses the times the lab passes in.

8. Check your understanding

A GraphQL API sits behind a gateway that allows 5 login requests a minute for each client. How many passwords can one client try in a minute?

You cannot tell from the gateway. It counts HTTP requests, and one request can carry as many aliased login fields, or as many batched operations, as the server will execute. The number is set by the limits inside the GraphQL server: how many login fields one request may hold and how many failures an account may have.

A team turns off introspection on GraphQL and reflection on gRPC and closes the finding "administrative operations are exposed". Is it closed?

No. The names are harder to find and the operations are as callable as before. Field suggestions, client code and guessing give the names back. The finding closes when the admin field's resolver and the admin method's interceptor rule refuse a caller who is not an administrator, and a test shows it.

A WebSocket endpoint checks the session cookie at the handshake and checks ownership on every message. Does it still need an Origin check?

Yes. The ownership check compares the object with the session's user. A page on another site that opens the socket from the victim's browser is that user as far as the server can tell, so it can read and change everything the victim can. The origin check, or a ticket the page must fetch and send, is what tells the victim's own page from someone else's.

A gRPC service's dashboard shows no HTTP errors for a week. What do you know?

That the transport worked. A gRPC response carries HTTP status 200 whether the call succeeded, was refused or timed out. The outcome is the grpc-status trailer, and a dashboard that does not read it would look the same during an attack that produced thousands of PERMISSION_DENIED results.

  • StandardThe GraphQL specification lets a document give a field an alias, and says the top level fields of a mutation are expected to perform side effects and that the mutation's root selection set "should be executed serially". Its validation rules require that fragment spreads form no cycles. They contain no limit on depth, list size or cost. GraphQL specification, September 2025, sections Field Alias, Mutation, and Fragment Spreads Must Not Form Cycles.
  • StandardThe GraphQL specification says "A GraphQL service supports introspection over its schema", through the meta-fields __schema and __type on the root of a query operation. GraphQL specification, September 2025, section Introspection.
  • StandardThe GraphQL over HTTP working draft says a server must support requests by POST and may support other methods such as GET; that "GET requests MUST NOT be used for executing mutation operations", with a 4xx response for which 405 is recommended; that a server must support POST bodies in application/json and may support others; and that a server may apply additional validation rules, with depth and complexity limits named as examples in a note. It is a working draft, not a released standard. GraphQL over HTTP, sections Request, GET, POST and Validation.
  • StandardThe same draft's Security section, which it marks non-normative, says that multipart/form-data or application/x-www-form-urlencoded bodies may be treated by a browser as a request that needs no preflight, "thereby opening the server up to Cross-Site Request Forgery (CSRF/XSRF) attacks", and lists limits it expects implementers to consider, among them document size, timeouts, pagination limits, and "query depth and complexity limits". GraphQL over HTTP, section Security.
  • StandardThe OWASP GraphQL Cheat Sheet recommends depth limiting, amount limiting, pagination, timeouts, query cost analysis, and rate limits applied in the business logic layer. For batching it gives three options: object request rate limiting in code, preventing batching for sensitive objects, and limiting the number of queries that can run at one time. It recommends authorization checks "on both edges and nodes", and disabling or restricting introspection, with the warning that "attackers can still guess fields by brute forcing them". Guidance, not a requirement. GraphQL Cheat Sheet.
  • StandardOWASP ASVS 5.0.0 requirement 4.3.1 (level 2): "Verify that a query allowlist, depth limiting, amount limiting, or query cost analysis is used to prevent GraphQL or data layer expression Denial of Service (DoS) as a result of expensive, nested queries." Awareness documents: they set no requirements. API4:2023 and API2:2023.
  • StandardThe gRPC protocol document defines a request as an HTTP/2 POST to the path /Service-Name/method name with a content type that begins application/grpc, an optional grpc-timeout header, and length-prefixed messages. The response's HTTP status is 200 and the outcome is the grpc-status trailer: "Status must be sent in Trailers even if the status code is OK." It says a server should assume an infinite timeout when the header is omitted. Project documentation, not a standard. gRPC over HTTP2, v1.84.0.
  • StandardThe gRPC status code document says the library returns UNIMPLEMENTED for a method not found at the server, DEADLINE_EXCEEDED when a deadline expires before the server returns a status, and RESOURCE_EXHAUSTED when a "Sent or received message was larger than configured limit".   • StandardThe gRPC documentation describes channel credentials and call credentials, says a token is normally verified by a server side interceptor, and lists server-side authentication and authorization among the uses of interceptors. It says gRPC sets no deadline by default and that the server application is responsible for stopping the work it started for a cancelled call. It says reflection is not enabled automatically and that the owner of a public API may not want to expose it. grpc.io guides: Authentication, Interceptors, Deadlines, Reflection.
  • StandardThe OWASP gRPC Security Cheat Sheet recommends TLS in production and mTLS between services; an authentication check for each protected method, noting that "Registering a unary interceptor does not protect streaming methods"; "method-level authorization checks based on the principle of least privilege"; validation of message fields, because "Protocol Buffers provide type safety but not business logic validation"; message size limits and limits on messages per stream; timeouts on client and server; and disabling reflection in production. Guidance, not a requirement. gRPC Security Cheat Sheet.

Review checklist items

These are collected into the site checklist.

  • Limits count operations, not HTTP requests Aliased fields, batch entries, stream messages and socket messages are counted where they run, and a sensitive field such as login is limited per request and per account.
  • Every GraphQL resolver that returns protected data checks the caller The check is on the type, so it runs for a root field and for every nested path, and a test names each path to another customer's object.
  • GraphQL documents are bounded before execution Batch size, depth, list page size and estimated cost each have a limit that refuses the document with no resolver called, and a timeout backs them up.
  • GraphQL mutations are accepted only by POST with application/json A mutation by GET returns 405 and another request media type returns 415, and the CSRF controls for a cookie session are still in place.
  • Introspection, reflection and field suggestions are off unless the API is published Errors are generic, and no finding is closed on the grounds that an operation's name is hidden.
  • Every gRPC method has an authorization rule, and a method without one is refused An interceptor enforces it for unary and streaming methods, the edge forwards listed method paths only, and handlers check the object.
  • Calls have deadlines and messages have size limits that run before the data is held The gRPC server enforces a maximum deadline and handlers stop on cancellation. gRPC and WebSocket messages have size, count and decoded-size limits.
  • The WebSocket handshake checks Origin against an allowlist and authenticates The match is exact, a missing or lookalike origin gets 403, the socket is served over wss only, and the session cookie is SameSite.
  • Every WebSocket message is authorized, and a revoked session loses its sockets Object and function checks run per message. The session is re-checked per message or on a stated interval, and logout closes open connections.
  • Monitoring reads the protocol's own outcome Alerts use grpc-status, GraphQL errors and per-message events, not the HTTP status, and each service logs refusals with the caller and the operation.
