1. The attack

Running example: a customer moves 10,000 airline miles into their hotel rewards account. ExampleAir's server sends the transfer to ExampleHotels' API. Company names are fictional.

With a plain API key, the key travels in every request. Anyone who captures one request, from a log, a proxy, or a debugging tool, has the key and can send any request they like. HMAC signing fixes that, but each partial version of it leaves a different attack open:

The last row never turns green. That's the built-in limit of a shared secret, covered in section 5.

2. Why it works

An HMAC is a hash computed with a secret key mixed in. Only someone holding the key can produce the right value, and anyone holding the key can check it. The sender computes an HMAC over a description of the request and sends the result, the signature, instead of the key.

Three broken assumptions cause most HMAC failures:

  • "A valid signature means a new request." It doesn't. A signature stays valid forever unless the signed data includes something that expires (a timestamp) and something that can only be used once (a nonce).
  • "Both sides will describe the request the same way." Only if they agree on exact bytes. "miles":10000 and "miles": 10000 are the same JSON but different bytes, so they produce different signatures.
  • "The signature proves the sender." It proves the sender holds the key. The receiver holds the same key, so it could have produced the signature too.

3. The control

What gets signed

Both sides build the same canonical string: fixed fields, fixed order, one per line. The body is represented by the SHA-256 hash of its exact bytes.

POST                       method
api.hotel.example          host: blocks replay against another environment
/v2/transfer               path
                           query string (empty here, but always present)
1716307200                 timestamp: limits how long the signature is valid
a1b2c3d4-5678              nonce: makes each request unique
application/json           content type
bb4cc23e...b7a85c78        SHA-256 of the raw body bytes

The right-hand notes are for this page only. They are not part of the string.

How the receiver verifies

  1. Look up the key by keyId. Unknown or retired key: reject.
  2. Check the timestamp is within the allowed window of server time. Outside it: reject.
  3. Hash the raw body bytes as received. Never re-serialize parsed JSON, and never trust a hash the caller sent.
  4. Rebuild the canonical string from the received request, compute the HMAC, and compare with a constant-time comparison.
  5. Only then record the nonce, using an atomic "set if absent". Already present: reject. Recording it after the signature check stops forged requests from filling the cache.
  6. Pass the request to authorization and business logic. A valid signature says who sent it, not whether they're allowed to do it.

5. What it proves, and what it doesn't

Proves: the request came from a holder of the key, the signed fields weren't changed, and, with timestamp and nonce checks, it is recent and new.

Doesn't prove: which of the two key holders created it. It doesn't prove the sender is allowed to perform the action. And it proves nothing once the key leaks from either side.

Replay protection is not idempotency. The nonce cache blocks the same request twice. If the caller times out and legitimately retries with a new nonce, the receiver sees a new, valid request. Operations that move money or points also need an idempotency key, such as the caller's transaction ID, stored durably. That's covered in module 11.

6. Prove it

A working implementation must reject every one of these. If any is accepted, the control is broken:

  • A body with one character changed, including added whitespace.
  • The same request sent to a different host or path.
  • A signature made with a different key, or a retired key after the rotation overlap ends.
  • A timestamp outside the window, in either direction.
  • An exact resend inside the window.
  • A valid signature copied onto a request with a different nonce.

8. Check your understanding

Why is the body hash computed from raw bytes rather than the parsed JSON?

Parsing and re-serializing can change whitespace, key order, or number formatting. The signature covers exact bytes, so the receiver must hash exactly what arrived.

An attacker captures a request and resends it 10 seconds later. Which check stops it?

The nonce check. The timestamp is still inside the window, and the signature is still valid.

ExampleHotels is breached and the shared key leaks. What can the attacker do, and what would have prevented it?

They can sign new requests as ExampleAir, because HMAC gives both sides the same signing power. Asymmetric signatures prevent this: the receiver holds only a public key, which can verify but not sign.

In canonical_string the body hash covers the bytes that arrived. Add json to the import line at the top of the lab. Then make canonical_string parse the JSON and hash a compact re-serialization instead:

body = json.dumps(json.loads(body), separators=(",", ":")).encode()
body_hash = hashlib.sha256(body).hexdigest()

2. The canonical string drops the host

Every option, and why

In Verifier.verify, move the nonce lookup and the line that records the nonce above the signature comparison, so the order becomes time window, nonce, signature.

What does the run print differently?

Every option, and why
  • Line 7 still rejects as a replayed nonce. Attempt 6 records that nonce under either order, so the exact replay is caught either way.
  • Line 9 still rejects with a bad signature. Checking the nonce earlier does not make a forged signature verify.
  • Correct, and it is the uncomfortable answer: all nine verdicts are identical, so the verdicts give no sign that anything is wrong. Reference

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardUse HMAC as RFC 2104 section 2 and FIPS 198-1 section 4 define it. FIPS 198-1 section 1 requires an approved hash function: "HMAC shall use an Approved cryptographic hash function". RFC 9421 section 3.3.3 defines HMAC with SHA-256.
  • StandardUse a key at least as long as the hash output length L, which is 32 bytes for SHA-256. This is a recommendation, not a requirement: RFC 2104, an Informational RFC, says in section 2 that "the minimal recommended length for K is L bytes", and in section 3 it strongly discourages shorter keys.
  • StandardCompare signatures with a constant-time function. The Python 3.14 documentation for the hmac module recommends hmac.compare_digest instead of == when verifying a digest, "to reduce the vulnerability to timing attacks". RFC 2104, FIPS 198-1 and RFC 9421 say nothing about comparison timing.
  • BaselineSign method, host, path, query, timestamp, nonce, content type, and the SHA-256 of the raw body, in a documented fixed order.
  • BaselineVerify in this order: key lookup, time window, body hash, signature, nonce record. Record the nonce only after the signature verifies.
  • BaselineAccept timestamps within 5 minutes of server time. Keep nonces for at least the same period. Keep clocks synchronized.
  • BaselineStore keys in a secrets manager on both sides, versioned. Rotate with a short overlap in which both versions verify, then retire the old one.
  • BaselineEnsure proxies and gateways pass signed components through unchanged, or verify at the edge.
  • OptionUse RFC 9421 HTTP Message Signatures, with the content-digest field from RFC 9530, instead of a custom format.
  • OptionUse asymmetric signatures when the receiver must not be able to forge caller requests.

Review checklist items

These are collected into the site checklist.

  • Signed M2M requests cover method, host, path, query, timestamp, nonce, content type, and the raw body hash The canonical format is documented, and both parties test against shared examples.
  • The receiver hashes the raw body bytes it received It never re-serializes parsed JSON, and never trusts a caller-supplied hash.
  • Timestamps are bounded and nonces are rejected on reuse The nonce is recorded only after the signature verifies. The cache TTL is at least the time window.
  • Signatures are compared in constant time Use a library function built for this, not string equality.
  • Keys are per partner, at least 32 bytes, and rotated with an overlap Both sides store keys in a secrets manager. Retired keys are rejected after the overlap ends.
  • Intermediaries do not alter signed components Gateway and proxy behavior is tested with signed requests end to end.
  • The shared-secret limitation is accepted in the threat model Otherwise use asymmetric request signatures.
