Part 4: AI and agents · Module 25

Supply chain, retrieval, and memory

Last reviewed 2026-10-01 · Jump to reference

Objective. After this module you can explain why filtering a retrieval result is not the same as filtering the corpus, say what a result count discloses about documents a caller cannot read, show why ranking hygiene is not a security control, and keep provenance on anything an agent writes down.

Before you start. Retrieval makes a document store part of your authorization surface. Whoever can put a document into the index, and whoever can get one out of it, are security-relevant roles, and in most systems both are treated as plumbing.

1. The attack

Running example: one vector index shared by three carriers, ExampleAir, ExampleRail and ExampleBus. Company names are fictional. All three have a refund policy document, and the documents are similar, because refund policies are similar.

OWASP covers this as LLM08:2025 Vector and Embedding Weaknesses, and the sentence that describes the deployment is short: "In multi-tenant environments where multiple classes of users or applications share the same vector database, there's a risk of context leakage between users or queries."

Three attacks, which are the three the lab runs.

AttackWhat it needsWhat it gets
Read another tenant's documentA system that ranks first and filters secondNothing directly, and a result set that silently shrinks while another tenant's document sat above yours
Probe for documents you cannot readA result count computed before the filterConfirmation that a matching document exists, from a query you were allowed to run
Put a document in the indexAny route that writes to the corpusFirst place in the ranking, inside the victim's own tenant
Have a claim written to memoryOne retrieval that the agent summarisedA fact with no source attached that survives the document's deletion

The last row is the one that lasts. OWASP's agentic list puts it in six words: "Memory poisoning reshaped behaviour long after the initial interaction."

2. Why it works

Filtering after you rank is not filtering

There are two places to apply a tenant filter and they are not equivalent. Rank the whole corpus and then drop what the caller may not see, or restrict the corpus and then rank what is left.

Checks 3 to 11 of the lab run both. Unfiltered, the top three for ExampleAir's own query are their refund policy, ExampleBus's, and ExampleRail's. Post-filtering that result leaves one document. The caller asked for three and received one, and the two that were removed are gone from the response with no record of what they were.

Pre-filtering returns three ExampleAir documents, two of which the post-filtered version never showed at all, because other tenants' documents had taken their places in the ranking. So post-filtering is worse in two directions at once: it leaks the existence of other tenants' content through the missing slots, and it withholds the caller's own documents by letting other tenants outrank them.

OWASP's mitigation names the shape directly: "Implement fine-grained access controls and permission-aware vector and embedding stores". Permission-aware means the store knows, not the code that reads the store's output.

A count is an answer

Part B is the quieter version of the same bug. The caller runs a query built from terms that only appear in another tenant's documents. They get no results, which is correct. The interface also tells them there were three matches, which is not.

Checks 12 to 17 separate those two numbers. Three matches across the index, zero that this caller may read, and a query matching nothing anywhere also returns zero. If the caller can tell the first case from the third, they have a membership oracle: a way to confirm that a document containing given terms exists, without ever reading one.

This generalises past counts. Anything computed before the filter and surfaced after it is the same bug: a total, a facet count, a "did you mean", a latency difference. The rule is that the filter goes first and everything downstream is computed from what survived it.

Ranking hygiene is not a security control

Part C puts a document in the index that was written to win, not to be read: the query's terms, repeated. It takes first place, above the real policy, with a raw cosine score of 0.62 against 0.53.

The obvious fix is the information-retrieval one. Damp repeated terms, so a word appearing ten times counts for less than ten times once. Check 25 is the result: the scores move to 0.59 against 0.53, and check 24 says the stuffed document is still first. I expected it to drop and it does not, because that document is made entirely of query terms, so damping the repetition narrows the margin without changing the order.

That is the useful finding in this module. Ranking adjustments are a quality measure, and an attacker who can write to your index will beat them, because they can see the ranking and iterate. Check 28 adds that tenant isolation did not help either: the stuffed document was uploaded into ExampleAir's own tenant, so pre-filtering keeps it.

What works is checks 29 and 30: rank only documents of internal origin, and the real policy is first again. The control is about where a document came from, which is LLM04:2025 Data and Model Poisoning: "The risks are particularly high with external data sources, which may contain unverified or malicious content", with the mitigations starting at tracking data origins and verifying legitimacy.

Memory outlives the document

An agent reads a retrieved document and writes down what it learned. Whether that write records where the claim came from is a one-line decision with a long tail.

Part D writes the same two claims into two stores. With provenance, one is usable and the other is marked as coming from a user-uploaded document. Without it, both are usable, and check 35 is the claim from the stuffed document now sitting in memory as an unattributed fact.

Then checks 38 to 40, which are the point. Removing the poisoned document from the index does not remove the memory written from it. The corpus is clean and the agent still believes the thing. With provenance, the memory is still there and still unusable, because the judgement travelled with the claim.

So memory needs the same two properties as the index: an origin on every item, and a rule that says which origins may inform a decision. Without those, deleting the source is not remediation, and you have no way to find what else that document taught the agent.

3. The control

  1. Filter the corpus before you rank it. The store is permission-aware, not the code reading its output.
  2. Compute every number after the filter. Totals, facets, suggestions and anything else derived from the corpus.
  3. Tag every document with its origin at ingestion, and classify it, which is OWASP's "Tag and classify data within the knowledge base to control access levels".
  4. Decide which origins may answer which questions, and keep untrusted origins out of the corpus for decisions that matter.
  5. Validate at ingestion, because that is the last point where you still know where a document came from.
  6. Treat ranking adjustments as quality, not security. They narrow margins. Someone who can write to your index iterates against them.
  7. Record provenance on every memory write, with the source document and its origin.
  8. Make deletion reach memory. If a document is removed, find what was written from it.
  9. Log retrievals. OWASP: "Maintain detailed immutable logs of retrieval activities to detect and respond promptly to suspicious behavior".

5. What it proves, and what it doesn't

Proves: that a caller's results contain only documents they may read, that no number in the response was computed over documents they may not, that every document in the corpus has a recorded origin, and that anything written to memory can be traced back and judged.

Doesn't prove: that the documents are true. Everything here is about where content came from and who may see it, not whether it is correct, and an internal document can be wrong or out of date. It also proves nothing about embeddings themselves, where OWASP notes that "attackers can exploit vulnerabilities to invert embeddings and recover significant amounts of source information", which is a property of the vectors rather than of your access control.

Deleting the document is not the remediation. Checks 38 to 40 remove the stuffed document from the index and find the claim still sitting in memory, unattributed, with nothing linking it to the document that is now gone. If your incident response for a poisoned corpus ends at the corpus, it ends too early.

6. Prove it

  • The retrieval code path, showing the tenant restriction applied to the corpus rather than to the result.
  • A test that a query crafted against another tenant's document returns nothing and reports nothing.
  • Every number in a retrieval response, with where in the pipeline it is computed.
  • The origin field on each document, and the ingestion step that sets it.
  • The list of routes that can write to the index, with who can use each one.
  • Which origins are permitted for decision-bearing retrieval, written down.
  • A test that a document from an untrusted origin does not appear in a decision-bearing result.
  • The memory schema, showing source and origin on every item.
  • The procedure that sweeps memory when a document is withdrawn, and evidence it has been run.
  • Retrieval logs, with retention, and what would be looked at after a report.

Checks 5 to 11 are the module's first point, and the thing to notice is that post-filtering fails in both directions at once. The caller receives one document instead of three, which tells them something was removed, and two of their own documents never appeared because other tenants' content outranked them. Pre-filtering fixes both, because the documents the caller may not read were never candidates.

Checks 12 to 17 are worth running against your own search. Three matches in the index, zero readable, and a nonsense query also returning zero. If your interface shows a total, a facet count or a suggestion computed before the filter, those two cases look different to a caller who is allowed to ask.

Checks 22 to 26 are where I was wrong and the lab corrected me. I expected damping repeated terms to drop the stuffed document below the real policy. It does not: the margin narrows from 0.08 to 0.06 and the order is unchanged, because that document is made entirely of query terms. Checks 29 and 30 show what does work, and it is not a ranking change: restrict the corpus to documents of internal origin and the real policy is first again.

Check 28 is the one to take to a design discussion about tenant isolation. The stuffed document was uploaded into ExampleAir's own tenant, so pre-filtering keeps it. Isolation answers "whose documents can I see" and says nothing about "who wrote the ones I can".

Checks 38 to 40 close it. The poisoned document is deleted and its claim is still in memory with no source attached. The store that kept provenance still holds the claim too, and still will not use it.

8. Check your understanding

Your retrieval fetches the top ten and then removes documents the caller may not read. What is wrong with that?

Two things. The caller sees fewer results than they asked for, which tells them documents exist that were removed, and their own relevant documents never appear because other tenants' content occupied the ranking. Restricting the corpus before ranking fixes both, because documents the caller may not read were never candidates.

A caller runs a query and gets no results, but the interface says "3 matches". What have they learned?

That three documents containing those terms exist somewhere in the index. That is a membership oracle, and it works from a query they were allowed to run. Every number in the response has to be computed after the filter, including totals, facet counts and suggestions.

Someone uploads a document stuffed with your query terms and it ranks first. Is better ranking the answer?

No. The lab damps repeated terms and the stuffed document stays first, because it is made entirely of query terms, so the margin narrows and the order does not change. Ranking adjustments are a quality measure and an attacker who can write to your index will iterate against them. The control is origin: restrict decision-bearing retrieval to documents whose provenance you trust.

You remove a poisoned document from the index. Is the problem over?

Not if an agent read it first. A claim written to memory survives the document's deletion, and if the write recorded no origin there is nothing linking the two, so you cannot even find what to remove. Record source and origin on every memory write, and make document withdrawal trigger a memory sweep.

Review checklist items

These are collected into the site checklist.

  • The permission filter is applied to the corpus, not the result Post-filtering returns fewer results than requested, which discloses removals, and lets other tenants outrank the caller's own documents.
  • Every number in a retrieval response is computed after the filter A total computed before it confirms that documents the caller may not read exist.
  • Decision-bearing retrieval excludes untrusted origins Ranking adjustments do not displace a document written to win. Origin does.
  • Every document carries an origin recorded at ingestion It cannot be recovered later, and the other controls depend on it.
  • Every memory write records its source document and origin A memory without provenance cannot be judged, found or cleaned up.
  • Withdrawing a document triggers a memory sweep The claim leaves the index before the document does. Deletion alone is not remediation.
  • Every write route into the index is enumerated and reviewed An upload form that feeds retrieval is an authorization decision.
  • Retrieval activity is logged with a stated retention OWASP asks for detailed immutable logs of retrieval activity.
  • No ranking adjustment is reported as a security control State the margin it changes. In the lab it was 0.08 to 0.06, with the order unchanged.
