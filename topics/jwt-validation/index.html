1. The attack

Running example: ExampleHotels issues JWT access tokens, and its balance API verifies them. Company names are fictional.

A JWT carries its own description of itself. The header says which algorithm signed it. The payload says who issued it, who it is for, and when it expires. A verifier that reads those fields and believes them is doing what the token asked, not what the application needed. RFC 7519 makes this explicit: for every registered claim, including iss, aud and exp, it says "Use of this claim is OPTIONAL." A plain JWT is not required to contain anything.

So the verifier's behaviour depends on how much it decided in advance:

A token with alg set to none and no signatureWorksBlockedBlocked
A token signed HS256, using the issuer's public key as the secretWorksBlockedBlocked
A genuine token issued for a different APIWorksWorksBlocked
A genuine token that expired an hour agoWorksWorksBlocked
An ID token where an access token was expectedWorksWorksBlocked
A current, genuine token stolen from the real clientWorksWorksWorks

The last row never turns green. Everything on this page checks that the token is genuine, not that the caller is its owner. Binding a token to its holder is module 7.

2. Why it works

Both algorithm attacks come from one mistake: letting the token choose the operation.

  • alg: none. RFC 7518 section 3.6 defines an Unsecured JWS, which uses the empty octet sequence as its signature. The specification is blunt about it: "Implementations MUST NOT accept Unsecured JWSs by default." A verifier that switches on the header's algorithm and has no branch for none other than "skip verification" accepts a token anyone can write.
  • RS256 to HS256 downgrade. This is algorithm confusion. The issuer signs with an RSA private key, and the verifier holds the matching public key. The public key is public. An attacker changes the header to HS256 and computes an HMAC over the token using that public key as the shared secret. A verifier that reads HS256 from the header and reaches for "the key it has" verifies successfully, because the attacker used the same value.

The remaining failures come from a different mistake: treating signature verification as the whole job.

  • "A valid signature means a valid token." It means the bytes were not altered since the issuer signed them. It says nothing about whether this token was meant for you, whether it is still current, or whether it is even the right kind of token.
  • "Every JWT has the claims I need." RFC 7519 marks all of them optional. Whether aud must be present is a decision your application makes, and if it does not make it, the answer is no.
  • "There is only one kind of token here." The same issuer commonly signs access tokens and ID tokens with the same key. Where one issuer can issue more than one kind of JWT, RFC 8725 section 3.12 requires the validation rules to be "mutually exclusive, rejecting JWTs of the wrong kind."

3. The control

What the application declares

Write the token profile down before any token arrives. Nothing in this list is ever read from the token being verified.

algorithms      RS256                      one entry, not a family
type            at+jwt                     RFC 9068 access token
issuer          https://auth.hotel.example exact match
audience        https://api.hotel.example  this API, not the family
required claims iss exp aud sub client_id iat jti
key source      the issuer's published keys, selected by kid
clock leeway    60 seconds, both directions

RFC 9068 section 2.2 is where the required claim list comes from. A different profile, such as an OpenID Connect ID token, has a different list and different rules.

How the verifier checks

  1. Read the header's alg and compare it against the declared allowlist. Not on the list, including none: reject. Do not use it to select the operation; use it only to decide whether to continue.
  2. Check the typ against the declared type. This is what stops an ID token being accepted as an access token.
  3. Verify the signature with the declared algorithm and a key from the declared source, selected by kid. Getting the key from the token itself, through jku or x5u, hands the attacker the key choice.
  4. Only now read the claims. Confirm every required claim is present before testing any of them. A missing claim is a rejection, not a default.
  5. Compare iss with the expected issuer, and confirm the verifying key belongs to that issuer. RFC 8725 section 3.8 requires this pairing.
  6. Confirm this API's own identifier appears in aud. RFC 7519 section 4.1.3: if the claim is present and the principal is not identified by a value in it, "the JWT MUST be rejected."
  7. Check exp, and nbf and iat where present, against server time with a small, documented leeway.
  8. Hand the request to authorization. The token being genuine, current and addressed to you says nothing about whether this caller may perform this operation on this object.

The whole system

Untrusted inputServer decisionsDeclared stateRejection path

Two things arrive at the verifier, and only one of them is trusted. Everything the token says is a claim to be checked against the profile, never a setting to be obeyed.

5. What it proves, and what it doesn't

Proves: the token was signed by a key you expected, has not been altered since, is the kind of token you were expecting, was issued for you by an issuer you trust, and is current.

Doesn't prove: that the caller presenting it is the party it was issued to. It is still a bearer credential. It also does not prove the token has not been revoked since issuance, and it says nothing about whether this caller may touch this particular object.

Validation is not revocation. A verifier checking exp accepts a token until it expires, even if the account was disabled a minute after it was issued. Nothing on this page detects that. Deciding how fast a withdrawn grant must stop working, and what that costs, is module 6.

6. Prove it

A working verifier must reject every one of these. If any is accepted, the control is broken:

  • A token with alg set to none and an empty signature.
  • A token with alg changed to HS256 and signed with the issuer's public key as the secret.
  • A token with a valid signature but the wrong iss.
  • A token whose aud names another service, including one in the same family of APIs.
  • A token missing any claim the profile requires.
  • An ID token, or any other JWT kind the same issuer signs, presented where an access token is expected.
  • A token with one bit changed anywhere in the signature.
  • A token signed by a valid key belonging to a different issuer.
  • A token whose exp has passed, and one whose nbf has not yet arrived, both outside the declared leeway.
  • A token whose kid is unknown, or names a key that was rotated out.

8. Check your understanding

Why does signing with the public key work against a verifier that trusts the header?

The verifier holds one key and chooses the operation from the header. Told HS256, it treats its key as a shared secret and computes an HMAC. The attacker did the same thing with the same value, because a public key is public. The fix is not a better key, it is refusing to let the token pick the algorithm.

Your verifier checks the signature, issuer and expiry, and the token passes. Name two attacks still open.

A token issued for a different service in the same estate is accepted, because aud was not checked. And an ID token signed by the same issuer is accepted where an access token was expected, because the token type was not checked.

Why is a required-claim list part of the profile rather than a property of JWT?

Because RFC 7519 marks every registered claim OPTIONAL. A bare JWT can legitimately contain nothing. What must be present is decided by the profile you are verifying against, such as RFC 9068 for OAuth access tokens, and if you never declared one, you are not requiring anything.

The account is disabled one minute after a one-hour token is issued. What does your verifier do?

It keeps accepting the token for the remaining 59 minutes, plus the 60 seconds of leeway. Every check on this page passes, because they all describe the token, not the current state of the grant. Closing that window is revocation, in module 6.

2. The leeway is subtracted from exp instead of added

In ProfileVerifier.verify, change the expiry test to now >= claims["exp"] - self.leeway.

Which check changes?

Every option, and why

  • The edit moves the cutoff by 120 seconds, not 60, and check 17 sits inside that difference by design.

Reference

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardThe caller must be able to specify a supported set of algorithms, and no others may be used. RFC 8725 section 3.1, which also requires that the alg header specifies the same algorithm actually used.
  • StandardApplications must only allow cryptographically current algorithms that meet their security requirements. RFC 8725 section 3.2.
  • StandardImplementations must not accept Unsecured JWSs, the alg value none, by default, and applications must not signal acceptance of them at a global level. RFC 7518 section 3.6.
  • StandardWhen a JWT contains iss, the application must validate that the keys used belong to that issuer, and must reject the JWT if they do not. RFC 8725 section 3.8.
  • StandardWhere one issuer can issue JWTs for more than one relying party, the audience value must be validated, and the JWT rejected if the audience is absent or not associated with the recipient. RFC 8725 section 3.9. RFC 7519 section 4.1.3 says that when aud is present, the JWT must be rejected if the principal is not identified by a value in it.
  • StandardWhere one issuer can issue more than one kind of JWT, the validation rules must be mutually exclusive and reject JWTs of the wrong kind. RFC 8725 section 3.12. Explicit typing is covered in section 3.11.
  • StandardThe current time must be before exp. RFC 7519 section 4.1.4, which allows a small leeway for clock skew.
  • StandardAn OAuth JWT access token requires iss, exp, aud, sub, client_id, iat and jti, and RFC 9068 section 2.1 requires the typ header to carry the access token media type, recommending the short form at+jwt. Section 4 requires the resource server to reject a token whose typ is neither at+jwt nor application/at+jwt. Under RFC 9068 section 2.2, a client credentials token still has sub, and the RFC recommends that it identify the client rather than a user.
  • BaselineDeclare the whole profile in configuration: algorithms, type, issuer, audience, required claims, key source and leeway. Read none of it from the token.
  • BaselineVerify in this order: algorithm allowlist, token type, signature, required claims present, then claim values. Reject before reading anything you have not yet authenticated.
  • BaselineSelect the key from the issuer's published key set by kid. Never follow jku or x5u from the token header.
  • BaselineAllow 60 seconds of clock leeway in both directions, and document it.
  • BaselineReturn 401 with no indication of which check failed. Log the specific reason with a correlation ID.
  • OptionUse a reviewed JWT library rather than writing the parsing yourself, and configure its algorithm, audience and issuer options explicitly, because most default to checking less than this list.
  • OptionSender-constrain the token with mTLS or DPoP where theft is a material risk. Module 7.

Review checklist items

These are collected into the site checklist.

  • The verifier selects the algorithm from its own allowlist, never from the token header Test a token with alg set to none and one downgraded to HS256 and signed with the issuer's public key. Both must be rejected.
  • The audience is validated against this service's own identifier A genuine token issued for a sibling service in the same estate is rejected. A missing aud is rejected.
  • The signing key comes from the issuer's published key set, selected by kid The verifier never fetches a key named by jku or x5u in the token header. An unknown kid is rejected.
  • The token profile is declared, and every required claim is checked for presence before use Name the profile, such as RFC 9068 for OAuth access tokens. A token missing any required claim is rejected rather than defaulted.
  • Different kinds of JWT from the same issuer have mutually exclusive validation rules An ID token is rejected where an access token is expected, and the reverse. Token type or an equivalent claim is checked.
  • Issuer and time claims are validated with a documented leeway iss matches exactly, the key belongs to that issuer, and exp, nbf and iat are checked against server time.
  • Rejection responses do not say which check failed Callers get 401. The specific reason is logged internally with a correlation ID.
  • Library defaults have been read, not assumed Confirm what your JWT library validates by default, and configure algorithms, audience and issuer explicitly. Test the negative cases against your own configuration.
