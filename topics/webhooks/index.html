1. The attack

Running example: ExampleHotels posts an event to ExampleAir when a payment settles, and ExampleAir credits the account. Company names are fictional.

The endpoint is a public URL that changes your data. It has no session, no token from a login, and no user. Being on the internet authenticates nobody, so the signature is not an extra layer here: it is the entire authentication, and everything about its strength is decided by what it covers.

Which means the interesting failures are not "no signature". They are signatures that verify correctly on a request you should have refused.

2. Why it works

There is a standard for this, and it is worth knowing

Most webhook implementations follow a vendor's convention. There is also an IETF answer, and it is specific: RFC 8417 defines a Security Event Token, a JWT describing "statements of fact from the perspective of an issuer about a subject", and RFC 8935 defines delivering one over HTTP POST. If you are designing a sender, these are worth reading before inventing a header.

RFC 8935 section 2 lists what a recipient verifies, and the list is a good checklist whatever format you use: that it can parse the event, that the event "is authentic (i.e., it was issued by the issuer specified within the SET)", that the recipient "is identified as an intended audience", that the issuer "is recognized as an issuer that the SET Recipient is willing to receive SETs from", and that the recipient "is willing to accept this SET from this SET Transmitter". Note that the last two are separate questions: who wrote the event and who handed it to you are different, and both need an answer.

RFC 8417 section 2.2 requires iss, iat, jti and events, and recommends aud. The jti is the one this module leans on: the specification notes it "MAY be used by clients to track whether a particular SET has already been received", which is module 11's idempotency key arriving under a different name.

What the signature covers is the whole question

A signature over the request body proves the body came from a key holder. It does not say when, so a body captured once is valid forever. Adding a timestamp to the request does nothing on its own, because the attacker sends the timestamp too. The timestamp has to be inside the signed data.

Once it is, the attacker has no move, and it is worth seeing both halves of that. Replay the original timestamp and the event is too old. Substitute a fresh timestamp and the signature no longer verifies, because the timestamp is part of what was signed. The lab shows the first; the second falls out of the same change.

Then the window has to actually be compared against the clock, which is a separate line of code from covering the timestamp, and skipping it leaves you exactly where you started.

Duplicates are normal

This is the part that gets designed wrong most often, because the instinct is to treat a repeated event as an attack. Delivery is at least once. A sender that does not receive your acknowledgement will send again, and it is right to. RFC 8935 section 2 is explicit about how to respond: when an event has already been received, "the SET Recipient MUST respond as it would if the SET had not been previously received".

That requirement does two things. It keeps honest senders from retrying forever, and it stops the response becoming an oracle: a receiver that answers differently for events it has seen has told a prober which event identifiers are real.

So record the identifier, apply the event once, and answer the same way both times. And record it before doing the work, not after, for the reason module 11 gave: two copies arriving close together both find nothing recorded, and both apply.

3. The control

  1. Apply size limits and a timeout first, then parse under module 13's rules. This is an unauthenticated endpoint until the signature verifies, so the parsing happens before you know who is calling.
  2. Verify a signature over the body and the timestamp together. One value, both inputs. A signature over the body alone is valid forever.
  3. Compare that timestamp against your clock and refuse anything outside a stated window.
  4. Compare in constant time, with a library function built for it.
  5. Claim the event identifier before doing the work, in a store every instance shares.
  6. Answer identically whether or not you have seen the event. RFC 8935 requires it, and it also keeps the endpoint from being a lookup service for event identifiers.
  7. Acknowledge fast and process asynchronously. A sender waiting on your business logic will time out and retry, which produces duplicates you then have to handle anyway.
  8. Do not trust order. Make each handler tolerate arriving first, and reconcile against the sender's state rather than assuming a sequence.
  9. Treat the event as data. Any URL inside it is a caller-supplied URL, which is module 14.

5. What it proves, and what it doesn't

Proves: that a key holder produced this exact body recently, and that you have applied it once.

Doesn't prove: that it arrived in order, that it is the only event in flight, or that the sender is who the body says they are rather than whoever holds the key. It also says nothing about the contents: a correctly signed event carrying a URL you fetch is module 14's problem, arriving with a valid signature.

A duplicate is usually your sender doing the right thing. The instinct to treat a repeated event as hostile produces receivers that answer differently the second time, which breaks honest retries and tells a prober which identifiers exist. Record the identifier, apply once, answer the same way, and the honest case and the hostile case become the same code path.

6. Prove it

For each webhook endpoint:

  • An unsigned post is refused.
  • A post signed with another sender's secret is refused.
  • A valid body with one byte changed is refused.
  • A captured event replayed outside the window is refused, and the test shows which check refused it.
  • A captured event replayed with a fresh timestamp is refused, which proves the timestamp is covered.
  • The same event delivered twice is applied once, with identical responses.
  • Two copies delivered concurrently are applied once, tested against two instances.
  • A large or deeply nested body is refused before parsing completes.
  • Events arriving out of order leave correct state, or the design says why they cannot.
  • All of the above are tests in the build.

Check 9 is the one worth sitting with. The signature covers the body and nothing else, so the attacker replays a year-old event and supplies a fresh timestamp of their own, and the freshness check has nothing to object to. The timestamp was present in the request the whole time and it was never evidence of anything, because the attacker wrote it.

Check 10 is the fix, and it closes both moves at once. Keep the original timestamp and the event is too old. Substitute a fresh one and the signature stops verifying, because the timestamp is part of what was signed. Check 11 is the reminder that covering it and comparing it are two separate lines of code.

Checks 15 to 17 are two copies of one event interleaved explicitly: both verify before either finishes. With the identifier claimed after the work, both apply. With it claimed first, the second copy is refused and the event happens once.

Checks 18 to 20 are the case that is not an attack at all. A sender that did not get your acknowledgement retries, which is correct behaviour, and your receiver answers identically and applies nothing. Check 19 is the requirement RFC 8935 states, tested.

8. Check your understanding

Your webhook signature covers the request body. What can an attacker who captured one event do?

Replay it, indefinitely. The signature is valid for as long as the secret is, and the body does not change. Adding a timestamp to the request does not help on its own, because the attacker supplies that too. The timestamp has to be inside the signed value, and then compared against your clock.

Why must a receiver answer the same way for an event it has already applied?

RFC 8935 requires it, and for two good reasons. An honest sender that did not get your acknowledgement will keep retrying until it does, and a receiver that answers differently the second time has told anybody who asks which event identifiers exist.

Your endpoint URL is a long random string. How much authentication is that?

None. A URL travels in logs, proxies, browser history, support tickets and configuration files, and it is sent on every delivery. Treat it as public and let the signature do the authenticating.

A refund event arrives before the payment it refunds. Whose bug is that?

Nobody's, in most systems. Delivery is at least once and unordered, so a receiver that assumes a sequence has assumed something the protocol never offered. Make each handler tolerate arriving first, or reconcile against the sender's current state where order genuinely matters.

  • StandardA Security Event Token is a JWT describing "statements of fact from the perspective of an issuer about a subject", requiring iss, iat, jti and events, with aud RECOMMENDED. RFC 8417 sections 1.2 and 2.2.
  • StandardThe jti "MAY be used by clients to track whether a particular SET has already been received". RFC 8417 section 2.2.
  • StandardVerify that you can parse the event, that it "is authentic (i.e., it was issued by the issuer specified within the SET)", that you are "identified as an intended audience", that the issuer is one you are "willing to receive SETs from", and that you are "willing to accept this SET from this SET Transmitter".   • StandardSecurity events carrying personal data or passing through third parties "MUST be encrypted using JWE or secured for confidentiality by other means", and integrity requires signing unless ensured by other means. RFC 8417 section 5.1.
  • StandardWhere the sender signs HTTP requests rather than the payload, use RFC 9421 and cover a body digest, as in module 3.

Review checklist items

These are collected into the site checklist.

  • The signature covers the timestamp as well as the body Test a replay with the original timestamp and a replay with a fresh one. Both must be refused, for different reasons.
  • The covered timestamp is compared against a clock Covering it and checking it are two separate lines. Test an event outside the window.
  • Event identifiers are claimed before processing, in a shared store Test two concurrent copies against two instances, not two sequential requests.
  • A duplicate gets the same response as the original RFC 8935 requires it. A different response breaks honest retries and reveals which identifiers exist.
  • Size limits and parsing limits apply before the signature check The endpoint is unauthenticated until the signature verifies, so the parser meets attacker input first.
  • One secret per sender, rotatable with an overlap A shared secret lets any sender forge as another.
  • Handlers tolerate out-of-order delivery Or the design states why order is guaranteed. Delivery is at least once and unordered.
  • The endpoint URL is not treated as a secret And the event contents are treated as untrusted input, including any URL inside them.
