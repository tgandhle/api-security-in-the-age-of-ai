SAML assertions and where they meet APIs

Last reviewed 2026-10-05 · Jump to reference

Objective. After this module you can read a SAML assertion and say what each part is for, list what a service provider has to check before it believes one, explain XML signature wrapping and the other ways assertion validation fails, and say what must happen before anything that came from an assertion reaches an API.

Before you start. You should have read module 35, OpenID Connect and ID tokens. SAML solves the same problem with older tools, and this module leans on that one for every comparison. Module 28, Browser sessions, cookies and CSRF, and module 4, OAuth basics, are where a SAML sign-in ends up. This is not a guide to deploying SAML. It teaches enough to review the edge where a SAML sign-in turns into API calls.

1. The attack

Running example: ExampleAir's staff sign in to the staff portal with their company account, and the portal then calls ExampleAir's rosters API for them. Company names are fictional.

SAML is the Security Assertion Markup Language. Version 2.0 is an OASIS standard from March 2005, and its main use is single sign-on in a browser: a person signs in once, at one place, and several applications accept the result. That place is the identity provider (IdP). An application that relies on it is a service provider (SP). The identity provider tells the service provider who signed in by sending an assertion. SAML Core section 2 defines it: "An assertion is a package of information that supplies zero or more statements made by a SAML authority". It is an XML document, and it is protected by an XML signature.

Most engineers who protect APIs meet SAML at exactly one place. An employee signs in to an application with SAML, and the application then calls APIs with OAuth access tokens. A worked example of the attack this module is named for. Mallory is cabin crew. She has an account of her own and signs in to the portal as herself. The identity provider's response passes through her browser, so she can stop it and edit it. She leaves the signed assertion about her exactly as it is, and moves it into a corner of the document. Where it stood she puts a copy that names Alice, a roster administrator. The portal checks the signature. It is valid, because the identity provider did sign that assertion and nobody changed it. The portal then reads the user from "the assertion", finds the first one in the document, and starts a session for Alice. Nothing was forged and no key was stolen.

2. Why it works

A signed assertion looks like proof. It is a statement with an address, a time limit and conditions, and each of those is a field somebody has to read. Seven broken assumptions:

  • "The signature is valid, so the document is genuine." An XML signature does not cover a document. It covers the element it references. SAML Core section 5.4.2 fixes how: "Signatures MUST contain a single <ds:Reference> containing a same-document reference to the ID attribute value of the root element of the assertion or protocol message being signed". The code that verifies finds that element by its ID. The code that signs the user in finds "the assertion" in its own way, often by name. If the two can be made to find different elements, a valid signature sits next to content nobody signed. That is XML signature wrapping. The W3C note on XML Signature best practices describes it with an approval document: the application "will be fooled into thinking that the approval element is properly signed, it just checks the name of what the element that the Reference points to. It should check both the name and the position of the element."
  • "There is a signature, so the assertion is signed." Core makes signing optional in general: "All SAML assertions MAY be signed using XML Signature" (section 5.1). The browser profile is what requires it. A service provider that verifies a signature when it finds one, and carries on when it does not, accepts a document with no signature at all.
  • "It verified, so our identity provider signed it." A signature verifies against a key. An XML signature can carry a key or a certificate with it, in an element called <ds:KeyInfo>. Core section 5.4.5 says SAML "does not require the use of <ds:KeyInfo>, nor does it impose any restrictions on its use". A verifier that takes the key from there is asking the message whether the message is genuine. The W3C note: "Just because an XML Signature validates mathematically with a public key in the ds:KeyInfo does not mean that the signature should be trusted."
  • "Our identity provider issued it, so it is for us." One identity provider serves many applications. It signs an assertion for the lunch-ordering site with the same key as one for the staff portal. What tells them apart is inside: the audience and the Recipient. Core section 2.5.1.4 says what an assertion means to anyone outside its audience: "the SAML asserting party explicitly makes no representation as to accuracy or trustworthiness to such a party".
  • "It arrived in this browser, so this user asked for it." A response reaches the service provider as a form that a browser posts. Any page can make a browser post a form. The profile also lets an identity provider send a response nobody requested. The approved errata added a warning to that section in 2012: "the use of unsolicited responses can lead to Cross-Site Request Forgery (CSRF) vulnerabilities due to the inability to ensure that a request from the client originated the SAML profile transaction". CSRF itself is in module 28.
  • "It is signed, so it is still true." A bearer assertion works for whoever holds it, for as long as it is accepted. The non-normative SAML security considerations document notes that the browser keeps a copy: the assertion a browser uploads "is available as part of the web browser state". A copy used a second time is a replay. A copy used hours later is the same thing with a longer wait.
  • "The API can trust what the identity provider signed." The assertion is addressed to the portal. An API that accepts it has the same problem as an API that accepts an ID token in module 35: it is acting on a statement that was made to someone else, about a sign-in, with no scope and no audience that names the API.

One more thing sits under all of these. The first thing a service provider does with a response is hand text from the internet to an XML parser. That parser is attack surface before any signature is looked at. Section 3 comes back to it.

A note on dates. The SAML V2.0 documents are from March 2005. The OWASP SAML Security Cheat Sheet dates the published attacks on SAML implementations later: "Vulnerabilities in SAML implementations due to XML Signature Wrapping attacks were described in 2012". The 2005 text does not describe wrapping. The approved errata of May 2012 come closest. They say verifiers should reject a signature that contains one particular element, because it "can be used in service of an attacker by carrying unsigned data". Section 3 names it.

3. The control

The sign-in, from request to session

SAML Profiles section 4.1 defines the Web Browser SSO profile. A profile is a set of rules for using SAML messages for one purpose. A binding is a way of carrying a SAML message over another protocol. This profile uses three bindings, and this module covers two: HTTP Redirect and HTTP POST.

  1. The user asks the service provider for a page and has no session there.
  2. The service provider creates an <AuthnRequest> with a fresh ID and sends the browser to the identity provider. The profile leaves it to the service provider how it connects the answer to this request. The lab keeps the ID in the browser session. With the Redirect binding the message is compressed, base64 encoded and put in the URL as a parameter named SAMLRequest (Bindings section 3.4.4.1).
  3. The identity provider identifies the user "by some means outside the scope of this profile". Module 27, Attacks on authentication endpoints, is about that step.
  4. The identity provider builds a <Response> that contains an assertion, and returns an HTML form that the browser posts to the service provider. This is the POST binding: the message is base64 encoded in a form field named SAMLResponse (Bindings section 3.5.4). Profiles section 4.1.2 rules the other binding out for this step: "The HTTP Redirect binding MUST NOT be used, as the response will typically exceed the URL length permitted by most user agents."
  5. The URL that receives the form is the service provider's assertion consumer service. It validates the response (next subsection).
  6. The service provider "can establish its own security context for the principal": its own session. From here on module 28 applies.

Both messages travel through the browser, which module 35 calls the front channel. The user can read them and change them. The third binding, HTTP Artifact, sends a reference through the browser and fetches the message directly. This module does not cover it.

SP-initiated and IdP-initiated. The steps above start at the service provider. The profile also allows a start at step 4: "an identity provider can initiate this profile at step 5 and issue a <Response> message to a service provider without the preceding steps" (the profile's own step numbers). Section 4.1.5 calls that an unsolicited response: "An identity provider MAY initiate this profile by delivering an unsolicited <Response> message to a service provider." It has no request, so it has no InResponseTo.

What the assertion in step 4 says, for Alice and the staff portal:

What the profile requires of a service provider

Profiles section 4.1.4.3 opens: "Regardless of the SAML binding used, the service provider MUST do the following". The list keeps each item at the strength the profile gives it. The approved errata of 2012 reworded parts of this section, mostly to deal with more than one assertion in a response (E26). Item 8 quotes the reworded text. The errata change nothing that the other items say.

  1. Signatures. Required: "Verify any signatures present on the assertion(s) or the response". Whether one must be present is a separate rule, in item 8.
  2. Recipient. Required: verify that the Recipient in the bearer <SubjectConfirmationData> matches the assertion consumer service URL the response was delivered to.
  3. Delivery window. Required: verify that the NotOnOrAfter in the bearer <SubjectConfirmationData> has not passed, "subject to allowable clock skew between the providers".
  4. InResponseTo. Required: verify that it equals the ID of the service provider's original <AuthnRequest>, unless the response is unsolicited, "in which case the attribute MUST NOT be present".
  5. Everything else in the assertion. Required: "Verify that any assertions relied upon are valid in other respects". That brings in SAML Core. Section 2.5.1.1: "An assertion that is determined to be Invalid or Indeterminate MUST be rejected by a relying party". Section 2.5.1.4: "The audience restriction condition evaluates to Valid if and only if the SAML relying party is a member of one or more of the audiences specified." The validity period is in the same <Conditions> element.
  6. Client address. Allowed, not required: if the confirmation data has an Address, the service provider may check the browser's address against it.
  7. What to do with a failure. Recommended, not required: "Any assertion which is not valid, or whose subject confirmation requirements cannot be met SHOULD be discarded and SHOULD NOT be used to establish a security context for the principal." Baseline for this course: treat it as a requirement. Core is firmer about a bad signature: "If it is invalid, then the relying party MUST NOT rely on the contents of the assertion" (section 2.3.3).
  8. A signature must be there, with the POST binding. The 2005 text of section 4.1.4.5 required the assertions to be signed. The errata reworded it: "each assertion MUST be protected by a digital signature. This can be accomplished by signing each individual <Assertion> element or by signing the <Response> element." Core section 5.3 calls the second case an inherited signature.
  9. One-time use, with the POST binding. Required by section 4.1.4.5: "The service provider MUST ensure that bearer assertions are not replayed, by maintaining the set of used ID values for the length of time for which the assertion would be considered valid based on the NotOnOrAfter attribute in the <SubjectConfirmationData>."
  10. Session end. Recommended: if the authentication statement has a SessionNotOnOrAfter, discard the session when that time is reached.

Two more requirements sit outside that list. Bindings section 3.5.5.2 covers a response that is itself signed: its Destination attribute must hold the URL it was sent to, and "The recipient MUST then verify that the value matches the location at which the message has been received." The identity provider has duties too. It must put a bearer confirmation with a Recipient and a NotOnOrAfter into the assertion, and an <AudienceRestriction> naming the service provider into each bearer assertion (section 4.1.4.2), and it "MUST ensure that any <AssertionConsumerServiceURL> or <AssertionConsumerServiceIndex> elements in the request are verified as belonging to the service provider to whom the response will be sent" (section 4.1.4.1). The lab's check 1 is the identity provider refusing a request that names somebody else's endpoint.

The order the lab's service provider uses

The lab's correct build applies the list in this order. Where a step says signature, the lab means its stand-in, an HMAC, and not XML Signature. Section 7 says exactly what it is. Each step is a few lines of parse_document, ServiceProvider.consume, examine or covered, and each refusal has a check of its own that fails when that refusal is removed.

  1. Refuse a document that contains a document type declaration, before parsing it. Baseline, explained below.
  2. Expect a <Response> with exactly one <Assertion> as its child. This is a simplification of the lab. The profile allows several, and the errata say that each "MUST be evaluated independently".
  3. Take the <Issuer> and look up the key configured for that identity provider. An issuer with no configured key is refused.
  4. Decide whether this assertion element is covered by a signature that verifies with that key: its own, or one on the response that contains it. If neither, refuse.
  5. Check NotBefore and NotOnOrAfter on <Conditions>, then the NotOnOrAfter of the bearer confirmation, each with the skew allowance.
  6. Check that the audience names this service provider.
  7. Check that Recipient is the URL the response arrived at.
  8. Check InResponseTo against the request this browser session is waiting for. Refuse an unsolicited response unless this service provider is configured to take them.
  9. Refuse an assertion ID that was used before, and remember this one.
  10. Create the service provider's own session. Keep the issuer, the NameID and the attributes. Do not keep the assertion.

Every value in steps 5 to 9 is read from the element that step 4 verified. The attributes of the <Response> element are a trap here. When only the assertion is signed, the response's own InResponseTo and Destination are outside the signature and Mallory can set them to anything. The profile's checks are on the Recipient and the InResponseTo inside the assertion, and the lab reads them only there (check 59).

Signature wrapping, and how to close it

Step 4 is where wrapping is stopped or let through. The naive build does the obvious thing: it finds a signature, resolves the reference by ID, verifies that element, and then asks the document for "the assertion". The correct build never asks twice. It decides which element it is going to read, and then requires the signature's reference to resolve to that same element. If the reference points anywhere else, the signature is about something else.

What the sources recommend, at the strength each has. None of the three sets requirements.

  • The W3C note, Best Practice 14: "When checking a reference URI, don't just check the name of the element." It goes on: "verifiers should check both the name and position of an element as part of signature verification". Best Practice 15: "Unless impractical, sign all parts of the document."
  • The OWASP cheat sheet: "Never use getElementsByTagName to select security related elements in an XML document without prior validation." It recommends validating the document against a schema before any security use, with "local, trusted copies of schemas", and tells the service provider to check "that the exact assertion used for authentication is protected by that validated signature".
  • The approved errata added a section on <ds:Object>, an element of XML Signature that can hold any content. It "is not defined for use with SAML signatures, and SHOULD NOT be present", and verifiers should reject a signature that contains one.

Core section 5.4 narrows XML Signature for SAML in ways that help. Signatures must be enveloped, which means the signature sits inside the element it signs. Section 5.4.4 says they should use no transforms beyond two named ones, and a verifier may reject any other. A verifier that does not reject them "MUST ensure that no content of the SAML message is excluded from the signature". A transform is a processing step applied to the element before it is hashed. The fewer a verifier accepts, the fewer ways there are to sign something other than what is read.

Baseline: do not write this yourself. Use a maintained SAML library, turn on every strictness option it has, and run the negative tests in section 6 against it. The lab's verifier is short because it leaves almost all of XML Signature out.

Which key

The verification key comes from the service provider's configuration for that identity provider, never from the message. The cheat sheet's wording: "Obtain the key directly from the identity provider, store it in a local file and ignore any KeyInfo elements in the document." The W3C note's Best Practice 2 is the general form: "Establish trust in the verification/validation key." The SAML security considerations document gives the reason: verifying a signature shows that the document "was actually signed by a given key", and "this does not confirm that the key used is actually the key of a specific individual appropriate for the time and purpose".

The lab shows two versions. In check 34 Mallory signs in the real identity provider's name with her own key and ships the key in the message. In check 36 she invents an identity provider. The naive build accepts both. The correct build refuses the first because the configured key does not verify it, and the second because nobody configured that issuer.

The XML parser

An XML document can begin with a document type declaration, a DOCTYPE. Inside it a document can define entities: names that the parser replaces with other text. An entity can be defined in terms of other entities, so a small document can expand into a very large one. An entity can also name a file or a URL for the parser to fetch. Both can happen while parsing, before any check the application wrote.

The sources this module read give no single clear rule for this, so the page reports what they do say and then states the course's own. The W3C note warns signers: "Do not transmit unparsed external entity references in signed material." It also notes that with remote document type definitions, entity expansion can give "another opportunity for a malicious party to supply different content between signature validation and an application's subsequent re-processing of the message". The cheat sheet says only, under input validation: "Just because SAML is a security protocol does not mean that input validation goes away." The 2005 SAML documents this module read do not mention the subject.

Baseline, as this project's own caution: a service provider has no use for a document type declaration in a SAML message, so refuse any message that has one, and configure the XML parser to resolve nothing external. The lab does the first on the raw text, before the parser is called, and counts parser calls to show it (check 38). It makes no claim about what any particular parser does by default. Find that out for the one you use. The general point, that a parser's cost and behaviour arrive before the application's checks, is module 13, Request and response contracts.

Time, and how much skew

Two periods are checked. <Conditions> says when the assertion is valid. The bearer confirmation's NotOnOrAfter says how long it may take to arrive. The security considerations document says validity periods should be as short as delivery allows: "This is typically on the order of a few minutes."

Clocks differ, so a relying party allows a margin, called skew. The errata added the guidance: "SAML system entities SHOULD allow for reasonable clock skew between systems when interpreting time instants and enforcing security policies based on them. Tolerances of 3-5 minutes are reasonable defaults". The lab uses 180 seconds. The margin is time in which an expired assertion still works, and it lengthens how long used IDs must be remembered (check 22). Checks 28 to 33 show both edges: two hours late is refused, 400 seconds is accepted only because of the skew, and an identity provider whose clock runs ten minutes fast produces assertions that are not yet valid.

Unsolicited responses, login CSRF and RelayState

The attack. Mallory obtains a genuine response about herself. She puts it in a form on a page she controls, and Alice visits the page. Alice's browser posts the form to the portal. If the portal accepts it, Alice's browser is now signed in as Mallory, and what Alice types next goes into Mallory's account. This is login CSRF. The lab's check 23 is the naive build doing it.

What stops it. In an SP-initiated sign-in the service provider stored a request ID in the browser session, and the assertion carries that ID back in InResponseTo. Alice's session is waiting for a different request, or for none, so a response that answers Mallory's request is refused (check 25). An unsolicited response has nothing to compare, and the correct portal refuses it for that (check 24). The cheat sheet says the service provider then "has no opportunity to create a pre-login session or verify that the authentication request was intentionally initiated by the user". The errata recommend a switch: "Service providers SHOULD have a means of disabling the acceptance of unsolicited responses if circumstances warrant." Baseline: off. Where a partner needs it, the one-time cache becomes the only thing between a captured response and a second sign-in, which is why the lab's replay check uses the provider that accepts unsolicited responses (check 21).

RelayState. A service provider uses it to remember where the user was going. Bindings section 3.5.3 says the value "MUST NOT exceed 80 bytes in length" and should be integrity protected by whoever created it. Section 3.5.5.2 says there is no mechanism to protect the pairing of a RelayState with the message beside it, so an attacker can recombine values from two exchanges. The errata added: "Implementations MUST carefully sanitize the URL schemes they permit". The cheat sheet: "If the contract of the RelayState parameter is a URL, make sure the URL is validated and explicitly on an allowlist." It names the attack that this counters as open redirect: a link to the real application that ends on an attacker's page. The lab's correct build goes further and never treats it as a URL. It sends a random handle, keeps the real destination in the session, and looks the handle up (check 27). Profiles section 4.1.3.1 points the same way: the service provider "SHOULD reveal as little of the request as possible in the RelayState value". An allowlist of paths is the alternative when the value has to be a URL.

From a SAML sign-in to an API call

This is why the module is in this course.

The assertion stops at the service provider. It is addressed to the portal: the audience names the portal and the Recipient is the portal's endpoint. Profiles section 4.1.3.6 leaves any later use of the assertion "at the discretion of the service provider and other relying parties, subject to any restrictions on use contained within them", and the audience restriction is one. Baseline for this course: the portal does not forward the assertion to a resource API, and no resource API accepts one. A resource API here is a resource server: the API an access token is for. One other kind of endpoint may take an assertion, an authorization server's token endpoint under RFC 7522, described below, and it requires an assertion addressed to itself. The reason for the rule is the one module 35 gives for ID tokens. A resource API that takes an assertion is skipping its own check of what the caller may do, and it becomes one more place where every attack in section 1 has to be stopped. In the lab the naive API accepts Alice's assertion from anyone who has a copy (check 40).

The portal creates its own session. Step 10 above. The session has the portal's own identifier and timeouts, as module 28 teaches. The assertion was a receipt for one sign-in and is not kept.

APIs get access tokens. To call the rosters API for Alice, the portal needs an access token issued by an authorization server for that API. One route is an ordinary authorization code flow from module 4. The authorization server can itself rely on the same identity provider to sign Alice in. Another is to exchange an assertion for a token.

RFC 7522. The SAML 2.0 bearer assertion profile for OAuth 2.0 defines a grant in which the client posts an assertion to the token endpoint and gets an access token back, "without a direct user approval step at the authorization server". Section 3 says "the authorization server MUST validate the Assertion according to the criteria below". At their stated strength:

  • Required: the <Issuer> identifies who issued the assertion.
  • Required: an audience that identifies the authorization server. "The authorization server MUST reject any Assertion that does not contain its own identity as the intended audience."
  • Required: a <Subject>, an expiry, and a bearer <SubjectConfirmation>. Where there is confirmation data, its Recipient must be the token endpoint, and "The authorization server MUST verify that the value of the Recipient attribute matches the token endpoint URL (or an acceptable alias) to which the Assertion was delivered."
  • Required: reject the assertion once the NotOnOrAfter on <Conditions> has passed, with allowable clock skew. Also required: reject a subject confirmation once the NotOnOrAfter on its confirmation data has passed. The rest of the assertion may still be used.
  • Required: "The Assertion MUST be digitally signed or have a Message Authentication Code (MAC) applied by the issuer. The authorization server MUST reject Assertions with an invalid signature or MAC."
  • Allowed, not required: replay protection. "The authorization server MAY ensure that Bearer Assertions are not replayed", and section 6 repeats it: "The specification does not mandate replay protection for the SAML Assertion usage for either the authorization grant or for client authentication." Baseline for this course: do it. The browser profile requires it of a service provider, and the assertion is the same kind of object.

The second item settles a question reviewers get asked. An assertion that was issued only for the portal cannot be used for this exchange. Its audience is the portal and its Recipient is the portal's endpoint. The lab's check 43 is the authorization server refusing it. The exchange needs an assertion that the identity provider addressed to the authorization server. RFC 7522 says how the client gets one "is out of scope", and the lab stands in for it with a direct call. Checks 44 to 49 are that token endpoint at work. Client authentication at the token endpoint is the subject of module 36, Client authentication, PAR and high-assurance OAuth. RFC 7522 leaves it optional for this grant. The lab's token endpoint requires it.

RFC 8693. Token exchange, from module 19, Delegation and token exchange, can take a SAML assertion as its subject token. Section 3 defines a token type identifier for it, urn:ietf:params:oauth:token-type:saml2, which "Indicates that the token is a base64url-encoded SAML 2.0 [OASIS.saml-core-2.0-os] assertion". RFC 8693 does not say how to validate one. Section 2.1 requires that "the authorization server MUST perform the appropriate validation procedures for the indicated token type", and adds that the validity criteria of any particular token "are beyond the scope of this document". This project's reading: the checks in this section are those procedures, including the audience.

Attributes and groups. An attribute statement is the identity provider's statement about the user at the moment of sign-in. Core section 2.5.1.2 says the validity times "do not guarantee that the statements in the assertion will be correct or accurate throughout the validity period". The portal's copy is older still. In the lab's check 52 Alice is removed from the administrators' group at the identity provider, and the portal's session goes on saying she is in it. Use attributes to set a session up. Decide what a request may do when the request arrives, at the API, from the access token and the object: that is object-level authorization, in module 9, Object-level authorization. A group name does not say whether this roster belongs to this user's base.

5. What it proves, and what it doesn't

Proves: that the identity provider named in <Issuer> stated, at IssueInstant, to the party named in <Audience>, that the subject it calls by this NameID authenticated at AuthnInstant, and that it described the subject with these attributes. When InResponseTo matches, it also shows that the statement answers the request this browser session started.

Doesn't prove the presenter is the subject. The confirmation method is bearer. A bearer credential works for whoever holds it. The Recipient, the delivery window, InResponseTo and one-time use narrow where and when a copy works. They do not tie it to a person.

Doesn't prove any authorization at an API. An assertion has no scope and its audience is the service provider. What the portal may do at the rosters API is in an access token, and the API validates that.

Doesn't prove the user's rights on any object. Knowing that the caller is Alice, or that Alice is in a group, does not say whether one roster is hers to change. Module 9.

Doesn't prove anything after it was issued. If Alice's account is disabled a minute later, the assertion does not change and the portal's session carries on. The security considerations document says it plainly: "an assertion, once issued, is out of the control of the issuer". SAML has a Single Logout profile. This module did not cover it.

Doesn't prove how good the authentication was. The same document: "Consumers of authentication assertions should be wary of blindly trusting these assertions unless and until they know the basis on which they were made." An <AuthnContext> helps only if both sides agreed what its values mean and the service provider checks it.

Doesn't prove the identity provider is honest or uncompromised. Whoever holds its signing key can sign in as anyone, at every service provider that trusts it. The cheat sheet: "if an attacker has access to use the IdP’s signing key, they can mint SAML responses containing any assertion they wish".

What the lab proves, and what it does not. The lab's signature is a stand-in. It is an HMAC over a fixed serialisation of the one element the reference names. Real SAML uses XML Signature, with asymmetric keys and canonicalization of the XML. The lab keeps the single property that Parts B and C depend on: a signature covers exactly one referenced element. So the lab shows that the order and the placement of the checks stop these attacks. It shows nothing about canonicalization, transforms, algorithms or any real library, and nothing in it is a usable SAML implementation.

An assertion is a receipt for one sign-in, addressed to one application. Validate it once at the assertion consumer service, create your own session, and put it away. Do not forward it to a resource API, and do not accept one there. The only endpoint that may take an assertion is an authorization server's token endpoint under RFC 7522, and only an assertion addressed to it.

6. Prove it

A working service provider must refuse every one of these at its assertion consumer service, and create no session:

  • A response in which the signed assertion was moved and another assertion stands where it was, with or without a copy of the signature.
  • A response with no signature, and one in which only a part that is not read is signed.
  • A response whose signed content was changed by one character.
  • A response that verifies only with a key or certificate carried inside it, and one whose issuer is not configured.
  • An assertion whose audience is another service provider of the same identity provider.
  • An assertion whose Recipient is another endpoint, including another environment of the same application.
  • A response delivered a second time, in the same browser and in a different one.
  • A response whose InResponseTo is not the request this browser session is waiting for, and an unsolicited response where those are switched off.
  • An assertion past its NotOnOrAfter by more than the skew, and one whose NotBefore is further ahead than the skew.
  • A document with a document type declaration, with or without an entity in it.

The rest of the system has its own list:

  • A changed or foreign RelayState sends the user to the default page, not to the value.
  • The identity provider refuses a request that names an assertion consumer service it has not registered for that service provider.
  • Every API refuses a SAML assertion as a credential.
  • A token endpoint that takes assertions refuses one whose audience is not the authorization server, one whose Recipient is not the token endpoint, and one it has seen before.
  • A group removed at the identity provider stops working at the API within a stated time.

7. Lab

Download labs/saml_lab.py and run it with Python 3. It needs no packages beyond the standard library. On Windows, use py -3 wherever this page shows python3. The identity provider, two service providers, the authorization server, the API and the browser sessions are Python objects. Nothing opens a socket, and the time is a number the lab sets. Keys and tokens are random on every run. No key, token, document, message ID, assertion ID or signature value is printed.

The signature is a stand-in, and this matters. The lab does not implement XML Signature or canonicalization. A "signature" in the lab is an HMAC-SHA256 by the identity provider over a fixed serialisation of one element: the element whose ID the <Reference> names, without that element's own <Signature> child. Real SAML uses XML Signature with asymmetric keys. The lab keeps only the property the wrapping attack turns on, which Core section 5.4.2 requires of a SAML signature: it references one element by ID and covers that element. Two consequences. An HMAC key is shared, so in the lab a service provider could forge an assertion, which a holder of a public key cannot. And <KeyInfo>, which in a real message carries a certificate or public key, carries in the lab the key Mallory signed with. It stands in for a key that arrived inside the message.

The portal exists twice. The naive build verifies the element a signature references, if there is a signature, with the key in the message if there is one, and then reads the first assertion in the document. It checks nothing else: no audience, no Recipient, no InResponseTo, no time and no reuse. The correct build is section 3. The lunch site is a second correct service provider that accepts unsolicited responses.

Other simplifications. There are no XML namespaces, no base64 and no HTML form: the XML text is passed directly. Times are whole seconds, not XML date values. The service provider accepts exactly one assertion and does not check Destination, which Bindings section 3.5.5.2 requires for a signed response. It refuses an assertion whose <Conditions> has no NotOnOrAfter, which is stricter than Core section 2.5.1.2. It reads the audiences of every <AudienceRestriction> as one list, where Core section 2.5.1.4 says each restriction "MUST be evaluated independently". The lab's identity provider writes one restriction with one audience, and no check covers either point. There is no encryption, no <Status>, no logout, no metadata and no artifact binding. The identity provider takes the lab's word for who is at the browser. The assertion addressed to the authorization server comes from a direct call to the identity provider. The token endpoint takes the assertion as XML text, where RFC 7522 section 2.1 requires base64url. It accepts one audience value, the authorization server's own identifier, where RFC 7522 also allows the token endpoint URL. It requires the client to authenticate with a secret. It runs the same examine function as the service provider, so its issuer, signature and time rules are the ones that checks 9 to 15, 29 to 33, 35 and 37 exercise. Check 60 sends it a badly signed assertion, and check 61 offers it a used one again. Access tokens are random handles that the API looks up at the authorization server, which is introspection from module 6, JWKS, revocation and introspection.

The lab uses xml.etree.ElementTree from the standard library. It refuses any text that contains a document type declaration before that parser is called, so the parser is never given one.

8. Check your understanding

A service provider's log says "signature valid" for a response, and the session it created is for a user the identity provider never issued an assertion about. How can both be true?

The signature covers the element its reference names, and the service provider read the user from a different element. In a wrapped response the signed assertion is still in the document, untouched, so verification succeeds. The assertion that was read stands where the application looks. In the lab, check 8 shows one document in which the signature verifies over an assertion about Mallory while the first assertion names Alice. The fix is to read only the element the verified signature covers.

The identity provider is trusted, its signature verified with the configured key, and the assertion has not expired. Name three things the service provider still has to check.

That the audience names this service provider, that Recipient is the URL the response arrived at, and that InResponseTo is the request this browser session is waiting for. A fourth: that this assertion ID has not been used before. The first two say the statement was made to this application at this endpoint. The third says this browser asked for it. The fourth says this is the first time. A valid signature says none of them. In the lab these are checks 17, 19, 25 and 21.

A team wants its API to accept the SAML assertion the portal received, "so the API knows who the user is without another round trip". What is wrong with that, and what should they do?

The assertion is addressed to the portal: its audience and Recipient name the portal. An API that accepts it either ignores the audience, and then accepts every assertion the identity provider issues to any application, or checks it and refuses. It also has to defend against wrapping, replay and the rest on its own. The portal should obtain an access token for the API from an authorization server and send that. Where the token is obtained by exchanging an assertion, RFC 7522 requires the assertion's audience to be the authorization server, so the portal's own sign-in assertion cannot be reused. In the lab, check 40 is the naive API, check 43 is the authorization server refusing the portal's assertion, and checks 44 and 45 are the correct path.

Why does the lab's replay check use a service provider that accepts unsolicited responses?

Because there the cache of used IDs is the only control. In an SP-initiated sign-in the service provider forgets the pending request when a response for it arrives, so a second delivery of the same response fails the InResponseTo check before the cache is consulted. Check 58 shows the forgetting on its own, with a second response to the same request. An unsolicited response has no InResponseTo. A copy of it works again, anywhere, until its delivery window ends, unless the service provider remembers the ID. The profile requires that memory whenever the POST binding is used.

A partner wants a link on the identity provider's home page that opens the portal. In main, change portal = ServiceProvider(PORTAL, PORTAL_ACS, trusted, clock) to portal = ServiceProvider(PORTAL, PORTAL_ACS, trusted, clock, allow_unsolicited=True).

Which checks change?

Every option, and why
  • That is the attack. The response is genuine and is about Mallory. The harm is that it was posted from Alice's browser, which is now signed in to Mallory's account.
  • Correct. Exit 1, one failure. Check 24 goes from reject: unsolicited response to accept. Every other rule still holds, and none of them can see the problem: the signature, the audience, the Recipient and the times are right, and the ID is new. Check saml-05 in the Reference layer asks whether unsolicited responses are needed at all.
  • Check 25 still prints reject: InResponseTo is not this browser's request. That response does carry an InResponseTo, so it is compared, and it is Mallory's request and not the one Alice's browser is waiting for.
  • The naive portal in check 23 was given the same response first, and the naive build keeps no record. The correct portal sees this ID for the first time.

  • StandardSAML V2.0 Profiles section 4.1.4.2, as reworded by the approved errata (E26 and E52), requires the identity provider to put a bearer subject confirmation in the assertion, with a Recipient and a NotOnOrAfter, and requires each bearer assertion to contain an audience restriction naming the service provider. Review checklist items

These are collected into the site checklist.

  • The service provider reads only the assertion that a verified signature covers The signature's reference resolves to the element being read, or to the response that contains it. A wrapped response, with the signed element moved and another in its place, is refused.
  • A signature is required, and it is verified with the key configured for the identity provider A response with no signature is refused. The key is chosen by the configured issuer and never taken from KeyInfo in the message.
  • Audience and Recipient are compared with this service provider's own name and endpoint An assertion issued for another application of the same identity provider is refused, and so is one issued for another endpoint or environment of this application.
  • A bearer assertion is accepted once Used assertion IDs are kept for as long as the assertion could still be accepted, in a store every server shares. A second delivery is refused.
  • InResponseTo is tied to a request this browser session started, and unsolicited responses are off unless needed A response for another session's request is refused. Where unsolicited responses are enabled, the design says which identity provider needs them and what stops login CSRF.
  • Validity times are enforced with a small, stated clock skew Both the conditions and the confirmation window are checked, NotBefore included. The skew is minutes, not hours, and assertion lifetimes are minutes.
  • The XML parser cannot be made to process a DTD or fetch anything A message with a document type declaration is refused before parsing, and the parser resolves no external entities. The test is a real message with a DOCTYPE in front.
  • No resource API accepts a SAML assertion, and the application never forwards one to a resource API Resource APIs receive access tokens issued for them. The only endpoint that takes an assertion is an authorization server's token endpoint under RFC 7522: it requires its own identity as the audience, checks Recipient, and refuses a second use.
  • RelayState is never followed as a URL without validation It is an opaque handle looked up in the session, or it is matched against an allowlist of the application's own paths. An unknown value leads to a default page.
  • Attributes from an assertion are treated as sign-in-time input The design says how long a group change at the identity provider takes to reach the application. Authorization on each request is decided at the API, per object.
