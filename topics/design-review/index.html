Design review

Objective. After this module you can run a design review against the course checklist, separate findings from questions the design does not answer, order what you found so the first line of the report is the right one, and say what your review did not cover.

1. The brief

You have a design document for the ExampleAir assistant platform. Company names are fictional. It is an agent that answers traveller questions, holds seats, issues refunds under approval, calls a partner's seat-map agent, and retrieves policy documents from a shared index. It touches most of this course.

A review of it produces three kinds of statement, and only the first is a finding.

What the review can sayWhat it meansWhat it is worth
The design states something, and it is wrongA finding, with a severity and a check idActionable now
The design states something, and it is rightAssessed and cleanWorth recording, so nobody re-reviews it
The design does not sayAn unanswered question, not a passA conversation, and often the worst item on the list

The third row is what this module is really about. In a summary, an unanswered question and a passed check look identical, and the difference is the whole value of the review.

2. Why it works

Unanswered is not passed

The design document answers 20 of the 24 questions the harness asks. The other four are silent, and three of those four sit on Critical rules: whether services authenticate for themselves on every path, whether request limits run before the parser, and whether the credential register has been reconciled.

Checks 17 to 23 of the lab keep those apart from the findings and then count them together. Fourteen findings, four unanswered, eighteen open items. A review that reported "14 findings" would be accurate and would have hidden four conversations, one of which is module 12's question about whether a gateway is a control at all.

So the harness never evaluates a rule when a fact it reads is missing. It records the rule, the severity it would have carried, and the fact it needed, and it reports those as their own list. That is a design decision worth copying: a checklist that silently passes on absent information will reliably tell you a system is fine.

Order the findings so the first line is the right one

Fourteen findings, twelve of them Critical, is not a report. Checks 11 and 14 order them worst first and name the Critical ids, and checks 15 and 16 are the sentence a reviewer actually leads with: eight of the twelve Criticals come from Part 4, and four from Parts 1 to 3.

That split is the finding above the findings. The Parts 1 to 3 issues are a missing audience check, no idempotency key, rate limit counters that are not shared between instances, and more versions answering than documented, which are ordinary and fixable. The Part 4 issues are token passthrough, an MCP server that does not validate its audience, agent cards verified against a fetched key, a model holding a tool credential, approvals bound to an identifier, a credential in the system prompt, a prompt built from whole records, and a retrieval filter applied after ranking.

Those eight are not eight separate oversights. They are one: the agent layer was built without anybody applying the rules the rest of the system already follows. That is a sentence a design review can earn its keep with, and you can only write it once the findings are grouped by where they came from.

Separate what a setting fixes from what a design decision fixes

Part D applies the six changes a team would realistically do in the first week: validate the token audience, validate it at the MCP server too, take the credential out of the system prompt, move the tool credential from the model to the application, build the prompt from a field allowlist, and move the retrieval filter before the ranking. Each is a setting or a few lines.

Findings drop from 14 to 8, and Criticals from 12 to 6. Check 27 names the six that remain, and check 30 counts them: agent card trust, approval binding, token passthrough, idempotency, a shared rate limit store, and version retirement. Every one of those needs a decision rather than a change, which is why they are the ones still open a quarter later.

Check 28 is the one to put in the report. The four unanswered questions are unchanged by all six fixes, because nobody answered them.

State what the review did not cover

Part E is the paragraph that belongs at the top of every review and is almost always missing. This review reached a conclusion about 16 modules, found issues in 12, assessed 4 as clean, and was blocked on 3 by missing information.

Naming the clean ones matters as much as naming the findings, because otherwise the next reviewer repeats the work. Naming the blocked ones matters more, because that list is what the review is waiting on, and it is the part a reader will assume was fine.

Check 37 assembles the first line: eighteen open items, four of them unanswerable from the document provided. A reader who sees only that sentence still knows what to do next.

3. The control

  1. Write the questions down first, as facts about the system, before you read the design. The checklist is the question list.
  2. Record three outcomes per question, not two: wrong, right, and not stated.
  3. Never evaluate a rule on missing information. A checklist that passes when it does not know will tell you the system is fine.
  4. Give an unanswered question the severity it would have carried, so it sorts alongside the findings rather than beneath them.
  5. Order findings worst first, and group them by where they came from, because the grouping is often a bigger finding than any single item.
  6. Separate what a setting fixes from what a decision fixes, and say which of the two each remaining item needs.
  7. State the coverage: what you concluded about, what was clean, and what you could not assess.
  8. Keep the harness, so the next review of the same system is a diff rather than a repeat.

4. Defaults and when to change them

Severity of an unanswered questionThe severity the rule carriesIt is what you would have raised. Downgrading it because you do not know is backwards.
OrderingWorst first, then by check idStable ordering makes two reviews of the same system comparable.

Coverage statementAt the top of the reportAlways. A reader assumes anything unmentioned was fine.

5. What it proves, and what it doesn't

Proves: that each question in the checklist was asked, that each answer was recorded as wrong, right or absent, and that the report distinguishes them.

Doesn't prove: that the system behaves as its design says. Every answer here comes from a document, and a design review is an assessment of a document. The checklist's "prove it" sections exist because the next step is evidence from the running system, and a design that passes this review can still fail every one of them.

A checklist that passes on absent information is worse than no checklist. Run the lab's first fault injection to see it: treat unknowns as passes and the harness reports the same fourteen findings while four questions disappear, three of them Critical. The report looks identical and is now wrong by omission.

6. Prove it

  • The question list, written before the design was read.
  • For each question, the answer taken from the design, with where in the document it came from.
  • The findings, with severity and check id, ordered.
  • The unanswered questions, with the severity each would have carried.
  • The modules assessed and clean, named.
  • The modules that could not be assessed, named, with what is needed to assess them.
  • For each finding, whether it is a setting or a decision.
  • The rule table, in version control alongside the system it reviews.
  • A date, and the document version the review was run against.

Checks 1 to 5 are the shape of every review. Twenty-four questions, twenty answers, four silences, and the silences block four rules from running at all. Nothing else in the harness touches those four.

Checks 15 and 16 are the sentence worth writing. Eight of the twelve Criticals come from Part 4 and four from the rest of the course, which says the agent layer was built without anybody applying the rules the service already follows. That is one finding about a process, and it is more useful than eight findings about settings.

Checks 17 to 23 are the module's argument. Fourteen findings is an accurate number and a misleading report. Eighteen open items, four of them unanswerable from the document, is the honest one, and the difference is three Critical rules that nobody can evaluate because the design does not say.

8. Check your understanding

Your checklist has 23 rules and the design answers 19 of them. What do you report?

Three numbers, not one. The findings among the 19, the modules the 19 showed clean, and the four you could not evaluate, each carrying the severity its rule would have had. Reporting only findings makes an unanswered question indistinguishable from a passed one, and the four are often the most important items on the list.

Twelve Critical findings, eight of them in the agent layer. What is the headline?

That the agent layer was built without applying the rules the rest of the system already follows. Eight findings in one area is usually one finding about that area, and a review that lists them as eight separate items hands the team eight tickets instead of one conversation.

Why give an unanswered question the severity its rule carries?

Because that is the severity you would have raised if the answer had been wrong, and you do not know that it is not. Downgrading it because you lack information inverts the logic: the less you know, the lower it sorts, and the less likely anyone is to go and find out.

Six configuration changes clear six Critical findings. Is the system half fixed?

No, and the split is the useful part. The six remaining Criticals each need a design decision rather than an edit, which is why they will still be open next quarter. Separating settings from decisions on day one is what lets a team plan rather than react.

Exercises

Change one thing and predict the output

Each exercise edits one place in labs/design_review_lab.py and asks what the run prints. The answers are the real output of each variant. One variant changes nothing, and its answer carries the measurement from a design the lab does not review.

1. The check for a missing answer is deleted

In review, delete the three lines that start at if gap is not None:. They test whether a fact the rule reads is missing, append the rule to unanswered and continue. Every rule's test now runs on whatever the design holds, including nothing.

What does check 6, findings raised, print?

Every option, and why
  • That is a different edit: keep the test and the continue, and delete only the append. Measured, that one fails ten checks and check 6 stays at 14. Here the test is gone too, so each rule is evaluated.
  • Correct. Exit 1, 21 checks fail. Check 6 goes from 14 to 18, check 7 from 12 to 15, check 9 from 0 to 1, and check 17 from 4 to 0. The four blocked rules are all written as not d[...], and a missing value is falsy, so each one fires. Check 23 still prints 18, and check 37 goes from 18 open items, 4 unanswerable to 18 open items, 0 unanswerable. The total is the same and the report is wrong: four questions for the team became four claims the document does not support, three of them Critical. Check rev-01 in the Reference layer says missing information blocks a rule. Without the block, the outcome depends on how each test happens to be written.
  • No test raises. not None is True in Python, so the four tests return a result and the run finishes with exit code 1 and a list of 21 mismatches.
  • The deleted lines are the only place unanswered is filled. Check 17 prints 0 and check 18 prints [].

4. A module with one silent rule counts as blocked

In coverage, stop removing the assessed modules from the blocked ones, so the last line reads:

return sorted(assessed), sorted(blocked)
Which checks change?

Every option, and why

Reference

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • BaselineThe review's rules are checklist items from modules 1 to 25. Where an item rests on a specification, the citation is on the page that introduced it; many items are this project's defaults and carry none. This module adds no new normative claim; it is a method for applying them.
  • BaselineRecord three outcomes per question: answered and wrong, answered and right, and not stated.
  • BaselineNever evaluate a rule whose input is missing. Block it and report it.
  • BaselineGive an unanswered question the severity its rule carries, so it sorts with the findings.
  • BaselineOrder findings worst first and then by check id, so two reviews of the same system are comparable.
  • BaselineGroup findings by their origin, and report the grouping when it is itself a finding.
  • BaselineMark each open item as needing a setting or needing a decision.
  • BaselinePut the coverage statement at the top: concluded, clean, blocked.
  • BaselineKeep the rule table in version control next to the system, so the next review is a diff.
  • OptionCarry a fourth outcome, "not applicable", where a rule genuinely does not apply, and require a reason for each one.
  • OptionRun the harness in the build against a machine-readable description of the system, so a design change that removes an answer fails the build.
  • OptionRecord the document version and date on the review, since a design review is an assessment of a document rather than of a system.

Review checklist items

These are collected into the site checklist.

  • Missing information blocks a rule rather than passing it A checklist that passes when it does not know will reliably report that the system is fine.
  • Unanswered questions are reported with the severity their rule carries Not downgraded for uncertainty, which would make the review quieter the less it knows.
  • The report states coverage: concluded, clean, blocked A reader assumes anything unmentioned was assessed and fine.
  • Findings are ordered worst first and grouped by origin Several findings in one area are usually one finding about that area.
  • Each open item is marked as a setting or a decision The decisions are the ones still open next quarter. Name them on day one.
  • The rule table and the review date are version controlled So the next review of the same system is a diff rather than a repeat.
