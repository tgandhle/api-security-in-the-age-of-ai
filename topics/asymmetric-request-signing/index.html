Asymmetric request signing

Last reviewed 2026-09-30 · Jump to reference

Objective. After this module you can say exactly what an asymmetric request signature adds over an HMAC and what it does not, build an RFC 9421 signature base, list the checks a verifier must make and the order they go in, and recognise the coverage mistakes that leave a signed request no safer than an unsigned one.

Before you start. Module 2 ended with one row that never turned green: take the key from the receiver and sign new requests as the caller. You should know what an HMAC proves, how a canonical string is built, and why a nonce is recorded only after the signature verifies.

1. The attack

Running example: ExampleAir signs requests to ExampleHotels' transfer API. Company names are fictional.

In module 2 both companies held the same 32 bytes. That is what let the receiver verify, and it is also what let the receiver sign. Nothing in an HMAC distinguishes the two. So a signed request proves the key was used, and both parties could have used it.

That is fine until one of three things happens. ExampleHotels is breached and the attacker can now issue transfers as ExampleAir. ExampleHotels itself has a reason to fabricate a request. Or a dispute arises about a transfer neither side can attribute, because either side could have produced it.

Two rows in the middle turn green, and that is the whole point of this module. The last three do not. One of them, the uncovered body, is the mistake this module spends the most time on, because it is the one that makes a correctly implemented signature worthless.

2. Why it works

An HMAC has one key and one capability. An asymmetric signature has two keys and splits the capability: the private key signs, the public key verifies, and holding the public key gives you no way to produce a signature. The receiver's key store stops being a forgery kit and becomes a directory.

Three consequences follow, and they are the reasons to pay the extra cost:

  • A breached verifier cannot forge. This is the row from module 2. It matters most when the receiver is the larger, more exposed party, which is the usual shape.
  • Many receivers cost nothing extra. With HMAC, every additional receiver is another copy of the secret and another place it can leak. With a keypair, the caller signs once and publishes one public key.
  • A third party can check. Anyone with the public key can verify a captured request without being able to have produced it. That is a useful property in an incident review or a dispute. It is not legal non-repudiation: it holds exactly as far as private key custody holds, and no further.

What changes is who can sign. What does not change is what the signature covers, and that is where real deployments fail. RFC 9421 section 7.2.1 is explicit that portions of a message outside the covered components remain "modifiable by intermediaries" without invalidating the signature. Section 7.2.8 goes further: the specification "does not define a means to directly cover HTTP message content", so the body is protected only by covering a digest header that describes it. Signing a request and not covering its body is a common and silent mistake, and the algorithm you chose has nothing to do with it.

3. The control

The signature base

RFC 9421 section 2.5 defines the thing that actually gets signed: the signature base, "an ASCII string containing the canonicalized HTTP message components covered by the signature". One line per covered component, each as a quoted lowercase name, a colon, a space, and the value. The last line is always @signature-params, which lists the covered set and the parameters. Section 2.3 defines it and requires that it never appear inside its own covered list.

This is module 2's canonical string with the guesswork removed. You no longer decide the separator, the ordering, or how a missing field is represented: the specification does, and both sides can be tested against it.

"@method": POST
"@authority": api.hotel.example
"@path": /v2/transfer
"content-type": application/json
"content-digest": sha-256=:u0zCPnrSXArDEbOkaTNMlcxECQy9moI7jortdbeoXHg=:
"@signature-params": ("@method" "@authority" "@path" "content-type" "content-digest");created=1716307200;nonce="n-001";keyid="exampleair-2026-a";alg="ed25519"

Names beginning with @ are derived components: values taken from the request line rather than a header. RFC 9421 section 2.2 defines @method, @target-uri, @authority, @path, @query, @query-param and @status. The content-digest value is an RFC 9530 field: a hash of the body, expressed as a structured field, which is the only way the body enters the signature at all.

The signed bytes travel in two fields, both dictionaries keyed by a label the signer chooses. RFC 9421 section 4.1 defines the first, section 4.2 the second:

Signature-Input: sig1=  the @signature-params value, byte for byte
Signature:       sig1=:base64 of the signature over the base:

The verifier reads Signature-Input, rebuilds the base from the message in front of it, and checks the result against Signature. If the two bases differ by one byte, the check fails, which is exactly the behaviour you want and exactly why the canonicalization rules are worth having in a specification rather than in your own documentation.

What a verifier checks, in order

  1. Resolve keyid to a key you already know. An unknown keyid is a rejection, never a prompt to go and fetch something the caller named.
  2. Check alg against your allowlist. RFC 9421 section 6.2.2 registers the identifiers; your application decides which of them you accept.
  3. Check that alg is appropriate for that key. Without this you have module 5's algorithm confusion in a new place: a message claiming hmac-sha256 against a key you hold as a public value.
  4. Check that every component your application requires is in the covered list. If content-digest is not there, stop. The signature will verify and it will mean nothing about the body.
  5. Rebuild the signature base from the message as received. A covered component that is not present is a rejection, not a blank line.
  6. Verify the signature. Nothing above this line was trustworthy; nothing below it is meaningful without it.
  7. Recompute the digest from the received body and compare. Covering content-digest ties the header to the signer. Recomputing is what ties the header to the bytes that arrived.
  8. Check created against your window, and expires if present.
  9. Check and record nonce, only now, for the same reason module 2 recorded it last: a forged request must not be able to fill your store.
  10. Hand the request to authorization. A verified signature says who signed; it says nothing about what they may do.

5. What it proves, and what it doesn't

Proves: that whoever holds the private key behind this keyid produced a signature over exactly these components, with these parameters, recently, and once.

Doesn't prove: anything about the parts of the message it did not cover. Not the body, unless a digest of the body is covered and recomputed. Not that the holder is the organisation you have in mind, only that they hold that key. Not that they may do what the request asks. And not non-repudiation in any legal sense, because that would require assurances about key custody that a protocol cannot give you.

The signature is not the hard part. Every check in the lab that fails does so for a reason you can read in one line. The two checks that succeed when they should not, numbers 10 and 12, are the realistic failure: a valid signature over a component list that leaves the body outside it, or a digest that was covered but never compared with the bytes that arrived. Both produce clean logs and passing tests.

6. Prove it

A working implementation must reject every one of these:

  • A request whose keyid you do not already hold.
  • A request whose alg is outside your allowlist, even when its signature is valid.
  • A request whose alg does not match the key that keyid names.
  • A request that does not cover a component your application requires, content-digest above all.
  • A request missing a component its own Signature-Input says is covered.
  • A request whose body does not match its covered content-digest.
  • A request signed by a key other than the one keyid names.
  • A request whose created is outside your window, in either direction.
  • A request whose expires has passed.
  • A second request carrying a nonce you have already accepted, including against a different instance.

And one it must accept: a captured, unmodified request, verified by a third party holding only the public key.

Check 3 is module 2's open row, reproduced inside RFC 9421 so that only the key differs. Check 5 closes it, and it closes for a mundane reason worth seeing in code: the object in the receiver's key store is an Ed25519PublicKey, which has a verify method and no sign method. There is nothing to call.

Checks 10 and 12 are the two accepts you should be unhappy about. In check 10 the digest header is present, describes the original body, and is not in the covered list, so swapping the body changes nothing the signature protects. In check 12 the digest is covered, so the header cannot be changed, but the verifier never compares it with the bytes that arrived. Checks 11 and 13 are the same two requests against a verifier that closes each gap.

Checks 19 and 20 are the same request, with a genuinely valid ECDSA P-256 signature, against two verifiers. One allows that algorithm and accepts. One does not and rejects. A signature being cryptographically sound is not the same as it being acceptable, and the allowlist is where you say so.

  • Set WINDOW_SECONDS to 86400 and rerun. Check 14 goes green. State what someone holding one captured request can now do for a day.
  • Change allowed_algs on server to include "hmac-sha256" and rerun. Check 18 tells you which line is now load bearing.

8. Check your understanding

Your verifier accepts a request, the signature is valid, and the body was replaced in transit. How?

Two ways. Either content-digest was not in the covered component list, so the body was never inside the signature at all, or it was covered but the verifier never recomputed the digest from the received bytes. Both produce a valid signature over a message whose body you cannot trust. Checks 10 and 12 in the lab are these two cases.

An HMAC and an Ed25519 signature both prove the key was used. What does the second one add?

That the verifier could not have produced it. With a shared secret, verifying and signing are the same capability, so a breached or motivated receiver can forge requests as the caller, and no third party can distinguish the two. With a keypair the receiver holds only a public key. That is the row that turns green.

A request arrives with keyid naming a key you have never seen. What do you do?

Reject it. The temptation is to resolve the keyid by fetching something, which hands the caller control of which key you verify against. Keys are established out of band, before the first request, and keyid only selects among the ones you already hold.

Why check the algorithm against the key as well as against an allowlist?

Because a key and an algorithm can each be acceptable and still be wrong together. A message claiming hmac-sha256 for a keyid you hold as a public value is asking you to treat a public value as a shared secret. RFC 9421 section 1.4 requires an application to define "a means of determining that the signature algorithm used is appropriate for the key material" for exactly this reason.

Quick check

What does asymmetric signing change?

You replace an HMAC request signature with an Ed25519 signature and change nothing else. Which attack stops working?

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardSign the signature base of RFC 9421 section 2.5, "an ASCII string containing the canonicalized HTTP message components covered by the signature", not a format of your own.
  • StandardThe @signature-params component is required as the last line of the signature base and must not be enumerated within the covered components of any signature, including itself. RFC 9421 section 2.3.
  • StandardCarry the covered components and parameters in Signature-Input and the signature in Signature, both Dictionary structured fields. RFC 9421 sections 4.1 and 4.2.
  • StandardUse a registered algorithm identifier from the HTTP Signature Algorithms registry, RFC 9421 section 6.2.2, such as ed25519, ecdsa-p256-sha256 or rsa-pss-sha512.
  • StandardRFC 9421 section 1.4 requires an application or profile to specify, at a minimum, the set of component identifiers and signature parameters that are expected and required, a means of retrieving key material, "the set of allowable signature algorithms to be used by signers and accepted by verifiers", "a means of determining that the signature algorithm used is appropriate for the key material", and the errors returned when validation fails. Write these down before you implement.
  • StandardCover a body digest explicitly. RFC 9421 section 7.2.8 states that the specification "does not define a means to directly cover HTTP message content", so the body is only protected by covering a digest field that describes it.
  • StandardTreat anything outside the covered components as untrusted. RFC 9421 section 7.2.1 notes that uncovered portions remain "modifiable by intermediaries" without invalidating the signature.
  • StandardCompute Content-Digest as defined in RFC 9530 section 2, using an active algorithm from its registry in section 7.2, currently sha-512 and sha-256.
  • StandardFor ecdsa-p256-sha256 the signature value is R and S concatenated, not a DER encoding. RFC 9421 section 3.3.4.
  • BaselineVerify in this order: resolve keyid, check alg against the allowlist, check alg against the key, check required coverage, rebuild the base, verify the signature, recompute the digest, check created and expires, record the nonce.
  • BaselineRecompute the digest from the received bytes on every request. Covering content-digest without recomputing it protects the header and not the body.
  • BaselineAccept a created value within 300 seconds of server time in either direction, and document that number as the replay window for anything you do not record.
  • BaselineRequire a nonce, record it only after the signature verifies, and store it where every instance serving the endpoint can see it.
  • BaselineResolve keyid only against keys established out of band. Never fetch key material from a location the caller supplies.
  • BaselineIssue a new keyid for every key and accept both during a rotation overlap.
  • OptionKeep an HMAC where both parties are the same organisation, there is one receiver, and no request will ever need attributing to one side. RFC 9421's hmac-sha256 lets you do that inside the same format.
  • OptionSign responses as well as requests, and bind a response to its request, where a client needs to prove what it was told. RFC 9421 supports both directions.
  • OptionHold the private key in a hardware-backed or non-exportable keystore, which is what makes the last row of the attack table hard rather than merely unlikely.

Review checklist items

These are collected into the site checklist.

  • A body digest is a covered component and is recomputed on every request Both halves. Test a swapped body against a request whose digest is covered, and against one where it is present but uncovered.
  • keyid resolves only to keys held out of band No fetching from a caller-supplied location. An unknown keyid is rejected, not resolved.
  • The algorithm is checked against an allowlist and against the key A valid signature with a disallowed algorithm is rejected. A message claiming a symmetric algorithm for an asymmetric key is rejected.
  • Every component the handler trusts is covered Method, authority, path, content type, body digest, and the query where it carries meaning. Anything uncovered is treated as untrusted in the code, not just in the design document.
  • A covered component missing from the message is a rejection The verifier does not substitute a blank value to complete the base.
  • Freshness and replay are both bounded created is inside a stated window, expires is enforced when present, and nonce is recorded after verification in a store shared across instances.
  • Key rotation works without a cutover A new keyid per key, both accepted during an overlap, and the retirement date recorded.
  • The choice of symmetric or asymmetric is written down with its reason If an HMAC is still in use, the threat model states that a breached receiver forging as the caller is accepted.
