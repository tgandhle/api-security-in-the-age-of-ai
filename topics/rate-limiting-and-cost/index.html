Rate limiting and cost controls

Objective. 1. The attack

Running example: ExampleAir's partner API, limited to 100 requests per minute. Company names are fictional. The limit is documented, implemented, and returns 429 when it fires.

The first attack does not exceed it. A caller sends 100 requests at 12:00:59 and 100 more at 12:01:00, and both batches are inside their minute. Two hundred requests in two seconds, from a service that promised a hundred a minute, and nothing was violated.

The other three do not even try. They stay under the limit and get what they want anyway, because a limit on the number of requests is not a limit on cost, on duration, on how many identities a caller may hold, or on how many of your instances are counting separately.

OWASP puts the consequence plainly in API4:2023 Unrestricted Resource Consumption, which names the cost side of this directly: exploitation can lead to "operational costs increase such as those related to the infrastructure due to higher CPU demand, increasing cloud storage needs, etc." Where the API fronts a language model, the bill is counted in model tokens, which are explained under the table below, and LLM06:2026 Unbounded Consumption says the same thing about the limit itself: "Traditional request-rate limiting alone is no longer sufficient."

The cost row, where a model does the work

ExampleAir adds an assistant endpoint to the partner API, and a language model answers each request. A model token is the unit a language model reads and writes text in: a chunk of text, often a word or part of a word. The provider bills for each one. It is not an access token, which is a credential, and it is not a token in a token bucket, which is a unit of allowance in a rate limiter. This page says "model token" every time it means the first kind.

The endpoint keeps the limit of 100 requests per minute. A normal partner sends 20 requests in a minute, each with 500 model tokens of input and room for 100 of output. Another caller sends 5 requests in the same minute, each with 100,000 model tokens of input and room for 20,000 of output. Nothing is refused. At the lab's prices, 1 unit for each input model token and 5 for each output model token, the first caller costs 20,000 units and the second costs 1,000,000: fifty times the bill from a quarter of the requests. LLM06:2026 calls this cost asymmetry: "Attackers can trigger disproportionately expensive computation at negligible cost to themselves".

2. Why it works

Three algorithms, and what each one permits at its worst

The differences are small to implement and large in effect, and the useful way to compare them is by their worst moment rather than their average.

  • Fixed window. Count per calendar minute, reset at the boundary. Its worst moment is the boundary, where two full windows fit inside two seconds, so the observed peak is twice the limit in an arbitrarily short time. Cheap to implement, and the peak is the part people do not picture.
  • Sliding window. Count the requests in the last sixty seconds, whenever the request arrives. There is no boundary, so there is no boundary burst. It costs more memory, because you are keeping timestamps rather than a counter.
  • Token bucket. A bucket of some capacity refilling at some rate. Capacity is the burst you are prepared to serve and rate is the average you are prepared to sustain, and separating those two numbers is the point. Its worst moment is a full bucket, which permits the whole capacity at once, on purpose.

The token bucket's row in the table above says 101 rather than 100, and that is not a rounding error: it is the full bucket at 12:00:59 plus the 1.67 tokens that refilled by 12:01:00. Watching a limiter produce a number you did not predict is the fastest way to find out what it actually enforces.

Four things a request count does not count

Cost. A request that reads one row and a request that runs a report are one request each. OWASP's prevention list starts with the resource side, "use a solution that makes it easy to limit memory, CPU, number of restarts, file descriptors, and processes such as Containers / Serverless code", and continues with the pricing side, "configure spending limits for all service providers/API integrations. When setting spending limits is not possible, billing alerts should be configured instead". Between those two sits the API's own answer: charge each request what it costs and limit the total.

Duration. A rate limit constrains a minute. It says nothing about a day, and one request a second for a day is 86,400 requests without a single refusal. If what you care about is the total, a rate limit is not the control; a quota is, and module 11 is where the number comes from.

Identity. A per-caller limit is exactly as strong as the cost of becoming another caller. Where identities are free, the limit is a formality. OWASP's advice here is to tune by endpoint rather than globally: "rate limiting should be fine tuned based on the business needs. Some API Endpoints might require stricter policies", and specifically to "limit/throttle how many times or how often a single API client/user can execute a single operation (e.g. validate an OTP, or request password recovery without visiting the one-time URL)".

Where the counter lives. Four instances with local counters enforce four times your limit, and they do it silently, because each one is correct about what it saw. This is module 11's shared-store argument in a second place, and it is the one most likely to be true in your system right now.

When a model does the work

The broken assumption is the first of the four: that requests cost about the same. It is further from true here than anywhere else in this module. The cost of a model call is set by two numbers the caller chooses, how many model tokens it sends and how many it lets the model write, and neither is visible in the route or the method. A weight per operation cannot capture that. The weight has to be worked out for each request, from its own sizes and a price table. In the lab one heavy request costs 200,000 units and one normal request costs 1,000, on the same endpoint.

The decision has to come before the call. Once the model has run, the model tokens are spent, and a refusal after that saves nothing. So the endpoint caps the input size, caps the output a caller may ask for, and estimates the cost from those two numbers before it calls the model. LLM06:2026 recommends the estimate and the check on input size: "Use pre-flight token estimation to reject requests before inference begins. This includes validation to ensure inputs do not exceed reasonable size limits." The token there is the model token. The entry does not list an output cap among its mitigations. This page adds one, because the output matters as much as the input: the entry says the risk is compounded by reasoning models "with large or insufficiently constrained output budgets", and in the lab's price table an output model token costs five times an input one.

Caps alone are not enough. A caller can stay inside every cap and still spend, one allowed request after another. LLM06:2026 makes the same point about large inputs: "the durable risk comes from requests that stay just within limits while inflating per-request cost". That is what the limits on model tokens per minute and per day are for, and behind them a budget ceiling for each caller.

An alert or a stop. Two OWASP entries speak to that last control, and they differ. API4:2023 is about APIs in general and says to "configure spending limits for all service providers/API integrations. When setting spending limits is not possible, billing alerts should be configured instead". LLM06:2026 is about applications built on language models and says of budget ceilings: "These must be enforcement mechanisms that halt inference when exceeded, rather than alerting thresholds that fast-accumulating workloads can outpace." The word "must" is OWASP's. Neither document sets requirements: each is a Top 10 entry that describes a risk and says what its authors recommend. They do not contradict each other. API4:2023 puts the limit first and accepts an alert only where no limit can be set. LLM06:2026 gives its reason in the sentence quoted: a workload whose spend builds fast can outpace an alert.

This project's Baseline for an endpoint backed by a model is the stricter of the two: a ceiling for each caller or key that your own code enforces before the model is called, with the alert kept as an addition, so that somebody knows the ceiling was reached. The reason is lab checks 39 to 43. The same ceiling and the same traffic cost 28,000 units when the ceiling halts and 400,000 when it only alerts, and the alert fires 93 times on the way. The fallback in API4:2023 is for a limit that cannot be set. Here it usually can be: the call to the model goes through code you own, so you can refuse it yourself, whatever the provider offers. Module 31 applies the same rule to one agent run, where this module applies it to one caller.

What to say when you refuse

429 is defined in RFC 6585 section 4, not in the core HTTP semantics document, and its definition is short and worth reading in full. It "indicates that the user has sent too many requests in a given amount of time", the response "SHOULD include details explaining the condition, and MAY include a Retry-After header indicating how long to wait before making a new request", and "responses with the 429 status code MUST NOT be stored by a cache". That last one is a requirement people miss and a cache will happily ignore on your behalf.

The security considerations for 429, section 7.2 of the same RFC, say something more interesting: servers "are not required to use the 429 status code; when limiting resource usage, it may be more appropriate to just drop connections, or take other steps", because "when a server is under attack or just receiving a very large number of requests from a single party, responding to each with a 429 status code will consume resources". A polite refusal is still work. Under attack, the cheapest response is the right one.

On telling clients their remaining quota: there is no standard. The IETF work on RateLimit header fields, draft-ietf-httpapi-ratelimit-headers, reached revision 11 in May 2026 and is still an Internet-Draft, with a "Not ready" early review of the previous revision, completed in January 2026. Emitting those headers is reasonable and common. Calling them standard is not, and a client that depends on them is depending on your implementation.

3. The control

  1. Pick the algorithm from the worst moment you will accept. Fixed window if double the limit in two seconds is fine. Token bucket if you want to permit a burst and name its size. Sliding window if you want neither.
  2. Count cost, not requests, wherever requests differ by more than a small factor. Assign each operation a weight and limit the total weight.
  3. Add a quota beside the rate. The rate protects the system from a moment. The quota protects the business from a day, and the number comes from whoever knows what the flow is worth.
  4. Decide what the limit is per, and price the alternative. Per caller, per account, per endpoint, per tenant. If a second identity is free, the per-caller limit is decoration.
  5. Put the counter in a store every instance shares, and test it against a second instance. Four local counters enforce four times your limit.
  6. Limit the resources underneath as well: memory, CPU, processes, file descriptors, execution timeouts. OWASP names these first for a reason, because they bound what a request can cost even when your accounting is wrong.
  7. Set spending limits on every paid integration, or billing alerts where limits are not available.
  8. Where a model does the work, decide before you call it. Cap the input size in model tokens. Cap the output a caller may ask for. Estimate the cost of the request from those two numbers and your price table, and refuse it if the estimate is over a limit for one request.
  9. Limit model tokens per minute and per day, for each caller, beside the request rate. These are steps 2 and 3 with the model token as the unit.
  10. Enforce a budget ceiling for each caller or key, one that halts. Add the estimate to what the caller has spent, and refuse the call that would take the total over the ceiling. Raise an alert as well, not instead.
  11. Refuse cheaply. 429 with a short body, no caching, and where the volume makes even that expensive, drop instead.

5. What it proves, and what it doesn't

Proves: that a single identified caller cannot exceed a stated number of weighted operations in a stated period, as counted by a store all your instances share.

Doesn't prove: that your total load is bounded, that your bill is bounded, or that a determined caller is bounded. Each of those needs something else: a global ceiling, a spending limit, and a view of how expensive a second identity is.

For an endpoint backed by a model, the controls in steps 8 to 10 prove: that no request the endpoint passes to the model is over the size caps or over the cost limit by your estimate, and that one caller's spend, as you count it, does not pass the ceiling.

They don't prove that the estimate is right. The lab's stub writes exactly the output it is allowed, so the estimate and the bill are equal. A real model can use model tokens the request did not show: LLM06:2026 lists short prompts that push a reasoning model into long loops, "consuming massive thinking-token budgets while bypassing input-size filters". An agent can also turn one request into many model calls, and module 31 bounds that with a step budget and a spend ceiling for each run. This module teaches neither. And a ceiling for each caller says nothing about fifty callers, which is the identity row again.

A limit is a claim about a number you chose to count. "100 per minute" is precise about requests and silent about work, about the day, about how many accounts one person has, and about how many copies of the counter exist. Every incident in this area is somebody discovering which of those four the limit was never about.

6. Prove it

For each limit you publish:

  • The worst-case burst is written down, and it matches what the algorithm actually permits.
  • A test drives traffic across the window boundary and asserts the number allowed.
  • A test drives the same traffic through two instances and asserts the shared counter held.
  • Operations carry cost weights, or there is a measurement showing they cost the same.
  • A daily or monthly quota exists beside the per-minute rate.
  • Sensitive operations have their own stricter limit, tested separately.
  • Platform resource limits exist: memory, CPU, processes, descriptors, execution timeout.
  • Every paid integration has a spending limit or a billing alert, and somebody receives it.
  • 429 responses are not cached, and there is a test that proves it.

For each endpoint backed by a model, also:

  • A request over the input cap is refused, and so is one that asks for more output than the cap. The test asserts the model was not called.
  • A request inside both caps whose estimated cost is over the limit for one request is refused before the call.
  • A caller is refused at the limit on model tokens per minute and at the quota per day, and is served again once each has aged out.
  • The call that would take a caller's spend over the ceiling is refused, and the spend never passes the ceiling.
  • The same test fails when the ceiling is switched to raise an alert and nothing else.

8. Check your understanding

Your limit is 100 per minute on a fixed window. What is the most a caller can send in two seconds?

Two hundred, by sending a full window's worth just before the boundary and another immediately after. Both batches are within their own minute, so nothing was violated. If that peak matters, use a sliding window, or a token bucket with a capacity you chose on purpose.

Why is a token bucket's burst not a bug?

Because capacity and rate are two separate numbers and the burst is the capacity. That is the feature: you can permit a client to catch up after being idle while still bounding the sustained rate. The mistake is not setting a capacity, it is not knowing what you set it to.

Every caller is within the limit and the bill has tripled. What happened?

Probably one of three things. Requests are not equal and something expensive got popular, so limit the cost rather than the count. Or the total over a day was never bounded, because a per-minute rate says nothing about a day. Or a paid integration has no spending limit, which OWASP lists as its own prevention item.

Your rate limiter is correct and callers exceed the limit anyway. Where would you look first?

At where the counter lives. If each service instance counts locally, your effective limit is the published one multiplied by the number of instances, and every instance is behaving correctly. Test the limit by sending traffic to two instances, not by sending two requests.

  • The caller and the traffic are the same. The counter is not, and a limiter only refuses what its own counter has seen.

4. The sliding window keeps a timestamp one second longer

In SlidingWindow.allow, change the test that drops old timestamps from self.seen[0] <= now - self.window to self.seen[0] < now - self.window.

Which checks change?

Every option, and why
  • Check 7 still prints 0 allowed. The edit keeps timestamps for longer, so it can only refuse more, and the batch from t=59 is one second old at t=60 under either test.
  • Check 17 still prints 4 allowed. Measured second by second, the two later requests are allowed at t=61 and t=62 where the published lab allows them at t=60 and t=61. The count is the same.
  • Correct. Exit 1, three failures. Check 9 goes from allowed to refused. The batch from t=59 is exactly 60 seconds old at t=119. The published test drops it there and the edited one keeps it for one more second, so the window is now 61 seconds long. This is the direction that fails safe, and it is still a finding: a caller who waits the published 60 seconds is refused. Part E uses the same class for model tokens, and its two checks on the same edge change too: check 35 prints refused: model tokens per minute and check 38 prints refused: model tokens per day. Check rate-02 in the Reference layer says to test the boundary, and check 9 is that test.
  • Check 9 sits exactly on the edge on purpose. A test one second later would have passed under both versions and shown nothing.

5. The estimate forgets the output

In ModelEndpoint.call, change estimate = cost_of(tokens_in, max_out) to estimate = cost_of(tokens_in, 0). The estimate made before the call now prices the input and nothing else. The spend recorded after the call still uses what the model wrote.

What does check 39, the ceiling of 30000 that halts, print?

Every option, and why
  • The spend is recorded in full, but the test before the call now adds an estimate of 2000 to it, not 4000. After 7 calls the spend is 28000, and 28000 plus 2000 is not over 30000, so the eighth call runs.
  • Correct. Exit 1, six failures. Check 39 goes from 7 calls, 28000 units to 8 calls, 32000 units, check 40 from refused: budget ceiling to ok, check 41 from no to yes, and check 43 from 93 alerts to 92. The limit for one request fails the same way: check 30 prints estimate 8000, ok and check 32 goes from 1 model call to 2. The 8000 there is worked out by the check from the price table. The endpoint's own estimate was 3000. Output is the dearer half of this price table, so an estimate that leaves it out is wrong by most of the bill. Check rate-10 in the Reference layer asks for a ceiling the spend never passes, and that needs an estimate that assumes the whole output.
  • The ceiling still halts the caller. It halts it one call late: the ninth request is refused, and 92 of the 100 are.
  • Fifteen calls at 2000 units is what you would get if the spend were recorded at the estimate. It is recorded from what the model wrote, 4000 units a call.

Review checklist items

These are collected into the site checklist.

  • Counters are held in a store every instance shares Tested by driving traffic through two instances. Local counters multiply the published limit by the instance count.
  • The worst-case burst is written down and matches the algorithm A fixed window permits twice the limit across its boundary. A token bucket permits its capacity. Test the boundary.
  • Expensive operations are limited by cost, not by request count Or there is a measurement showing operations cost about the same. For an API backed by a model, OWASP LLM06:2026 recommends limits on model tokens and on estimated cost per request, beyond requests per second.
  • A quota exists beside the rate A per-minute limit does not bound a day. One request a second is 86,400 with nothing refused.
  • Every paid integration has a spending limit or a billing alert And somebody receives the alert. OWASP lists this as its own prevention item. For an endpoint backed by a model an alert alone is not enough: see rate-10.
  • Sensitive operations have their own stricter limits One-time-password validation, password recovery, anything that sends a message or spends money.
  • Platform resource limits are set Memory, CPU, processes, file descriptors and execution timeouts, so a wrong limit is not an unbounded one.
  • 429 responses are uncacheable and cheap RFC 6585 requires they not be stored by a cache, and permits dropping instead when answering is itself the cost.
  • A model endpoint caps request size and limits model tokens, before the model is called An input cap, a cap on the output a caller may ask for, an estimated cost for each request, and model tokens per minute and per day for each caller. A request-rate limit alone refuses none of this.
  • A model endpoint has a budget ceiling for each caller or key that halts The call that would take the spend over the ceiling is refused before the model is called, so the spend never passes it. An alert is an addition, not the control.
