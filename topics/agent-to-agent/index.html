Agent-to-agent

Last reviewed 2026-10-04 · Jump to reference

Objective. After this module you can say what an agent card does and does not prove, verify one the way the specification describes, refuse a mid-task credential request on principle rather than on instinct, and validate a webhook URL a counterparty hands you.

Before you start. This module pins to release v1.0.1 of the A2A specification, published 28 May 2026, the newest release when this page was reviewed. The protocol version it defines is 1.0: section 3.6 says patch numbers "do not affect protocol compatibility", and the v1.0.1 page's own banner still reads "Latest Released Version 1.0.0". Sections 7 (Authentication and Authorization), 8 (Agent Discovery: The Agent Card) and 13 (Security Considerations) were read in full for this review. The rest comes from the v1.0.1 copies of the protocol's own documentation pages, which are guidance and not the specification. Each is named in Sources.

1. The attack

Running example: ExampleAir's booking agent hires a seat-map agent from a partner to hold a seat. Company names are fictional. The booking agent finds the partner by fetching its agent card, sends it a task, and gives it a webhook URL to call when the task finishes.

Every one of those three steps takes something off the network and treats it as true. That is the module. OWASP files the category as ASI07 Insecure Inter-Agent Communication in the Top 10 for Agentic Applications for 2026.

The last two rows are the same feature read from each end, and both ends have work to do. The server must not POST wherever it is told, and the webhook must not believe whoever POSTs to it.

2. Why it works

What an agent card is, and what signing it buys

The specification requires the card to exist: "A2A Servers MUST make an Agent Card available. The Agent Card describes the server's identity, capabilities, skills, and interaction requirements." The standard discovery path is https://{server_domain}/.well-known/agent-card.json.

Cards may be signed. Section 8.4 says "Agent Cards MAY be digitally signed using JSON Web Signature (JWS) as defined in RFC 7515 to ensure authenticity and integrity", and section 8.4.1 says that before signing the content "MUST be canonicalized using the JSON Canonicalization Scheme (JCS) as defined in RFC 8785". Canonicalization is there because a card is a JSON document that will be reserialised by every library it passes through, and two serialisations of the same document are not the same bytes. Checks 3 to 5 of the lab are that point: a card with its keys in the opposite order is a different byte string and the same canonical document, and the signature still verifies.

Then the rule that is easy to get wrong: "The signatures field itself MUST be excluded from the content being signed to avoid circular dependencies." This is not a style preference. If the signature were computed over a document containing the signature, the value would have to be inside its own input. Check 9 signs a card with the field left in, and check 10 is the consequence: a verifier that follows the specification cannot check that card at all. It is not a weaker signature, it is an unverifiable one.

What a verified card still does not tell you

A signature over a card proves that whoever holds the key wrote the card. It does not say who that is, and the card's own name field is just a string in the signed content. Check 11 of the lab verifies a card perfectly, under the attacker's own key, and check 12 shows the name it claims is the partner's.

So the useful question is not "does this card verify" but "does it verify under a key I already associate with this counterparty". That is a key distribution problem, and the specification leaves it open. Section 8.4.3 has the verifier "Retrieve the public key using the kid and jku (or from a trusted key store)". The jku is a URL in the signature's own protected header, so the specification allows a verifier to follow the card to the key. The trusted store is optional: "Clients MAY maintain a trusted key store for known agent providers". This course's baseline makes that store the only route. The documentation's advice points the same way: it "strongly recommends the use of out-of-band dynamic credentials rather than embedding static secrets within the Agent Card", and for anything sensitive it recommends "authenticated extended agent cards" and "access controls on the HTTP endpoint serving the Agent Card" such as mTLS, network restrictions or HTTP authentication.

Two further things a card does not establish, both of them this course's baseline rather than a requirement of the specification. First, that the endpoint the card points at is on the domain the card came from. Check 16 of the lab is a card signed with the partner's real key whose interface URL is somewhere else entirely, and it verifies. Second, that the endpoint behaves as the card says. A card's securitySchemes is a claim about an endpoint, not a measurement of one, and its skills list is a claim about what the endpoint answers. Checks 20 to 22 are module 12's argument again: the declared list and the reachable list are different lists, and the difference is where the finding is.

A task that stops and asks for a credential

A2A tasks can reach an interrupted state, among them input-required and auth-required, where the remote agent needs something before it can continue. For credentials, the documentation is clear about where the client obtains them: if an agent needs additional credentials for another system during a task, the "client is then responsible for obtaining these secondary credentials through a process outside of the A2A protocol itself". Section 7.6.1 of the specification states the rule from the agent's side, with one exception: "Agents MUST arrange to receive credentials via an out-of-band means, unless an in-band mechanism has been negotiated out-of-band or via an extension."

This course negotiates no in-band mechanism, which turns that into a test you can apply without judgement. A request that wants the credential typed back into the task conversation is refused on its face, whatever it says it needs the credential for. And a request for the credential your agent already uses to authenticate to that counterparty is not a secondary credential at all; it is the counterparty asking for its own key back, with more of it. Part C of the lab is four variants and one acceptable case.

This is also the part of A2A where the attacker's message is read by a model rather than a parser, which is module 22. The control here is structural: decide in advance which systems your agent can obtain credentials for and by what path, so that a mid-task request is matched against a list rather than assessed on its wording.

The webhook, from both ends

Push notification configuration carries "a url (the HTTPS webhook URL), an optional token (for client-side validation), and optional authentication details", supplied either with the initial message or later through the create-config method.

For the server receiving that URL, the documentation is explicit: "Servers SHOULD NOT blindly trust and send POST requests to any URL provided by a client", naming SSRF and amplification as the risks and allowlisting, ownership verification and network controls as the mitigations. Section 13.2 of the specification says the same at the same strength: agents "SHOULD validate webhook URLs to prevent SSRF", by rejecting private, localhost and link-local addresses and using allowlists "where appropriate". That is module 14 with the roles swapped: here you are the server being asked to make the request. Part D of the lab is an allowlist on the host name followed by a check on the address it resolves to, and then the reason both are needed: checks 37 to 41 validate an allowlisted name that resolves to a public address, and resolve it again at send time to an internal one. The allowlist checked a name. Names are not addresses.

For the notification itself, both ends have a duty. The server "MUST authenticate itself to the client's webhook URL" per the configured scheme, and the webhook "MUST rigorously verify the authenticity of incoming notification requests", with notifications that "SHOULD include a timestamp" so replays can be rejected. Part E is module 16's receiver applied to A2A, including the token, which binds a notification to the task it is about rather than merely to your webhook.

The receiver has one more duty, and it is about the payload, not the sender. Section 4.3.3 of the specification says "Clients MUST validate the task ID matches an expected task". Section 13.2 repeats it at a lower strength: "Clients SHOULD verify the task ID in the payload matches an expected task they created". A notification can be authentic, fresh and carry your token, and still name a task you never started. Check 48 of the lab sends that notification, and the webhook refuses it because the task id is not in the set of tasks the client created. Check 49 sends the same kind of notification for a task in that set, and the webhook accepts it.

3. The control

  1. Pin the counterparty's key, not the card. Verification is only worth something against a key you associated with that partner out of band. A card that carries its own trust anchor carries none.
  2. Canonicalize with JCS before signing or verifying, and exclude the signatures field from the content, as section 8 requires.
  3. Check that the interface URL is on the origin you expect, and refuse a card that redirects you elsewhere even when its signature is good.
  4. Measure the skills and the scheme rather than reading them. The card is the claim; the endpoint is the fact.
  5. Decide in advance which credentials your agent may obtain and by what path, so a mid-task request is matched against a list.
  6. Never deliver a credential inside the task conversation. Section 7.6.1 requires the agent to arrange to receive it out of band unless an in-band mechanism was negotiated beforehand, and this course's baseline is to negotiate none.
  7. Allowlist webhook hosts, then validate the resolved address, and treat the gap between validation and connection as real.
  8. Authenticate your notifications, and verify them at the receiving end: signature, freshness, the task token, a task id that matches a task you created, and an identifier you have not already handled.
  9. Keep the card's endpoint and the card itself separately access-controlled where either carries anything sensitive, with an authenticated extended card for the detail.

5. What it proves, and what it doesn't

Proves: that the card you acted on was written by the holder of a key you had already associated with that counterparty, that its endpoint is where you expected, that no credential left your agent through the task conversation, and that every notification you accepted was authenticated, fresh, about a task you were waiting on, and handled once.

Doesn't prove: that the counterparty is honest. Every check here is satisfied by a correctly identified partner behaving badly, and a signed card from a compromised partner verifies exactly as well as one from a healthy one. It also proves nothing about what the remote agent does with what you send it, which is the limit of the whole protocol rather than of your implementation.

A signature that verifies answers a question you did not ask. Check 11 of the lab verifies a forged card perfectly, because it was signed with the key of whoever sent it. The question worth asking is whether it verifies under a key you already held for that counterparty. If your verifier takes the key from the card, or from the domain that served it, it will answer yes to both cards and tell you nothing.

6. Prove it

  • The protocol version the implementation targets, written down and dated.
  • For each counterparty, the key you verify its card against and the out-of-band route you got it by.
  • A test that a card signed by an unknown key is refused even though its signature is internally consistent.
  • A test that a card whose interface URL is off-origin is refused.
  • A comparison of each counterparty's declared skills against the ones its endpoint answers.
  • The list of systems your agent may obtain credentials for, and for each one the out-of-band path.
  • A test that a credential request arriving inside a task is refused.
  • The webhook host allowlist, plus evidence that the resolved address is checked at send time and not only at configuration time.
  • A 2xx and a rejection captured from your own webhook, showing signature, freshness, token, expected task and replay checks each firing.
  • A test that a notification with a valid signature, a fresh timestamp and the right token is refused when its task id is not one your client created.
  • Whether the public agent card contains anything you would not publish, and if so, what moved to the extended card.

Checks 3 to 5 are the case for canonicalization in three lines. The same card with its keys reversed is not the same bytes, and is the same canonical document, and the signature verifies. Remove the key sorting and checks 3 and 5 fail, which is what a signature scheme without a canonical form looks like in production: it works until something reserialises the document.

Checks 9 and 10 are the rule people get wrong. A card signed with its own signatures field inside the signed content is not weakly signed, it is unverifiable, because a verifier following section 8 computes over a different document than the signer did. There is no way to check it short of guessing what the signer included.

Checks 11 to 15 are the forged card, and the thing to notice is that it is internally consistent. It verifies. Its origin matches. The only wrong thing about it is the name field, and that is a string in the signed content rather than something the signature establishes. If your verifier obtains the key from the card or from the domain serving it, checks 11 and 1 are indistinguishable.

Checks 16 and 17 are the opposite failure and the more subtle one: the partner's real key, correctly verified, and an interface URL on another host. A key check alone passes this. That is why the origin check is in the control list, and why it is labelled Baseline rather than Standard: it is not a requirement of the specification.

8. Check your understanding

An agent card's JWS signature verifies. What have you established?

That whoever holds the signing key wrote the card. Nothing about who that is. The card's name is a string inside the signed content, so a forged card signed with the forger's own key verifies perfectly and claims whatever name it likes. The check that is worth something is whether it verifies under a key you already associated with that counterparty by some other route.

Why must the signatures field be excluded from the signed content?

Because otherwise the signature value would have to be part of its own input. Section 8 states it as a MUST. The practical consequence is not a weaker signature but an uncheckable one: a verifier computing over the document without signatures, as the specification says to, is computing over different bytes than a signer who left it in.

A task you sent comes back in an interrupted state asking for a credential to a vendor API, to be sent in the next task message. What do you do?

Refuse the delivery route regardless of the rest. The documented flow has the client obtain secondary credentials "through a process outside of the A2A protocol itself", and this course's baseline is that the credential does not travel in the task conversation, whatever it is for. Separately, check whether that vendor is on your pre-agreed list; if it is not, the request is a finding rather than a step.

You allowlist webhook hosts. Is the SSRF risk handled?

Not on its own. The allowlist checks a name, and the request goes to an address. An allowlisted name can resolve to a loopback, link-local or private address, which checks 33 to 35 of the lab show, and it can resolve differently between the moment you validate and the moment you connect, which checks 37 to 41 show. You need the name check, the address check, and an awareness that the second one has a shelf life measured in whatever your resolver's cache does.

A2A v1.0.1 sections 8.4 and 8.4.1.
  • Standard"The signatures field itself MUST be excluded from the content being signed to avoid circular dependencies." A2A v1.0.1 section 8.4.1.
  • StandardCredentials "must be transmitted in standard HTTP headers as per the requirements of the chosen authentication scheme"; A2A payloads "don't carry user or client identity information directly"; the documentation says servers should respond 401 when credentials are missing or invalid and 403 when valid credentials lack permission. A2A: Enterprise Implementation of A2A.
  • StandardAuthorization "should be applied based on the authenticated identity", can be controlled per skill as advertised in the Agent Card, and agents "must grant only the necessary permissions required for a client or user". A2A: Enterprise Implementation of A2A.
  • StandardWhere an agent needs further credentials during a task, the "client is then responsible for obtaining these secondary credentials through a process outside of the A2A protocol itself". A2A: Enterprise Implementation of A2A. The specification adds: "Agents MUST arrange to receive credentials via an out-of-band means, unless an in-band mechanism has been negotiated out-of-band or via an extension." A2A v1.0.1 section 7.6.1.
  • Standard"Servers SHOULD NOT blindly trust and send POST requests to any URL provided by a client", with SSRF and amplification named as the risks and allowlisting, ownership verification and network controls as mitigations. A2A Streaming and Asynchronous Operations. The specification says agents "SHOULD validate webhook URLs to prevent SSRF". A2A v1.0.1 section 13.2.
  • StandardThe server "MUST authenticate itself to the client's webhook URL"; the webhook "MUST rigorously verify the authenticity of incoming notification requests"; notifications "SHOULD include a timestamp" to prevent replay. A2A Streaming and Asynchronous Operations. In the specification, agents "MUST include authentication credentials in webhook requests" and clients "MUST validate webhook authenticity using the provided authentication credentials". A2A v1.0.1 section 13.2.
  • Standard"Clients MUST validate the task ID matches an expected task". A2A v1.0.1 section 4.3.3. Section 13.2 states the same duty as a recommendation: "Clients SHOULD verify the task ID in the payload matches an expected task they created". A2A v1.0.1 section 13.2.
  • StandardPush notification configuration carries "a url (the HTTPS webhook URL), an optional token (for client-side validation), and optional authentication details". A2A Streaming and Asynchronous Operations.
  • Standard"Any Agent Card containing sensitive data must be protected with authentication and authorization mechanisms", and the documentation "strongly recommends the use of out-of-band dynamic credentials rather than embedding static secrets within the Agent Card". A2A Agent Discovery.
  • StandardTasks can reach an interrupted state such as input-required or auth-required. To continue an interaction, clients can send later messages with the same contextId. A2A Life of a Task.
  • StandardUnder JCS, "JSON object properties MUST be sorted recursively", with names "formatted as arrays of UTF-16 [UNICODE] code units" for the comparison. RFC 8785 section 3.2.3, June 2020, which is Informational and an Independent Submission rather than an IETF standard.
  • BaselineVerify a card only against a key obtained out of band for that counterparty, and never against a key the card or its domain supplies.
  • BaselineRefuse a card whose interface URL is not on the origin the card was served from, signature notwithstanding.
  • BaselineCompare each counterparty's declared skills with the ones its endpoint answers, and treat the difference as a finding.
  • BaselineMaintain a list of systems your agent may obtain credentials for, with the out-of-band path for each, and match mid-task requests against it.
  • BaselineAllowlist webhook hosts and check the resolved address, treating the two as separate checks because one tests a name and the other an address.
  • BaselineVerify every inbound notification on signature, freshness, task token, expected task id and identifier, and treat the webhook URL as public.
  • OptionServe a minimal public card and put the detail behind an authenticated extended card, which the documentation recommends for sensitive content.
  • OptionPut mTLS, network restrictions or HTTP authentication on the card endpoint itself where the card's existence is not public information.
  • OptionRe-resolve and re-check the webhook address immediately before each POST, where the gap between validation and connection is in the threat model.

Review checklist items

These are collected into the site checklist.

  • Agent cards are verified against an out-of-band key per counterparty Not against a key the card names or the serving domain supplies. A forged card signed with the forger's own key verifies perfectly.
  • Credentials never travel inside a task conversation Section 7.6.1 has agents receive credentials out of band unless an in-band mechanism was negotiated beforehand. With none negotiated, a request to deliver one in-band is a finding.
  • Client-supplied webhook URLs are allowlisted and address-checked A name check and an address check are different checks. The A2A documentation says servers should not POST blindly to any URL a client provides.
  • Inbound notifications are verified on signature, freshness and task token And on the task id: section 4.3.3 says clients MUST validate that it matches an expected task. And on an identifier, so a replay is handled once. The webhook URL should be treated as public.
  • Card signing canonicalizes with JCS and excludes the signatures field Both are stated in section 8. Including the field makes the card unverifiable rather than weakly signed.
  • A card's interface URL is on the origin that served the card Or the split is a recorded decision. A signature check alone does not catch an off-origin interface.
  • Credentials your agent may obtain are a pre-agreed list With the out-of-band path for each, so a mid-task request is matched rather than assessed on its wording.
  • Declared skills are compared with the skills the endpoint answers The undeclared one is the one with no review behind it.
  • The public agent card contains nothing you would not publish Sensitive detail moves behind an authenticated extended card, and the card endpoint is access-controlled if its content warrants it.
  • The targeted protocol version is recorded and reviewed A2A is versioned and still moving. A review against an older version can be wrong rather than merely stale.
