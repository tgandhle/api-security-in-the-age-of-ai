MCP server authorization

Last reviewed 2026-10-02 · Jump to reference

Objective. After this module you can say what the MCP specification requires of a server as an OAuth 2.1 resource server, explain why token passthrough is forbidden rather than merely discouraged, validate an audience and a canonical resource URI correctly, and handle a scope challenge without losing permissions.

Before you start. This module pins to MCP protocol revision 2026-07-28, which MCP's Versioning page calls the current protocol version. MCP revisions are dated strings and the identifier changes when a backwards incompatible change lands, so check the pin before you apply any of this to a deployment.

1. The attack

Running example: an MCP server that exposes a company's CRM to an assistant as a set of tools. Company names are fictional. The MCP server is at https://mcp.exampletools.example/mcp, the CRM API behind it is at https://api.examplecrm.example, and both are protected by the same authorization server, which is the common arrangement.

An MCP server is an OAuth 2.1 resource server with a tool-shaped front end. The specification says so directly: "A protected MCP server acts as an OAuth 2.1 resource server, capable of accepting and responding to protected resource requests using access tokens." Almost every rule it places on that server is one you have already met in this course. What is new is how many of them are stated as MUST, and how many deployments fail them anyway.

Five attacks. The lab runs the first four, and module 22 picks up the fifth.

AttackWhat the attacker doesWhat the MCP documents say

Missing audience validationReuses any token the shared authorization server issued, for any resourceServers "MUST validate that access tokens were issued specifically for them as the intended audience"

The third row is the one that catches people out, and it is not a defect in the specification. Authorization being optional is what lets a local stdio server work without an OAuth flow, and the specification is explicit that such servers "SHOULD NOT follow this specification, and instead retrieve credentials from the environment". The problem is a server that moves to an HTTP transport and keeps the posture it had when it was a local process.

2. Why it works

One authorization server, two resources, and only one thing telling them apart

Here is the mechanism, and it is the whole reason token passthrough is common rather than exotic. Your MCP server and the CRM behind it are both protected by the same authorization server. That server has one signing key. So a token issued for the CRM verifies perfectly at your MCP server: right issuer, right key, correct signature, not expired. Every check except one passes.

The one that fails is the audience. It is the only thing in the token that distinguishes "for the MCP server" from "for the CRM", and if your server does not look at it, there is nothing else in the request that would have told you. Checks 3 and 4 of the lab are exactly that pair: the token is refused on its audience, and its signature verified.

This is also why the specification requires the client to do its half. MCP clients "MUST implement Resource Indicators for OAuth 2.0 as defined in RFC 8707", include the resource parameter "in both authorization requests and token requests", and it "MUST identify the MCP server that the client intends to use the token with". The specification then adds the sentence that matters operationally: "MCP clients MUST send this parameter regardless of whether authorization servers support it." You send it even where it will be ignored, so that the day the authorization server starts honouring it, your clients already do.

Why passthrough is forbidden and not just discouraged

The security best practices document names token passthrough as "an anti-pattern where an MCP server accepts tokens from an MCP client without validating that the tokens were properly issued to the MCP server and passes them through to the downstream API", and separates it into two dimensions: audience validation failures, and the forwarding itself. The forwarding is what turns a broken check into a confused deputy, because "the downstream API may incorrectly trust the token as if it came from the MCP server or assume the token was validated by the upstream API".

The reasons given are not abstract. Security controls that depend on the token's audience are bypassed. The audit trail breaks in both directions: "The MCP Server will be unable to identify or distinguish between MCP Clients when clients are calling with an upstream-issued access token which may be opaque to the MCP Server", and "The downstream Resource Server's logs may show requests that appear to come from a different source with a different identity". Checks 7 and 8 of the lab are that pair of log lines, and they name different callers for the same user.

The correct shape is the one module 19 built: two tokens. The specification states it plainly. "If the MCP server makes requests to upstream APIs, it may act as an OAuth client to them. The access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server MUST NOT pass through the token it received from the MCP client."

What changed in this revision

Three changes in 2026-07-28 matter for a review, and none of them is where you would look for it.

MCP is stateless and has no protocol-level sessions. Servers that need state across requests "mint an explicit handle, such as a shopping cart ID or a workflow ID, and receive it back as an ordinary tool argument on each request". That makes the handle a parameter supplied by the caller, which is module 9's problem wearing a new hat, and the Security Best Practices document's answer is the same: bind the handle server side, "for example by keying stored state as <user_id>:<handle> where the user ID is derived from the verified token rather than supplied by the client". Part E of the lab is that one line of difference.

Dynamic client registration is deprecated. Authorization servers and MCP clients "SHOULD support OAuth Client ID Metadata Documents" and "MAY support the OAuth 2.0 Dynamic Client Registration Protocol", with DCR "deprecated and retained for backwards compatibility". If you reviewed an MCP deployment against an earlier revision and recorded DCR as expected, that note is now out of date.

Mix-up protection is now explicit. The client records the issuer before redirecting and validates the iss parameter on the way back, per RFC 9207, and the comparison is "simple string comparison". The specification goes out of its way to forbid being helpful about it: clients "MUST NOT apply scheme or host case folding, default-port elision, trailing-slash, or percent-encoding normalization" first. Part C of the lab is the four-row table and then three issuers that differ only by the normalisations you are forbidden to apply.

3. The control

  1. Validate the audience on every request, and treat the shared authorization server as the reason to, not a reason not to. A correct signature from your own issuer tells you nothing about which resource the token was for.
  2. Never forward the inbound token. If the server calls an upstream API, it is an OAuth client to that API and holds its own token, with the user as the party it acts for.
  3. Publish protected resource metadata at the well-known location, since the specification makes RFC 9728 a MUST for servers and the discovery route a MUST for clients.
  4. Send the resource parameter from the client in both the authorization and token requests, with the canonical URI, whether or not your authorization server honours it yet.
  5. Challenge with a scope. Return 401 with resource_metadata, and 403 with error="insufficient_scope" and the scopes the operation needs, all of them in one challenge.
  6. Keep scopes_supported minimal, because a client whose challenge carries no scope is documented to fall back to requesting everything in it.
  7. Bind state handles to the authenticated user server side, and generate them with a secure random source rather than a counter.
  8. Validate the iss parameter by simple string comparison, against an issuer recorded before the redirect, with no normalisation applied first.
  9. Treat tool descriptions from a server you do not operate as untrusted input, which is where module 22 picks up.

5. What it proves, and what it doesn't

Proves: that a token presented to the MCP server was issued for the MCP server, that the server's upstream calls are attributable to the server acting for a named user, and that a caller cannot reach another caller's state by supplying its handle.

Doesn't prove: that the tool call should have happened. Every check in this module is satisfied by a correctly authorized request to do the wrong thing, which is what the rest of Part 4 is about. It also proves nothing about a tool description's honesty: the specification says those should be considered untrusted unless they come from a trusted server, and does not give you a mechanism for deciding which server is trusted.

A correct signature is not an audience check. If your MCP server and the API behind it share an authorization server, a token for either one verifies against the same key. Check 4 of the lab confirms the signature on a token the server correctly refused. Any deployment that treats "the signature verified" as "this token is for me" is already failing a MUST.

6. Prove it

  • The protocol revision the implementation targets, written down, and a note of when it was last compared with the current one.
  • A test that a token issued by your own authorization server for a different resource is refused with 401.
  • A test that the server's upstream calls use a token whose subject is the server, not the user.
  • A grep of the codebase showing the inbound token is never placed in an outbound Authorization header.
  • The protected resource metadata document, fetched from the well-known path, with scopes_supported reviewed against what the tools actually need.
  • A 401 and a 403 captured from the running server, showing resource_metadata and a scope parameter.
  • A test that a state handle minted for one user is refused for another.
  • Evidence that handles come from a secure random source, not a counter.
  • A test for each row of the iss validation table, including an issuer differing only by a trailing slash.
  • SSRF controls on the client side of OAuth discovery, since those URLs come from the server you are connecting to.

Checks 3 and 4 are the module in two lines. The token is refused because its audience names the CRM, and its signature verified, because the same authorization server issued it. Nothing else in that request was wrong.

Checks 9 and 10 are the easy case, and they are there for contrast. A token from an unrelated authorization server fails on its signature, and it fails on the server that skips the audience check too. That is why the audience check feels unnecessary until the day you consolidate onto one identity provider, at which point it becomes the only check doing the work.

Checks 7 and 8 are the audit consequence. The same user's request produces an upstream log line naming user-41 under passthrough and one naming the MCP server, acting for user-41, when the server holds its own token. The second is the one you can investigate.

Part B runs the specification's own examples, including both that it rejects. The mcp.example.com hostnames in that part are the specification's, quoted unchanged so you can compare the lab with it line by line; everywhere else this course uses the reserved .example domain. It is worth noticing that mcp.example.com fails for a boring reason, a missing scheme, and that the fragment case needs its own rule because a URI with a fragment is otherwise perfectly well formed.

Part C is the part most likely to be implemented wrongly, because every instinct in URL handling says to normalise before comparing. Checks 25 to 27 are three issuers that differ from the recorded one only by a trailing slash, a capital letter and an explicit default port. All three are rejections, and the specification lists each of those normalisations as one clients MUST NOT apply.

Check 34 is the quiet one. A client that responded to the cart:write challenge by asking for cart:write alone now gets a 403 on read_cart, a tool its first token was allowed to call. Nothing failed; it threw away a permission it already held. The union in check 31 is a client-side responsibility and the specification says so.

Part F is the one that reads as a server bug and is usually filed as a client bug. When a challenge carries no scope, the client's documented behaviour is to request every scope in scopes_supported. Check 43 is a seven-scope token including admin:all, produced by a correct client against a server that published its whole catalogue.

Try next:

  • Set check_audience=False on the strict server and rerun. One check fails, and it is the only one that was protecting you.
  • Make check_iss lowercase and strip a trailing slash before comparing, the way you would for any other URL. Two checks fail, 25 and 26, and each one is a normalisation the specification forbids. Check 27, the default port, still rejects.
  • Set bind_handles=False on the bound server and rerun. One check fails: check 36 now prints 200 seat-14C for the other caller, and check 40 still reports a random 21-character handle. Decide whether you would have caught that in review.
  • Add a tool that needs two scopes. This takes more than a new entry in tools: call compares one scope string against the token, so change it to check each scope in turn, then return the missing ones in separate challenges and count the authorization round trips. It is two, against one when both scopes are in a single challenge.
  • For an MCP server you run or connect to: find where the inbound token goes. If it appears in an outbound request, you have found the finding.

8. Check your understanding

Your MCP server verifies the token's signature against your authorization server's key and the token is not expired. Is that enough?

No. If the same authorization server also protects the API behind your MCP server, a token issued for that API verifies identically. The audience claim is the only thing separating them, and validating it is a MUST: servers "MUST validate that access tokens were issued specifically for them as the intended audience".

Why is forwarding the client's token to the upstream API worse than merely accepting it?

Accepting it breaks one boundary; forwarding it breaks a second. The upstream API may treat the token as having come from the MCP server, or as having already been validated by it. Audit breaks in both directions: the MCP server cannot distinguish its clients, and the upstream's logs name a different identity than the service actually calling. The specification states MUST NOT for the forwarding specifically.

A client receives a 403 with scope="files:write". It re-authorizes asking for files:write. What has it done wrong?

It dropped whatever it already had. The specification makes scope accumulation a client-side responsibility and tells clients to compute the union of previously requested scopes and the challenged ones, because servers emit per-operation challenges and are not required to include scopes already granted.

Your MCP server mints 32-character random workflow handles. Is handle hijacking addressed?

Only partly. Random handles make guessing impractical, but the Security Best Practices document's requirement is that possession of a handle MUST NOT be treated as authentication. A handle that leaks, through a log or a shared transcript, still works unless the server binds it to the authenticated user and rejects it when anyone else presents it.

  • StandardMCP clients deployed to a server "MUST consider SSRF risks" when fetching OAuth-related URLs, "SHOULD require HTTPS" and "SHOULD block requests to private and reserved IP address ranges". MCP 2026-07-28, Security Best Practices, Server-Side Request Forgery. RFC 9728 section 7.7.
  • BaselineRecord the protocol revision the implementation targets, and recheck it against the current one on a schedule.
  • BaselineTest audience validation with a token your own authorization server issued for a different resource, not only with a forged one.
  • BaselineKeep scopes_supported to the minimal set for basic functionality, since the client's documented fallback requests all of it.
  • BaselineRequire authorization on any HTTP-transport server, treating the specification's optionality as covering stdio servers only.
  • BaselineGenerate state handles from a secure random source and bind them to the authenticated user.
  • OptionBind the MCP server's access tokens to their holder with the mechanisms in module 7 where a stolen bearer token is in the threat model.
  • OptionExpire state handles as well as binding them, where the workflow has a natural lifetime.
  • OptionRoute the client's OAuth discovery requests through an egress proxy that blocks internal destinations, which the Security Best Practices document suggests for server-side client deployments.

Review checklist items

These are collected into the site checklist.

  • The MCP server validates that each token's audience is itself Tested with a token your own authorization server issued for another resource, because a shared issuer means the signature check cannot tell them apart.
  • The inbound token is never forwarded to an upstream API The server holds its own token for the upstream. The specification states MUST NOT for passing the inbound one through.
  • An HTTP-transport MCP server requires authorization This project treats the specification's optionality as covering stdio servers reading credentials from the environment, not an unprotected HTTP endpoint.
  • State handles are bound server side to the authenticated user Possession of a handle must not be treated as authentication. Test that another caller's handle is refused.
  • Clients send the resource parameter with a canonical URI In both the authorization and token requests, whether or not the authorization server honours it. No fragment, no trailing slash.
  • The iss parameter is compared as a simple string Against an issuer recorded before the redirect, with no case folding, port elision, trailing-slash or percent-encoding normalisation applied first.
  • scopes_supported is the minimal set, and challenges carry a scope A challenge with no scope sends a correct client to request the entire published catalogue.
  • The targeted protocol revision is recorded and reviewed MCP revisions are dated and change on backwards incompatible changes. A review against an older revision can be wrong rather than merely stale.
