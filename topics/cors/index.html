CORS

Last reviewed 2026-10-02 · Jump to reference

Objective. Explain what a successful CORS check does and does not establish, find the two configurations that hand a response to any site, and test a preflight that refuses what it should.

Before you start. You should be able to read an HTTP request and a Python function. An origin is the scheme, host and port of a URL taken together. CORS is the mechanism by which a server tells a browser that a response may be handed to a page from another origin. It is enforced by the browser, not by the server.

1. The attack

ExampleHotels runs an internal reporting API at api.examplehotels.example. It authenticates with a session cookie. A partner dashboard on app.examplehotels.example needed to call it from the browser, so a developer added the two headers that made the error go away: echo back whatever Origin arrived, and allow credentials. These companies are fictional. The configuration is not.

An attacker publishes a page on booking-rewards.example. A logged-in employee visits it. The page runs a fetch with credentials included. The browser attaches the cookie, because that is what including credentials means. The server echoes Access-Control-Allow-Origin: https://booking-rewards.example and Access-Control-Allow-Credentials: true. The browser's CORS check passes, and the attacker's JavaScript reads the report. This is an illustration, not a command.

2. Why it works

The browser's gate is the CORS check, and the Fetch Standard defines it in eight steps. Condensed: if there is no Access-Control-Allow-Origin header, fail. If it is * and the request did not include credentials, succeed. Otherwise it must equal the request's serialised origin exactly. If credentials were included, Access-Control-Allow-Credentials must also be the byte string true.

A server that echoes the Origin header passes step 4 by construction. There is nothing left to compare. The check is not asking whether this origin is trusted; it is asking whether the server named it, and an echoing server names every origin that asks.

The standard is explicit about why the protocol has to be opt-in: "It needs to be an opt-in mechanism to prevent leaking data from responses behind a firewall (intranets). Additionally, for requests including credentials it needs to be opt-in to prevent leaking potentially-sensitive data." On credentials specifically it says that "both sharing responses and allowing requests with credentials is rather unsafe, and extreme care has to be taken to avoid the confused deputy problem" (Fetch Standard sections 3.3 and 3.3.5).

Two further reasons this configuration survives review. First, Origin is not an authentication mechanism. A browser sets it and will not let a page forge it, but curl sets whatever it is told to, so the header means something only inside a browser. Second, the preflight is widely read as an authorisation step. It is not. The standard describes it as a request "that checks to see if the CORS protocol is understood".

3. The control

In order:

  1. Keep a list of exact serialised origins. Compare the incoming Origin against it byte for byte. A serialised origin has no trailing slash and no path, so https://app.examplehotels.example/ never matches.
  2. Never build the header from the request. If the origin is on the list, send that origin. If it is not, send no Access-Control-Allow-Origin at all. Omitting the header is how the protocol says no.
  3. Never pair * with credentials. The standard forbids it, and so does every browser: with credentials included, * fails the check. The same applies to * in Access-Control-Allow-Methods, Access-Control-Allow-Headers and Access-Control-Expose-Headers.
  4. Send Vary: Origin whenever the response depends on the request's origin, so a shared cache cannot serve one origin's allowed response to another.
  5. Name Authorization explicitly in Access-Control-Allow-Headers. It is the one CORS non-wildcard request-header name, so * does not cover it, and neither does a cached preflight entry stored as *.
  6. Put a bound on Access-Control-Max-Age. It defaults to 5 seconds, browsers cap it, and a long value delays the moment a policy change takes effect.
  7. Keep authorisation on the server. CORS decides who may read a response. It never decides who may cause one.

4. Defaults and when to change them

Access-Control-Max-Age. Absent or unparsable, it is 5 seconds. Browsers also clamp it to their own ceiling, so a value of 86400 does not mean a day. Short values cost a preflight on almost every request; long values mean a tightened policy keeps being ignored until the cache expires. Set it deliberately and know your ceiling.

Access-Control-Allow-Origin: *. For genuinely public data this is correct, not sloppy, and the standard says so plainly in a background section it marks as informative only. Its test is worth memorising: "if a resource cannot be accessed from a random device connected to the web using curl and wget the aforementioned header is not to be included. If it can be accessed however, it is perfectly fine to do so." The failure case it names is data "protected through IP authentication or a firewall", where CORS is unsafe, because the browser of someone inside the perimeter becomes the way in.

The safelist thresholds. A request avoids a preflight only if its method is GET, HEAD or POST and every header is CORS-safelisted. Two limits decide that: no single safelisted value may exceed 128 bytes, and the safelisted values together may not exceed 1024 bytes. Cross either and the request preflights, which is a behaviour change you did not configure and will see as a latency change.

Reflecting the origin. There is one defensible version: reflect only after checking the origin against a list, which is what sending the matched origin back amounts to. There is no defensible version that skips the check.

5. What it proves, and what it doesn't

Proves: that the server named this origin in a response header, and, when credentials were included, that it also said credentials may be shared. That is the whole of it.

Doesn't prove: anything about who the user is, or whether the operation was allowed. The CORS check runs in the browser after the response arrives.

Doesn't stop the request. This is the row in the table above that catches people. A cross-origin POST with a safelisted content type is sent with no preflight at all, the server authenticates the cookie and does the work, and the browser then withholds the response. The write happened. Preventing unwanted cross-origin writes is the job of anti-forgery tokens and same-site cookies, not CORS.

Doesn't apply outside a browser. A server-to-server client sets Origin to whatever it likes, or omits it. Treating the header as an access control decision is treating attacker input as a credential.

Doesn't survive a wildcard in the wrong place. A preflight that answers Access-Control-Allow-Headers: * has not allowed Authorization, and a request carrying it will fail. That is a correctness trap more often than a security one, but it is the reason a working integration breaks when someone adds a bearer token.

6. Prove it

A working configuration must refuse every one of these. If any is accepted, the control is broken:

  • A request from an origin that is not on the list gets no Access-Control-Allow-Origin header at all.
  • A request from an origin that is a prefix or suffix of an allowed one, such as https://app.examplehotels.example.evil.example, is refused.
  • The same host over http instead of https is refused.
  • An allowed origin with a trailing slash is refused, which proves the comparison is on the serialised form.
  • No response that allows credentials ever carries Access-Control-Allow-Origin: *.
  • Every response whose headers depend on the request's origin carries Vary: Origin.
  • A preflight for a method the endpoint does not support is answered without that method, and the real request never follows.
  • A request carrying Authorization fails against a preflight that answers only Access-Control-Allow-Headers: *, and succeeds when the header is named.
  • A preflight answered with a redirect or a 500 fails, rather than being treated as permissive.
  • All of the above are tests in the build, asserted against the response headers rather than checked by hand in a browser console.

Three results are worth sitting with. Checks 10 to 16 reproduce the hazard the standard documents in a note: a request carrying Content-Type twice, once as application/json and once as text/plain, is correctly preflighted under the specified safelist, because each header is judged on its own. Under a forgiving parser that lets the last valid value win, the same request would skip the preflight while a server reading the first value still treats the body as JSON. The strictness is the defence.

Checks 23 to 28 show the aggregate limit doing something invisible. Eight safelisted headers of exactly 128 bytes total exactly 1024, which is not over 1024, so a GET still goes straight out. A ninth header tips the total to 1152 and every safelisted name turns unsafe at once, so the same GET now preflights.

Checks 44 and 45 are the Authorization trap from section 5, and checks 58 and 59 show the same rule inside the preflight cache: an entry stored as * matches Content-Type and never matches Authorization.

8. Check your understanding

Your API echoes the Origin header back in Access-Control-Allow-Origin and sets Access-Control-Allow-Credentials: true. Which origins can read the response?

All of them. The CORS check compares the header against the request's own origin, so echoing makes step 4 compare a value with itself and it can never fail. The configuration is equivalent to publishing every authenticated response to any site a logged-in user happens to visit.

A cross-origin POST was blocked by CORS. Did the server process it?

Almost certainly yes. If the content type was safelisted there was no preflight, so the request went straight out, the cookie went with it, and the server did the work. The browser then refused to hand the response to the page. What CORS blocked was the reading, not the writing. Use anti-forgery tokens and SameSite cookies for the writing.

You add a bearer token to a working cross-origin integration and it starts failing the preflight, even though the server answers Access-Control-Allow-Headers: *. Why?

Authorization is the one CORS non-wildcard request-header name, so * does not cover it. The server has to name it. The same rule applies to the preflight cache, so an entry previously stored as * will not match it either.

Is Access-Control-Allow-Origin: * a finding?

Only with context. For data that anyone could already fetch with curl, it is the correct header and the standard says so. It is unsafe in exactly one shape: when the resource is protected by where the caller is rather than by who they are, such as an IP allowlist or a firewall, because then a browser inside the perimeter becomes the route in. Ask what protects the resource before writing the finding.

Review checklist items

These are collected into the site checklist.

  • The allowed origin is never taken from the request Test a disallowed origin and a lookalike such as an allowed host with an extra suffix. Both must come back with no Access-Control-Allow-Origin header.
  • No credentialed response allows a wildcard origin Access-Control-Allow-Origin cannot be * when credentials are included. Assert it on every endpoint that allows credentials, not just the ones you remember.
  • State-changing endpoints are protected independently of CORS A safelisted cross-origin POST is sent with no preflight and the server does the work. Anti-forgery tokens and SameSite cookies are what stop it.
  • Origin comparison is on the serialised form Byte for byte, no trailing slash, scheme and port included. Test the same host over http and with a trailing slash.
  • Vary: Origin is sent wherever the response depends on the origin Otherwise a shared cache can serve one origin's allowed response to another.
  • The Origin header is never used as an authorisation decision A non-browser client sets it freely. It is attacker input outside a browser.
  • Authorization is named in the preflight response It is the one non-wildcard request-header name, so Access-Control-Allow-Headers: * does not cover it and neither does a cached * entry.
  • Access-Control-Max-Age is set deliberately and bounded It defaults to 5 seconds and browsers clamp it. The value is how long a tightened policy keeps being ignored.
  • Preflight responses are asserted in tests, not confirmed by hand Include a method the endpoint does not support, a request carrying Authorization, and a preflight answered with a redirect.
