Workload and agent identity lifecycle

Objective. After this module you can state the facts a credential record must carry, set and defend a rotation interval, reconcile a register against a deployment in both directions, and say precisely what an inventory cannot tell you.

Before you start. Modules 1 to 7 gave you the mechanisms: API keys, shared secrets, signing keys, access tokens and the keys they are bound to. This module is about what becomes of those credentials over the following four years, which is where most of them are still sitting.

1. The attack

Running example: ExampleAir's estate of service credentials, built up over four years. Company names are fictional.

Nothing in this module is a protocol weakness. Every credential here was issued correctly by a mechanism from the previous seven modules. The attacker's route is an API key created for a pilot that ended eighteen months ago, still accepted, owned by a team that was reorganised out of existence.

What makes it useful to an attacker is not that it is weak. It is that nobody is watching it, nobody would recognise its use as unusual, and nobody knows how to turn it off.

The last row is the one this module is really about. Every control above it operates on the list, so every control above it is exactly as complete as the list is. That is a much stronger claim than it first sounds, and the lab makes it concrete.

2. Why it works

Credentials outlive the things they were made for. A project ends, a team is reorganised, a service is replaced by its successor and left running beside it for a migration that never finishes. The credential does not notice any of that. It keeps working, because working is the only thing it knows how to do.

Three structural reasons the pile grows:

  • The specifications do not set a lifetime for you. RFC 6749 defines the client credentials grant and requires that it be used only by confidential clients, and says nothing about how long a client secret should live. RFC 9700 recommends asymmetric client authentication over shared secrets and does not set a rotation interval either. NIST SP 800-57 Part 1 gives you the concept, a cryptoperiod, defined as "the time span during which a specific key is authorized for use", and then treats its length as a judgment driven by consequence and cost: section 5.3.6 suggests periods for each key type and calls them "only rough order-of-magnitude guidelines". So the interval is yours to choose, write down and enforce. Nobody will choose it for you.
  • Ownership gets recorded as a person. A person is a valid answer to "who made this" and a poor answer to "who owns this", because people move. A team or a role survives the individual, and reassignment is a normal operation rather than an archaeology exercise.
  • The register is written once. It is accurate on the day it is created and decays from then on, in both directions. Credentials appear in systems without being recorded, and records persist for credentials that were deleted. Neither drift announces itself.

Agents sharpen all three. An agent that acts for many users typically holds one credential whose blast radius is every user and every tool it can reach, and agent deployments create credentials quickly and in volume. OWASP's Top 10 for Agentic Applications lists ASI03, Identity & Privilege Abuse, among its ten entries. The lifecycle questions do not change for an agent. The number of times you have to answer them does.

3. The control

What a credential record must carry

Six facts, and every one of them exists to answer a question somebody will ask under time pressure:

  1. Owner, as a team or role. Answers "who decides whether this can be turned off". Never a person.
  2. Purpose and scope. Answers "what does this reach". A credential whose scope nobody recorded cannot be assessed, only guessed at.
  3. Rotation interval, and the date it was last rotated. Answers "how long has this value been exposed". Both halves: an interval with no last-rotated date is an intention.
  4. Retirement condition. Answers "when does this stop". Recorded at issue, when someone still knows, not at review time when nobody does. Rotation replaces the value and keeps the credential, so without a stated end nothing ever asks whether it should still exist. A record with neither a date nor a named event is a finding, and the lab reports it as one. That rule is this project's. The nearest source text is NIST SP 800-57 Part 1 section 9.2.1, which says a key inventory should indicate each key's expiration date. That is the end of one key's cryptoperiod, not the end of the credential's purpose.
  5. Revocation route. Answers "how do we turn it off in the next ten minutes". Recorded and tested, because an untested route is a plan.
  6. Last used. Answers "is this still doing anything". This is the one fact the register cannot hold on its own; it has to come from the systems.

The record holds none of these things as a secret value. An inventory that stores credentials is one place worth breaching instead of many, which inverts the reason you built it.

The lifecycle, and where it usually stops

Issued, active, rotated, retired, destroyed. Most estates manage the first three and stop. NIST SP 800-57 Part 1 names the end state precisely: a key reaches the destroyed state "when it is destroyed", and although the key no longer exists, "its previous existence may be recorded (e.g., in metadata or audit logs)". That distinction is the whole of step five. The record of the credential outlives the credential, on purpose, so that a later question about what happened has an answer.

Retirement and destruction are two operations and they happen in one order. Revoke the credential in the system that accepts it, confirm it is refused, and only then remove the record. Doing it the other way round produces a clean register and a live credential, which is the worst of both: nothing to review and nothing stopping it.

Reconciliation, in both directions

The registerReviewableStale recordUnknown credential

Only one of the two sources can tell you what still works, and it is not the register. Reconciliation has to read the deployment, which means the systems that accept credentials need to be able to enumerate the ones they accept. If one of yours cannot, that is the finding, and it outranks everything the register says.

When the credential can be an identity instead

Some of this pile exists because a static shared secret was the only option available. Where the platform can issue a workload identity, much of the lifecycle problem changes shape: there is nothing long-lived to rotate, and the question becomes whether the issuing infrastructure is sound.

SPIFFE is one concrete form. A SPIFFE ID is "an RFC 3986 compliant URI comprising a 'trust domain name' and an associated path", written spiffe://trust-domain/path, and carried in an X.509 certificate as a URI entry in the Subject Alternative Name extension. The specification is careful that there is "no centralized authority for regulation or registration of trust domain names", so the trust domain means what your infrastructure makes it mean, and nothing more.

The same move is available inside OAuth without changing platforms. RFC 9700 section 2.5 recommends asymmetric client authentication, mutual TLS or a signed JWT, over a client secret, and gives the reason plainly: with those methods "authorization servers do not need to store sensitive symmetric keys, making these methods more robust against leakage of keys". That is module 3's lesson applied to the credential your service uses to get a token, rather than to the requests it signs afterwards.

5. What it proves, and what it doesn't

Proves: for every credential you know about, who owns it, what it reaches, how long its current value has been in use, when it stops, and how to withdraw it today.

Doesn't prove: that the list is complete. Until it has been reconciled against the systems, an inventory is a record of what you remembered. It also says nothing about whether a credential is being misused right now, which is detection, and nothing about whether its holder should be allowed to do what it is doing, which is Part 2.

Two very different situations look identical on a dashboard. A register with no findings can mean every credential is owned, scoped and current. It can equally mean the register is a year out of date and the credentials that matter were never in it. The number that distinguishes them is not the finding count, it is the date of the last reconciliation and the count of unknowns it returned.

6. Prove it

A working process must produce all of these:

  • A list of credentials each system actually accepts, produced by reading the systems rather than the register.
  • The set difference in both directions, with a named owner for each item in it.
  • Every credential with an owner that is a team, not a person.
  • Every credential with a rotation interval and a last-rotated date, and the overdue ones named.
  • Every credential with a retirement condition, and the ones past it named.
  • Every credential with a revocation route that someone has executed at least once.
  • Evidence that a withdrawn credential is refused, taken from the system, dated after the revocation and before the record was removed.
  • The date of the last reconciliation, visible next to any statement that the estate is clean.

Part A is the part that feels like work and is the easy half. Six of eight credentials have a finding, and every one of them is a question a person could answer in a minute if you could find the person. Check 8 names the two records that never say when the credential stops, cred-002 and cred-006. The other six carry a date or a named event.

Check 11 is the module. The register has no opinion about cred-009, not because it is healthy but because it is absent, and every rule in Part A ran to completion without mentioning it. A rule engine over an incomplete list produces a clean report, which is indistinguishable from a clean estate until you compare the list with the systems.

Part C separates the three remediations that get confused with each other. cred-008 is a record fix: the credential was fine, the record was not. cred-002 and cred-006 are a record fix and then a rotation, because once the owner, the interval and the retirement condition are written down both are still overdue. cred-004 is a rotation plus a split, because a credential two systems share is the one that never gets rotated. cred-005 is a withdrawal: revoked, then removed. cred-003 is the stale record from check 10, so only its record goes. Both leave the register entirely.

Check 21 is the order-of-operations trap. Delete the record without revoking the credential and every report goes green while the credential keeps working. Check 22 is the standing cost: the reconciliation was correct on the day it ran, and cred-010 appeared the day after.

8. Check your understanding

Your credential register has no findings. What have you actually established?

That every credential you recorded is owned, scoped and current. Nothing about the credentials you did not record. The register alone cannot distinguish a clean estate from a stale list, which is why the date of the last reconciliation and the number of unknowns it found belong next to any statement that the estate is clean.

Why is a credential shared by two systems the one that is never rotated?

Because rotating it is a coordinated change across two owners and two deployment schedules, so it is always a worse time than next quarter. The fix is structural rather than procedural: issue one credential per system so that rotation is a local operation.

A pilot ended eighteen months ago. Someone removes its credential from the register. What is the state of the system?

Unchanged, and now unreviewable. The credential is still accepted and the last record of its existence is gone. Revocation happens in the system that accepts the credential, and removing the record comes after you have confirmed it is refused.

What does a workload identity change about this problem, and what does it not?

It removes the long-lived value that had to be rotated and distributed, so rotation and leakage largely stop being your problem. It does not remove ownership, scope, retirement or reconciliation: something still issues those identities, something decides what each one reaches, and you still have to know which workloads exist. An identity is not an authorization: deciding what each identity may do is Part 2.

Controls

Standard backed by a cited specification. Baseline this project's default, with reasoning above. Option valid depending on the threat model.

  • StandardNIST SP 800-57 Part 1 Revision 5 section 2.1 defines a cryptoperiod as "the time span during which a specific key is authorized for use or in which the keys for a given system or application may remain in effect", and section 5.3 says the risk and consequences of exposure "should be carefully considered when selecting the cryptoperiod". This module treats the active life of a credential as one.
  • StandardCarry the lifecycle through to an end state. NIST SP 800-57 Part 1 Revision 5 section 8.3.4 requires that all copies of a private or secret key "shall be destroyed as soon as they are no longer required". Section 2.1 says a key reaches the destroyed state when it is destroyed, and that although the key no longer exists, "its previous existence may be recorded (e.g., in metadata or audit logs)".
  • StandardThe client credentials grant "MUST only be used by confidential clients", so a credential used with it belongs to a component that can keep a secret. RFC 6749 section 4.4, with section 2.1 on the confidential and public client distinction.
  • StandardPrefer asymmetric client authentication. RFC 9700 section 2.5 recommends mutual TLS or a signed JWT over a client secret, because then "authorization servers do not need to store sensitive symmetric keys, making these methods more robust against leakage of keys".
  • StandardWhere workload identity is available, a SPIFFE ID is "an RFC 3986 compliant URI comprising a 'trust domain name' and an associated path", carried as a URI entry in the certificate's Subject Alternative Name extension, and an X.509 SVID "MUST contain exactly one URI SAN". SPIFFE-ID specification section 2 and X509-SVID specification section 2.
  • StandardDo not read more into a trust domain than it carries. The SPIFFE-ID specification, section 2.1.1, states there is "no centralized authority for regulation or registration of trust domain names".
  • BaselineEvery credential record carries six facts: owner as a team, purpose and scope, rotation interval with last-rotated date, retirement condition, revocation route, and last used.
  • BaselineThe register holds metadata only. Never the secret value.
  • BaselineRotate shared secrets every 90 days and asymmetric signing keys every 365, with the successor published before the cutover, and record a reason for any interval you lengthen.
  • BaselineIssue one credential per system. A credential two systems share is the one that never gets rotated.
  • BaselineWithdraw an active credential unused for more than 90 days, or record why it is kept.
  • BaselineReconcile the register against the deployment monthly, reading the systems, and report both directions of the difference.
  • BaselineRevoke first, confirm the credential is refused, then remove the record. Never the other order.
  • BaselinePublish the date of the last reconciliation and the count of unknowns beside any statement that the estate is clean.
  • OptionReplace static secrets with platform-issued workload identities where they are available, which converts a rotation problem into a question about the issuing infrastructure.
  • OptionIssue a distinct credential per agent instance or per task where the platform allows it, so that the blast radius of one is not the whole fleet.

Review checklist items

These are collected into the site checklist.

  • The register has been reconciled against the systems, and the date is published Both directions of the difference are reported. An unreconciled register is a record of what was remembered, and any clean report from it means nothing.
  • Every credential has an owning team, never an individual Reassignment is a normal operation. If the only honest answer is a person, that is the finding.
  • Withdrawal revokes before it deletes the record Evidence that the credential is refused, dated after the revocation and before the record was removed.
  • Every credential has a rotation interval and a last-rotated date Both halves. Overdue ones are named and assigned, not counted.
  • Every credential has a revocation route that someone has executed Tested on a credential you can afford to lose, before you need it on one you cannot.
  • Every credential has a retirement condition recorded at issue A date or a named event. Pilots, migrations and single-partner integrations get the end of that thing.
  • No credential is shared across systems, and none is unused One credential per system. Anything active and unused past the threshold is withdrawn or justified in writing.
  • The register stores no secret values, and scopes are recorded Metadata only. A credential whose scope was never recorded cannot be assessed.
